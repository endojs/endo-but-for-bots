## Summary

- **What:** Adds policy enforcement to `@endo/compartment-mapper`: per-package policy controls cross-package imports, top-level globals, and access to built-in (exit) modules, plus a separate attenuation compartment and tests covering aliasing-based bypasses.
- **Why:** Lets applications limit supply-chain risk by restricting what each transitive dependency can access.
- **Themes:** compartment-mapper, security
- **Status:** merged

## Description

**notes:**
- policy is built into `compartmentMap` in graph translation. Compartment descriptors for items not covered by policy are not preserved.
- package location abbreviations are used to differentiate packages that might otherwise have the same (or confusingly similar) names. If a malicious package declares a bundled dependency called `request` it won't steal the policy to access network from the real package
- app uses policy to manage what its dependencies can have access to and limit supply chain risks; user endows the app with globals and can still decide how much to give it, but doesn't decide the access internal bits of the app get. 
- if an endowment granted by policy is missing, it's simply undefined. It seems like it'd make sense to throw an error about a missing endowments, but in real life globals are often used to detect platform capability and so need to be allowed by policy even if they may not exist.

**requirements:**
- [x] enforce policy for builtins (exit modules)
- [x] enforce policy for importing across package boundaries
- [x] enforce policy for top-level globals
- [x] separate attenuation compartment
- [x] deny policy bypass with aliases
- [x] expand tests of policy enforcement

### @naugtur (MEMBER) — 2023-01-25T11:04:57Z

Responding to points from @kumavis below. I'll add numbers for ease of reference.

#### K1
> * we call `<root>` as `$root$` because we use `>` as a separator.

Initially I wanted to keep it consistent with `<ATTENUATORS_COMPARTMENT>` and that one was using `<>` because they are not allowed in file locations. Now that I've eliminated the need to surface  `<ATTENUATORS_COMPARTMENT>` in the policy, this is no longer needed.  
We could have something even more familiar as the root key in policy - **maybe we should call it `"."` by convention from package.json->exports?**

#### K2
> * LM `$root$` does not have a policy and can have everything. goal is good DX

When LM builds on top of compartment-mapper I believe we'd maintain that top compartment gets it all. We could generate it from the endowments we prepare or add a feature to specify "allow all" in the policy.  
For the wider Endo usecase I believe this is valuable, because **it allows an app/archive to come with a specification of what it needs**. In the grand scheme of things this would give us a better understanding of what the app wants to get and open up ways to improve UX for the person granting those permissions.

#### K3
> * in LM endowment globals come from the `$root$` compartment instead of the start compartment

I'm not sure what the consequences of this difference would be. Compartment-mapper requires explicit endowments, but if we endow all globals to the app I think it'd be equivalent to how LM currently works.

#### K4
> * in LM we transform function endowments to be called with the start compartment globalThis instead of their compartment's globalThis

Yes, this would have to be added on. ~~My assumption was I'd implement attenuators support for globals and allow an attenuator to decide what to do. Unless there's reasons to rebind all functions by default?~~  
Update: Binding can happen outside compartment-mapper, on the globals passed in as endowments, which could be beneficial for both LM and non-LM usecases. Binding all functions by default could conflict with some usecases and the sophistication/complexity of it would be limited by having to be generic enough to happen by default.
