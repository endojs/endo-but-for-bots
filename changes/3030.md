## Description

This PR introduces a new package, `@endo/geny`, which provides an OCapN host for spawning and managing OCapN child processes. This package is designed to facilitate integration testing and development of distributed OCapN applications by allowing a parent process to control and interact with isolated child processes.

Key features include:
- **`makeGenyHost`**: Creates a host capable of spawning child processes.
- **Child Process Entry Point (`src/child.js`)**: Configures an OCapN client in the child, listening on a specified port and exposing a control object via a random swissnum.
- **Control Object**: Exposed by each child, allowing the parent to:
    - `shutdown()`: Gracefully terminate the child process.
    - `eval(code, endowments)`: Evaluate arbitrary JavaScript `code` within a new `Compartment` in the child, with `E` and `Far` exposed, and `Passable` `endowments` available.
- **Integration Test**: Demonstrates spawning two children, evaluating a counter object in one, and passing that counter as an endowment to an `eval` call in the second child, which then increments the counter. This verifies cross-process capability invocation.

This PR also adds necessary exports to `packages/ocapn/package.json` to allow `@endo/geny` to import specific client and netlayer modules.

## Security Considerations

The `eval` primitive exposed by the child's control object is powerful. However, it is executed within a new `Compartment` for each call, limiting its access to the child's global scope to only `E`, `Far`, and the explicitly provided `endowments`. The `tcp-test-only` netlayer is used, indicating this is intended for testing and development environments where network isolation is assumed or managed externally, not for production use with untrusted network peers.

## Scaling Considerations

Spawning child processes and establishing OCapN connections incurs overhead. While this package is primarily for development and testing, be aware that a large number of children would consume significant CPU, RAM, and network resources. The current implementation uses a new TCP port for each child, which could lead to port exhaustion on systems with many concurrent children.
