### @warner — APPROVED — 2020-02-21T18:35:07Z

Looks good to me, and I'm pretty sure it'll address the swingset program I was having (which, as discussed, I could also solve in less-intrusive ways, if we decided against this idempotency feature).

Having `lockdown()` return a value: I don't have any immediate need for this, but it does feel like a nice-to-have might-be-useful kind of thing. If `lockdown` weren't so special, I'd say it shouldn't be there: code should not be able to sense that it's inside a virtualized environment. But 1: `lockdown` isn't available inside arbitrary Compartments, it's only available inside the start compartment, and then only because it's been imported from the SES library. And 2: `lockdown` is effectively a shim, called just once, to get us from a Node- or browser- style environment into a SES environment. It's not like the Realm constructor, or the Compartment constructor, where each layer of virtualization would be using it to create another layer.

I can imagine another argument against this approach (maybe @erights has a stronger opinion about it), which is the static `previousOptions` variable. In most of our code, when we need something like that, we split it into e.g. `makeHardener()` and the produced function `harden()`, so that the static variable is allocated by the maker and closed over by the actual utility. This avoids the risk of a communication channel through the shared variable.

But again, `lockdown` is special, and only called once, and not available from non-start Compartments, so I think that argument isn't strong here. We may need to pay attention to how non-start Compartments are allowed to import modules, to make sure things like `lockdown` aren't then usable as a channel, but that's true for all non-pure modules, so we're already planning for that.
