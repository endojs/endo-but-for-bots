## Description

This PR improves the GitHub Action pinning update process:
- Weekly patch/minor updates open a PR with a report linking upstream diffs.
- Monthly major updates are separated into their own workflow.
- The pinning script is path-scoped (`jobs.*.steps[].uses` and `jobs.*.uses`) and can enforce pinning in CI.
- CI verifies that all `uses:` entries are pinned to SHAs.
- Contributor docs describe how to run the updater and resolve failures.

### Security Considerations

This improves our stance against supply chain attacks through Github action repositories.

This change adds automated PRs for updating GitHub Action pins, but the PR body links to upstream compare, release, and commit views for review. Major upgrades are isolated to a monthly cadence to reduce risk. CI prevents unpinned `uses:` entries from landing.

### Scaling Considerations

CI adds one lightweight job that only runs on PRs touching `.github/workflows/**`.
Weekly/monthly workflows run on a schedule and are short-lived.

### Documentation Considerations

`CONTRIBUTING.md` documents how to update pins and how to address CI failures.
No user-facing docs changes are required.

### @boneskull — APPROVED — 2026-01-31T00:06:20Z

In general, a good idea.  One concern I have is _age_. How long has the SHA existed?  Was it pushed five minutes ago?  Should we wait 5 business days before adopting it?

Only related because we're mucking around in workflows: adding the following to a workflow will cause subsequent pushes against the same ref to cancel old workflows.  Practically speaking, if you have a PR and push _and then push again_ before the original workflow has completed, GHA will abort the old one.  In my experience this is applicable to most test/lint workflows but most useful with the slower ones.

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```
