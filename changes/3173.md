## Summary

- **What:** Replaces the broken summed-code-unit edge-weight in `@endo/compartment-mapper`'s `GenericGraph` with a `GenericGraphNode.toString()`-keyed comparison delegated to `@endo/path-compare`, fixing canonical-name instability where anagrams (e.g. `"endo"`/`"node"`) tied and a few wide-codepoint chars could outweigh longer ASCII paths.
- **Why:** @gibson042 demonstrated the prior weight function could produce non-deterministic shortest paths and thus unstable canonical names (e.g. `<FF8F FF8F>` outweighing `"AAA"`).
- **Themes:** compartment-mapper, security
- **Status:** merged

## Description

This removes the built-in "edge weight" logic in `GenericGraph` with an implementation provided by @gibson042:

> To provide much-belated commentary, this function is not correct—the value of each successive code unit in two strings can differ by up to 0xFFFF, which can overcome a single-character length difference in just two characters (e.g., the weight of <FF8F FF8F> "ﾏﾏ" is 2 × 65536 + 0xFF8F + 0xFF8F = 261_918, which is greater than the length of the longer <0041 0041 0041> "AAA" at 3 × 65536 + 0x41 + 0x41 + 0x41 = 196_803). Further, ignoring the position of each code unit means that anagrams are incorrectly given equal weight (e.g., both "endo" and "node" are weighted at 4 × 65536 + 0x64 + 0x65 + 0x6E + 0x6F = 262_566), potentially thwarting the stability sought by this PR.

> Honestly, this approach seems like an abuse of graph edge costs ("weights")... we want e.g. "foo" → "A" → "bar" to be preferred over "foo" → "B" → "bar", although it's less clear to me that "foo" → "B" → "C" → "bar" should be preferred over "foo" → "ABC" → "bar". But even if that is fine, achieving it correctly seems to require non-scalar definitions for both weights and distances, in which case you could weight "A" as [1, 65], "B", as [1, 66], "C" as [1, 67], "ABC" as [3, 65, 66, 67], and "B" → "C" as [1, 66, 1, 67] (comparing lexicographically and defining the weight of a path by concatenation), but having gone that far it seems reasonable to just define costs using strings directly and operate on a corresponding non-generic Graph.

As written, his suggestions (found [here](https://github.com/endojs/endo/pull/2872/changes#r3042170892)) would inhibit the `GenericGraph` from representing non-`string`-type nodes, meaning the graph would no longer be particularly "generic."  To that end, I've defined a `GenericGraphNode` type which demands a node has a `toString()` method, and it uses the returned value for shortest-path calculations.  To support his implementation, `@endo/compartment-mapper` (once again) pulls in `@endo/path-compare`.

This breaks the `GenericGraph` API, but since it's internal, this is not a breaking change.
