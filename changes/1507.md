## Summary

- **What:** Replaces `@endo/compartment-mapper` `exitModules` linking with a unified `importHook` for exit modules; the legacy `modules` option remains as a wrapper but its implementation routes through `internalExitModuleImportHook`, making module records distinct per consumer and moving exit-module loading out of `moduleMapHook`.
- **Why:** Lets dynamic exit modules participate in attenuation and aligns exit-module handling with regular import-hook semantics.
- **Themes:** compartment-mapper, security
- **Status:** merged

## Description

This implements `importHook` option in compartment-mapper which works like any importHook that we know, but specifically for exit modules.  
The `modules` option remains for backward compatibility, but the implementation is removed and handled by `internalExitModuleImportHook` which wraps both ways of passing exitModules into one. 

Major changes:
- `modules` no longer require wrapping in a compartment as they no longer pass the export namespace brand check directly (as a result of wrapping them in records; they also are not the same reference if one exitModule is passed to two apps)
- exitModule logic is gone from moduleMapHook and exitModules are loaded in the importHook
- passing different/inconsistent implementations of `importHook` to archive-making and runtime steps will cause less-than-desirable behavior. Missing cjs modules have their errors deferred and even if the `importHook` passed to `importArchive` returns the module, the error deferred from archive making will be thrown first.
