## Summary

- **What:** Initial draft of `@endo/ocapn-noise`, a Noise Protocol netlayer for OCapN authenticating XX-x25519-ChaChaPoly1305-Blake2 with ed25519 signing keys (the locator's identity), implemented over a small Wasm VM per session and intended to expose accepted connections as async iterators of `Uint8Array` ranges.
- **Themes:** ocapn, security
- **Status:** merged (encoding negotiation and high-level API still TBD)

## Description

This change covers an implementation of a Noise Protocol suitable for an OCapN netlayer that authenticates and preserves confidentiality for a session between a pair of peers, including the mechanisms necessary for public and private keys.

The selected protocol variant is XX-x25519-ChaChaPoly1309-Blake2 with ed25519 key signing, which presumes that the initiator knows the ed25519 signature verification key of the responder. In OCapN, that key is expressed by the locator. The protocol also allows the responder to discover the public key of the initiator, which is useful for resolving crossed hellos and preserving the identity of targets throughout an OCapN network implementing 3-party-handoff. The ed25519 keys are conveniently small and easy to capture in an OCapN locator. Elliptic curves are a heck of a thing.

The intention for this netlayer is for it to support multiple transport protocols, message delimiters, and potentially even multiple concrete encodings. As such, this implementation is incomplete because it doesn’t do encoding negotiation in the three-way-handshake yet, but the scaffold is in place.

This change also leaves the high level API unwritten. My intention is for the OCapN package to accept a netlayer implementation and that interface is not yet implemented here. I am assuming that we will implement a listener as an async iterator over accepted, negotiated connections with their public key, where each connection is itself a pair of async iterators over Uint8Array ranges. There is some room for avoiding buffer copies out of the WasmMemory and using the iterator protocol to release messages.

This implementation assumes that the overhead of a small Wasm VM for each connection will be acceptable, so does not attempt to manage allocation and tracking for multiple concurrent sessions, leaving that concern to JavaScript. The intent is to later introduce separate exports for Node.js and web implementations, with a default implementation that throws "not implemented", for environments where the mechanism for importing the WebAssembly implementation is less certain. In time, I hope we can use `import source` across multiple platforms.
