## Summary

- **What:** Refactors `ses` and Endo internals to export functions as `export const` instead of `export function`, dropping the live-binding requirement.
- **Why:** Refs #175 — prepares for an Endo-internal bundler that has no scope proxy beneath SES, so live bindings cannot be supported.
- **Themes:** ses-lockdown, compartments, tooling
- **Status:** merged

## Description

Toward #175, an upcoming change introduces a JavaScript module bundler based on our own `StaticModuleRecord`’s internal module-to-program transform and linkage calling conventions. This would allow our module system to host itself.

However, beneath SES, we would not have a scope proxy, and the scope proxy is necessary to facilitate live bindings, such as exported function declarations. We do not need live bindings, so it’s a sensible compromise to use `export const` functions instead. This change prepares SES and the Endo internals for such a bundler.

### @erights — APPROVED — 2021-05-11T02:20:41Z

LGTM

As discussed verbally, this should not be needed because of the module transform. It seemed that way because the module transform is currently buggy. (Was buggy?) However, this change is an improvement anyway. The old code had more hidden semantics than the new code. IOW, the new code more obviously says what it means and means only what it says. The hidden semantics of the old code removed by this PR:

* `function` functions have a `[[Construct]]` behavior in addition to their `[[Call]]` behavior. Arrow functions have only a `[[Call]]` behavior.
* Related, `function` functions have a non-deletable `prototype` property that arrow functions do not.
* This PR reminded me: `function` functions have their own `arguments`. Arrow function deference `arguments` into the enclosing lexical scope. (Likewise for `this` of course)
* The stringification of a `function` function is either a function declaration or a function expression depending on parser start production. In a normal `eval` it is a declaration, and therefore does not appear as the completion value. Arrow functions stringify to an arrow function expression.
* The `const` declaration makes clear that there cannot be any assignment to this variable elsewhere. A `function`, `let`, or `class` declaration can only be known to be effectively const after looking for any statically apparent assignments (or direct eval).
* Uniquely, `function` declarations hoist. They are never in temporal dead zone. Arguably this makes their semantics simpler than `const`, `let`, or `class`. But it is a difference that is hard to reason about.

I took this opportunity to capture all this in anticipation of discussions about preferred programming style.
