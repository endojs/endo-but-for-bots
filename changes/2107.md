## Description

Exports `console-tools.js` from `ses`, so PRs like https://github.com/endojs/endo/pull/2101 can use these to manipulate consoles ***ONLY*** for testing and debugging purposes. Some of our other packages export testing support API with an export named "tools.js". But ses already exports a "tools.js" with a different meaning.

Other than arranging this new availability, this PR itself should have no observable change whatsoever. In that sense, we can consider it a pure refactoring.

### Security Considerations

The powers exported from `ses` as `console-tools.js` should only be available to privileged code, such as ses-ava and instrumentation that runs in the start compartment. But as an export from the "ses" package, can we prevent others from importing it within the way we're currently using our tooling? @kriskowal , I think this is a question mostly for you.

### @kriskowal (MEMBER) — 2024-02-29T23:07:05Z

In advance of my full review, some things to consider when deciding whether to export a module or a global:

What is the intended outcome for the usage pattern we encourage on the web, where `ses` is not bundled but injected with an early `<script>`? Would the outcome be acceptable if the bundled application imports an eval twin from`ses/console-tools.js`? My intuition is that, for this feature, there is important shared state and an eval twin would not be desirable.

Is the intention to treat consumers that import as having a higher level of privilege than other code that runs in the original realm / start/initial compartment? My intuition is that imports and globals in the start compartment have equal privilege.

How does using a module for some facilities and globals for other facilities impact the narrative for standardization? Is the intention that anything imported by a module would not participate in the standard? I don’t think console tools are standards track, but they could be factored in such a way that the essential primitive (error unboxing) would be standard.

Is the intention of using a module to communicate a lower level of commitment to backward compatibility within the `^1` semver range? That’s not consistent with my view of our obligations. This is why I’m encouraging a refactoring of `@endo/permits` out of `ses`, so that `ses` can depend on any major version of `@endo/permits` internally without any impact on its own obligations for backward compatibility. That particular case is also not affected by eval twins and ideally would use “nested dependencies”, if such a feature existed.
