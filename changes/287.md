## Summary

- **What:** Adds a `compartment.module(specifier)` method to SES that returns a proxy module-exports namespace, allowing one compartment to alias a module in another via a weak-map-tracked module map before the module has loaded.
- **Why:** Enables cross-compartment imports without resolving exports up front; property accesses on unloaded namespaces throw `ReferenceError` instead of silently producing `undefined`.
- **Themes:** compartments, ses-lockdown
- **Status:** merged

## Description

For a module in one compartment to import a module in another compartment, the Compartments must pre-arrange for a module specifier to alias the other compartment. The mechanism @erights and I discussed to make this possible is the introduction of a compartment.module method that would return the module exports namespace object for a module, possibly before that module has even been loaded. Behind the scenes, a weak map tracks the corresponding compartment and specifier for each module exports namespace object, so the Compartment constructor can infer the alias for any module exports namespace object received through its module map.

To facilitate this, the presentation of a module exports namespace needs to be a proxy for the eventual internal representation, so that any property access on the namespace can throw a reference error before the shape of the exports are known.

It is, however, `importNow` has the side-effect of executing the module. There’s another tool we need that would assemble `Compartment` instances from a set of `package.json` files (or a lock file, or policy files). From there, you have a choice of either bundling all the modules that were loaded, or executing from an entry point. Either way, we don’t want to execute every inter-compartmental link as if it were its own entry point. That would result in needless execution in the best case, and unwanted side-effects in the worst.

### @kriskowal (MEMBER) — 2020-05-09T01:22:14Z

So that my hard bought thoughts survive the weekend…

I need to do a rewrite of module-proxy.js because it transpires that the module-instance’s proxied exports can’t be sealed before they’re executed. The module functor passes an update record back to the module instance when it’s executed, and that contains information the module instance needs to populate any of the exports that came from an `export * from 'specifier'` directive.

As @erights points out, it is possible to discover the closure of exports statically. It just requires walking the module static record graph to collect any of the export names from dependencies that might surface due to an `export * from 'specifier'` directive.

So, we create a function that collects those names. Activating an exports proxy then means creating a pass-through accessor property for every exported name and then preventing any further extensions to the target. Each accessor would just pass through to the proxied exports. But, critically, these properties would be added to the proxy target and all of the proxy handler traps would either throw an exception or use reflection on the `target`, not the proxied exports! This mitigates the disagreement between the property descriptors of the target and the proxied exports.

### @kriskowal (MEMBER) — 2020-05-12T01:10:51Z

I’ve posted follow-up commits. Instead of syncing the exports proxy target with the proxied exports upon activation, the the proxied exports *is* the exports proxy’s target initially. Both the `exportsProxy` and `proxiedExports` are allocated up front with an `activate` method the first time the module exports namespace gets allocated. The `exportsProxy` is public and the `proxiedExports` and `activate` eventually arrive in the module instance. Executing the module instance adds the exported properties to the `proxiedExports`, then seals, then activates. Only upon activation does the `exportsProxy` delegate through to its underlying, sealed `proxiedExports`.
