The general pattern for wrapping a function-which-may-be-a-constructor with another function, such that the wrapping function forward to the original preserving both the call behavior of the original, the construct behavior of the original, and even the subclassing behavior of the original (especially relevant if the original is a class):

```js
  const OriginalFoo = Foo;

  const NewFoo = function Foo(...rest) {
    if (new.target === undefined) {
      // It was called as a function
      return Reflect.apply(OriginalFoo, this, rest);
    }
    // It, or a subclass, was called as a constructor
    return Reflect.construct(OriginalFoo, rest, new.target);
  };
```

### @warner (CONTRIBUTOR) — 2020-07-17T20:59:07Z

I guess the high-order bit is whether this lives in SES-shim or agoric-sdk, but anticipating it breaking when you introduce per-compartment `Compartment` constructors, I'm inclined to think it belongs in SES-shim. It's certainly not agoric-sdk -specific.

But yeah, I could move it into an un-separately-published module within `@agoric/import-bundle`, which is the first customer. The plus side is not needing to choose a public name yet, the downside is that it'll stop working (poorly) when you make that change. "Poorly" because I don't think this code has a direct dependency on any particular version of SES (it doesn't import SES, it merely expects to be given a `Compartment` argument that behaves in a particular way), and when each compartment has a distinct constructor, the wrapper will start confusing those together, silently. I could make `@agoric/import-bundle` depend upon a particular version of SES, but it really needs to be the same version as what `@agoric/install-ses` uses or things will get *really* weird.

It kind of comes down to how we anticipate the SES ecosystem going. We expect that there will be helper libraries that are widely used but live outside the Compartment proposal. We don't know what else will be in these libraries yet, nor what they ought to be called. So yeah, maybe waiting until we have a second use case is a good idea.

So I'll ask for feedback on the implementation here, but I won't land this PR. Instead, I'll move the module into agoric-sdk `@agoric/import-bundle`. I'll add a note to try and remind us that when we change `@agoric/install-ses` to use a newer version of SES (with the constructor-per-compartment), we need to rewrite the wrapper too.
