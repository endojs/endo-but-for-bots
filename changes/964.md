## Summary

- **What:** New `@endo/stream` package: provides `Reader`/`Writer` types layered over async iterators with a tighter generic shape than WHATWG streams, plus a reductive `makePromiseKit` so it has no eventual-send dependency.
- **Why:** Foundation for hardened-JS streaming (CapTP, Endo browser, netstring/JSON adapters); WHATWG streams' helper-method API was awkward to extend with iterator semantics.
- **Themes:** captp, eventual-send
- **Status:** merged

## Description

Adds a small stream library that provides a foundation for streaming with async iterators. The types are a bit more rigid than AsyncIterator in order to mesh better in TypeScript.

The library includes a reductive makePromiseKit since the AsyncQueue requires a “soft” object and doesn’t require much else that `@agoric/promise-kit` might provide, but nevertheless, I took a cue from attempting to use `@agoric/promise-kit` and implemented the library atop hardened JavaScript.

### @kriskowal (MEMBER) — 2021-12-27T19:40:46Z

In an aside with @mhofman, we discussed why I chose not to use an async generator function to implement the JSON writer in #966. The position is that Node.js pipelines can be expressed as generator function, where the pipeline effectively inverts the writer and reader. This is possible because any abstraction on streams has this reflexive duality. So too with this stream library, it should be possible to express adapters to writers using reader adapters.

It’s clear that you can invert a stream from reader to writer using `makePipe()`, but a naïve first attempt to do that resulted in a difference of parity: the back-pressure signal of the returned writer was one-off from the back-pressure signal of the accepted writer. So, the existing tests failed.

I did eventually come up with a solution that worked, and it would justify adding a method to this library by a name that I haven’t found yet, tentatively `pump`. The insight here is that we have to use the iterator protocol to communicate with a generator, but the back-pressure signal continues to get transported by an async queue. This requires a slightly different entanglement of the async queues for the involved streams.

```js
/**
 * @template Input
 * @template Output
 * @template Return
 * @param {Writer<Input, Return>} acceptedWriter
 * @param {(reader: Reader<Input, Return>) => Reader<Output, Return>} transform
 * @returns {Writer<Output, Return>}
 */
export const pump = (acceptedWriter, transform) => {
  const input = makeQueue();
  const output = makeQueue();
  const acks = makeQueue();
  const inputReader = makeStream(input, output);
  const returnedWriter = makeStream(acks, input);
  const outputReader = transform(inputReader);

  /** @param {Promise<IteratorResult<Output>>} resultP */
  const crank = resultP => {
    resultP.then(
      ({ done, value }) => {
        if (done) {
          acks.put(acceptedWriter.return(value));
        } else {
          acks.put(acceptedWriter.next(value));
          crank(outputReader.next());
        }
      },
      error => {
        acks.put(acceptedWriter.throw(error));
        crank(outputReader.throw(error));
      },
    );
  };
  crank(outputReader.next());

  return returnedWriter;
};
harden(pump);
```

With this primitive, the JSON writer adapter looks like:

```js
// @ts-check
/// <reference types="ses"/>

/* Adapts a Writer<Uint8Array> to a JSON Writer<any>, where reader and writer
 * streams are modeled as hybrid async iterators + generators.
 */

import { pump } from '@endo/stream';

const textEncoder = new TextEncoder();

/**
 * @param {import('@endo/stream').Reader<ReturnType<JSON.parse>, void>} reader
 */
async function* transform(reader) {
  for await (const value of reader) {
    const json = JSON.stringify(value);
    const bytes = textEncoder.encode(json);
    yield bytes;
  }
}

/**
 * @param {import('@endo/stream').Writer<Uint8Array, void>} writer
 */
export const makeJsonWriter = writer => {
  return pump(writer, transform);
};
harden(makeJsonWriter);
```

This passes the same tests, but with the JSON adapters, implementing the async iterable iterator protocol directly results in a clearer program, so I defer this chunk of code to a future change, when it’s better motivated.
