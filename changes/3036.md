## Description

## Description

This change introduces a new `@endo/exo-stream` package that provides a CapTP abstraction for bridging async iterator streams. The package offers a stable client API designed to allow protocol evolution without modifying clients.

The PR also refactors `@endo/daemon` and `@endo/cli` to use the new `exo-stream` package, removing the old `reader-ref.js` and `ref-reader.js` modules from daemon.

### New Package: `@endo/exo-stream`

Four exported functions provide symmetric conversions between local iterators and remote passable streams:

| Function | Purpose |
|----------|---------|
| `streamIterator` | Convert local `AsyncIterable<Passable>` → remote `PassableStream` |
| `iterateStream` | Convert remote `PassableStream` → local `AsyncIterableIterator<Passable>` |
| `streamBytesIterator` | Convert local `AsyncIterable<Uint8Array>` → remote `PassableBytesStream` |
| `iterateBytesStream` | Convert remote `PassableBytesStream` → local `AsyncIterableIterator<Uint8Array>` |

The byte stream variants automatically encode/decode via base64 for CapTP transport. This is a temporary measure, pending support for byte arrays in CapTP, based on existing support in pass-style for immutable ArrayBuffer that simply hasn’t been fully realized.

### Refactored Modules

**`@endo/daemon`:**
- `src/directory.js`, `src/host.js`, `src/guest.js` → use `streamIterator`
- `src/daemon.js` → uses `iterateBytesStream`
- `src/daemon-node-powers.js` → uses `streamBytesIterator`
- Removed `src/reader-ref.js`, `src/ref-reader.js`, and their re-exports

**`@endo/cli`:**
- `src/commands/store.js`, `make.js`, `install.js`, `bundle.js` → use `streamBytesIterator`
- `src/commands/list.js`, `inbox.js`, `follow.js` → use `iterateStream`
- `src/commands/cat.js` → uses `iterateBytesStream`
- `demo/cat.js` → uses `iterateStream`

### Security Considerations

No new security concerns. The package uses existing hardened patterns (`makeExo`, `harden`) and InterfaceGuards from `@endo/patterns`. The abstraction maintains the same security boundaries as the previous implementation.

### Scaling Considerations

This change implements an improved protocol, no longer relying on `next` invocations. We transit async chains of nodes directly. The initiator provides the synchronizer queue and the responder returns the acknowledgement queue.

### Documentation Considerations

- The new package includes a README with usage examples
- `DESIGN.md` provides detailed implementation specifications
- `PROTOCOL.md` provides a draft proposal for the corresponding over-CapTP protocol, as a basis for collaborating on over-CapTP protocols with OCapN community constituents.

### Testing Considerations

- Unit tests in `packages/exo-stream/test/index.test.js` cover all four functions
- Tests include empty streams, single items, large streams (1000 items), and round-trip scenarios
- Existing daemon and cli tests should continue to pass

### Compatibility Considerations

**Breaking for internal consumers only:**
- `makeIteratorRef`, `makeRefIterator`, `makeReaderRef`, `makeRefReader` are no longer exported from `@endo/daemon`
- These were only used internally within daemon and cli, which have been refactored

### Upgrade Considerations

No upgrade steps needed. The refactoring is internal and the wire protocol remains compatible.

### @kriskowal (MEMBER) — 2026-01-10T06:37:08Z

I’ve had second thoughts about recapitulating the parity problems with JavaScript generators, since they muddy up the signature of either TRead or TWrite depending on the stream direction. Streams that can send data both directions aren’t really necessary. We only need readers and writers, or pairs of them. For a reader, the buffer should be a number of undefined synchronizations, and all syncs should be expected to be undefined in any case. For a writer, the buffer should be how many undefined acks the initiator should presume have already been sent, where the tail of the chain is resolved with the ack chain from the responder.

Also, feedback out-of-band from @grypez tells me I should think harder about how this utility composes, given that the method that initiates a stream might not always have the same name. This is already the case for `streamBase64`, but outside here, it’s also the case that `followMessages` should just return a stream reader suitable for consumption with an async iterator light client.

And from that conversation, I began to think about what this would look like if we blessed it with an `E` operator, like `E.reader(host).followMessages()`, which would produce an async iterator. We may as well look forward to that possibility and have similar ergonomics. It would make sense for this package to provide a Proxy device much like `E`, such that:

```js
for (const message of R(inboxRef).followMessages()) {
}
```

```js
makeExo('Inbox', InboxI, {
  followMessages: makeReadable(iterable),
})
```

### @kriskowal (MEMBER) — 2026-02-28T16:25:10Z

> What's the relationship between @endo/exo-stream vs @endo/stream ?

`@endo/stream` deals with local streaming, does not do defensive pattern checking, and has less overhead. We use `@endo/stream` for underneath CapTP (for transports) and use `@endo/exo-stream` above CapTP.
