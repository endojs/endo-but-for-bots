## Summary

- **What:** Inlines a JSZip-derived Zip library into `@endo/compartment-mapper` (under `src/zip`) with stricter integrity checks and no dependency on Node.js streams or `new Date()`.
- **Why:** Lets the compartment mapper run under SES and embed in XS binaries without Node-only or non-deterministic dependencies.
- **Themes:** compartment-mapper, ses-lockdown
- **Status:** merged

## Description

This change subsumes a variation on the popular JSZip library. See README.md in `packages/compartment-mapper/src/zip` for details about how the library varies.

The objectives are:

1. To eliminate the dependency on the Node.js readable streams built-in library.
2. To convert entirely to ECMAScript modules so the compartment mapper can be embedded in an XS binary.
3. To work under SES. Notably, to not depend on `new Date()`.

In refactoring, I introduces stricter integrity checks than JSZip, consistent with our security focus, at the possible expense of compatibility with some archives.

The implementation is sufficient for round tripping an archive, and for third-party tools to be able to read that archive, but not sufficient to be able to read archives generated by other tools, notably if they use Zip64 or any kind of compression. While this is sufficient for our needs, these features are recoverable with some work.

Zip64, to the extent of 53 bit addresses, or with a major BigInt refactor for 64 bit addresses, is relatively straightforward. Recovering *FLATE compression just requires converting the `pako` package to ESM and affords an opportunity to reuse the CRC-32 package, perhaps publishing these as `@agoric/crc32`, `@agoric/inflate`, and `@agoric/zip` (or even just `zip` since I own that).

I also removed asynchrony. JSZip supports a mode where it will periodically yield to avoid monopolizing the event loop, emitting progress updates. This feature could be recovered with a parallel API that drives the synchronous buffer writer using async functions, and streaming Uint8Array async iterators, which is entirely out-of-scope for our needs.

That said, our needs may eventually include lazy archive reading, which could be done with an async seekable reader, much like the included buffer reader.

I’ve elected to inline the implementation now to defer the higher bar needed to commit to public API’s and to be more generally useful.

(cc JSZip authors @stuk and @aadsm)
