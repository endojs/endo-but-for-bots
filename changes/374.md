### @coder-mike (NONE) — 2020-07-08T05:04:35Z

I'm not sure if this is the best place to document this, but I've been looking into how to automate the generation of `index.d.ts` from the JSDoc typing comments, and these are my conclusions so far in summary:

 - TypeScript cannot consolidate all the typings into a single output `index.d.ts` output file. I've reached this conclusion after spending hours looking for a way to do it and not finding it, and also from the readme for the package [dts-generator](https://www.npmjs.com/package/dts-generator) which says "the TypeScript compiler doesn’t allow you to actually create a single bundle out of [all the definition files]"

 - In the TypeScript projects I've worked on in the past, one path is just to let typescript just "do what it does", which is to output a `.d.ts` file corresponding to every input file, where you would consider the entry point `.d.ts` file being the one that corresponds to the entry point `ts` input file (this would be `main.js` in the case of ses, and the corresponding `main.d.ts` file). This is the approach I have for Microvium, where the TypeScript entry is `./lib.ts` and the corresponding distribution entries are `./dist/lib.js` and `./dist/lib.d.ts`. There is no `index.d.ts`. I don't think this approach has many negative impacts, and I'm quite happy with it so far.

 - Or, if a single consolidated output file (bundle) is required for some package, then one uses a bundler. This can apply to both the distributed JS and the corresponding declaration file: if you want one `.js` file output, and one `.d.ts` file output, then you use a bundler that produces these. If memory serves, Webpack does this (taking in a set of JS/TS files, and outputting a single distributable JS file and a single distributable `d.ts` file). It uses typescript as a plugin. I do not personally like Webpack, nor is it the bundler than SES is using.

 - I spent some time trying to get TypeScript to work as a plugin to the rollup bundler as part of the ses build pipeline, but was unable to achieve the desired outcome of producing a single, clean `index.d.ts`. The closest I could get was generating a `.d.ts` per input file (module), which isn't that great IMO but it would work.

 - Another option might be to run a separate pipeline in parallel to rollup, using TypeScript to produce definition files as an _intermediate_ build artifact, and then using `dts-generator` to consolidate these into a single `index.d.ts` for distribution. 

I personally don't like any of these solutions.

Oh, and one other conclusion I've come to from looking at JSDoc comments for typing is that they are ugly and verbose compared to the equivalent pure-typescript syntax. I would personally not choose them for any project since I think they detract from readability rather than contributing to it. But I may be biased here because I've been using pure TypeScript for a long time.

### @FUDCo (CONTRIBUTOR) — 2020-07-08T08:23:38Z

> @FUDCo any strong desire to fix this, rather than having to specify `/* global harden */` everywhere?

I've got mixed feelings about this.  On the one hand, `/* global harden */` is _in_ the file and therefor is more localized -- you don't have the ability of a source file to pass `eslint` depending on some voodoo happening someplace else.  I'm generally opposed to non-local causality wherever it rears its ugly head.  On the other hand, not having to put the magic comment in a bunch of files makes for a cleaner source base _and_ it makes the source files look the way they will look once `harden` becomes part of the official language spec.  On the whole, I think I favor the `package.json` approach more; at the time I put all those `/* global harden */` comments in I hadn't realized an `eslint` config in `package.json` was an option, and I sort of wish I had.  It's also good that if we shift to the `package.json` approach we don't have to change everything all at once, we can revise incrementally.
