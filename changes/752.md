### @kriskowal (MEMBER) — 2021-05-28T03:40:34Z

I see. The version numbers of packages that have never been released are arbitrary. It seems that, without alternation to Lerna, given that my intention is that the first released version be numbered `0.1.0`, I should set the version of any never-released package to `0.0.0+1-dev`. We do not want the first version to be `0.0.1` since `^0.0.1` does not upgrade to any subsequent version, so there must be at least one commit with `feat` to induce the increment of the minor.

If I understand correctly, going forward, without modifying Lerna, for any package that is pre-1.0.0, we would need to take care to use `feat` only in the case of breaking changes and use `fix` for features and bugfixes. We would not use the breaking-change sigil `!` until we intend to publish `1.0.0`.

So there’s a misalignment between what the conventional commit annotations say and the behavior I intend Lerna to effect. But, we could patch Lerna to be sensitive to major version `0` so that it behaves consistently with the effect on how the package manager interprets `^0`, or compensate by using different conventional commit annotations for pre-1.0 packages.

Regardless, because I’ve used `!` to imply breaking, `feat` to mean feature, and `fix` to just mean fix up to this point, I’ve induced behavior from Lerna that is different than my intentions so I’ll have to hand-roll this one. But, if we either patch Lerna or adjust how we do conventional commits, we could use `lerna version` for the next round of publications.

I think my preference would be to alter the behavior of Lerna, based on the patch you provided so I’ll look into that tomorrow.
