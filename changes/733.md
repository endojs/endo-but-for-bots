## Summary

- **What:** Closed proposal adding `ses` `assert.atomic(f)` and `assert.notThrows` that fail-stop the unit of computation if a throw happens after the explicit `commit()` call.
- **Why:** Models post-commit-point failures in ERTP-style transactional logic; agoric-sdk#3144 is the consumer.
- **Themes:** ses-lockdown, errors
- **Status:** closed-unmerged

## Description

Our transactional logic, for example in ERTP, has us do all tests which might fail before a commit point, and then perform all state update after the commit point, so that either all these updates happen or none of them do. However, if a throw happens after the commit point, it could leave behind corrupt state where some of these updates happened and others did not.

This PR adds `assert.atomic` so that code within such an atomic block can explicitly say when it crosses the commit point, by calling a `commit()` function. If the atomic block exits with a throw *after* that commit point, then this does an `assert.fail` with this same assert instance. Thus, such an atomicity failure will terminate/abandon whatever unit of computation that `assert.fail` does. For example `zcf.assert.atomic(f)` will immediately terminate that `zcf`'s contract if `f` fails after its commit point.

See https://github.com/Agoric/agoric-sdk/pull/3144

    assertAmountEqual(srcPaymentBalance, optAmount);

### @kriskowal — APPROVED — 2021-06-10T19:11:18Z

Thanks for adding `notThrows`.

I do not understand the motivating use-case for `atomic` nor how it relates to atomicity or even how you would build transaction safety from it. From a read of the code, the verbose form of the name would be “must not throw an error after committing, may throw before committing, must commit either once _or not at all_.”

Without an additional invariant, “must call commit exactly once”, I believe any program framed in terms of `atomic` can be trivially reframed as `notThrows` by moving the code before `commit` out of the scope of the action. The only observable difference is the addition of an annotation if it throws before commit, which could be accomplished in terms of a simpler primitive like `assert.section(preamble, note); assert.notThrows(critical, note)`.

Please add a note to NEWS.md about these new features.

### @dtribble (CONTRIBUTOR) — 2021-06-20T19:42:39Z

The pattern I have in mind for this general thing is to have an outer scope that provides the controls for that "transaction". Then it can transition in state so that for example failure can have different effects depending on the state.  e.g.,

```
vat.runWithCommit(scope => {
   scope.assert(...);  // failure throws
   scope.commit();
   scope.assert(...); // failure abandons
   someHelper(scope); // abandon vs. throw depends on where it's used. Here, it abandons
}
```
And since a commit was expected, we could require the block to commit and return or throw.

This pattern could be used with ZCF handlers, where their asserts before the commit throw, and after the commit fail the contract. That would be integrated with the virtual objects or other state tools so they throw if those tools are mutated prior to the commit.
