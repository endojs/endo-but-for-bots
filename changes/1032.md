## Summary

- **What:** Teaches `harden()` to handle typed arrays the way it handles Map/Set: integer indices remain mutable like map entries, but the object is sealed and other own properties become non-writable/non-configurable.
- **Why:** Closes #1029 — typed arrays could not previously be hardened, blocking their use as values across SES boundaries (e.g. streams).
- **Themes:** ses-lockdown, pass-style
- **Status:** merged

## Description


Harden can now handle typed arrays.  Although typed arrays cannot be frozen because their integer properties cannot be made non-writable by any mechanism, these properties are analogous to the entries in a map, which can be hardened.  This change makes harden treat typed arrays as the moral equivalent of a map.  Hardening a typed array seals the object and makes all other properties non-writable and non-configurable.

Fixes #1029

### @kriskowal (MEMBER) — 2022-01-29T23:12:58Z

I took a run at using an error trampoline instead of brand checking every single object. The code fit pretty well, but whenever freeze threw an error for a typed array, the queue would have to be resumed flushing from the beginning. Deleting entries from `toFreeze` is not an option: they all need to be added to the WeakMap of hardened objects later. So, the alternative was to mark the object and reflush the queue from the beginning. So, there ended up being a brand check before freeze regardless of the mechanism. Just calling `isTypedArray` on every turns out to be considerably simpler, and probably performs no worse than checking for the object’s existence in a WeakSet.
