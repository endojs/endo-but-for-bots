## Summary

- **What:** Introduces `ModuleStaticRecord` in `ses` (parsed-module token produced from module text via `@agoric/babel-standalone` + `@agoric/transform-module`) and adds it to the lockdown whitelist.
- **Why:** Compartment import hooks need a reusable opaque parsed-module reference.
- **Themes:** ses-lockdown, compartments, compartment-mapper
- **Status:** merged

## Description

Compartment import hooks will be obliged to eventually return ModuleStaticRecords. These are reusable references to a parsed module. The ModuleStaticRecord constructor produces an opaque token from module text.

### @kriskowal (MEMBER) — 2020-04-30T00:28:24Z

@michaelfig So, the rollup of SES for some reason excludes Babel and assumes it’ll be able to link against a `babel` global variable. So, to test that hypothesis, I added a script tag referring to `@agoric/babel-standalone`’s own `babel.min.js`. Then I set the document’s charset to UTF-8 since Babel has some non-ASCII regular expressions. Then I sandwiched another script to rename the global `Babel` produced by the babel bundle to the global `babel` received by the SES bundle. Then `transformModule` was missing. That was enough progress to conclude that for some reason, rollup is not capturing any of the SES dependencies. So this is another Rollup configuration issue. It looks like @jfparadis ran into similar problems and had to divide the integration test between a Browserify component and a Rollup component.
