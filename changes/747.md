## Summary

- **What:** `@endo/compartment-mapper` sorts compartment-map keys (using `Object.keys` and `Array.prototype.sort`) so that emitted archives are byte-deterministic.
- **Why:** Non-deterministic ordering produced different archive bytes across runs, blocking reproducible Endo archives; reviewers also raised whether sort/keys should be stashed against future vetted-shim threats.
- **Themes:** compartment-mapper, bundle-source, security
- **Status:** merged

## Description

This change addresses a non-determinism bug in the production of compartment maps and is necessary for consistent production of archives.

> I defer to @erights, but stashing the globals here is not providing any protection that’s not better served by lockdown. This is just in keeping with the rustic style and I’d be happy to back it out if it improves readability.

Once we support vetted preloads (such as vetted shims), the vetted preloads will run after basic safety repairs but before `lockdown`. The primordials will still be mutable in this state. We also expect to propose support for vetted preloads.

So, for each thing the SES shim is getting from the primordials, we need to ask ourselves how we expect to specify that aspect of SES. For example, if we sort, do we want to use whatever the current value of `Array.prototype.sort` is, or do we want to specify that we use the internal builtin sort? If the latter, then we need to sample these before a vetted preload can corrupt it.

In addition, the shim only does currently support `__allowUnsafeMonkeyPatching__`. This raises the same issue. Do we want this unsafe monkey patching to disrupt SES internal mechanism, or do we want it only to be able to foul its own nest?
