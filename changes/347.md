## Summary

- **What:** Adds `endo`'s `archive.js`, a variant of `import` that loads the compartment graph from disk and writes a Zip archive containing all modules plus a rewritten compartment map (one `name@version#unique` directory per compartment).
- **Themes:** bundle-source, compartment-mapper
- **Status:** merged

## Description

The archive module is a variation on the import module.
After loading a compartment graph off disk, instead of executing the
entry module, it creates a Zip archive of the working set of modules
and a compartment map.

The bulk of the work in archiving is rewriting the compartment map
to match the archive layout.
Instead of having packages scattered hierarchically on the file system,
the archive has a single directory for each compartment.
The compartment names are arbitrary, but must be unique and ideally
human-readable, so the format is name@version#unique.

Looks good. Am I correct in believing that you use a recording import hook to accomplish a form of tree-shaking? You load the modules just enough to learn what their `import` statements are, and then only populate the archive with the modules that were actually imported?

If we didn't do that optimization, would the archive creation be usefully simpler? We'd walk the exported modules list from each compartment and copy everything into the archive.

Oh, but, does that exported-modules list include aliases like `index.js` and alternate spellings like `foo`/`foo.js`/`foo/index.js`? That would make it a poor source for enumerating importable modules. So maybe doing the recording load is the better option.
