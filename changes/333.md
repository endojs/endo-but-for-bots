## Summary

- **What:** Strips ~1500 lines of duplicate logic from `@agoric/harden` and `@agoric/make-hardener` that was redundant with `ses`, removing pre-`lockdown` and `makeHardener({...options})` paths.
- **Why:** Calling `harden` outside `ses`/before `lockdown` is now discouraged because multiple hardens don't compose efficiently; this is a deliberate compat break.
- **Themes:** ses-lockdown, chore
- **Status:** merged

## Description

The code for `harden` and `make-hardener` had all sorts of logic that was redundant with ses, possibly out of sync with ses, and in any case a maintenance burden to keep in sync. All of this in support of the now-obsolete use of `harden` outside ses and/or before `lockdown`.

This PR removes the bulk of this obsolete logic. It is a compat break to any code calling `makeHardener` with any options or trying to use `harden` prior to `lockdown`.

### @kriskowal (MEMBER) — 2020-06-01T02:34:58Z

Discussed offline:

One of the tensions evident here is needing to test `harden` before a SES `lockdown`, though it’s clear that `harden` before `lockdown` is not a mode we wish to support.

The `harden` package exists in order to support this `harden` but-without-SES `lockdown` mode that we’re no longer pursuing. The `make-hardener` package remains sensible as a utility of `ses` that we expect no other package to use. But, publishing a package that no other package should use is arguably telegraphing the wrong message.

The `harden` package also serves as a built-in module shim. We’ve decided to at least temporarily decouple the SES proposal from built-in modules to de-risk SES, so users can expect there to be a global `harden` instead. This answers all our questions for now about how to feature-detect and shim.

Between these, we can make an argument that we should at least deprecate `harden` (publish a new breaking-changes version with no API, only a deprecation message that explains that `harden` is now a global that the `ses` shim provides, that only works in combination with `lockdown`: accept no substitutes).

We also could make an argument that `make-harden` should be subsumed into `ses` and deprecated.

For purposes of review, we would be looking to ensure that the invariants of `harden` are preserved after this change. To that end, it would be desirable to copy the `make-hardener` and `harden` tests into `ses`, where they can be exercised in the only sensible configuration: after `lockdown`.

Then it would make sense to move the `make-hardener` implementation into `ses`, as it would not be used or testable anywhere else.

After we’ve ensured that we’re maintaining the invariants established by the existing tests, it would make sense to deprecate the `harden` and `make-harden` packages.
