## Summary

- **What:** Fixes XDG conventions in `@endo/where`: corrects `XDG_CACHE_DIR` to `XDG_CACHE_HOME`, applies XDG everywhere (Darwin/Windows except the named pipe), and separates state from cache; threads OS info through the API.
- **Why:** Daemon needs persistent state (logs, snapshots) versus runtime artifacts (PIDs, sockets) clearly delineated.
- **Themes:** daemon, ecosystem-compat
- **Status:** merged

## Description

1. There’s a typo for `XDG_CACHE_DIR` that should be `XDG_CACHE_HOME`
2. `XDG` prefixes should be respected everywhere, including Darwin and Windows, except (probably) for the named pipe on Windows.
3. State and Cache should be clearly delineated, except on Windows where there does not appear to be an (obvious) separation within its native conventions.

Based on feedback out of band, I intend to use whereEndoState to locate anything intended to persist between daemon restarts, including logs. I no longer have anything in mind for whereEndoCache. whereEndoSock is using the runtime directory for PID files and Unix Domain Sockets.

Thank you for these constructive notes. For now, at least at this layer, I think it’s helpful to say Endo is “Docker but JavaScript”. The Docker part implies confinement of the guest programs, and that’s intentional. As with all other “X but Y”, the framing doesn’t capture the whole, but I find that it helps inform the shape of the CLI, since there are analogues and UX patterns that we can usefully borrow to foster familiarity.

Endo is also “Browser but just Extensions”, “Browser but Decentralized”, “Chat but mostly with Bots”, or a number of other useful framings. Another useful framing is:

Microsoft unified the office productivity segment (word processor, spreadsheets, &c) with object linking and embedding (but mostly, copy and paste). Endo is (aims to be) that except improving the suite of (chat, web, apps, authentication, authorization, key management, and wallets) with object linking and embedding. You can `@` _anything_.
