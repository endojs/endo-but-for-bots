## Summary

- **What:** Migrate `@endo/compartment-mapper`'s JSDoc types to dedicated `.d.ts` files (with manual conversion of `internal.d.ts`/`external.d.ts`), thread compartment name through exit import hooks, relax `ERef` to `Promise` in some shapes, regularize `@module` pragmas, and flip `checkJs` on by default.
- **Why:** `.d.ts` lets option groups extend each other without intermediate names, exposing structural mistakes (e.g. `languageForExtensions` misplaced on the import path); also enables stripping types from bundles.
- **Themes:** compartment-mapper, types, docs
- **Status:** merged

## Description

This refactor converts the JSDoc types in Compartment Mapper with TypeScript definitions. It also takes liberty to use our new trick for omitting types from bundles, but leaving continuity through importing types from JavaScript sources.

Much of this conversion was automatic, except `internal.d.ts` and `external.d.ts` are manually converted. Much of the motivation for this change was to take advantage of the expressivity of `.d.ts` over jsdoc typescript documents, allowing option groups to extend each other without otherwise useless intermediate names. The motivation for that consolidation, in turn, was to ensure that certain symmetries are preserved. For example, execute options are threaded through all functions that ultimately execute. I was looking specifically at the `languageForExtensions` option, which we misplaced on the `import` path when it belonged down the `mapNodeModulesPath`. That fix comes separately.

### @boneskull (MEMBER) — 2024-11-05T22:52:18Z

For type-checking, I'd strongly recommend just renaming `.d.ts` files to `.ts` files.

Using `skipLibCheck: false` makes us responsible for the correctness of the types of our dependencies--not just our own. To solve problems, we might have to do things like:
- Introduce a new dependency to fix a "missing" type only
- "Missing" types may have no actual impact on our own type fidelity (as we're not guaranteed to be actually _using_ any of those types)
- "Missing" types may have no actual impact on the type fidelity of our users (and probably won't)
- Incorrect types may need to be fixed by using module augmentation
- Incorrect types may need to be addressed via `patch-package` (or whatever `yarn` does here) . Those fixes will not cascade to our consumers unless we use lifecycle scripts

A concern is that using `.d.ts` files guarantees that the files contain _only_ types. That is virtuous--but there are other ways to enforce this. I can think of:

- It's likely ESLint can be bent in this direction (someone probably has had this problem already)
- Use `export type * from './foo'` in a barrel `index.d.ts` may work; this barrel won't be typechecked, but everything else would, I think (haven't tried this)
- PR reviews 😄 

We can also use [emitDeclarationsOnly](https://www.typescriptlang.org/tsconfig/#emitDeclarationOnly) to ensure no `.js` files are ever generated. This won't _enforce_ that the `.ts` files remain execution-free, but it will prevent compilation to JS.
