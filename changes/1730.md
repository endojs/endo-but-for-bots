## Summary

- **What:** Corrects the typed location of `assert.fail` in the new `@endo/assert` package and renames the exported `error` utility to `makeError` (undoing internal name drift from ses' `assert.js`); withdraws unused `makeAssert`.
- **Why:** The d.ts had `fail` on the wrong namespace; reviewers floated renaming the package to `@endo/errors`.
- **Themes:** errors, types
- **Status:** merged

## Description

`assert.fail` was correctly on the newly exported `assert` object and not in the exported utility functions. But the types seemed to imply otherwise.

### @erights (CONTRIBUTOR) — 2023-08-23T17:08:39Z

Agree that it is not clear which way to resolve this, and that your points for moving `fail` into the exported utility functions make sense. Counter points

   * Even though this assert package never mentions the term `Fail` in anything it exports, we will always rename `throwRedacted` to `Fail` on import. Putting `fail` and `Fail` into the same namespace still seems unpleasant. This package, where we separate out the assertions on `assert` from the exported assert utility functions is our opportunity to put them in separate namespaces.
   * `fail` is kinda the degenerate case of the various assertion functions: `assert.string` -> `assert.typeof` -> `assert` -> `assert.fail`. Not compelling by itself, but an adequate rationalization given the first bullet.

### @erights (CONTRIBUTOR) — 2023-08-23T21:15:19Z

In light of internal discussions that did not resolve the question above, I added a commit that 
   * withdraws `makeAssert`, as we have not found it useful in practice, and mostly have not used it.
   * renames the exported `error` utility function to `makeError`, which is much more understandable as a standalone function (and which actually happens to undo the internal rename of this function in ses' `assert.js` module).

I kept this as a separate commit so that we could easily back out of these additional changes if we decide to before merging this PR.
