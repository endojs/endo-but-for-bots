- **Themes:** ses-lockdown, errors

## Description

From the text added to `NEWS.md`

* The `assert.quote` function re-exported by `@agoric/assert` as `q`
  has always done only a best effort stringify, intended only to
  be interpreted by a human under benign conditions. Within that constraint
  its best effort is now better, providing informative though ambiguous
  renderings of values problematic for `JSON.stringify`, still including
  cycles, but now also functions, promises, `undefined`, `NaN`, `Infinity`,
  bigints, and symbols.

### @erights (CONTRIBUTOR) — 2021-02-25T04:10:29Z

@michaelfig just brought the stringify function at https://github.com/Agoric/agoric-sdk/blob/master/packages/cosmic-swingset/lib/ag-solo/vats/repl.js to my attention, which is the Print part of our REPL. This has the same overall goal -- to be a best effort rendering of an object to be informative to the human at the REPL, without any reversibility or desire to support any automated processing. I think the `bestEffortStringify` here and the `q` function people use to get to it should not be gratuitously different, which looks easy. Two interesting differences will remain:
   * The REPL is at a higher level of abstraction, sitting on top of SES, Endo, and more of our infrastructure. By contrast, `assert` is at the SES level of abstraction. It is below most of SES in that it must work before `lockdown` and the SES implementation itself must be able to call it. Thus, while the REPL, for example, knows about presences, `bestEffortStringify` cannot. I don't think this difference is a big deal in practice.
   * `bestEffortStringify` customizes the output using a replacer to parameterize `JSON.stringify` itself. As a result, it can only render a valid JSON string, leading to all the ambiguity in interpretation. Is `"undefined"` and encoding of `undefined` or `'undefined'`? There's no way to tell. By contract, the REPL's `stringify` is more like the Node console, it that it is JSON-like but purposely leaves JSON syntax when showing values that don't encode into JSON.

So @FUDCo , I'm curious about your reaction to the second bullet above. The REPL's `stringify` is better at being human interpretable because it leaves JSON. For a best efforts rendering intended only to be human informative, is this the right tradeoff here too?

### @FUDCo (CONTRIBUTOR) — 2021-02-25T19:20:34Z

> Attn @FUDCo the blocking question above:
> 
> > So @FUDCo , I'm curious about your reaction to the second bullet above. The REPL's stringify is better at being human interpretable because it leaves JSON. For a best efforts rendering intended only to be human informative, is this the right tradeoff here too?

This is one of those things that vary a bit by use case, unfortunately.

The REPL-style stringify is better in those contexts where it is chosen primarily on grounds of legibility.  In particular, the generated strings are very often embedded inside *other* strings (e.g., in diagnostic messages or error strings) that are not themselves purporting to be or attempting to be (nor even plausibly ever could be) JSON parseable.  In these use cases you just want a convenient quick-n-dirty rendering in human readable form (literally, "stringify").  In practice `JSON.stringify` often gets used in these situations because it is easy to use and universally available, even though the fact that it will choke on BigInts or circularaties means something akin to `q` would be a better tool for the job.

However, another use case is generating things like structured log entries that are expecting to be processed in bulk by automation, where being parseable as JSON is very important *but* where faithful round-trip reproduction of the original objects is not a requirement nor an expectation.  In my experience it is common in such cases for some parts of the data to be interpreted by the automation in detail (and thus require some level of accuracy) and others more as annotation (where it's being used more like a kind of structured string literal).  The original producer of the original stringified object needs to make sure that the parts that are going to be interpreted in detail are always things that can be faithfully rendered by JSON, but this has never in my experience ever been any source of difficulty.  In such cases, rendering everything that doesn't have a direct JSON representation as, say, a string is fine (possibly with some simple annotation *inside* the string, such as putting the value in brackets or the like, to act as a hint to a human reader as to what's going on).

longior, non legi: in some circumstances one strongly prefers human readability and in others one really requires parseable JSON.  In other words, there's no universal One Way To Do It.  I'm not sure this is the answer you were seeking, but I think that's the answer.

### @FUDCo (CONTRIBUTOR) — 2021-02-25T19:37:45Z

> @FUDCo @michaelfig @kriskowal
> Reviewing [Agoric/agoric-sdk#2486](https://github.com/Agoric/agoric-sdk/pull/2486) reminded me of the `abbreviateReplacer` which @dckc copied from the kernel. Given the purpose of `q`, should this PR also fold this abbreviation logic into `bestEffortStringify`? If so, should `q` then replace these uses of `abbreviateReplacer`?

The `abbreviateReplacer` is being used in `testLog`, and was originally used for the purpose implied by its name, which is to truncate long strings (remember, `testLog` is generating an in-memory log to be used as fodder for checks in unit tests).  It got augmented to also guard against BigInts, which started appearing in the stuff being logged and causing tests to crash, and it was the latter problem that I think motivated Dan's incorporation of it.  This, however, is a very special use.  I'm not at all sure that string truncation is a thing we want universally, though we *do* want robustness against BigInts.  **But**, the specialized string truncation logic is realized by a replacer, which is not a thing Mark's encoder supports, so I don't know that we can satisfy all the constraints concurrently.

My hot take is: don't do string truncation in `q` and just continue using `JSON.stringify` with a replacer in `testLog`.  The uses of `testLog` are sufficiently narrow, specialized, and within our sphere of control that it's not unreasonable to put the obligation to avoid the limitations of JSON encoding on the caller of `testLog`.
