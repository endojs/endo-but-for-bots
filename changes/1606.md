## Summary

- **What:** Adds `assert.bare` (initially `assert.raw`) in `@endo/ses` for embedding unquoted strings inside `details` tagged templates and improves the remotable matcher error message.
- **Why:** Replaces the awkward "quoting without quotes" idiom of pre-splitting template strings around the value to insert.
- **Themes:** errors, ses-lockdown
- **Status:** merged

## Description

When working on #1600 and #1605, I noticed patterns like
```js
// quoting without quotes
const details = X([`${realKind} `, ` - Must be a ${kind}`], specimen);
```

Rather than manually manipulating the input of a function intended for use in tagged templates (and mixing up the order in which parts appear), it seems more clear to have a function that is like `quote` but does not add quotes (replacing the above with ```const details = X`${r(realKind)} ${specimen} - Must be a ${r(kind)}`;```). Also tagging @FUDCo, who IIRC has asked for this in the past.

### @gibson042 (MEMBER) — 2023-06-03T01:34:56Z

> Also wonder about the decision to fall back on `quote` if the payload is not a string (or whatever additional test) vs error if not a string. I think I like the fallback better too, but would like to hear your thoughts.

The reason for the fallback to `quote` is pragmatic—this code supports error visibility, and inappropriate construction of details (or a successful attempt to put a details-relevant variable into an unexpected state) should not preclude best-effort rendering of the original details. For example, I'd rather have ``` X`shape violation: ${value} of tag type ${raw(tagType)} is not a Pattern` ``` render like «_shape violation: (an object) of tag type "$#*!" is not a Pattern_» than see another error in place of the "shape violation" message, similar to how [marshal makes an exceptional allowance for non-hardened Error instances](https://github.com/endojs/endo/blob/7a685f59a8f61c63da9dbec5ef78cec0d1b17d3b/packages/marshal/src/marshal.js#L101-L104).
