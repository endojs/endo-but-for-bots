### @kriskowal — COMMENTED — 2025-06-24T20:13:29Z

Preliminarily, I think we should have this and more like it.

You mention that there are overlapping concerns with the `powers.js` conventions in Compartment Mapper (and elsewhere). The substance of those conventions is that the web/node/xs portable portion of a package should be the primary functionality exported by a package, and the package *may* provide convenient adapters for constructing those powers from the material laying around in Node.js, the web, or whereever. This package, like `@endo/stream-node`, adapts Node.js APIs to a more portable, netural, and ocappy interface. So, I’d expect to import the powers types from `@endo/pola-io` and have `-node-` or `-web-` and `-powers.js` somewhere in the module specifier to indicate which platform the power maker adapts. I chose to make `make*Powers` functions pluck methods in-situ from Node.js modules for ease-of-use, but without obviating the option of letting the caller pluck the methods themselves.

I think `fetch` highlights a need for a category of `powers.js` that can be made from material that is laying around both on the web and node, but I also would be content with using `@endo/pola-io/web-powers.js` to make web powers even if I’m using the `fetch` as implemented in Node.js.

I think there’s an opportunity to build on `@endo/stream` and `@endo/stream-node` with this package, but not necessarily in the first cut. I believe you’ve left the requisite void for that feature to fill, in the way that the `fetch` API produces a `Readable` that in turn has `text()`, `json()`, but also a `body` `ReadableStream`, we have the option of adding a streaming read method to a file cell later. Ideally, we share an abstraction between readable cells on the web, on a file system, in a zip file.

The pet daemon has an Exo for a readable cell of its CAS. That overlaps too, but this is beneath the Exo layer. We should just have a coherent approach. The Readable cell in Dæmon happens to have `text()` and `json()` like the web’s fetch/ReadableStream, and also `sha512()` since that’s laying around. I think Exo-layer streaming is still an unsettled design issue, but at *this* layer definitely should be `stream()` returning an AsyncIterator or AsyncIterable of Uint8Array. At the Exo layer, that’ll be hardened immutable ArrayBuffers over some other streaming protocol that may resemble iterator protocol, but maybe not.

I am hoping that I can convince you to avoid abbreviation in the public names exported by this package, like `makeCommand` over `makeCmd`, `makeReadableFile` and `makeMutableFile` over `makeFileRd` and `makeFileRW`.
