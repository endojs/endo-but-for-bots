## Summary

- **What:** Threads source-map generation through `@endo/static-module-record` (`sourceMapHook`), `@endo/compartment-mapper`, `@endo/bundle-source` (writes per-user cache, on by default), and `@endo/import-bundle` (reunites with cached maps); locates the cache via `@endo/where`.
- **Why:** First half of mitigating #926 — gives debuggers usable source positions for SES-bundled modules without bloating the bundle itself.
- **Themes:** bundle-source, compartment-mapper, daemon, tooling
- **Status:** merged

## Description

This change, as documented inline, introduces a per-user source map cache and all the necessary instrumentation for generating and reuniting a local debugger with these generated source maps.

This change is one of two steps toward mitigating #926, with the other being a better Babel code generator. This addresses debugging where the other better addresses auditing and debugging in production.

I’ve elected (and open debate) to have `bundleSource` generate source maps by default. This is acceptable only because the cache only creates one entry at a time for every physical module location on the user’s system. So, clearing caches should not be necessary in most cases. The cache cache _can_ be found with the Endo CLI (`endo where cache`), and I expect to add an `endo cache clear` command to make this easy. So, this is sharing some infrastructure I built originally for the Pet Dæmon but is suitable for this purpose.

@mhofman expressed a desire to be able to pin source maps for historical bundles. This is certainly an option in the fullness of time. The Pet Dæmon prototype (branch `endo`) has a similar need for pinning and garbage collection, based on pet names.
