## Summary

- **What:** Fixes `ses` module-instance caching so a module whose `execute()` throws is not corrupted: the error is captured and rethrown on subsequent imports rather than re-running `execute`; covers `try { require(x) }` user patterns and falsy throws.
- **Why:** Closes #1116 — user code that catches `require` errors previously left the module half-initialized and re-ran top-level on retry.
- **Themes:** compartments, errors, ecosystem-compat
- **Status:** merged

## Description

fixes #1116

I didn't observe negative consequences of calling activate() more than once, but that could be avoided.

ALso, it would be possible to hold on to the error and rethrow it instead of running execute each time, but I think that could get cached higher the dependency chain than needed.

### @kriskowal (MEMBER) — 2022-03-17T21:03:55Z

From our conversation out-of-band, consider dependency graph A imports B imports C. If you import A, you’re arranging for a working set that will initialize in order C, B, A. My expectation, which requires confirmation, is that if B were to throw an error during initialization, that error would contaminate A but not C. So, any subsequent import that depends on B or C would replay the same error, but A would be fine. No module should ever be initialized twice, or initialized at all if one of its dependencies failed to initialize.

I can confirm this. In addition, if a module that is within an import cycle throws an error, it contaminates everything in its cycle, even if some others had started earlier.

Put another way, any directed graph can be considered to be a directed acyclic graph of *strongly connected components*. A failure contaminates its own strongly connected component and all dependent strongly connected components.
