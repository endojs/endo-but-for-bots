## Description

Many of Endo’s modules would be useful before lockdown but, until #2976, we did not have a strategy for implementing a module that could use `harden` without obligating the environment to be locked-down first. New strategies emerged with the insight that we can have `@endo/harden` “race” to provide a fake `harden` upon first invocation, in a way that prevents `lockdown` from succeeding, so partitioning the supported applications strictly between those that use `lockdown` and therefor only use a reliable `harden` after `lockdown`, or those that use a fake `harden` and _never_ call `lockdown`.

Consequently, we can now use `@endo/harden` throughout all Endo packages that use `harden` to enforce the defense of their integrity, so a single implementation can work with or without `lockdown`. This change validates #2976 by performing all necessary ramified relaxations necessary to make the Endo stack work without `lockdown`, without compromising its post-lockdown integrity. This change also makes some adjustments to `@endo/ses-ava` to allow a each package’s test suite to be used in a no-lockdown or post-lockdown configuration, and the changes necessary to adopt this feature in all improved packages.

These relaxations generally take two forms:

1. We do not have a mechanism in place that allows `@endo/ses-ava` to unredact error messages before lockdown, so many tests need to generalize their error message pattern matching to tolerate redaction. This is a potentially reversible commit, so it is separated.
2. Some pass-style invariants presume a functional `harden` and needed to relax in the presence of `harden.isFake`. These relaxations were previously accomplished with `lockdown` in `unsafe-fast` `hardenTaming` mode, which cheated by lobotomizing the MOP. With these relaxations, `unsafe-fast` may become unnecessary.

### Security Considerations

This change merits both close design and implementation review and is emphatically not small. To ease review, the changes are in individually reviewable commits to make obvious which changes are mechanical or closely related.

Particularly, the changes that relax `isFrozen(x)` to `!harden.isFake || isFrozen(x)` rely on `harden.isFake` being inviolable in a `lockdown` environment. To that end, it should be noted that `@endo/harden` selects to reflect either `globalThis.harden` or a new `Object[Symbol.for('harden')]`, preferring the former, and the former can be deliberately corrupted by the creator of a `Compartment` by replacing `globalThis.harden`, or be corrupted by any module sharing a compartment with a mutable `globalThis`. `importBundle` by default creates compartments with a frozen `globalThis` _but can be configured not to_.

It is possible to reverse the precedence of `globalThis` vs `Object`, but the hazard of providing a corrupted `globalThis.harden.isFake` is very small and being able to configure `globalThis.harden`, even a fake one, on a compartment-by-compartment basis may be useful.

- [ ] This is in any case a design consideration this change puts before its reviewers.

### Scaling Considerations

This change does slightly increase the linkage size for Endo modules, and benefits from `-C hardened` as a build condition to slightly mitigate the increase in size. Omitting the fake implementation of `@endo/harden` is unlikely to make bundles much smaller. The previous attempt at this feature, #2782, provided a much larger pre-lockdown implementation of `harden`.

### Documentation Considerations

The news for the affect modules should be sufficient for now to signal that these packages can be used without `lockdown`.

- [ ] We have long needed to provide an article with guidance on how to make “hardened modules”, modules that defend their interface against supply chain attacks, and with this change, we can add a footnote that this defensive posture does not come at the expense of usability without `lockdown`.

### Testing Considerations

This change mostly concerns the relaxation of tests so that they pass with or without `lockdown`. The machinery to do dual mode testing is included.

### Compatibility Considerations

This change is intended to be backward compatible.

### Upgrade Considerations

Per #2976, this change accounts for new modules on old versions of SES, which is the primary consideration for upgrade. 

- [ ] This change must be accompanied by a passing integration test in Agoric SDK.
