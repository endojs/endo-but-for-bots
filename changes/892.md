### @mhofman — COMMENTED — 2021-09-17T18:55:50Z

So how much of this is spec violation by v8, and how much is spec issue?

From my reading of the spec, `freeze` is not guaranteed to succeed, and the namespace exotic object should not allow [setting a property to `writable: false`](https://tc39.es/ecma262/#sec-module-namespace-exotic-objects-defineownproperty-p-desc), whether that's through a user `defineOwnProperty` or through [`freeze`](https://tc39.es/ecma262/#sec-setintegritylevel)'s internal [`DefinePropertyOrThrow`](https://tc39.es/ecma262/#sec-definepropertyorthrow) call.

I'm also unclear on the actual impact to proxy. Sounds like the proxy invariants are themselves respected, just that the target is breaking more fundamental invariants. What security risk does this bear onto proxy? Is it in the same category as Host exotic objects which may not respect language invariants?

Regarding the shape of the PR, I'm a little uncomfortable merging a test for a behavior that's broken without clearly marking that the expected behavior is not the one being tested.

### @mhofman (CONTRIBUTOR) — 2023-07-05T20:20:18Z

I [contributed a test262](https://github.com/tc39/test262/pull/3213) that checks that module namespace exotic objects cannot be frozen, which was used by [v8 when fixing their implementation](https://github.com/v8/v8/commit/fee41d59b60d4d36d091e0a2e5fb5b4508b1e9f0).

We can port the test262 test here, which basically creates a module namespace object with `let` exports (which under all future specifications must stay writable), and verifies that freezing the namespace object will not make the property non-writable. However I still don't know how such a test can be included in this repo given it will fail under some of the engines we support (namely Node 16 LTS)

The v8 fix landed in v8 version `9.6.155`, which has been part of node since [17.2](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V17.md#2021-11-30-version-1720-current-targos). As such it's included in 18 LTS but not 16 LTS.
