# Host-Held `idForRef` for Every Formula-Generated Object

|---|---|

| **Status** | Not Started |
| **Source** | kriskowal's approving review of [#1306](https://github.com/endojs/endo-but-for-bots/pull/1306#pullrequestreview-5253000171) (slice 2/3 of #1125), 2026-09-19 |

## What is the Problem Being Solved?

The daemon keeps one reverse table from live references to formula
identifiers: `idForRef`, a `WeakMultimap` in `makeDaemonCore`
(`packages/daemon/src/manager.js`), populated only by `evaluateFormula`
when a formula's maker returns a value. Every "is this a capability this
daemon minted, and which one?" question goes through it: `getIdForRef`
(injected into `makeHostMaker` and `makeDirectoryMaker`),
`mustGetIdForRef` (the `marshal` formula's marshaller, so `storeValue`
and mail send), and `getLocalIdForRef` (the residence tracker).

That table answers only for the *top-level value* of a formula, and only
when that value is `typeof 'object'`. Everything else a formula's value
mints is invisible to it:

| Minted object | Maker | Formula identity today |
|---|---|---|
| `EndoDirectory.readOnly()` view | `makeReadOnlyDirectoryView` via `makeDirectoryNode` (`directory.js`) | none: a memoized local exo |
| mailbox and message-hub read-only views | `makeReadOnlyDirectoryView` in `manager.js` (`mailReadableView`, `messageReadableView`) | none |
| `EndoMount.lookup()` sub-views, `entry()`, opened files, `readOnly()` trees and blobs | `makeMount`, `makeReadableTreeView`, `makeMountFileExo` (`mount.js`) | none; tracked instead in the `mountRecords` side `WeakMap` |
| read-only Git faces | `@endo/exo-git` (`isGitReadOnly`) | none; recognized by a brand predicate |
| function-valued formula results (a `Far` function from `eval`, for example) | any maker | none: `evaluateFormula` skips `typeof value === 'function'` |

The consequences are concrete and already visible in merged code:

- **#1306's `networks` option does not accept the read-only view it was
  written for.** `getAgentDirectoryId` (`host.js`) calls `getIdForRef` and
  demands `formula.type === 'directory'`, so
  `provideGuest(name, { networks: await E(dir).readOnly() })` throws
  "networks must be a daemon-minted directory". The PR body promised the
  opposite.
- **`provideHostPath` refuses mount sub-views and read-only mounts**
  because "those exos do not have a formula identifier so we cannot prove
  they were minted by this daemon" (its own docstring). Callers must
  re-mint `provideMount` against a host path they are not supposed to
  need.
- **`storeValue` and mail `send` reject these objects** with "No
  corresponding formula for …" because the marshaller's `mustGetIdForRef`
  misses. A guest cannot pet-name or forward the read-only view a host
  handed it.
- **Parallel identity tables grow beside `idForRef`**: `mountRecords`,
  the Git brand check, and the per-view `cancelled` liveness flag in
  `makeDirectoryNode` each rebuild a piece of formula identity (provenance,
  attenuation, revocation) that the formula graph already provides.

The maintainer's direction (the review, verbatim): *"I would actually like
`idForRef` to work properly for any object generated by a formula, but
that `idForRef` should be closely held by hosts and not provided to
guests. That migration does not need to occur in this change, but
creating an ephemeral wrapper object to make a formula identifier
inscrutable to the host is not a goal."*

## Goals and non-goals

Goals:

1. `getIdForRef(ref)` returns an identifier for **every** object a formula
   generates for export: the formula's own value (object *or* function)
   and every attenuated face its value mints.
2. Ref-to-id translation stays **host-held**: no guest-facing method,
   and no guest-reachable composition, turns an arbitrary reference into a
   formula identifier.
3. Retire the parallel identity side tables (`mountRecords`, the read-only
   view liveness flag) in favor of the formula graph's own dependency
   and cancellation.

Non-goals (anti-design steers):

- **No ephemeral wrapper objects that hide a formula identifier from the
  host.** A face whose purpose is to be unrecognizable to the daemon is
  exactly the gap this design closes. Considered and rejected: keeping
  `readOnly()` as an identity-free exo "so the host cannot see it".
  Reason: maintainer anti-goal; the host already holds the parent's
  authority.
- Promises stay out of `idForRef`, as the table's own comment states
  ("not for 'what is my name for this promise'"). Promise formulas keep
  their existing `formulatePromise` path.
- No change to the 256-bit identifier format
  ([daemon-256-bit-identifiers](daemon-256-bit-identifiers.md)).

## Design

### Derived formulas

Every attenuated face becomes the value of a **derived formula**: an
ordinary persisted formula whose record names its parent and the
derivation, whose maker runs in the daemon (no worker), and whose
lifetime is tied to the parent by `context.thisDiesIfThatDies(parentId)`.

| Formula type | Record | Value |
|---|---|---|
| `readable-directory` | `{ hub: <directory, mailbox, or message-hub id> }` | the `makeReadOnlyDirectoryView` exo over the provided hub |
| `mount-view` | `{ mount: <mount id>, path: string[], readOnly: boolean }` | the sub-view or read-only `ReadableTree` |
| `mount-file` | `{ mount: <mount id>, path: string[], readOnly: boolean }` | the `EndoMountFile` or `ReadableBlob` face |
| `git-view` | `{ git: <git id>, readOnly: true }` | the read-only Git face |

The formula number is **deterministic**: `sha256` over the parent
identifier, the formula type, and the canonical (sorted-key JSON)
record. Re-deriving the same face therefore yields the same identifier,
so:

- `readOnly()` stays idempotent without a per-object memo, and a guest
  looping `readOnly()` or `lookup()` does not grow the formula store: the
  store grows only per *distinct* derivation, and formula collection
  reclaims unreferenced ones like any other formula.
- CapTP identity (`===` across a round trip) and formula identity agree.

Deriving goes through one core helper,
`formulateDerived(parentId, type, record)`, under
`withFormulaGraphLock`, which either returns the already-live controller
for the deterministic id or formulates and evaluates it. The exo makers
(`makeDirectoryNode`, `makeMount`, the mailbox makers) call that helper
instead of calling `makeReadOnlyDirectoryView` / `makeReadableTreeView`
directly, so no face reaches a caller before it is registered in
`idForRef`.

Revocation moves onto the graph: cancelling the parent formula cancels
the derived formula, whose maker's `context.onCancel` severs the face.
The `cancelled` flag in `makeDirectoryNode` and the `revocation` record's
role as a provenance carrier go away; the `revocation` record stays only
as the mount's filesystem-level kill switch.

### Functions

`evaluateFormula` registers any value where
`(typeof value === 'object' && value !== null) || typeof value === 'function'`
in `idForRef` and `refForId`. `getLocalIdForRef` already accepts
functions; this aligns the writer with the reader.

### Consumers after migration

- `getAgentDirectoryId` accepts `directory` for `pins` and
  `directory` **or** `readable-directory` for `networks` (network
  enumeration reads through the view's hub id). This delivers what #1306
  described.
- `provideHostPath`, `provideGit`, `provideShell`, and `provideGitClone`
  resolve a `mount-view` by walking `mount` and `path` to the top-level
  `mount` / `scratch-mount` formula, which remains the only thing with a
  host path, and carry `readOnly` forward as an attenuation that can
  only narrow.
- The marshaller needs no change: every face now has an id, so
  `storeValue` and mail `send` accept them.
- `mountRecords` is deleted; `provideHostPath` reads the formula.

### Host-held, guest-withheld

`getIdForRef` and `mustGetIdForRef` remain **daemon-core closures**.
They are injected only into makers whose returned faces are host
authority (`makeHostMaker`) or whose use returns *names, never ids*
(`makeDirectoryMaker`'s `reverseLookup`, the marshaller, the residence
tracker). The invariant to hold, and to test:

> A guest can learn the formula identifier of a value only by naming it
> first (`identify`, `locate`, `listIdentifiers` on its own pet store).
> No guest-reachable method maps an arbitrary reference to an identifier,
> an identifier-bearing locator, or the formula record behind it.

Derived formulas raise the stakes of that invariant, since a
`readable-directory` record names the *writable* parent. Two existing
guards keep the parent out of guest reach and must stay host-only:
`getFormula` (host-only since [formula-inspector](formula-inspector.md))
and the formula graph snapshot. A guest that holds a read-only view and
names it learns only the view's own identifier, and `lookupById` of that
identifier returns the view, not its parent.

The guest's `makeGuestMaker` does not receive `getIdForRef` today; the
migration adds a regression test that asserts this at the maker's argument
list, so a future refactor cannot hand it over silently.

## Ownership map

| Boundary | Mechanism | Policy | Durable state | Lifecycle / commit authority | Value crossing |
|---|---|---|---|---|---|
| exo maker (directory, mount, mailbox) → daemon core | `formulateDerived` | the maker chooses the derivation type and record | the derived formula record (core) | core, under `withFormulaGraphLock` | `{ parentId, type, record }` in, the registered face out |
| daemon core → host facet | `getIdForRef` closure | host decides what to accept (`getAgentDirectoryId`, `provideHostPath`) | none new | core | a reference in, a `FormulaIdentifier` out, never re-exported |
| daemon core → guest facet | none: no ref-to-id closure | the invariant above | the guest's pet store | core | names only |

Persistent state is owned by the daemon core's formula store; commit or
discard is the core's formulate path; restart and replay reincarnate
derived formulas through `provideController` like any other formula; and
execution is always daemon-local (no worker) for all four derived types.
Naming check: the derived types name the *face* (`readable-directory`,
`mount-view`), not an outer policy concept such as "guest view" or
"network grant".

## Phased implementation

1. **Functions and the invariant test.** Register function values in
   `evaluateFormula`; add the guest-maker argument test and a guest-surface
   test that no `EndoGuest` method returns an identifier for an unnamed
   reference.
2. **`readable-directory`.** Add `formulateDerived` and the formula type;
   route `EndoDirectory.readOnly()` and the mailbox and message-hub views
   through it; delete the view liveness flag; extend
   `getAgentDirectoryId` for `networks`. Test: `provideGuest` with a
   read-only `networks` view, and `storeValue` of a read-only view,
   including across a daemon restart.
3. **`mount-view` / `mount-file`.** Route `lookup`, `entry`, file opens,
   and `readOnly()` through `formulateDerived`; teach the `provide*` host
   methods to walk to the top-level mount; delete `mountRecords`. Test:
   `provideHostPath` of a sub-view returns the joined path; of a read-only
   view, a read-only binding; revoking the parent mount severs every
   derived face.
4. **`git-view`.** Same for read-only Git faces; `provideGitRemote` keeps
   rejecting them by record, not by brand.

Each phase is a separate PR against `llm`.

## Design Decisions

1. **Derived formulas, not identifier-only registration.** Registering a
   face in `idForRef` under a synthetic, unpersisted id would make
   `getIdForRef` answer, but the id could not be pet-named, stored, or
   reincarnated, and revocation would still need a side table. A formula
   gives all three for the cost of a record.
2. **Deterministic formula numbers.** They bound the growth a looping
   caller can cause and keep `===` identity and formula identity aligned
   without a memo per face. The hash is one-way: a derived identifier
   reveals nothing about its parent's identifier, and computing a derived
   identifier requires the parent's, which already carries more authority.
3. **No public ref-to-id method in this design.** Hosts use `getIdForRef`
   through the host methods that already need it. See the open questions.

## Open questions

1. Should hosts get a public, host-only `EndoHost` method that returns
   the identifier for a reference (the ref-to-id counterpart to
   `getFormula`), or should `getIdForRef` stay internal to the daemon
   core, used only through host methods like `provideHostPath`?
2. Should mount sub-paths be derived formulas at every `lookup` depth, or
   only when a face is stored, sent, or passed to a host method (formulated
   on first use by `mustGetIdForRef` / `getIdForRef`)? The first is
   simpler; the second avoids a formula record for every transient
   directory walk.
3. Is it acceptable that `lookup` on a `readable-directory` continues to
   return the backing directory's live, writable children (the shallow
   attenuation documented on `ReadableNameHub.lookup`), or should this
   migration make the view recursively read-only by deriving
   `readable-directory` faces for nested directories?
4. The `endo-guest-stdio-mcp` bridge hands a guest's own identifier to a
   confined process through the environment. Should the invariant above
   explicitly allow a host to hand identifiers to guest-side processes,
   or should that path move to a capability handle?
