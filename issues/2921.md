## Description

In `@endo/compartment-mapper`, there was a type reference missing from `src/policy.js` (`SomePackagePolicy`).  This missing type caused a broken `src/policy.d.ts` upon generation of type declarations (from `prepack` script).

However, neither `tsc` nor `tsc -b tsconfig.build.json` raised an error about the problem.

At first glance, both `tsconfig.json` and `tsconfig.build.json` both reference [`tsconfig.eslint-base.json`](https://github.com/endojs/endo/blob/master/tsconfig.eslint-base.json) (which has both `compilerOptions`  `allowJs` and `checkJs` enabled). I have _definitely_ seen type errors come out of `tsc` in `compartment-mapper` before, so it's not like it's _completely_ broken.

Curiously, when I import the type in `src/policy.js` to fix the problem, the syntax highlighting in VS Code reports shows this type as unused (dimmed), even though a) it is referenced twice, and b) the references highlight as type errors when the type is missing.  It's possible this is a bug in TypeScript itself.

It's also worth noting that the references themselves are used in `@overload` blocks. 

Because these missing types only occur (for me) in the context of VS Code, it will be tedious to check each source manually.  However, the errors _do_ surface in the generated declaration files.

So then, one way to detect these issues more easily is so create a dummy package which:

- Depends on `@endo/compartment-mapper` 
- Imports all of its `@endo/compartment-mapper`'s exports
- Configures its `tsconfig.json` to use `skipLibCheck: false`

This should raise errors from the public API surface, at least.  

It's also likely there are some config flags that would help us. For example, if we used project references (though this suggestion has been repeatedly rejected due to it being a disruptive change to workflow), generated `.d.ts` files would be in use by workspaces depending on `@endo/compartment-mapper`; errors from its definitions would then become more apparent. Maybe strict mode would help? 

Open to any ideas.  There are known issues concerning types erroneously reported as unused, but I wasn't able to find something that looked like this one.

It's likely that this problem extends to all workspaces in this repo.
