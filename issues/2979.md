## Description

## What is the Problem Being Solved?

We currently have 2 different type definitions designating remotables:
- `RemotableObject`, a structural type expressing what `pass-style` considers to be a remotable object, aka one with a `Symbol.passStyle` property with a `remotable` value (and an interface spec for the `Symbol.toStringTag`).
- `RemotableBrand`, a "nominal type" that carries embedded in it (as a TS `private`) the "behavior type" of the remotable, so that operations like eventual-send can provide static typing for operations on these remotables. There is also an attempt for `RemotableBrand` to support ["aux data"](https://github.com/Agoric/agoric-sdk/issues/2069), which creates some complications.

On top of this we created a bunch of helpers like `Remote` in agoric-sdk to express whether a value may be a local remotable or a remote presence (as a type union of the behavior and of the remotable brand).

Exos, the `Remotable` tool, and Guard all express their return value as a combination (intersection) of the behavior type, `RemotableObject` type and `RemotableBrand` type.

## Description of the Design

A single type that describes a remotable object, capturing both the structure (pass-style symbols) but remains nominal carrying the behavior type.

I attempted this once before and ran into complications integrating with agoric-sdk, which has a lot of assumption of the type of some values (local vs remote, with or without pass-style symbols).

## Test Plan

Any changes in endo would need to be coupled with type fixes in agoric-sdk, and tested against them.

Having some regression testing of the type usages in agoric-sdk would likely facilitate the implementation (agoric-sdk relies a lot on `ReturnType` tricks and generics)

## Compatibility Considerations

While type changes are usually considered non-breaking, we should avoid regressions in agoric-sdk.
