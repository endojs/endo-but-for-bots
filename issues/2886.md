# #2886: compartment-mapper: captureFromMap incompatible with dynamic requires

## Description

I'm not sure how I missed this before, but I can note that there is no test of dynamic require which attempts the operations described below.

`mapNodeModules` creates a `CompartmentMapDescriptor` based on the state of a dependency tree.  When passing this `CompartmentMapDescriptor` into `captureFromMap`—to generate a minimal, absolute-path-less policy—any packages which are _only_ required dynamically will be tossed out of the resulting digested  `CompartmentMapDescriptor`; `captureFromMap` only _loads_ modules. Dynamic imports, by definition, are excluded from this operation.

If we use the resulting digested `CompartmentMapDescriptor` to generate policy (via `@lavamoat/node`), packages will be missing and their sources will not be inspected for globals, builtins, etc. (via `lavamoat-core`).  Passing the resulting policy _back_ into `importLocation()` results in many policy enforcement failures because the policy is insufficient.

`captureFromMap()` weaves `Sources` (which includes the byte arrays of modules and lists of imports/exports/etc.) into the resulting `CompartmentMapDescriptor`, and we (likely) need that information to be able to inspect these modules. It also determines which _modules_ are actually loaded instead of just which _packages_ (as `mapNodeModules()` does).

It may simply be that `captureFromMap()` is not fit for our purpose.  Ultimately, I don't think there _is_ a minimal policy when dynamic requires are involved. We could not know which packages were actually "used"  until _after_ runtime; even then, that minimal policy is not necessarily minimal for the _next_ execution. In other words, it seems dynamic imports/requires make "minimal" policy generation an impossible task.

If true, then `captureFromMap()`'s scope may need to be explicitly reduced to the archival use-case.

So I think we probably need a new API that does what `captureFromMap()` does but _does not_ do any tree-shaking.
