## Description

## Document Supported Platforms

Endo should document the list of browsers and runtimes that it intends to support.  This naturally correlates with the language features the platform implements.  Currently, `ses` is using [features from ES2022](https://caniuse.com/sr_es13).  From what I can interpret from the data, the (current) minimum supported browser versions are then:

| Browser | Version |
| ------- | ------- |
| Chrome  | 94+     |
| Edge    | 94+     |
| Firefox | 93+     |
| Opera   | 79+     |
| Safari  | 16.4+   |

For Node.js, `ses` currently appears to support v18.0.0+.

I don't know about XS or any other runtimes.

## Document Support Policy

It follows that Endo should determine _why_, _when_, and _how_ to drop support for old versions of platforms.  

I wouldn't recommend being too rigid about this. It's OK for the policy to be fuzzy, but it should nevertheless be documented.

## Tooling

Requisite to supporting platforms, Endo should assert it _actually_ supports the platforms it means to support. Practically speaking, Endo must run CI on those platforms.  

It's trivial to run CI against a specific Node.js version, so there's probably nothing to do here unless the build matrix needs updating.

For browsers, a service like SauceLabs or BrowserStack can provide this freely for OSS projects.  Given these tests are likely to be _slow & flaky_, it may be best to run them on a schedule (and as a pre-release task) instead of with every push to every branch.

Given _slow & flaky_, I would recommend keeping the browser build matrix as small as possible. The MVP could  be the minimum supported version of each browser. The next to add would be the latest version of each browser.  I'd also avoid duplicating browser tests against the same engine (if one Chromium-based browser passes, they likely all do).
