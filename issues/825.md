## Description

If `harden` throws while it's traversing and freezing an object graph – i.e., for the current implementation, during its `dequeue` step – the object graph will become partially hardened. If such a partially hardened object were, for example, shared between different compartments, this could serve as an unintended communication channel between those compartments.

This "partial hardening hazard" can be completely avoided through defensive programming. For example, if references to hardened objects can only be be obtained from the functions wherein they are hardened (i.e. `return harden(obj)`), a reference to a partially hardened object can never be obtained. We should document the partial hardening hazard and how to avoid it.

### @erights (MEMBER) — 2021-07-14T04:15:29Z

A terminology clarification first:

If `harden` throws during `dequeue`, the object graph is partially frozen, but not partially hardened. Nothing new has been added to the `hardened` set. Trying to harden again will not skip anything due to the previous failed harden attempt.

If `harden` throws in the midst of the `commit` step, then it can indeed leave the graph in a partially hardened state. An object `x` may be marked hardened even though it points at an object `y` that is not hardened. This would violate a fundamental invariant of `harden`. A second call to `harden(x)` will be misled into returning successfully and early, without having hardened `y`. `harden` returning successfully guarantees that the graph reachable from `x` is all hardened. 

However, to my surprise during the red team effort, this broken guarantee is harmless. It would be harmful if `y` might be mutable in ways that violate hardening. However, a throw during `commit` only skips marking as hardened objects that were already candidates for hardening. Without a separate `isHardened` query, it seems this form of failure is not even observable.
