## Description

# Problem to be solved

members of the `Assert` type don't show their jsdoc on the member properties.

For example, [FailTag has comprehensive documentation](https://github.com/Agoric/agoric-sdk/blob/6e3bc14aa0a77d8bdfad72ca8f0d8893c1f80b5f/packages/assert/src/types.js#L282-L338). But when hovering on the symbol it's all elided:
<img width="604" alt="Screenshot 2022-12-06 at 9 41 44 AM" src="https://user-images.githubusercontent.com/21505/205983558-83482ec5-5ae3-40b0-b7cc-06d32d8670c9.png">

# Design

One option that works is to keep the docstrings in the `d.ts` files too. The downside is having to keep them in sync. To solve that we could build the .js from .ts. If we need .js without .ts, then we'll have to move the `Assert` type out of .d.ts, but I'm not sure we can then express it in JSDoc since it will be nested.

### @SMotaal (MEMBER) — 2022-12-28T23:24:47Z

I went ahead created an experimental branch to try to explore this further.

I decided to reduce the clutter and start fresh in [`endo/retyped`](https://github.com/SMotaal/endo/tree/smotaal/retyped-ses-experiment/retyped) where I worked on a minimal example of how to ensure the JSDoc doc would propagate.

Being further out and going with what is reflected in threads and code, I hope my efforts spark some discussions, which would allow me to better understand the tradeoffs and concerns. Based on my understanding so far, the pattern I am using ensures that there is a single source of truth and that it is the JavaScript code itself.

This pattern still requires a package-level [`types.d.ts`](https://github.com/SMotaal/endo/blob/smotaal/retyped-ses-experiment/retyped/packages/retyped-ses/types.d.ts) file for consumers, which is generated with `tsc` and can theoretically be a `prepare` or similar package script.

The funny thing about TypeScript is that there are not so subtle differences in the types it will generate from subtle differences in the JavaScript code which ultimately would not have any observable runtime differences. That said, sometimes it takes more JavaScript to make sure TypeScript is happy.

One example I included to make this point is the non-constructable [`DetailsToken`](https://github.com/SMotaal/endo/blob/261bf0eb7411f94070c554f526e685a3b17e4751/retyped/packages/retyped-ses/src/error/internal/details.js#L7-L24) pre-es2015-style class. The [types this pattern yields](https://github.com/SMotaal/endo/blob/261bf0eb7411f94070c554f526e685a3b17e4751/retyped/packages/retyped-ses/types.d.ts#L2-L7) aside, I think more work will be needed to see if tree-shaking will remove the clutter from JavaScript as needed.

One requirement that is attainable only through hand-coding the `.d.ts` as far as I know at least is the [modifications made to the `globalThis` object when importing the module](https://github.com/SMotaal/endo/commit/261bf0eb7411f94070c554f526e685a3b17e4751#diff-db2edcb7094422c6cfa2f5b4a52ef94c4c0ec3903c0e5801e23baf25ff36e81a), which for the foreseeable future cannot be generated or inferred from JavaScript.

This is all just to explore the types paradigm, not implementation. With this in mind, I opted to take a minimal subset of the logic, broken in any number of ways, but [spread out across modules](https://github.com/SMotaal/endo/blob/261bf0eb7411f94070c554f526e685a3b17e4751/retyped/packages/retyped-ses/modules.log) for clarity.

Please see [`endo/retyped/README.md`](https://github.com/SMotaal/endo/blob/smotaal/retyped-ses-experiment/retyped/README.md) for additional details. As this is just experimental code not bound to be merged, please comment on SMotaal/endo@261bf0eb7411f94070c554f526e685a3b17e4751 directly.
