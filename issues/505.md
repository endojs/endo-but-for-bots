## Description

Consider:
```javascript
const weirdThing = {
  get x() {
    return 'huh?';
  },
};
E(other).say(weirdThing);
```
`weirdThing` is not actually serializable, so the serializer will throw a `TypeError`, but unless you are expecting it and think to await the error/rejection, this will silently behave as a no-op: no errors show up in the log, and the next statement continues executing as if nothing had happened, as if the message send line were a comment or something.  It seems like there ought to be some kind of indicator; in the context in which I encountered this, it was not obvious that the thing I was trying to serialize had accessor methods and was thus unusable in this way, and so the failure was deeply mysterious.

In one sense this is really an issue with one-way message send: since there's nothing attending to the response (since no response is expected), errors in transmission also get lost.  However, my experience has been that other kinds of errors in this sort of context typically manifest some kind of log entry or other indication, even if the flow of execution is not actively disrupted.  Node will ordinarily complain about uncaught promise rejections, but that doesn't happen in this case; I'm not sure why.  Perhaps if we elevate one-way message send to a first class operation (as opposed to a regular message send where we just ignore the response) there might be a place to stand to deal with this.  In any case, some kind of diagnostic indicator during development would be helpful.

Addendum: @erights suggested trying this case using the one-way message send operator, `E.sendOnly` -- as in `E.sendOnly(target).method(args)` instead of `E(target).method(args)` -- so I did.   Interestingly, it's worse, because it swallows the serialization error whole, whereas without `sendOnly` you can at least catch it or put in a rejection handler.
