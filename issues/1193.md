## Description

# Problem to solve
What we call `Far` has gone through some iterations and still has room for improvement. One source of confusion is that a Far object can be near (in the same vat). It's also been known as "primary remotable", which doesn't suffer from that confusion but is much less wieldy. 

According to @erights , 
> The term “Far object” was always misleading, and therefore unfortunate terminology. The source is the Far function, which is used to make one. We originally called them “primary remotable” … But I never found myself using that in casual conversation. Nor have I used “remote” by itself for the other side. Whenever I tried, I’d have to take a beat to explain my terminology, and it never lasted from one conversation to another. For “remote”, I have adopted “remote presence” whose meaning seems reliably remembered. But it is a remote presence of what? What is the remotable that the remote presence designates? When you E(remotePresence).foo(args), what should we call the object with the foo method that receives this message?
> the distinctions … for explaining abstractions for app programmer use, are different than those … for talking about the kernel implementation. The remotable object that a remote reference designates, that received its messages with one of its methods, may be an in-memory object, or a virtual object, or a durable object.
> Now that we have `defineKind` and `defineDurableKind`, we use the `Far` function only to make the in-memory one of these. @warner calls these in-memory objects made by Far “precious objects” … By “Far object”, I mean the category that includes all three of these, i.e., the object that is designated by a remote presence, no matter how it is implemented. Most of its client semantics is independent of these implementation choices. Since virtual and durable such objects are not tied to the function named Far, now would be a good time to choose another name for this concept.

Our [documentation on Far](https://agoric.com/documentation/guides/js-programming/far.html) isn't _wrong_ but could be made more clear:
> On the specific issue, it looks like this uses “remotable” in a way that might not technically be wrong, but would lead one to think that only far objects are remotables. IOW, I’d guess people exposed to just this document would not realize that remote presences are also remotables. Once that is realized, then “remotable” is no longer adequate to mean specifically the object that remote presences designate. This document has no noun for that. It never uses the term “far object”.

# Acceptance criteria

- decision process and rationale documented for posterity
- terms cover all cases
- internally consistent and unambiguous
- practical to use for kernel developers
- just enough complexity for new app programmers
