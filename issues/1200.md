## Description

The SES shim replaces the global `eval` in the start compartment with a "safe" evaluator. That causes any direct eval usage in the start compartment to in fact become indirect.

However unlike code executed in compartments created by the SES shim, the `rejectSomeDirectEvalExpressions` does not execute, even for evals normally detectable by regexp.

Example:

```js
import '@endo/init';

let foo = 42;
eval('foo++');
assert(foo === 43);
```

Using evaluators in the start compartment is fairly unsafe anyway as they have access to the initial `globalThis` with powers left over.

It arguably would be safer to just disable/neuter `eval` in the start compartment, maybe leaving an `eval.indirect` behind in case users really need to use indirect `eval` in the start compartment. Similarly, maybe we should do the same with the `Function` constructors in the start compartment.

This touches on the SES vs Jessie distinction. SES is trying to include as much of std JS as it can safely, in order to safely run a lot of existing js code that was not written to run under SES, but happen to stay within SES restrictions. Early on during the separation of realms vs compartments, we did have a "paper" design for two levels of start context, differing in safety. I do agree that too much code runs in the one unattenuated start compartment we have. Perhaps we should revisit the two-start-context idea. At this point, it would not require any new foundational change to SES. Just convention and tooling to support using it in a way that is already possible: to move most setup execution into a non-start compartment created for purposes of running such setup code. Legacy JS code unaware of SES should then never run in the actual start compartment. It should at least be moved to the attenuated setup compartment.
