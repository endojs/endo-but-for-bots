## Description

As mentioned in #367, when `tap` sees a failed assertion under `errorTaming: 'safe'`, it does not display a stack trace. The following short program:

```js
import './install-ses-safe.js';
import tap from 'tap';

function sub(t) {
  t.equal(1, 2);
}

tap.test('failed assertion', t => {
  sub(t);
  t.end();
});

```

(where `install-ses-safe.js` just imports SES and calls `lockdown()`), when run against current trunk (817fe1a7e320d4f9cc4a526b548ef639f172feb8), produces the following:

```
$ node test/t1.js
TAP version 13
# Subtest: failed assertion
    not ok 1 - should be equal
      ---
      compare: ===
      at: {}
      diff: |
        --- expected
        +++ actual
        @@ -1,1 +1,1 @@
        -2
        +1
      ...

    1..1
    # failed 1 test
not ok 1 - failed assertion # time=25.8ms

1..1
# failed 1 test
# time=34.226ms
```

If we change the lockdown to include `errorTaming: 'unsafe'`, we get:

```
$ node test/t1.js
TAP version 13
# Subtest: failed assertion
    not ok 1 - should be equal
      ---
      compare: ===
      at:
        line: 5
        column: 5
        file: file:///home/warner/stuff/agoric/SES-shim/packages/ses/test/t1.js
        function: sub
      stack: |
        sub (file://test/t1.js:5:5)
        Test.<anonymous> (file://test/t1.js:9:3)
        file://test/t1.js:8:5
      diff: |
        --- expected
        +++ actual
        @@ -1,1 +1,1 @@
        -2
        +1
      ...

    1..1
    # failed 1 test
not ok 1 - failed assertion # time=27.635ms

1..1
# failed 1 test
# time=36.455ms
```

Regular try/catch Errors show stack traces normally under both environments, because we haven't yet tamed Error so much that safe-mode removes stack traces. So it's a bit surprising that `tap` loses the stack when under the safe taming mode.

I suspect this has to do with the `.prepareStackTrace` manipulation that tap does. Under safe taming mode, this is disabled: changes to `.prepareStackTrace` are just ignored. So the resulting `.stack` property will be a simple multi-line string. I'm guessing that tap is unprepared to deal with `.prepareStackTrace` not working: maybe it uses PST to sample the full callSite list, and reads from `.stack` to trigger it, but ignores the `.stack` value. Then when its overridden PST was not called, it's left with nothing.

If that's true, then there's not much we can do. But if there's some workaround or fallback we can use, it'd be helpful, because it's annoying to figure out which assertion failed unless you add distinctive labels/comments to each one (`t.assert(1, 2, 'distinctive label')`). The immediate workaround is unsafe mode, but in the long run we need to prevent confined compartments from mutating their Error constructor.
