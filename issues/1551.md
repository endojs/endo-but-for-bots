## Description

Currently, there is no way to run code inside a Compartment and ban access to all possible ways of turning a string of text into a behavior.  
Such a ban would be useful if a use-case involves getting strings from the outside (eg. making http requests) but wants to limit the program to only pre-existing behavior. 

*Description below is a slightly redacted message from @erights*

We could introduce an option on compartment construction that creates a compartment with no evaluators exposed to code within the compartment. 

Within that compartment:
- eval(…) throws
- Function(…) and new Function(…) throws. 
  Note that (()=>{}).constructor(…) already throws, because that navigation reaches Function.prototype.constructor that throws. So the option could make them the same, or approx the same except for a more informative error message.
- new Compartment(…) does not throw. It still works, but…
-  (new Compartment(…)).evaluate(…) throws.
   The no-evaluator constraint is propagated to such nested new compartments even if not explicitly set.

Similarly:
- new ShadowRealm(…) does not throw. It still works, but…
- (new ShadowRealm(…)).evaluate(…) throws.
    The no-evaluator constraint is propagated to such nested new shadow realms.



Then, finally, there is the issue of “evaluation” of module text, where “evaluation” refers more generally to turning strings representing code into behavior according to that code. For modules, that journey takes two steps: a) from source text to a source module record, b) from a source module record to a module instance.  
From recent conversations it seems it would be better for “no-eval” to suppress (b).
