# `@endo/codex-sandbox`

A bounded Endo capability adapter for the official Codex app-server protocol.
It keeps Codex-specific JSON-RPC and process lifecycle details out of consumers
such as Floot.

The lifecycle factory provisions through an injected resource owner and refuses
to run unless it receives the exact effective sandbox attestation.
The low-level client remains injectable for protocol tests and adapters:

```js
import { makeCodexClient } from '@endo/codex-sandbox';
import { startAppServerTransport } from '@endo/codex-sandbox/app-server-transport.js';
import { E } from '@endo/eventual-send';

const client = makeCodexClient({
  sessionId,
  start: () => startAppServerTransport({ slice, cwd: '/workspace' }),
  threadId: storedThreadState.threadId,
  savedToolSetId: storedThreadState.toolSetId,
  savedRecovery: storedThreadState.recovery,
  saveThreadState,
  reportCleanupFailure: recordOperatorAlert,
  auditEvent: (kind, payload) => E(auditWriter).append(kind, payload),
  dynamicTools,
  callTool,
  toolSetId,
});

const reader = await E(client).send('Review the current changes');
```

App-server is the Codex CLI transport, not an independent billing identity.
When the CLI is authenticated with ChatGPT it operates against the eligible
ChatGPT subscription; when authenticated with an API key it uses API billing.
This package deliberately exposes neither authentication nor account/session
administration to the sandboxed agent.
Hosted subscription deployment remains disabled until an external credential
broker can support the pinned stock CLI without placing reusable credentials in
the slice; see [SUBSCRIPTION-AUTH.md](./SUBSCRIPTION-AUTH.md).

`send()` returns an Endo reader of provider-neutral events:

- `phase`
- `commentary-delta` (progress only; do not persist or speak as the answer)
- `text-delta`
- `tool-call`
- `tool-result`
- `usage`
- terminal `end` or `abort`

Only one turn may run at a time. Closing the reader interrupts that exact turn;
a second concurrent `send()` is rejected. `models()` reads the app-server model
catalog rather than relying on hard-coded model or reasoning-effort lists.
A successful `end` contains an opaque checkpoint. A durable consumer stores it
with the committed conversation node and calls `acknowledge(checkpoint)`; if
that call is lost, it supplies `acknowledgedCheckpoint` on the next `send()`.

The container recipe pins the base image digest, Debian snapshot, npm integrity
lock, and Codex CLI 0.152.0. Protocol changes must be reviewed
against schemas generated by that exact binary with
`codex app-server generate-json-schema` or `generate-ts` before updating the
pin.
Build with `oci/build-reproducible.sh [tag]` and verify two independent builds
under the same pinned Podman/Buildah release with
`oci/verify-reproducible.sh`.
The recipe removes package-manager clock-bearing logs, but it is not considered
a release image until that verifier succeeds in the release builder and records
its builder version and manifest digest.
The resulting digest must be separately approved by the operator and supplied
to the backend factory; accepting any syntactically valid digest is forbidden.

The process transport also exposes bounded stderr diagnostics and `wait()` to
its owning provisioner. `CodexClient` deliberately does not place untrusted
process diagnostics into the model/reply event stream; a caller that needs
operator diagnostics should retain the transport it created in `start()`.
`reportCleanupFailure` must write late teardown failures to operator-visible
telemetry; they are also retained in the client's bounded `status()` result.
