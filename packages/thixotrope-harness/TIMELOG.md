# Time log: where the build's time goes

A measured record of how the Thixotrope harness build spends its time: per
workflow, per agent and per category, backfilled from the start of the build
(the first workflow, 2026-11-16) and re-generated after every workflow.

## Method

- Source: the PM session's transcripts (one per agent, the workflow records
  and the PM's own transcript) and, from 2026-11-18, the run-lock log
  `<THIX_HARNESS_HOME>/runs.jsonl`. Nothing from them is copied here except
  durations, counts, agent labels, workflow names and category names.
- A tool call lasts from the model's line that asks for it to the line that
  carries its result. An agent's wall time (first to last line) is cut at
  every timestamp and each piece goes to one category: the highest-priority
  call in flight (run-lock workload first, then probes, cargo, installs, unit
  tests, lint, git, other shell, reads, edits, other tools); else model time
  when the next line is the model's; else idle.
- Shell commands are sorted by patterns in `scripts/process-time.mjs`.
  Polling loops (`until ...; sleep`) and idle stretches go to the background
  job in flight (a `run_in_background` command, ended by its notification) or
  to the poll's own words; what matches neither is "idle".
- Lock wait: before the run-lock log existed, a locked command whose output
  holds the lock's "waiting" line is taken to wait until the other locked
  command in flight at its start ended. From now on `runs.jsonl` measures
  waits and holds directly (table "Run-lock log").

## Limits

- Agents run in parallel, so summed agent time exceeds wall time; shares in
  "Top time sinks" are shares of summed agent time, not of the calendar.
- Polls and background jobs started with `nohup ... &` inside a foreground
  command are only attributed by the poll's words; a workload polled through
  a log file named after nothing recognisable lands in "idle" or in the
  run-lock category by keyword ("perf", "integ", "lane" ...). Before
  `runs.jsonl`, time an agent spent polling while its job waited for the lock
  counts as holding, so lock wait is a lower bound.
- "Model" includes the API's latency and any time a tool call spent waiting
  for permission. A running workflow's end is its latest transcript line.
- The PM's direct agents (outside workflows) are numbered, not named.

## Regenerate

From `packages/thixotrope-harness`:

```sh
node scripts/process-time.mjs <session-dir> --git-range 48d6f3e08b..HEAD
```

`<session-dir>` (or `THIX_PROCESS_SESSION_DIR`) is the PM session's
transcript directory. Only the block between the two marker lines below is
rewritten; text outside it (the Findings) is kept. `--stdout` prints the
block, `--json` the full report.

   lane, not by the model.
2. Model time (thinking and writing) was 18.5 h (28 %); edits, reads, lint, git
   and cargo together were under 3 h (4 %).
3. Agents were 1.4 deep on average (66.3 h of agent time over 48 h): with a
   CPU at 20 % or less, running independent lanes in parallel is the largest
   saving available.
4. Long single runs dominate: 31 commands ran over 30 minutes (31.9 h between
   them, 19.8 h under the lock) and 11 ran over an hour (18.8 h), most of them
   fixed-count perf or acceptance runs polled in the background.
5. core-perf (12.5 h wall, 10.8 h under the lock) and m1b (10.5 h, 7.8 h) were
   the slowest workflows; both were mostly perf measurement.
6. Measured lock wait is only 10 minutes because agents queued their runs in
   the background and polled; 36.2 h of agent time was spent waiting on
   background jobs or poll loops, which hides the queueing that runs.jsonl
   now records directly.
7. The PM's own working time was 40 minutes in the build window, and the gaps
   with nothing running added up to 16 minutes: the PM is not a bottleneck.
8. The saving with the most leverage is to make perf checks rate-per-fixed-time
   (run for a set number of minutes, report the rate and its trend) instead of
   fixed-count runs that take hours, then to run lanes concurrently.
