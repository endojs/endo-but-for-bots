# Lossless paging for the chat transcript

**Proposal, November 25.** Open a chat at its newest turn. Show an ordinary reply in one bubble and finish loading a visible long reply automatically. Opening, scrolling, reconnecting and closing a viewer are all read operations. The supervisor owns execution with zero, one or two viewers.

## Why change the reader?

In session `s23/t4`, Chromium displayed 1,024 of the 2,519 saved characters. The November 24 fix fetches full records for a settled turn marked `cut` and keeps its streamed text on screen during the read. This restores the reply, but the excerpt and full records repeat the prefix. The round text and final field can repeat the same reply again. For visible chat the renderer already prefers the round text. Recovery and raw inspection have different field requirements and retain their existing interfaces. ## First implementation

Use a read-only, session-scoped transcript page. Start with a whole nonempty field or record whenever it fits an empty page. If it only exceeds the *remaining* space, defer it to the next page. Continue a field or an intent list only when its own encoded representation exceeds an empty page. Send ordinary visible text once. For a stored large field, return the existing ranged-read capability and its size. Start that read when the assistant bubble is visible. A collapsed tool result needs only its identity and display metadata. The stored turn-start record contains only attachment labels. Deliver those labels to the existing mention chips and export zero attachment objects. Negotiate support on open and retain the current reader for sessions served by older implementations. An error from a supported reader belongs on the affected turn with a retry. | Contract | Proposed behavior |
| --- | --- |
| Stable position | Bind each snapshot page cursor to the authorized session and an exclusive upper bound on absolute append indexes captured at open. A record’s identity is its original append index in that session. A cursor also records traversal direction and the position inside a split record. Newer appends are eligible on refresh. Validate the cursor against the session capability on every read. Never resolve a caller-supplied filesystem path, archive key or blob ID. |
| Retained and sealed data | Preserve the original index through sealing. Existing segment data covers contiguous ranges, so an index can be derived from the segment start and physical record offset before grouping by turn. A resolution can be appended after its turn was sealed. Read the authoritative unsealed tail for that case, then the segment that contains the resolution once sealed. Apply the same upper bound and identity on both paths. The current archive resolution index stores the note and time. The reader needs the append index as well. |
| Rendering order | Walk turn history backward for scrollback and assemble each turn in reading order. Pair tools by intent order and operation ID, even when results complete in reverse order or arrive on different pages. Keep groups with missing counterparts provisional. For each turn return a fixed-size flag indicating whether any eligible round supplies displayable text at this read’s upper bound. Use the page’s record identities for individual replies. Render a fallback final only once this is known. Two rounds with identical text still produce two bubbles. Preserve the existing handling of whitespace-only fields. |
| Text and structure | Identify each field by record, field name and, for an intent, item position. For stored UTF-8 blobs use the reader’s returned byte offset. For inline JavaScript strings keep slices of the original UTF-16 units and never split a valid surrogate pair. Measure encoded **bytes** for budgeting. This preserves a lone surrogate already in an inline record and the actual stored bytes of a staged field. Return a continuation for intent metadata too. If the next unit cannot fit the remainder, finish the page and consume it on a fresh one. Every nonterminal page must advance. |
| Bounds | The harness’s 24,576-byte string-content budget, the pinned supervisor’s 65,536-byte encoded vat ingress ceiling and the gateway’s WebSocket ceiling cover different boundaries. Budget the proposed response conservatively and check the actual encoded return including escaping, keys, slots and cursor. Count intent items as work. Keep the retained page’s 40-record cap initially and measure reads or decoding needed to assemble the page, including oversized turns. |

The record log already assigns absolute indexes. Its existing presentation helper can reorder *earlier* result slots when a later parallel call finishes. Applying that helper independently to each page can mispair or duplicate results. The archive’s turn index also omits a resolution that still lives only in the raw retained tail. These are the reasons to page by append identity and project display order separately. [Record indexes and ordering](../guest/session/records.js) · [Segment format](../resources/agent-host/impl/archive/segment.js) · [Archive turn and resolution lookup](../resources/agent-host/impl/archive/history.js) · [Transport budgets](../config/defaults.js)

Apply the exclusive upper bound to the turn’s state, resolution, round-text flag and every other derived summary. A historical read cannot substitute the current state for the state at that bound. For example, take a cursor while a turn is running, then let it settle and seal. Retrying the cursor must return the same running projection. The targeted settlement refresh takes a *new* bound for that turn and updates the view without advancing outstanding scrollback cursors. Derive summaries from committed records or maintain a bounded index keyed by append position.

## Following new records and scrolling back

Use two independent positions per view. Opening the latest page captures `H`, the index of the next record that could be appended. The response includes an **older cursor** for reading farther back within that snapshot and a **follow position** starting at `H`. The follow position covers the part of the log *after opening*. A reader can use it before fetching any older pages.

| Reader action | Proposed contract |
| --- | --- |
| Scroll up | Follow the older cursor backward within the original upper bound. Exhausting it means the beginning of history. Later commits never move this cursor. |
| Wait at the live edge | `whenAdvanced(F)` is a session-scoped, cancellable read. If the durable head exceeds `F`, it returns the current head immediately. Otherwise it waits for the next advance. The comparison and registration must be atomic with respect to commit. Multiple advances can wake a viewer once. |
| Catch up | Given the returned head `T`, read the finite append range `[F, T)` forward. Its page continuations retain that same end until the range is drained. Apply records by identity and then advance the follow position to `T`. Lazy text references count as applied once attached to their records. Partially received required inline fragments must be assembled or safely retryable before advancing. Wait again from `T`. |

For example, if a chat opens at 100 and receives three new records while the user scrolls up, the forward reader consumes indexes 100–102. Its next wait starts at 103. The older cursor still reads below 100. A commit during catch-up satisfies that next wait immediately. A lost response can be retried over the same range. On reconnect, resume from the last applied position if the corresponding view state is still present. A fresh view starts with a fresh snapshot.

Wake followers from the committed record log. A resolution of an old sealed turn can append a record while the existing live channel stays quiet. Wire the wakeup to all append paths, including that one, and expose a head only after its append commits. Keep one outstanding wait per viewer, release it on disconnect, and recheck the durable head when reattaching. The existing channel still supplies low-latency text deltas. Its `seq` and `rev` belong to the live channel and have different meanings from a durable record index. [Record append and count](../guest/session/records.js) · [Turn resolution](../guest/session/turn.js) · [Live sequence and revision](../resources/agent-host/impl/channels.js)

At the bottom, new text stays in view. Once the user scrolls up, continue consuming committed updates but preserve the visible record and offset, including when the update changes a turn above it. Returning to the bottom resumes automatic scrolling. Apply late resolutions to the original turn once. When an older page arrives afterward, preserve the newer resolution. If an offscreen turn’s updates were discarded to bound memory, refresh that turn through the applied follow position when it enters view. Its original snapshot page stays reproducible. ## Live handoff and read-ahead

Keep the existing watch and live subscription for the active turn. Its first event is a bounded snapshot. Multiple deltas can share one revision, and the subscription does not replay every delta since the requested revision. Use the revision to detect a gap and re-watch, and the per-view generation to discard answers after navigation. On settlement, read by the affected turn’s identity even if a newer turn already occupies the first page. Keep the live bubble until the authoritative reply for that turn and round is assembled. Live-only thoughts have no stored history to reconstruct. [Live channel](../resources/agent-host/impl/channels.js) · [Controller](../ui/src/controller/index.js)

Use one outstanding visible-text read and at most one adjacent history page of speculative work per view. Visible content takes priority. Stop scheduling on close or session switch and discard late answers. Retries are idempotent at the same cursor. Anchor scroll position to a visible record and an offset within it when prepending into the same turn. The reader should show progress on a large reply without waiting for the whole body to allocate or print. [Current scroll anchor](../ui/src/conversation/Conversation.js)

A gateway-local reader is a second experiment. A bare `next()` awaited once per page still costs one browser round trip per page. Prototype it only if traces show idle gaps between required chunks or repeated source lookups. Give it one page of credit, explicit close/disconnect cleanup and a resumable cursor. Measure under an artificial round-trip delay as well as on loopback. [Current gateway capability rules](../resources/agent-host/impl/gateway/guard.js)

## Pinned-worker acceptance and decision

- Compare visible output to the stored fields after settlement, reload and reconnect. Test the 2,519-character ordinary reply, a final-only turn, identical text in two rounds, a 1 MiB reply, and a large collapsed tool result. Count bytes of final text sent when the round already supplied it. Check leading/trailing whitespace, quotes, control characters, a leading BOM, a lone inline surrogate and a four-byte character at a boundary. Split the largest accepted intent list across pages.
- Pause between two out-of-order tool results and append, resolve or seal while scrolling. Resume a saved cursor on both sides of sealing, and repeat a request after a lost response. Check the ordered transcript against a one-shot read at the same upper bound. Open two sessions that both contain `t1`, try the other session’s cursor, then switch views with a read still pending. Count provider dispatches with two viewers and with both closed.
- Put one viewer at the bottom and one halfway through an older turn. Append before the wait registers, during a split page, and just after catch-up. Resolve an old sealed turn with no further live traffic. Disconnect for more than one page of appends. Both viewers must converge on the same committed transcript without duplicate bubbles or lost updates. The first follows new text, the second retains its reading position, and returning to the bottom shows the same latest reply.
- Instrument work on both sides of the page boundary. The retained reader can materialize every record for a turn, and a cold archive lookup can parse a whole segment. Measure cold index construction separately from warm lookups, with explicit caps on resident index and segment cache bytes. Require bounded per-page scans after initialization. Assemble chunks incrementally and measure source allocation, renderer peak memory, and total work when reply length doubles. A queue limit alone would miss repeatedly copying an ever-longer prefix. Include the supported 1,024-round limit. [Record lookup](../guest/session/records.js) · [Segment decoding](../resources/agent-host/impl/archive/segment.js) · [Workload limits](../guest/lib/limits.js)
- Use the current Chromium cases and the cached 300-turn fixture. Record median and p95 to first visible text and complete visible reply, requests, encoded bytes, vat deliveries, discarded prefetch, and peak queued bytes per view. Separate retained and sealed reads. An older run saw 256 ms median for a retained page versus 2.5 ms for an archived page. Those were RPC times. Rerun the current reader and candidate under the same conditions. Adopt lossless pages when the ordinary case avoids the repeated prefix, retained page median stays within the existing 300 ms target, and complete-visible-reply measurements improve without a repeatable regression in first paint or scroll position.
