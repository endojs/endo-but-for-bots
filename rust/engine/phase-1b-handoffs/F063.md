# F063: compiler totality follow-up

Status: **Partially implemented, 2026-09-17; finding remains open.**
This handoff recorded work deferred under the Phase 1 prohibition on editing
`ironhorse-vm/src/interp.rs`.
That prohibition has lifted, and proposals 1 (for the two named sites), 2 and 3
below have landed.
The reachability audit that proposal 1 asks for in general HAS since been run,
at `27e637606`, and it refuted the claim it was auditing — see "The audit, and
what it found" below.
It is not an amendment to the architecture review or evidence of closure.

## What landed

- Three guest-facing sites are routed through the coder's error channel or the
  parser's, each with an explicit KIND.
  `({a = 1})` reports `ParseErrorKind::Syntax`, because it is a spec early
  error and the guest should see a catchable `SyntaxError`.
  The static-block fold reports `ParseErrorKind::Unsupported`, because it is a
  coverage gap.
  A multi-binding for-in/of head (`for (let x, y in {})`) is rejected in the
  parser: five shapes reached `code_assign`'s unreachable arm and panicked, and
  two of them sat in the committed test262 expectations as
  `skip:compiler-unimplemented:parse`.
- A reported error STOPS the pass.
  `Coder::report_kind` latches the error and unwinds with a private payload
  that `compile_parser` catches, which is XS's `longjmp` expressed in Rust.
  The first attempt latched and returned, guarded by a `poisoned()` flag
  consulted at one of the file's eighty-odd panic sites; the pass walked on and
  died at an unguarded one, losing the classification it had just recorded, so
  the diagnosis was worse than the `panic!` it replaced.
  `compile_budget.rs`'s `a_reported_early_error_stops_the_pass` gates it by
  cost, because a flag nothing reads cannot be tested.
- `SourceCompileError::Invariant` exists, the eval bridge maps it to an
  uncatchable `Halt::EngineInvariant("eval:compiler-invariant")` dropping the
  panic text rather than exposing it, and the production adapter
  (`ironhorse-runtime`) constructs it: its `catch_unwind` used to map a caught
  panic to `SourceCompileError::Unsupported`, i.e. to
  `Halt::NotImplemented("eval:compiler-unimplemented")`, which is the finding's
  claim at the live seam.
- `compile_atoms_budgeted_firewalled` and its UTF-16 sibling are the one place
  a panic becomes `CompileError::Invariant`, so an embedder does not hand-roll
  a catcher and guess what a panic means.
  Every adapter in the tree, the `thixotrope-ironhorse-worker` binary included,
  compiles through them.
- The test262 harness files a caught panic as a `Fail` named
  `compiler-panicked:<phase>` (`Category::IronhorseFailure`) instead of sharing
  `compiler-unimplemented:<phase>` with real coverage gaps.
  Filing it as a named *skip* was the first attempt and was still wrong: an
  unclassified skip label falls to `Category::Infrastructure`, which the report
  renders as "not Ironhorse gaps", so the fault left the Ironhorse column
  altogether.
- `corpus_compiler_totality.rs` compiles every one of test262's 53,575 sources
  and requires that none of them panics.
  It currently passes; with the for-in fix reverted it names the two cases
  that fail.
  `ironhorse-compile/tests/compiler_totality.rs` is the hand-written net beside
  it, and `ironhorse-vm/tests/compiler_fault_classification.rs` gates the VM
  seam: a fault and a coverage gap produce different halts, and the fault is
  uncatchable.
- `expectation_shards.rs`'s `committed_expectations_record_no_compiler_fault`
  refuses to let a compiler fault be written down as a baseline.

## The audit, and what it found

Superseding the "What did not" section below, which described the state before
`27e637606`.

The audit ran and found two reachable sites, so the claim that the remaining
ones are unreachable invariants was false.
`try{}catch{function f(){}}` — valid ES2022 — aborted the compiler under every
goal, because `code_catch` coded its body's defines through an asserting
helper where `code_block` uses the real one.
A module-goal `async function f(a=await 0){}` reached `code_await` with no
return target; that one is a spec early error, and the rule now lives in the
parser so all four goal/strictness modes refuse it.
Both are fixed and pinned by
`the_audits_reachable_panics_return_rather_than_panic`.

The asserting helper has since been deleted in `e8a03e9f6`.
Both loop coders now code their body's defines through the same path as blocks
and catches.

The scoper follow-up adds targeted tests for the `body_scope` parameter-default
window and `scope_of`'s agreement between the hoist and bind traversals.
The latter requires every legal fixture to compile in each applicable goal,
including static fields, private accessors, binding patterns and module exports;
an earlier rejection cannot silently remove a fixture from the traversal audit.
Three temporary mutations that skip hoisting a computed field key, a field
initializer value or a private method each fail at `scope_of`.
The parser's `node_id` precondition is also held by
`every_public_parse_entry_point_calls_finish_tree`.

F063 remains partially open.
The other seven scoper `expect`/`unwrap` shapes now have a
[source-level invariant audit](../architecture-review/2026-09-06/F063-SCOPER-AUDIT.md):
`scope`, `function_scope`, the two declare-index pairs, the two field-scope hoists
and the catch statement scope.
Private phase-boundary tests check their receipts and indexes, with four
independent mutations verified to fail; no additional source-triggered panic was found.
The two targeted probe suites are empirical coverage, not proofs of totality.
The [coder follow-up](../architecture-review/2026-09-06/F063-CODER-AUDIT.md)
removes six logical-assignment target unwraps and examines 24 local/control-flow sites.
The declaration follow-up examines ten further sites and all 29 declaration-index readers.
It checks function aliases, module indirections and disposal adjacency against the producer
roster, with 2,240 generated cases, 34 boundary cases and three damaged-tree controls.
The scope-receipt follow-up examines 22 more sites, with 1,920 nested-class cases,
82 boundary cases and 13 damaged-tree controls.
It checks resolution, scope, frame-count and class-plan contracts, including shared
getter/setter brands and base-constructor captures.
It leaves 21 explicit AST-shape sites, including the parser preconditions used by these
arguments, rather than claiming that a finite test roster proves the compiler total.
The AST pass has since repaired two demonstrated panic paths: property references in
arrow parameters and Spread nodes inside ordinary grouped expressions.
The fixes reject them as parser Syntax errors, including nested invalid binding targets.
`cover_binding_totality.rs` checks 300 invalid cases and 270 valid controls; the runtime
checks 16 catchable eval/Function cases through its real compiler adapter.
The full AST producer/consumer audit is still pending, so its 21-site count is unchanged.
The template family then produced a third defect of a different kind.
`template_expression` skips the substitution expression when the token after `${` is
`}`, exactly as `fxTemplateExpression` does, so a spec early error compiled and
`code_tagged_template`'s `(items.len() / 2) + 1` string count was wrong for it.
No panic resulted — an array extended itself over the discrepancy — which is why the
53,575-file corpus sweep could not have found it and a source audit had to.
The parser now rejects it and the coder counts the `TemplateMiddle` items it writes.
`template_substitution_totality.rs` holds 125 rejections and 125 control compilations;
the runtime checks 16 catchable eval/Function cases through its real compiler adapter.
Running the rest of the AST pass as a generated matrix rather than a hand roster then
found a fourth defect that IS a panic: `var [a];` reaches `code_node_inner`
(coder.rs:1588) as `unsupported node kind ArrayBinding`.
A `BindingPattern` declaration requires an initializer, so it is a spec early error, and
a guest raises the panic with `eval("var [a];")`.
The parser rejects it now, conditionally — `ForBinding` takes none, so
`variable_statement` reports the bare pattern back to `for_statement`.
Whether a call IS a `ForBinding` is an argument, not a read of `flags::FOR`, after two
wrong answers: reading the flag after the binding rejected 638 valid corpus files (a
nested default clears it), and reading it at entry left the opposite hole, since the
flag is ambient over the whole head including nested bodies — `for (() => { var [a]; } ;;)`
still panicked, uncatchably, in all five modes, and a `for-of` head reached it through
the LHS where the deferred answer is never consulted.
Take the lesson for the rest of this audit: a guard that reads ambient parser flags is
how both of those happened, and an argument is what fixed it.
`destructuring_declaration_totality.rs` holds 305 rejections and 195 control
compilations; `ast_shape_matrix.rs` checks in the generated net (27,135 compilations,
no panics); the runtime checks 24 catchable eval/Function cases.
Neither gate caught the arrow-body hole on its own — review did — and both were
extended so they now would.
A before/after compile of all 53,575 corpus sources in three modes changes none of the
160,725 outcomes, so neither fix moves an expectation line.
Next in this family: `code_template`'s own `panic!("template without items list")`, and
the rest of the inventory, which this pass leaves at 21 AST-shape sites — not 20.
`code_node_inner`'s fifth site is a catch-all over every unhandled node kind; one kind
becoming unreachable does not discharge it, and `544d225d` already kept the count at 21
after fixing `Spread` reaching that same catch-all. An earlier draft claimed 20.
Two pre-existing defects of the same ambient-flag root cause are open beside it:
`for (()=>{ return "a" in {}; };;)` is valid and refused, and `for (var x = "a" in {};;)`
is an early error and accepted. Both want `arrow_expression` to clear `flags::FOR` the
way `function_expression` does; that is a shared-invariant change needing its own
corpus differential, so it is filed rather than folded in here.
Widening `ast_shape_matrix.rs`'s two lists is the cheapest way to keep looking; it found
the declaration panic that four hand-written rosters had missed.
Five checked-in matrices require 17,534 successful compilations; 180 runtime
cases separately check logical-assignment values and evaluation counts.
These replace reliance on the earlier unreproducible generated-source negative
with a new reproducible floor, not a reconstruction of that historical run.

## What did not (before `27e637606`)

The reachability audit. `coder.rs` still holds other `panic!` and
`unreachable!` sites and `scoper.rs` a wider `expect`/`unwrap` surface; most
are invariants over the parser's own output, but nothing has established that,
so the compiler is not total. The finding stays open on this.

What the corpus sweep establishes is narrower than the audit and is worth
stating exactly: no source in the pinned test262 corpus reaches any of those
sites. That is a strong empirical floor and it is not a proof — test262 is not
the set of all JavaScript, and a source outside it may still reach one.

## Proposed changes, including the frozen file

Proposals 1 (for the named sites), 2, 3 and 4 have landed; proposal 1's general
audit is partially complete, as described above.

1. Audit guest-reachable coder/scoper failure sites and classify each as an early
   error, deliberate unsupported feature, or internal invariant.
   Reject cover-initialized names such as `({a = 1})` during grammar refinement;
   preserve valid destructuring forms.
   For deliberate folds, use the structured error channel and poison the pass on
   its first error so it cannot serialize partial output or trigger later panics.
   **Landed for the named sites; the audit of the rest remains partial.**
2. In `interp.rs`, add a distinct compiler-invariant variant to `SourceCompileError`
   and handle it as an uncatchable `Halt::EngineInvariant`, with a stable diagnostic
   label rather than arbitrary panic text exposed to guests.
   The exact variant and label names are proposals, not an implemented API.
   Preserve the existing syntax, unsupported, meter, and heap mappings.
   **Landed** as `SourceCompileError::Invariant` and
   `Halt::EngineInvariant("eval:compiler-invariant")`.
3. Update compiler adapters, including the harness and production integration, to
   preserve that distinction through reporting and worker failure handling.
   A caught unexpected panic must not become `Unsupported` or a guest `SyntaxError`.
   Audit all public compilation entries and callers, not just the eval bridge.
   **Landed**, and the audit found the production adapter doing exactly that.
4. Retain unwind containment as defense in depth for internal bugs while removing
   guest-reachable panic control flow.
   Do not remove the `panic=abort` build rejection as part of this change.
   **Landed** as `compile_atoms_budgeted_firewalled`; the `panic=abort`
   rejection is untouched, and it is now load-bearing twice over, because the
   coder's own reported-error path unwinds.

Some compiler-local repairs can be made without changing `interp.rs`.
They would be partial work: the runtime classification obligation above would
remain unresolved.
This handoff does not claim that every component individually needs the frozen file.

## Machinery to preserve

[The meter](../ironhorse-compile/src/meter.rs) deliberately uses a private `Refused`
unwind payload and `catch_refusal` to implement sticky work refusal.
Do not convert that payload into an invariant error, swallow a callback panic, or
lose charges accrued before a refusal or compiler failure.
Preserve the accounting and retained-index contracts described in
[W4](../architecture-review/2026-09-06/W4-IMPLEMENTATION.md) and
[the performance tradeoffs](../architecture-review/2026-09-06/PERFORMANCE-TRADEOFFS.md).

## Acceptance tests for the follow-up

- Oracle-free compiler tests must obtain structured results, without unwinding,
  for static blocks containing lexicals and invalid cover-initialized names,
  including nested object forms; valid destructuring must still compile.
- Exercise every public entry, Script/Eval/Module goals, and budgeted/unbudgeted
  variants over the audited cases in debug and release builds.
- Use an injected `SourceCompiler` in `ironhorse-vm/tests/` to distinguish syntax,
  unsupported, invariant, meter, and heap outcomes at the real runtime bridge.
  A guest `try/catch` must not catch an invariant halt.
- Check sticky refusal and exact charged-work retention for failure paths, then
  run the existing compiler budget and corpus suites.

The first three are landed and passing; the fourth is landed for the budget and
corpus suites.
The audit is now partial, with the remaining shapes listed above.
The traversal tests cover the five goal/strictness modes through
`compile_atoms_goal`; they do not claim every public compilation entry is
