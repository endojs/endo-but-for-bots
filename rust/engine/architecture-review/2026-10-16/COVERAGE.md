# Coverage review

Reviewed commit `61cd656cb`.

This document checks two things.
First, that nothing in scope was missed: no in-scope file, map blind spot or test262 failure
cluster went unexamined.
Second, that nothing found was lost between the region maps, verification, the lenses and the
summary.
It combines a mechanical scan, which lists the in-scope files that no audit document mentions, with
four independent sweeps:

- blind spots and unread files;
- test262 failures that no finding explained;
- leads that a map, verifier or lens flagged but nobody verified;
- inventory rows and verification corrections that never reached a lens.

It also records the clean re-run of the Rust probes that a shared build directory had exposed.
Every new finding the sweeps proposed went through the same adversarial verification as the region
findings.
All 19 survived; they are numbered COV-1 to COV-19 under [New findings](#new-findings).
Paths are repo-relative at `61cd656cb`.
Probe paths (`probes/...`), map paths (`maps/...`) and lens paths (`lenses/...`) are relative to
this directory.
The verification records (`verify/<map>.json`), the merged severity ledger (`ledger.json`) and
the synthesis notes (`synthesis/`) are the audit's working files.
They are not published with this review; the summary's finding index carries their content.

## Unexplained test262 failures

**Method.**
The sweep took every non-passing case from the oracle-off report as judged by
`probes/test262-sweep/ih_alone.py`'s `verdict()`: 8,898 cases (7,464 fail and 1,434
unsupported).
It clustered them by their first three path components and by normalized sweep reason, which gives
85 clusters of 10 or more cases.
It then re-ran cases on the plain host:

- All 2,565 non-Temporal, non-intl, non-module sync cases, and 655 non-Temporal `intl402` cases.
  Each case was assembled as `assert.js` + `sta.js` + its includes + its body, run as one Script
  on `ironhorse-xst`, with a `"use strict";` variant and node alongside
  (`probes/coverage-review/test262-clusters/run262.py`).
- All 589 async cases, through a temporary Rust probe that reads a `$DONE` latch after the job
  drain (`probes/coverage-review/test262-clusters/zz_audit_cov_1.rs.txt`).

The raw result files of these runs are too large to publish; the cases that matter for the
headline are listed in `probes/coverage-review/writer/one-script-passes.txt`.

Then `label.py` assigned each case a root cause from the sweep reason, the one-Script result, the
message and the path, and `render.py` printed the tables.
About 40 cases in about 25 groups, each smaller than 10, remain unexplained (listed below).

### COV-1 — `new` on a bound cross-segment target runs the caller's bytes (high)

**Sweep:** blind-spots (BLIND-1).
**Lens:** correctness.

`enter_construct_bound` walks the bound chain to a bytecode target, reshapes the frame, and
returns `self.enter_call(total, ret_pc, true)`.
The RUN arm then sets `pc = body_start` and continues the same dispatch loop over the *current*
code buffer.
Nothing checks that the target's code segment is the active one.
Every other in-place entry does check:

- The plain call path routes a callee in another segment through
  `cross_segment_callee`/`call_cross_segment`, and its comment names exactly this hazard ("rather
  than continuing in-loop at an offset into the wrong bytes").
- The call and apply trampolines compare `callee_segment != self.active_segment` and fall back to
  `dispatch_entered_cross_segment`.
- `calls_in_place` requires the same segment.

`bound_construct_enters_bytecode` (`rust/engine/ironhorse-vm/src/interp/apply.rs:438-446`) tests
only that the ultimate target is a non-native, non-method function.
So `new B()` executes the caller's bytes at the target's offset whenever B is a bound function
whose target came from `eval`, `new Function`, `Compartment.prototype.evaluate`, or an earlier
crank.
Binding a constructor from an earlier crank is the normal case for a long-lived vat.
The result is either an uncatchable halt, which kills the crank even inside `try`, or the wrong
bytes running as guest code.
A failed crank also leaves the machine non-quiescent, so it cannot be checkpointed.
Bytecode reads are bounds-checked, which is why this is high and not critical.

**Where:**

- `rust/engine/ironhorse-vm/src/interp/apply.rs:493` (`enter_construct_bound`) and `:548`, the
  return that lacks a segment guard.
- `rust/engine/ironhorse-vm/src/interp/dispatch.rs:2721`, where `pc = body_start` runs on the
  current buffer.
- The guards it lacks: `rust/engine/ironhorse-vm/src/interp/dispatch.rs:2810`,
  `rust/engine/ironhorse-vm/src/interp/apply.rs:311` and `:425`, and
  `rust/engine/ironhorse-vm/src/interp/invoke.rs:796`.

### COV-2 — Strict computed-key writes drop a rejected `[[Set]]` silently (high)

**Sweep:** test262-clusters (NEW-1).
**Lens:** correctness.

`XS_CODE_SET_PROPERTY_AT` (`o[k] = v`) calls `property_at_set`.
For a named key (a non-index string or a symbol) on an ordinary object, and for a non-numeric key
on a TypedArray, that function does `let _ = self.ordinary_set(...)?` and drops the boolean result
of `[[Set]]`.
These are the only two such sites in `ironhorse-vm/src`.
Every other write path checks `if !accepted && self.strict` and throws: the static `o.k = v` path,
the index arms and the array-length arm.
So strict `o[k] = v`, `o[k] += 1`, `o[k]++` and the destructuring target `[o[k]] = [v]` complete
silently, leaving the value unchanged, in four cases:

- the object is frozen;
- the property is non-writable;
- the property is a getter-only accessor;
- the object is non-extensible and the key is new.

XS throws in all of these.
Integrity holds, because the value never changes.
What is lost is the signal: Hardened JavaScript code is always strict and works on frozen objects,
so a rejected write is how a library learns it tried to mutate a hardened object.
Control flow continues past a write that did nothing.

### COV-3 — Crank completion and uncaught-throw rendering is unbounded, unmetered host work (high)

**Sweep:** handed-off-leads (HOL-1).
**Lenses:** correctness, memory-performance.

Every completed run renders its completion value into a host `String`: `run_inner` builds
`RunOutcome.result` with `self.render(&completion)`.
Every uncaught throw is rendered too: `finish_step` builds `Halt::Throw.rendered` with
`render_uncaught`, which calls `render_or_stub` and then `render`.
`render` is a `&self` walker with three gaps:

- It is bounded only by nesting depth (`render_descend`, 2,048 levels), with no bound on output
  size and no count of visited nodes.
- It cannot charge computrons.
- It allocates outside both heap ceilings.

Arrays render index by index, so arrays that share children render exponentially many leaves.
An array of N references to one long string renders N × L bytes.
`Interp::run`, `run_script_shared` and the Machine and Compartment `evaluate*` paths all go
through `run_inner`.
Nested `eval` and guest `Compartment.prototype.evaluate` do not render, so only the crank
boundary is affected.
The guest pays computrons for building the arrays (O(n)), and the host then does O(2^n) work after
the meter has stopped.
Allocation failure ends in a Rust abort, not a typed halt.
The reference stub is used only when a render is refused on depth, never to bound size.

This mechanism explains the correctness lens's "485 MB end-of-run" lead (see Unverified leads).
Reach:

- Any embedder that evaluates a guest-chosen script as a crank: the endo seam's `Machine::eval` /
  `evaluate` and `PersistentMachine::eval`, `endor run -e ironhorse`, `ironhorse-xst`, and the
  test262 lanes.
- Any guest that lets an exception escape a crank.

The thixotrope worker's crank sources are trusted wrappers (`thixotropeDispatch(...)` returns
`undefined`, `packages/thixotrope/src/worker-peer-xs.js:60-93`), so its completion values are not
guest-chosen.
INT-5 notes that `JsMachine` has no production consumer yet.
A reviewer who discounts the API surface for that reason would land at medium.

**Where:**

- `rust/engine/ironhorse-vm/src/interp.rs:3223-3242` (`run_inner`) and `:3271-3276`
  (`finish_step`).
- `rust/engine/ironhorse-vm/src/interp/render.rs:11-13`, `:41-96`, `:377-378` and `:416-418`.
- `rust/engine/ironhorse-vm/src/interp.rs:2888-2890`.
- Consumers: `rust/endo/src/ironhorse_engine.rs:777-780`,
  `rust/thixotrope-ironhorse-worker/src/main.rs:175-179` and
  `rust/engine/ironhorse-262/src/bin/ironhorse_xst.rs:82-103`.

**Evidence:**
`probes/coverage-review/handed-off-leads/l3_dag_24.js`:

### COV-5 — Functions created before the first guest `Compartment` stay unhomed for life (medium)

**Sweep:** handed-off-leads (HOL-3).
**Lens:** correctness.

The mechanism has four steps:

1. `capture_global_environment` returns NULL while `shared_compartments` is false.
2. A closure records that NULL at creation.
3. On entry, `switch_environment(NULL)` is a no-op.
4. The flag first becomes true when the guest constructs a Compartment, and nothing re-homes the
   functions that already exist.

So every start-compartment function created earlier runs in the caller's environment.
That includes hoisted declarations and closures created after `lockdown()`: guest `do_lockdown`
does not set the flag (`rust/engine/ironhorse-vm/src/interp/realm.rs:275`).
SES and XS run such a function in start.
The result is an integrity break.
A child endowed with a start function can redefine the free globals that function consults, so
an authorization check passes for a user the child picks.
And the start function's global writes land in the child.

The affected hosts are those on a bare `Interp::new()` with the native Compartment:
`ironhorse-xst`, `endot-ih`, the test262 and hardened262 lanes, and any `Interp` embedder
(`rust/engine/ironhorse-vm/src/interp/realm.rs:752-755` lists them).
`Machine::new()` is not affected, because it sets the flag at construction
(`rust/engine/ironhorse-vm/src/interp/realm.rs:854`).
The thixotrope worker is not affected, because the SES shim replaces `globalThis.Compartment`
(`packages/ses/src/compartment-shim.js:12`).
ONT-30 (low, documentation drift) mentions this behaviour only as a consequence bullet, and the
ontology lens lists it as an unverified lead.
No design document accepts it.

`rust/engine/ironhorse-vm/src/interp/function.rs:348`,

### COV-15 — Direct eval takes its early-error context from XS's flags, not PerformEval (low)

**Sweep:** handed-off-leads (HOL-2).
This finding settles the correctness lens's `eval("super()")` lead and the ontology lens's
`new.target` lead.
**Lens:** correctness.

`eval_source_in` builds an `EvalContext` from the immediate callee:
`new_target: slot_is_constructor(caller)` and `super_property: home != NULL`.
`EvalContext` has no derived-constructor bit.
`compile_atoms_units_eval_with_meter` seeds only `flags::TARGET` and `flags::SUPER`, never
`flags::DERIVED`.
So `super(` in eval code always fails with "invalid super", and `new.target` is accepted only when
the immediate caller can construct.

ECMA-262 PerformEval works differently.
It derives inFunction, inMethod and inDerivedConstructor from GetThisEnvironment, which skips
arrow frames to the enclosing non-arrow function.
It allows `new.target` in any non-arrow function, and `super()` when that function is a derived
constructor.
XS's `fxRunEval` (`c/moddable/xs/sources/xsRun.c:4623-4633`) sets only `mxTargetFlag`
(constructor-capable) and `mxSuperFlag` (home object), so IronHorse is faithful to XS.
The repository already tracks these divergences as open gaps: they are rows of the `SHARED` table
in `rust/engine/ironhorse-262/tests/xs_departures.rs:660`, which `shared_gaps_still_match_xs`
(`:852`) ratchets.
The gap is known and documented but not fixed.

**Where:** `rust/engine/ironhorse-vm/src/interp/eval.rs:56-71`;
`rust/engine/ironhorse-vm/src/interp.rs:242-248`;
`rust/engine/ironhorse-compile/src/coder.rs:1469-1475` and `:1513-1523`;
`rust/engine/ironhorse-compile/src/parser.rs:1486-1493`.

**Evidence:**
