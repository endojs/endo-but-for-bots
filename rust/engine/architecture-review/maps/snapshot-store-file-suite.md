## Purpose and responsibilities

**`store_file.rs` — `FileStore`.** The single-file, std-only,
`forbid(unsafe_code)` *reference* implementation of the `HeapStore`
trait (store-seam design § "The seam is three layers", design line
3742). It exists to pin the semantics every backend must match —
epoch/seal succession, geometry drop, byte-exact rows, leaf hashes,
page-edge summaries, free-list segments — on a durable medium with
lazy point reads and an atomic whole-file-rewrite commit. It is *not*
the production backend: the daemon opens `SqliteHeapStore`
(`rust/endo/src/ironhorse_engine.rs:396`). `FileStore` is exported
unconditionally from `lib.rs:94` (`pub use store_file::{FileStore, FILE_MAGIC}`).

**`store_suite.rs` — the backend-parameterized acceptance suite.**
Compiled into the library only under the `store-suite` cargo feature
(`Cargo.toml:26`, `lib.rs:65-66`), pulling in `ironhorse-compile` to
compile real-JS fixtures. Exposes four `pub fn`s generic over
`HeapStore`: `metamorphic_suite` (346), `lazy_working_set_bound` (505),
`checkpoint_acceptance` (541), `resume_equals_uninterrupted` (600).
Instantiated by `tests/metamorphic_determinism.rs` (Memory + File),
`tests/store_checkpoint.rs:53-108` (Memory + File), and
`rust/endo/ironhorse-store-sqlite/tests/store_suite.rs` (SQLite
`:memory:` + on-disk WAL). CI runs both (`ci.yml:746`, `:750`).

**`test_dir.rs` — `TempDir`.** A `pub(crate)`, `cfg(test)`-only scratch
directory guard (`lib.rs:69-70`) used by `store_file.rs`'s unit tests;
an acknowledged verbatim twin of `tests/common/mod.rs`.

## Architectural observations

- **Layering is clean.** `FileStore` contains no admission logic of its
  own: succession, row-length, grown-region, summary-coupling and root
  recombination all come from `check_succession`/`apply_batch` in
  `store.rs`, run against the durable prior. A backend cannot drift on
  semantics; it can only drift on layout/durability. This is the right
  shape for a reference backend.
- **Duplication inside the file.** `atomic_replace_and_reload` (115-148)
  and the tail of `commit` (709-811) are the same tmp/fsync/rename/
  dir-sync/reload sequence written twice (temp-name construction,
  cleanup-on-failure, `Path::parent()` fallback, reload). The doc claim
  that migration "shares this so atomicity can never drift from
  commit's" is one-directional. A streaming writer closure would unify
  them.
- **Whole-file reads in migration.** Both `replace_manifest_*` methods
  `std::fs::read` the entire store (399, 444), whereas `commit` streams
  rows with O(row) buffers. The ladder (`store.rs:2043-2062`) can run
  up to 18 steps from a v5 store, each a full read + full rewrite +
  fsync + rename + reload.
- **Post-rename failure = misreported commit + stale-inode view.** After
  `rename` (784) succeeds, a failure at 805/809/810 returns `Err` while
  the file has advanced; `self.state` still points at the unlinked
  previous inode, so subsequent point reads through this handle are
  self-consistent but stale relative to disk. Fail-closed at the next
  `commit` (EpochMismatch). The design ledger records this
  ("dir-sync ack-uncertainty … STILL OPEN, by design", design 822-826).
- **Platform dependence.** `File::open(dir).sync_all()` (143, 805) is a
  POSIX idiom; on Windows std cannot open a directory handle this way
  (no `FILE_FLAG_BACKUP_SEMANTICS`), so every commit would take the
  post-rename failure path above. Not executed here; medium confidence.
  Consensus is unaffected (store durability is not guest-observable),
  and production uses SQLite, but a "reference" backend that cannot
  commit on one major OS is worth stating.
- **Clean rows are trusted at commit.** `Source::Prior` copies bytes and
  the durable leaf without re-hashing (765-774, 648-655). At-rest
  corruption of a never-faulted row is carried into every later epoch
  and re-sealed; it is caught only when that row is read (`store_to_image`
  re-verifies all rows, store.rs:2876-2909; lazy fault verifies per
  row). A deliberate O(dirty) trade, but not stated at the commit site.
- **`open` is structural only.** `FileStore::open` never recombines
  leaves against the root; `read_slot_page` etc. are `pub` and return
  unverified bytes. Fail-closed content integrity depends on every
  caller routing through `validate_store`/`store_to_image`. The trait
  doc ("reads return the raw stored bytes", store.rs:1741) makes this
  contractual, but `open`'s doc reads stronger than it is.
- **Panics/unwraps on untrusted data — clean.** In `load`, the only
  `unwrap`s are `try_into()` on fixed-size sub-slices of a
  `[u8; 12]` (224-225) — infallible. Every `vec![0u8; n]`/`with_capacity`
  is clamped by `file_len`. In the migration rewrite, `try_into().unwrap()`
  on `chunks_exact(12)` rows (488) is infallible. Mixed arithmetic:
  `checked_add` for some terms (460-473) but bare `small_end + 4`,
  `small_end + 8`, and `at + 4` inside `read_u32` (446-451, 467-468) —
  unreachable overflow on 64-bit with u32-derived operands, but the
  discipline is inconsistent.
- **Determinism.** `commit`'s `HashMap<u32, usize>` (582-594) is used
  for lookup only, never iterated; `Loaded` is all `Vec`. No f64, no
  time, no locale. The suite compares in-process and relies on the
  golden vector (`metamorphic_determinism.rs:159, 252`) for cross-host
  bytes — a sound split. Cross-region note (store.rs, not my region):
  `check_batch`'s `symmetric_difference().next()` (store.rs:1211) picks
  a HashSet-order-dependent page for `SummaryMismatch { page }` when
  several pages mismatch — error-payload nondeterminism only.
- **`File::create` for the temp (126, 722)** is `O_TRUNC`, not `O_EXCL`;
  uniqueness rests on naming. After pid reuse a stale `.tmp-{pid}-{n}`
  could be truncated and reused — harmless because temps are inert.
- **Suite parameterization is EMPTY-store-only.** `fresh: FnMut() -> S`
  and `&mut dyn HeapStore`; the trait has no open/close/path concept, so
  the shared instrument cannot drop a handle and reopen. Durability
  across reopen is exercised only per-backend.
- **Suite does not exercise the trait's negative commit contract.**
  Every `checkpoint_to_store` is `.expect("checkpoint")` (202, 254,
  561); no replay, fork, `NotEmpty`, shrink, or omitted-grown-row
  case. Those locks are MemoryStore/FileStore-specific in
  `store_checkpoint.rs` and SQLite-specific in its `lib.rs` tests
  (1468, 1475). The design's "same instrument" claim is therefore
  about determinism, not the full trait contract.
- **Test ownership is inverted for FileStore's collector coverage.**
  `query_gc.rs:117-119` (in the downstream SQLite crate) says FileStore
  "had NO partial_collect coverage anywhere" and supplies it there. The
  engine workspace's own CI job would not notice a FileStore
  `partial_collect` regression unless the SQLite job also runs.
- **`carry()` is a workaround for positional symbol ids.** The suite
  must pad every crank with a dead mention block and assert identical
  symbol vectors (298-343) because `link_intrinsics` is called once
  from crank 1's names and a name first interned in crank 2 resolves to
  nothing. This is an engine API-boundary hazard surfaced by test
  scaffolding; flag for the vm/machine readers.
- **Variants other than baseline do not assert `completed`** (109-111,
  199-201, 251-253). A halted crank would still be caught — the final
  `write_snapshot(...).expect("quiescent machine snapshots")` panics
  on a non-quiescent machine — but with a misleading message.
- **`test_dir.rs` is a byte-for-byte twin of `tests/common/mod.rs`**
  (both 43 lines, differing only in `pub` vs `pub(crate)`). Acknowledged
  in its header; a `#[path]` include would remove the duplicate.
- **Metering doctrine.** The suite asserts per-crank computron
  equality across residency schedules (85-91) — exactly the
  "determinism per release" property the design makes unconditional,
  and it correctly does not compare against XS.
- **Library carries test scaffolding.** `store_suite` `pub fn`s
  `assert!`/`panic!` and hard-code `Signature::new("ironhorse-worker-v1")`
  inside the library crate (feature-gated). Acceptable; noted.

## Candidate findings

Ordered most architecturally significant first.

### 1. The shared acceptance suite cannot observe durability: it never reopens a backend
- **File:line:** `ironhorse-snapshot/src/store_suite.rs:346`, `:140`, `:237`, `:513`, `:541`
- **Claim:** No function in `store_suite` drops a store handle and re-acquires the same backend from its medium, so a `HeapStore` that buffered commits in memory and never flushed would pass all four suite entry points.
- **Evidence:**
  `pub fn metamorphic_suite<S: HeapStore + 'static>(mut fresh: impl FnMut() -> S)` (346)
  `let store = Rc::new(RefCell::new(store));` (140, 237, 513) — one handle per variant
  `/// `fresh` must return an EMPTY store` (293)
- **Why it matters:** The design says every backend "runs the SAME instrument rather than a hand-copied subset" (design 134-149; store_suite.rs:1-6), but the suite's parameterization (empty-store factory, `&mut dyn HeapStore`) structurally excludes the property a durable store exists for. Reopen coverage is hand-copied per backend (`store_file.rs:887-903`, `store_checkpoint.rs:112-132`, SQLite `engine_lifecycle.rs`). Adding an optional `reopen: Option<&mut dyn FnMut(S) -> S>` parameter would close it without a trait change.
- **Category:** verification. **Severity:** medium. **Confidence:** high.

### 2. The suite does not exercise the trait's negative commit obligations (succession refusal, geometry drop, grown-row refusal)
- **File:line:** `ironhorse-snapshot/src/store_suite.rs:202`, `:254`, `:561`; contract at `store.rs:1774-1777`, `:1708-1711`
- **Claim:** Every commit the suite issues is a legitimate successor (`.expect("checkpoint")`); no scenario replays, forks, commits into a non-empty store, omits a grown row, or is designed to shrink `chunk_len`, so a backend violating "Must enforce the epoch discipline … and drop rows beyond the new geometry" passes the shared instrument.
- **Evidence:**
  `checkpoint_to_store(&mut session, &sig(), &mut *store.borrow_mut()).expect("checkpoint");` (202)
  `/// Apply one checkpoint atomically. Must enforce the epoch discipline via [`check_epoch`] and drop rows beyond the new geometry.` (store.rs:1774-1776)
  The locks exist only per-backend: `store_checkpoint.rs:158-193, 261-274` (Memory), `:199-256` (File), SQLite `lib.rs:1468, 1475`.
- **Why it matters:** The trait's most safety-relevant obligations (split-brain refusal, stale-row drop after compaction) are exactly what a new backend is most likely to get wrong, and the shared suite — whose stated purpose is to prevent hand-copied subsets — is silent on them. A `commit_contract(store: &mut dyn HeapStore)` entry point using `image_to_batch` + `reseal_batch` (already used in `store_file.rs:942, 1038`) would be small.
- **Category:** verification. **Severity:** medium. **Confidence:** high (shrink: I did not run the suite to prove no compaction occurs; the claim is that nothing is designed or asserted to shrink).

### 3. A successful rename followed by a failed dir-sync/reload is reported as a failed commit and leaves the handle reading an unlinked inode

### 6. Clean rows are copied forward at commit without leaf verification, so at-rest corruption of an unfaulted row propagates and is re-sealed
- **File:line:** `ironhorse-snapshot/src/store_file.rs:765-774`, `:648-655`
- **Claim:** `Source::Prior` streams the previous file's bytes and reuses the previous leaf hash; `apply_batch` recombines the root from the stored leaves, not the bytes, so a corrupted clean row passes `commit` and is carried into every later epoch until something reads that row.
- **Evidence:**
  `Source::Prior(entry) => { … f.read_exact(&mut buf) …; tmp.write_all(&buf) … }` (765-773)
  `let mut leaf_pages = durable.as_ref().map(|(l, _)| l.leaf_pages.clone()).unwrap_or_default();` (648-651)
- **Why it matters:** Not a silent-pass — `store_to_image`/`root_hash`/`export_to_container` re-verify every row (store.rs:2876-2909) and lazy faults verify per row — but `commit` is not an integrity checkpoint and the store never self-heals. That is a legitimate O(dirty) trade (module doc 10-11) that should be stated at the commit site; a backend author copying the reference could reasonably assume commit re-verifies.
- **Category:** robustness. **Severity:** low. **Confidence:** high.

### 7. Migration writes read the whole store into memory and the ladder rewrites the file once per schema step

## What is done well

- **Admission logic is centralized, not re-implemented.** `FileStore::commit` delegates succession, row-length, grown-region, summary-coupling and root recombination to `check_succession`/`apply_batch`, and runs them against the DURABLE prior it just re-read — the ping-pong and stale-handle classes are closed by construction (565-572, 664-671; locked by `second_file_handle_cannot_clobber_a_commit`).
- **Malformed-count discipline is applied consistently in `load`.** Every count and length is clamped against `file_len` before any reservation, outer vectors grow against real reads where a `with_capacity` would amplify (259-264), and every directory entry is `checked_add`-bounded. No `unwrap` in `load` touches untrusted data. The hardening sweeps (`store_hardening.rs:457, 575, 663`) exercise this with 400 random and 400 header-concentrated mutations plus a per-word edge-section sweep.
- **The durability sequence is the correct one**: unique sibling temp, `sync_all` on the temp, `rename` onto the target, `sync_all` on the parent directory, with the bare-relative-filename parent case handled and temp cleanup on both write and rename failure (locked by `failed_rename_removes_the_temp_file`).
- **The metamorphic suite is a genuinely strong determinism instrument**: seven execution ways × 13 real-JS scenarios covering the graduated side-table families, comparing per-crank computron vectors (not just the last), final blob bytes, and — via the adversarial-evict arm — asserting eviction actually happened rather than degrading into a prefetch duplicate. The anchored-symbol discipline is enforced up front with a clear message rather than surfacing as a buried `TypeError`.
- **The in-file comments carry the review lineage** (wave numbers, finding ids, the reason a guard exists), so a reader can tell which lines are load-bearing fixes and which are structure — unusually good for a codebase of this size.
- **Feature-gating keeps test scaffolding out of production builds** while still letting an external crate (`ironhorse-store-sqlite`) instantiate the same suite; the self-dev-dependency trick (`Cargo.toml:41`) is documented.
