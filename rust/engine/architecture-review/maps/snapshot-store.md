## Purpose and responsibilities

`store.rs` is the **paged logical image** and the **backend-neutral persistence contract** for a suspended
machine. It sits between the atom container (`image.rs`) and the arenas (`ironhorse-vm`) and owns:

1. The `HeapStore` trait (1744–1916): point reads of slot pages / chunk extents / free-list segments,
   metadata reads (inventory, leaf hashes, page-edge summaries), one atomic `commit`, two migration-only
   write surfaces, and default GC-shaped reachability queries.
2. The wire formats the trait moves: `StoreManifest` (170–419), `SmallState` (1293–1698, 30 length-prefixed
   sections), `CheckpointBatch` (1700–1732), free-list segments (558–595), page-edge summaries (477–498).
3. The integrity machinery: leaf hashes (597–605), per-class Merkle trees (607–779), `RootLedger`
   incremental maintenance (781–982), the v5 flat root kept for migration (984–1024), the commit seal chain
   (421–475), and the admission gauntlet `check_batch` / `apply_batch` / `check_succession` / `check_epoch`
   (1026–1291, 2626–2681).
4. The schema ladder `migrate_store` v5→…→v23 (1918–2624).
5. The bridges: `image_to_batch` (2733–2834), `store_to_image` (2839–3047), `validate_store` →
   `ValidatedStoreState` (3055–3361), `export_to_container` / `import_from_container` / `root_hash` (3363–3407).
6. The in-memory reference backend `MemoryStore` (3409–3599) and 22 unit tests (3601–4316).

It does **not** own: dirty/residency bitmaps and `PageSource` (vm `value.rs`), the checkpoint producer, the
lazy fault installer and the partial/generational collectors (`machine.rs`), the file backend
(`store_file.rs`), or the SQLite backend (`rust/endo/ironhorse-store-sqlite`).

## Architectural observations

**Coupling / monolith symptoms.**
- `SmallState` is a 29-field struct whose fields, encode array, decode sequence, `image_to_batch` copy,
  `store_to_image` copy, and two `check_image_slot_bounds` call sites (2975–3008, 3317–3350) must all be
  edited in lockstep for every new side table — six sites per graduation, plus a ladder step, plus the
  `MachineImage` mirror in image.rs. The schema-23 history shows this has been done 18 times; the mechanical
  nets live elsewhere (the vm's visitation registry, the snapshot ledger), not here.
- The migration ladder is 16 copies of one 30-line function (2106–2624) differing in a constant and a
  schema number; the copy-paste has already produced a misattached doc comment (2540–2544 vs 2570).
- `store.rs` mixes five concerns (wire formats, Merkle/seal crypto, admission logic, migration, reference
  backend) in one 4.3k-line file; the trait itself is only 170 lines.

**Hidden state.** `RootLedger` is a derived cache whose coherence is guaranteed only by the owner's
discipline (790–800). `MemoryStore.last_commit` is test telemetry. Nothing else hidden.

**Panics / unwraps / indexing on untrusted data.** The module is careful: every decode bounds-checks before
slicing; `rows_by_page[i]` (1215) is guarded by the symmetric-difference check at 1211; `class_tree_root`
`leaves[0]` (688) is guarded by the match; `update_class_tree` indexing is guarded by `patch_class`
(909–913). The two `try_into().unwrap()` on `chunks_exact(4)` (2971, 3282) cannot fail. The ledger's
"recorded but not verified" `i + len` overflow (1441, 1951) cannot overflow `usize` on 64-bit targets since
`len ≤ u32::MAX` and `i ≤ p.len()`; on a 32-bit target a wrap would pass the check and the slice would panic
(a crashed crank, not unsafety). `chunk_extent_count` saturating to `u32::MAX` (250) makes a crafted
`chunk_len ≈ u64::MAX` cost a 4-billion-iteration loop in `check_batch` (1098) only if the batch also
supplies the rows, so it fails at the first missing extent.

**Determinism hazards.** Rows and summaries are index-ordered; `derive_page_edges` and all reachability
results are `BTreeSet`s; no f64, no host time, no locale. The one nondeterministic value is the *error
payload* at 1211–1213 (`HashSet::symmetric_difference(..).next()` picks a hash-seed-dependent page).
`check_batch`'s `HashSet`/`HashMap` are otherwise membership-only. `MemoryStore` uses `HashMap<u32, Vec<u8>>`
for rows but never iterates it observably (`inventory` walks by index, 3507–3523).

**GC-root and side-table hazards.** See the load-bearing invariant above. Additionally, freed records keep
their bytes (design 3966), so `derive_page_edges` includes stale edges from dead records — over-retention
only, deterministic, and the design names it ("retention-only divergence"). Whether `free_pages` on a dead
page also retires side-table rows *owned* by slots in that page is a machine.rs/interp question; if owner
keys are not counted as refs by `each_side_table_ref`, a dead page with side-table-owning slots could be
freed with its rows left dangling (not verified here; flagged for the vm/GC readers).

**Snapshot-coverage hazards.** `SmallState` carries 24 side-table sections; the persist gates that refuse
still-Pending state (`PendingStateUnsupported`) are produced in machine.rs. The section-order doc at
1361–1367 is two entries stale (missing error frames, promise cluster).

**Metering-doctrine drift.** None in this file: the cost-table gate compares `MeterImage.cost_table_version`
to `COST_TABLE_VERSION` (3050–3052, 2010) — consistent with "determinism per release".

**Error-handling shape.** `Result<_, StoreError>` everywhere; `StoreError` is `Eq` but has no `Display` or
`std::error::Error` impl (only `From<SnapshotError>`, 164); `Io(String)` discards `io::ErrorKind`.
`BaselineMismatch{expected, found}` is overloaded for three distinct conditions (root mismatch, prev_seal
mismatch, seal forgery) — 1285, 2637, 2657 — so a caller cannot tell "corrupt at rest" from "forked lineage".

**API-boundary leaks.** `CheckpointBatch` and `StoreManifest` are fully `pub` with `pub` fields, so any
caller can construct a manifest with an arbitrary `store_schema`/`signature`/`creation`; the commit gate
does not pin these against the stored lineage (finding 5). `ValidatedStoreState` correctly hides its fields.

**Performance-architecture.** Every trait read returns an owned clone (`Vec<u8>`, `Vec<Vec<u32>>`,
`Vec<[u8;32]>`); `summary_page_count` and the three reachability defaults each clone the entire edge table
per call (1784–1801, 1866–1915). The SQLite backend overrides these; MemoryStore/FileStore do not.
`validate_store`'s "no O(heap) row I/O" is honest about bytes but each of `inventory`, `leaf_hashes`,
`page_edges` is O(pages) allocation.

**Integrity model precision.** The root and seal are unkeyed SHA-256; they detect corruption and forks, not
a writer who rewrites row+leaf+root coherently. The module header's "Store contents are untrusted" (396) is
therefore carried by the *semantic* gates (`check_image_slot_bounds`, per-fault bounds), not by the hashes.
That is coherent with the design's trust class ("daemon-private state") but the doc at 222–229 reads
stronger than what an unkeyed hash can promise.

## Candidate findings

1. **The fail-closed commit gauntlet is a per-backend convention, not a trait invariant** —
   `store.rs:1744-1777`, `1026-1030`. Claim: nothing in `HeapStore` forces a `commit` implementation to run
   `check_succession`/`check_batch`; a backend that omits them compiles and persists forged or
   geometry-inconsistent batches. Evidence: `fn commit(&mut self, batch: &CheckpointBatch) -> Result<(), StoreError>;`
   (1777) with the doc "Must enforce the epoch discipline via [`check_epoch`]" (1774); the `check_batch` doc
   itself records that "free-segment grown-region and summary coupling were previously checked in some
   backends and not others" (1029–1030). Why it matters: three backends (memory, file, SQLite) re-implement
   the same admission sequence by hand; a provided `commit` that runs the gauntlet and delegates to a
   narrow `persist_verified(...)` hook would make the property structural. Category: api-boundary.
   Severity: medium. Confidence: high on the code fact.

2. **Manifest fields outside the root (`cranks`, `epoch`) are unauthenticated at rest** —
   `store.rs:221`, `3106-3361`, `2137`. Claim: a length-preserving byte flip of `cranks` in a stored manifest
   passes `validate_store` and changes when the resumed replica next runs `partial_collect`. Evidence:
   "the ROOT is computed over the small-state leaf and the row leaves, and the manifest is in neither"
   (2137); `validate_store` never recomputes or verifies `seal` (it cannot — no prev_seal or rows) and checks
   `epoch` only for `== 0` (3142). Why it matters: the doc for `cranks` (201–221) says the cadence must be
   "resume-invariant" so replicas do not "fork the durable heap, with identical per-crank results and
   computrons hiding it" — a flipped `cranks` produces exactly that fork, and the root's "length-preserving
   byte flip at rest fails closed" promise (222–229) does not cover it. Fix shape: fold the manifest core
   (or at least `epoch`, `cranks`) into the root's `combine_class_roots` preimage. Category: determinism.
   Severity: medium. Confidence: high on the code; impact requires at-rest corruption/tampering.

3. **`derive_page_edges` under-approximates the collector's edge relation; soundness rests on an
   unstated cross-file parity** — `store.rs:477-498` vs `gc.rs:137-138`, `interp.rs:44661-44692`. Claim:
   the stored summaries omit every `GcHooks::extra_edges` edge, so `reachable_page_set` alone is unsound;
   `partial_collect` is sound only because it roots every side-table-referenced page, which requires
   `extra_edges ⊆ each_side_table_ref`. Evidence: `r.each_ref_slot(|t| { … })` (485) — `each_ref_slot`
   visits only `next` and `Payload::Reference` (value.rs:371–379); the marker does
   `slots.get(idx).each_ref_slot(..); hooks.extra_edges(idx, ..)` (gc.rs:137–138). Why it matters: this is the
   GC-root-omission bug class relocated into the store; store.rs documents `derive_page_edges` as "a page's
   outgoing edge summary" with no mention that it is arena-only, and the parity that makes the collector
   safe is neither stated nor locked in this crate. Category: gc-roots. Severity: medium (currently sound by
   the vm's over-approximation; fragile). Confidence: high on the code facts; whether a test locks
   `extra_edges` vs `each_side_table_ref` is unverified.

4. **The commit gate does not pin manifest identity/schema across a lineage** — `store.rs:1059-1223`,
   `2630-2663`, `301-303`, `391-395`. Claim: a batch whose `manifest.store_schema`, `version`, `signature`
   or `creation` differ from the stored manifest's (or whose schema ≠ `STORE_SCHEMA_VERSION`) is accepted by
   `check_succession` + `apply_batch`. Evidence: `check_succession` compares only epoch, `prev_seal`, and
   the recomputed seal (2634–2661); `check_batch` never reads `batch.manifest.store_schema`; `encode`
   emits the `cranks` tail only `if self.store_schema >= 8` (301). Why it matters: a batch stamped schema 7
   silently drops `cranks` on a file/SQLite re-read (cranks := 0 at 391–395 → cadence reset); a batch
   stamped > 23 wedges the store (validate and migrate both refuse). The design already treats
   `CheckpointBatch` forgery as in scope ("`CheckpointBatch` is a public type, so without recomputation a
   forged constant seal could…", 2642–2646). Category: robustness. Severity: low-medium. Confidence: high
   on the code; honest producers stamp correctly (machine.rs:879).

5. **`RootLedger::apply` can fail after partially mutating the ledger, with no poison** —
   `store.rs:892-981`. Claim: when the extents/frees/edges class reports `MissingRow`, `self.pages` and
   `self.pages_levels` have already been patched, leaving a half-advanced cache that `root()` will happily
   report. Evidence: four sequential `patch_class(...)?` calls (947–978), each mutating `leaves`/`levels`
   before the next is range-checked; the coherence rule is prose: "on ANY failed or refused commit the owner
   must DROP it" (792–794). Why it matters: the fast path replaces `apply_batch`'s full recombination with
   this cache; a stale cache on a later successful commit would seal a wrong root. Range-check all four
   classes before mutating any, or return `Err` by value and consume `self`. Category: robustness.
   Severity: low-medium. Confidence: high on the code; SQLite's owner comments say it drops (lib.rs:859).

6. **Sixteen near-identical migration steps** — `store.rs:2106-2624`. Claim: every step from 6→7 onward
   is the same "verify root, append N zero-length section headers, restamp" function differing only in
   `N` and the target schema; the duplication has already caused a doc mix-up. Evidence: 2540–2544 reads
   "20 → 21: synchronous generator activations … Schema 21 -> 22: append the (empty) error-frames section"
   above `migrate_v21_to_v22`, while `migrate_v20_to_v21` (2570) has no doc. Why it matters: the ladder is
   consensus-adjacent (it rewrites the durable root) and should be a small table
   `[(from, to, appended_bytes)]` driven by one audited function; the `STORE_SCHEMA_VERSION` doc (74–88)
   also stops describing steps at v7. Category: modularity. Severity: low.

7. **Clone-everything trait surface makes GC-shaped queries O(pages) allocation per call** —
   `store.rs:1784-1801`, `1866-1915`. Claim: the default `summary_page_count`, `reachable_page_set`,
   `externally_referenced`, and `reachable_within` each call `self.page_edges()?`, which returns a fresh
   `Vec<Vec<u32>>` of the entire table. Evidence: `Ok(self.page_edges()?.len() as u32)` (1785);
   `let edges = self.page_edges()?;` (1868, 1895). Why it matters: `partial_collect` issues two of these
   per collection (machine.rs:1975, 2000); for MemoryStore/FileStore that is several full-table clones per
   cadence tick; the trait offers no borrowed or streaming read (`&[u8]`, iterator) at all. Category:
   performance. Severity: low.

8. **Nondeterministic error payload from `HashSet` iteration** — `store.rs:1211-1213`. Claim: when more
   than one page is present in `slot_pages` xor `page_edges`, the page named in
   `SummaryMismatch { page }` varies run to run. Evidence:
   `if let Some(&odd) = batch_pages.symmetric_difference(&edge_pages).next()`. Why it matters: host-visible
   only, but the crate's tests match on exact error values and the seam design wants every refusal
   reproducible; a `BTreeSet` or `min()` fixes it. Category: determinism. Severity: low.

9. **`StoreError` implements neither `Display` nor `std::error::Error`; `Io(String)` erases the kind** —
   `store.rs:100-168`. Claim: no `impl Display`/`Error` exists anywhere in the workspace. Evidence: the
   only impl is `impl From<SnapshotError> for StoreError` (164); repo-wide grep for `for StoreError`
   returns that one line. Why it matters: the daemon must pattern-match variants to report anything; three
   distinct conditions share `BaselineMismatch` (1285 root, 2637 prev_seal, 2657 forged seal), so callers
   cannot distinguish "corrupt at rest" from "forked lineage" from "forged batch". Category: error-model.
   Severity: low.

10. **Small state admits two encodings of an empty table, so the store root is non-canonical after
    migration** — `store.rs:1455-1465`, `1386-1428`. Claim: a migrated store (zero-length sections) and a
    freshly-committed store with identical logical state have different `small` bytes and therefore
    different `root` values until the next commit rewrites `small`. Evidence: "An EMPTY section (zero
    length, distinct from an empty LIST's 4-byte count header) is accepted as the empty table" (1456–1457);
    the writer always emits `encode_arrays(&self.arrays)` etc. (1394). Why it matters: the CAS key
    (canonical export) is unaffected, but the "store-native identity" root (229) is then not a function of
    logical content; this is the store-side sibling of the ledger's open P3-2 canonical-form item.
    Category: verification. Severity: low.

11. **Batch canonical form is not enforced (duplicate/unsorted rows)** — `store.rs:1087-1092`,
    `1207-1208`, `1257-1281`, `3571-3583`. Claim: a batch containing `(p, bytes_a)` and `(p, bytes_b)` passes
    `check_batch` (sets collapse duplicates), and "last wins" is decided independently by `apply_batch`'s
    leaf loop, `rows_by_page` (HashMap `collect`), and each backend's insert order. Evidence:
    `let batch_pages: HashSet<u32> = batch.slot_pages.iter().map(|(p, _)| *p).collect();` (1087–1088);
    `let rows_by_page: HashMap<u32, &Vec<u8>> = … .collect();` (1207–1208). Why it matters: the seal covers
    the raw Vec so this is not forgeable, but one logical commit has many valid encodings and a backend that
    resolves duplicates differently (e.g., first-wins) would silently diverge from the leaf table.
    `seal_commit`'s doc claims "in the batch's sorted order" (423) but nothing sorts. Category: verification.
    Severity: low.

12. **Doc drift inside the module** — `store.rs:1361`, `1430`, `1387`, `271-275`, `1762`, `188`, `423`.
    Claim: at least five doc comments describe a previous version of the code. Evidence: "twenty-eight
    sections" (1361, 1430) vs `[Vec<u8>; 30]` (1387) and "thirty sections" (1658); manifest layout doc
    omits `free_len`/`root`/`seal`/`cranks` (271–275); "[`apply_batch_leaves`]" does not exist (1762);
    `slot_count` "Monotone" (188) is not enforced (1254, 3588). Why it matters: this crate's docs are the
    only spec for two external backends. Category: docs-drift. Severity: low.

13. **`slot_count` shrink is accepted despite the documented monotone invariant** — `store.rs:188`,
    `1093-1097`, `1254`. Claim: a batch with `manifest.slot_count` smaller than the stored one is admitted;
    the grown-region range is simply empty and `pages.resize` truncates. Evidence: `for page in
    prior_pages_len as u32..n_pages as u32` (1093) — empty when shrinking; `pages.resize(n_pages, [0u8; 32])`
    (1254). Why it matters: a lazily attached session freezes `snapshot_count` at attach (value.rs:72); a
    shrink would let a resident-bit vector outlive its geometry. No honest producer shrinks, so this is an
    unenforced invariant rather than a live bug. Category: robustness. Severity: low.

14. **32-bit `i + len` wrap in the two section readers (ledger's "recorded but not verified" item)** —
    `store.rs:1441`, `1951`. Claim: on 64-bit targets the check `i + len > p.len()` cannot wrap (both
    operands ≤ `u32::MAX`-ish), so it is sound; on a 32-bit target it can wrap, pass, and then panic at
    `&p[i..i + len]`. Evidence: `let len = u32::from_be_bytes([…]) as usize; i += 4; if i + len > p.len()`
    (1439–1441). Why it matters: closes the ledger's open question — a crashed crank, not unsafety, and
    only on 32-bit; `i.checked_add(len)` would make it target-independent. Category: robustness.
    Severity: low. Confidence: high.

## What is done well

- **Decode discipline is exemplary**: every length is bounds-checked before a slice, trailing bytes are
  refused in both the manifest and small state (399, 1661), reservations are clamped, and `check_epoch`
  uses `checked_add` — no panic path on untrusted bytes was found on 64-bit targets.
- **The proof-token pattern** (`ValidatedStoreState` with private fields, 3072–3092) makes it impossible for
  resume code to mix a validated manifest with small state from another epoch.
- **Migration is verify-then-restamp with signature and cost-table gates before the first byte changes**
  (1988–2015), a strict-advance guard against no-op or cycling backends (2037), and `reread_manifest` to
  defeat stale handle caches (1803–1825) — each with the review finding that motivated it recorded inline.
- **Reference semantics are honest**: `MemoryStore::commit` verifies on clones before mutating (3566–3570)
  so a refused batch is a true no-op; `CommitStats` lets tests measure O(dirty) proportionality rather than
  assert it.
- **Determinism hygiene is deliberate**: page edges are `BTreeSet`-sorted, reachability returns ordered
  sets, free-list order is locked at the 4096/4097 boundaries (3992–4014), and the v6 incremental tree is
  property-tested against a from-scratch rebuild across widths and dirt patterns (4068–4101, 4117–4234).
- **Design-to-code traceability**: nearly every non-obvious check cites the review wave or finding that
  motivated it, which made auditing this file far faster than its size suggests.
