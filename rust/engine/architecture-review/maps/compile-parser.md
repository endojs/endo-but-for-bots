## Purpose and responsibilities

`parser.rs` is a method-for-method transliteration of the expression grammar of XS's `xsSyntaxical.c`
(`fxCommaExpression` … `fxLiteralExpression`, `fxCallExpression`, `fxNewExpression`, `fxGroupExpression`,
`fxObjectExpression`, `fxPropertyName`, `fxTemplateExpression`); `parser/stmt.rs` is the statement / binding /
function / class / module half (`fxProgram`, `fxModule`, `fxStatement`, `fxForStatement`, `fxBinding` and the
`…FromExpression` cover conversions, `fxClassExpression`, `fxImportDeclaration`, `fxExportDeclaration`).
The parser pulls tokens from `Lexer` (with two re-entry points: `read_regexp` at parser.rs:1054 and
`next_template_part` at parser.rs:1636), keeps XS's `parser->flags` mode word (`Parser::flags`), builds XS's exact
tree on a node stack (`Parser::stack: Vec<Item>`, XS `parser->root`), and returns the first error as a
`ParseError` (fail-fast, mirroring `fxReportParserError` + `longjmp`).

`ast.rs` is the tree model: `Item` (four XS stack-slot kinds: node / bare symbol / NULL / node list), `Node`
(`token`, `line`, `flags`, positional `children: Vec<Item>`, leaf `Value`), the XS flag-bit table (`flags`), the
XS node-name table (`node_name`, preserving XS misspellings such as `PrivateIdenfifier`), and the fixture `dump`.
It is explicitly "not a nicer AST" (ast.rs:5–11): downstream scoper/coder byte-identity depends on XS's shapes.

Consumers: `coder::compile_atoms_with` / `compile_module_atoms` (coder.rs:934–935, 986–987), `scoper::run` tests
(scoper.rs:370–378), `lib::parse_computrons` (lib.rs:52–56), the fuzz parse target (`ironhorse-fuzz/src/lib.rs:1903–1914`),
and — at runtime — the VM's `eval`/`Function` bridge through `ironhorse_vm::SourceCompiler` implemented in
`ironhorse-262/src/lib.rs:47–75` (harness) and `rust/endo/src/ironhorse_engine.rs:162, 496` (production, no
`catch_unwind`).

## Architectural observations

- **Recursion is the architecture.** Each nesting level of `(`/`[`/`{`/arrow/template costs ~25 Rust frames
  through the precedence cascade; with `Lexeme` (~150 B, cloned into locals) and `PResult` plumbing this is
  ~32 KiB/level in debug and ~2.2 KiB/level in release. Measured first-abort depths (this host, x86_64):

  | construct | debug 2 MiB | debug 8 MiB | release 2 MiB | release 8 MiB | release 32 MiB |
  |---|---|---|---|---|---|
  | `(((x)))` | 64 | 261 | 926 | 3,714 | 14,870 |
  | `[[[ ]]]` | 68 | 273 | 982 | 3,939 | 15,765 |
  | `({a:{a:…}})` | 61 | 250 | 981 | 3,937 | 15,763 |
  | `x=>x=>…` | 62 | 251 | 939 | 3,768 | 15,083 |
  | `` `${`${…}`}` `` | 64 | 258 | 733 | 2,942 | 11,779 |
  | `f(f(f(x)))` | 87 | 352 | 1,332 | 5,344 | 21,394 |
  | `function f(){…}` | 208 | 834 | 3,349 | 13,432 | 53,762 |
  | `{{{ }}}` | 258 | 1,033 | 10,048 | 40,295 | >100,000 |
  | `!!!x` | 1,278 | 5,210 | 21,743 | 87,279 | >100,000 |
  | `x=x=x=…` | 2,241 | 9,139 | 21,743 | 87,279 | >100,000 |

  Whole `compile()` (parser+scoper+coder) in debug at the CI 16 MiB: 523 parens, 503 arrows, 1,668 nested functions.
  This is why CI needs `RUST_MIN_STACK=16777216` (ci.yml:824–832 attributes it to regexp suites; the parser is
  at least as deep) and why `xst.rs:1368–1374` pins 32 MiB case threads "so a deeply-nested source … [does not]
  SIGSEGV the whole batch". The harnesses work around an engine property the engine should own.
- **Panic-vs-Result split at the front-end boundary.** The parser is `Result`-total, but early errors XS raises
  at *code* time are `panic!`s in the coder (coder.rs:2403 "coder: invalid initializer", 4958–4960 "no reference
  for assignment target", 2997 "static block with lexical declarations deferred", 1150 "unsupported node kind" …).
  `compile()`'s `Result<_, ParseError>` signature therefore lies, and the 262 harness / fuzz / compile_diff all wrap
  `catch_unwind` — production `ironhorse_engine.rs:162, 496` does not. The parser's cover-grammar design
  (parser.rs:1389–1397 builds a `Binding` inside an `Object` and never rules on it) is where this originates.
- **Positional, untyped AST.** `Node.children: Vec<Item>` with meaning by index: 238 `children[` sites
  (coder 210, scoper 13, parser+stmt 14, ast 1). The shape contract exists only as parser push order plus the dump
  fixtures; any drift is an out-of-bounds panic, not a type error. This is a faithful port of XS's pointer-stack
  build but forfeits Rust's main structural tool.
- **Hidden / hand-managed state.** `Parser::flags` is XS's single mode word (parser bits and node bits share one
  namespace; `STRING_LEGACY` aliases `EVAL`, ast.rs:38–44). Save/restore is manual at ~12 sites
  (`let saved = self.flags … self.flags = saved`), correct only because errors are fail-fast. `property_name_async_flag`
  is an out-parameter smuggled through the struct (parser.rs:131–135, 1354, 1434, 1577). `statement(block_it: i32)`
  keeps XS's `-1/0/1` magic values.
- **Lookahead vs lexer re-entry.** `ahead`/`ahead2` are lexed in operator mode and never invalidated when the
  parser later asks the lexer to rescan a regexp from the cursor (`read_regexp`, parser.rs:1054). Safe wherever
  the lookahead happens *after* a token that cannot be `/` — except `for_statement` (stmt.rs:704), where it is
  unconditional. Confirmed: `for (/a/;;) {}` and `for (/a/g.test(s);;) {}` → `SyntaxError "missing ?"`.
- **Directive strictness is one token late for non-identifier tokens.** `semicolon()` (stmt.rs:468–471) lexes
  the token after `"use strict";` before `consume_directive` (95, 194–225) flips `STRICT`; `check_strict_keyword`
  repairs only identifiers. Confirmed: `"use strict"; 010` and `function f(){ "use strict"; 010 }` compile
  (`(Integer 8)`). Possibly XS-faithful (XS's `fxSemicolon` also pre-lexes), but a spec deviation either way.
- **Determinism.** No `HashMap`/`HashSet`, no host time/locale/env, no libm. `f64` handling is confined to
  `number_to_index` (saturating `as u32` re-checked by equality, 1922–1923) and `number_to_ecma_string`
  (Rust `{:e}`, pure Rust), plus test-only `dump_number`. `Value::Number` derives `PartialEq` (NaN ≠ NaN) but
  equality is never used observably. The **only** determinism hazard in this region is the stack-depth one:
  the same release binary accepts or aborts on the same source depending on the hosting thread's stack.
- **Metering doctrine.** Design § Metering lists "Parse unit — `fxMeterSome` calls from the parser" as an
  increment point. Here the meter is per *token* in the lexer (meter.rs:43–48), has no check point, and its value
  never crosses the `SourceCompiler` seam (`CompiledSource` has no meter field). Node construction, cover
  re-parses, and the post-parse `__proto__` walk are unmetered host work proportional to source size.
- **Performance shape.** Symbol strings are owned `String`s cloned per identifier and per call (`top_access_symbol`
  clones just to compare with `"eval"`, parser.rs:951); cover unwraps clone the inner subtree per nesting level
  (541, 1023); `array/object_binding_from_expression` clone the whole literal as a fallback before converting
  (1129, 1145); `export const …` clones the whole declaration (stmt.rs:1785). All O(n)–O(depth²), bounded by
  the shallow recursion ceiling in practice; not hot.
- **Error messages are API.** `e.message` is thrown verbatim into the realm (interp.rs:8008) and compared with
  XS's `String(exception)` by the harness. Ordering differences (post-parse `__proto__` check) or wording drift are
  result-divergence, not cosmetics.
- **Test shape.** Dump-and-compare fixtures are strong for *shape*. Robustness tests are 13 + 9 literal strings
  (tests.rs:349–359, 671–680); no depth test; a `#[should_panic]` test (777–784) enshrines the coder panic as the
  intended contract for a valid-looking early error. The 262 baseline (`refresh-20260829`) reports 0 failures over
  29,867 covered cases, so the two confirmed divergences below sit outside the covered corpus.

## Candidate findings (most architecturally significant first)

1. **Unbounded recursion: hostile/deeply nested source aborts the process, at a depth that depends on the host thread stack and build profile** — `parser.rs:626–642` (`assignment_expression` → `conditional_expression` → … → `group_expression` 1785 → `assignment_expression`), `stmt.rs:266` (`statement` → `block` → `statements` → `statement`).
   Claim: there is no nesting counter or stack check anywhere in the parser, so `(`×64 on a 2 MiB debug thread / `(`×3,714 on an 8 MiB release thread / `(`×14,870 on the endo 32 MiB runner overflows the native stack (SIGABRT, not a panic, not a `Result`).
   Evidence: `README.md:118` "the parser carries its own stack checks." — grep finds none; `ci.yml:828–832` "overflowing the 2 MiB default test-thread stack … the recursion depth is an engine property" — `RUST_MIN_STACK: '16777216'`; `xst.rs:1369–1374` "ironhorse-compile's recursive-descent parser … recurse on this thread's native stack … would overflow and SIGSEGV the whole batch (uncatchable by catch_unwind)".
   Why it matters: JS source is untrusted; `eval("(".repeat(4000)+"x"+")".repeat(4000))` kills the worker process (all co-hosted machines on a shared platform), and the outcome is host-configuration-dependent — a consensus engine must make accept/reject a function of the source alone (a fixed depth constant → `SyntaxError`, as XS's `fxCheckParserStack` does with a stack margin; a *counter* rather than an address check would also be deterministic). Confidence: high (measured).

2. **Front-end error model is split: parser returns `Result`, coder `panic!`s on early errors the parser deliberately leaves unresolved; production does not catch** — `parser.rs:1389–1397` (object cover `{c = 2}` built as `Binding`, never validated), `coder.rs:2403` (`panic!("coder: invalid initializer")`), `rust/endo/src/ironhorse_engine.rs:162, 496` (`compile_atoms_with(...).map_err(...)` — no `catch_unwind`).
   Claim: the valid-looking early error `({ a = 1 })` (and `class C { static { let y; } }`) panics `compile()` instead of returning `Err`, so a guest program that XS rejects with a catchable `SyntaxError` kills the Ironhorse worker.
   Evidence: `tests.rs:777–784` `#[should_panic(expected = "invalid initializer")] fn cover_initialized_name_as_expression_is_error`; probe: `({ a = 1 })` → `PANIC "coder: invalid initializer"`, `class C { static { var x; let y; } }` → `PANIC "static block with lexical declarations deferred"`; `ironhorse-262/src/lib.rs:40–42, 56` "Total over the coder's panics (catch_unwind)".
   Why it matters: `compile() -> Result<_, ParseError>` is not total, every caller must know to wrap it, and the production path doesn't; result parity (catchable vs process death) is violated on trivially crafted input. Confidence: high.

3. **`for` header does an unconditional one-token lookahead before dispatch, breaking a leading regexp literal** — `stmt.rs:704` `self.look_ahead_once()?;` then `if self.cur.token == Token::Semicolon … else if … else { self.comma_expression()?; }`.
   Claim: when the init expression starts with `/`, the token after `/` is lexed in operator mode into `ahead`; `literal_expression` then calls `lexer.read_regexp` (parser.rs:1054) from the cursor *past* that token and `get_next_token` replays the stale `ahead`, so `for (/a/;;) {}` and `for (/a/g.test(s);;) {}` are rejected.
   Evidence: probe output `for (/a/;;) {}` → `ERR ParseError { line: 1, kind: Syntax, message: "missing ?" }`; `for (x in y) /a/g.test(s);` → OK (lookahead absent); XS's `fxForStatement` only looks ahead inside its `let`/`using`/`await` arms.
   Why it matters: a deterministic reject of valid JS — a result-parity bug the byte-identity/dual-run corpus did not reach (0 failures in `baseline/refresh-20260829`). Fix is local: move the lookahead into the three arms that need it. Confidence: high.

4. **Parse metering is telemetry-only and never crosses the compiler/VM seam; runtime `eval`/`Function` compilation is unmetered and un-abortable** — `parser.rs:185–189` (`meter()`), `meter.rs:28–62` (no limit/abort), `lib.rs:52–56` (`parse_computrons`, test-only), `interp.rs:56–61` (`CompiledSource { bytecode, symbols }`).
   Claim: no computrons are charged for compiling source at runtime and there is no check point during a parse, so compile cost is outside the crank meter.
   Evidence: `grep parse_computrons` → only `tests/parse_meter_determinism.rs`; `pub struct CompiledSource { pub bytecode: Vec<u8>, pub symbols: Vec<u8> }`; design § Metering table row "Parse unit | fxMeterSome calls from the parser | cost-table entry".
   Why it matters: metering-doctrine drift (an increment point the design names is absent from the consensus meter), and a guest can burn unmetered host CPU proportional to eval'd source length. Confidence: high on the facts; medium on severity (source length is itself bounded by heap metering).

5. **Positionally typed AST: node shape is an implicit contract enforced only by panics** — `ast.rs:153–165` (`pub children: Vec<Item>`), consumers index `children[0]`, `children[1]`, `children.len() - 1` (238 sites; coder 210; e.g. `stmt.rs:1049, 1073, 1108, 1113, 1210, 1221, 1285`).
   Claim: there is no typed accessor layer between the parser's push order and the scoper/coder's slot reads, so any shape drift or unanticipated node kind surfaces as an index panic (`coder.rs:1008, 1150, 4958`) rather than a compile error.

   Why it matters: monolith symptom — the byte-identity fixtures are the only safety net for a 6k-line consumer; a typed `enum NodeKind { Binary{lhs,rhs}, … }` or per-token accessor fns would turn a class of runtime panics into type errors without changing the emitted tree. Confidence: high (structural), medium (impact).

## What is done well

- Faithful, legible transliteration: every method names its XS counterpart (`fxCommaExpression`, `fxCheckReference`, …) and the flag bits/masks are XS's exact values (ast.rs:28–112), which makes oracle-driven debugging tractable and is why byte identity was reached.
- The node-stack primitives are defensive where it counts: `push_node_struct`/`push_node_list` reject under-count with `Err` (parser.rs:378–380, 391–393) instead of panicking, and the audited `pop`/`swap_nodes`/index sites are all guarded by construction.
- Fail-fast `Result` discipline is consistent throughout ~4k lines; no `unwrap()` on untrusted data, `unwrap_or_default` for optional lexeme payloads, `unreachable!()` only behind an exhaustive match.
- Lexer/parser mode synchronization (`sync_lexer_flags`, parser.rs:245–249) and the two lexer re-entry points (regexp, template) are explicit rather than hidden in the lexer.
- Strings are carried as UTF-16 code units end to end (ast.rs:124–132), so lone surrogates in literals survive to CESU-8 emission — the right representation for the engine's settled string model.
- No determinism hazards inside the region: no hash containers, no host time/locale, pure-Rust float formatting; the dump format is deliberately address-free.
- `#![forbid(unsafe_code)]` holds; the fuzz parse target exists and the crate's error surface is structured (`ParseErrorKind`, `LexErrorKind`) rather than stringly-typed.
