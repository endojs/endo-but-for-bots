## Purpose and responsibilities

This region is the *consensus-artifact core* of ironhorse-vm minus the interpreter itself:

- `meter.rs` — the 16.16 fixed-point `Meter` (`index`/`interval`/`count`/`last_reported`), the XS-shaped
  primitive weights (`CODE_METERING = 1<<16`, `BUILTIN_METERING = 1<<14`, `SLOT_ALLOCATION_METERING = 1<<8`,
  `CHUNK_ALLOCATION_METERING = 1`, `STRING_METERING`/`BIGINT_METERING = 1<<16`), the `MeterState`
  suspend projection, and `COST_TABLE_VERSION = "ironhorse-meter-1"`.
- `cost.rs` — the `cost-calibration` feature firewall: a zero-sized `CostRecorder` when off, an
  opcode/builtin histogram plus `CostModel` work-function classification when on.
- `opcode.rs` — generated `#[repr(u8)] Opcode` enum (246 values), `CODE_SIZES: [i8; 246]`,
  `CODE_NAMES`, `from_u8`, `instruction_len` (the total, fail-closed bytecode length walker) and
  `remap_ids` (the symbol-id rewriter used by per-crank relinking).
- `symbols.rs` — `parse_symbols`: decoder for the `SYMB` atom (id→name table).
- `default_keys.rs` — `DEFAULT_KEYS`: XS's boot-interned `gxIDStrings`, used by the meter to decide whether
  a new property key is "novel" (charged) or pre-interned (uncharged).
- `lib.rs` — crate root: `#![forbid(unsafe_code)]`, module list, the public re-export surface,
  and four convenience entry points (`run_program`, `run_program_bounded`, `run_program_with_symbols`,
  `disassemble`) plus `regexp_source_compiles` for snapshot validation.
- `Cargo.toml` — deps (`ironhorse-regexp`, exact-pinned `icu_normalizer`/`icu_segmenter = "=2.2.0"`),
  dev-dep on `ironhorse-compile`, and the `cost-calibration` feature (default off).

## Architectural observations

- **The cost table has no reification.** "ironhorse-meter-1" names a *behavior*, not a datum. The weights are 6 consts in meter.rs, 207 in interp.rs, the position of every `tick_*` call in a 45k-line file, the `DEFAULT_KEYS` set (which decides a 280-raw charge at interp.rs:10642), and `PROGRAM_INVOCATION_COMPUTRONS`/`PROGRAM_ENV_SETUP_METERING` aggregates. The design's promise that "the previous table remains addressable by its version so old metered outcomes stay reproducible" (design § Metering) is unimplementable in this shape: there is no table to keep addressable — only a git revision.
- **Two meter versions under one namespace.** `COST_TABLE_VERSION = "ironhorse-meter-1"` (vm) and `PARSE_METER_RELEASE = "ironhorse-meter-0"` (ironhorse-compile/src/meter.rs:22). The parse meter and the run meter are versioned independently but share the `ironhorse-meter-N` namespace the design defines as a single release-wide id; the snapshot `METR` atom carries only the run-meter version. A consumer cannot tell from `"ironhorse-meter-1"` which parse weights were in force. (migration.rs:141–194 shows a bump from 0→1 did happen and is tested — good discipline, wrong granularity.)
- **Doctrine drift is embedded in the code's own documentation.** meter.rs:3–4, lib.rs:10–11, interp.rs:21–39 all describe an XS-parity meter ("exactly XS's weights", "bit-exact"). meter.rs:19–20 and the design describe an Ironhorse-own calibrated table. The code is the former wearing the latter's label. This matters for consensus because the *reason* to trust a weight ("calibrated on a named reference platform") differs from the actual reason ("equals XS 8.2.3 at commit 48ee02d8").
- **Overflow discipline.** `Meter` mixes explicit `wrapping_add`/`saturating_add` (check/rearm) with plain `+=`, `*`, `-=` everywhere else; the workspace has no `[profile] overflow-checks` setting, so a debit exceeding the index panics in debug and wraps in release. The credits (`ASYNC_FUNCTION_DEFINE_DELTA = 33536`, `ASYNC_AWAIT_FASTPATH_CREDIT = 16104`, `THROW_HOST_ESCAPE_METERING = 1<<15`) are each preceded by a larger charge in the paths I read, so this is unreachable in practice — but the invariant "index ≥ sum of outstanding credits" is nowhere stated, and `check()`'s wrap guard can legally zero `index` mid-run. `begin(interval)` shifts `interval << 16` with no range check: a host interval ≥ 2^48 silently loses its high bits (no validation at `arm_meter`, interp.rs:10667).
- **Generated files are hand-patched.** opcode.rs says "GENERATED … Do not edit" yet carries a hand-corrected PROFILE size with a 15-line comment; no generator script is checked in (I found none under rust/engine). A regeneration at the new pin would silently revert the patch unless the generator is taught it.
- **Pin provenance ambiguity.** opcode.rs:2 and ~10 interp constants cite `48ee02d8cfe0` (8.2.3); README.md:29–31 says the pin was bumped to `23b4d6b0a65f` (8.3.1). Either the tables/constants were re-validated at 8.3.1 without updating their headers, or the current oracle is not the engine the constants were measured against. Unverifiable here; flag for the oracle/262 reader.
- **Encoding seam at SYMB.** XS emits CESU-8; ironhorse-compile emits Rust UTF-8 (`e.string.as_bytes()`); `parse_symbols` uses `from_utf8_lossy` (correct for the compiler's atom, lossy for XS's). Bytecode STRING payloads are decoded by a real CESU-8 decoder (`cesu8_to_units`, interp.rs:41424) on both. Consequence: astral identifiers/keys behave consistently only in the ironhorse-compile pipeline; the README's "SYMB atom … byte for byte" claim (crate table row for ironhorse-compile) cannot hold for astral names; and `symbols.rs`'s tests are ASCII-only.
- **Lenient decoding + silent default.** `parse_symbols` ignores the count and drops an unterminated tail; `id_name` returns `""` for unknown ids; `""` is a pre-interned default key. So a SYMB/bytecode mismatch turns into "every unknown id is the uncharged empty-string property" rather than a `Halt`. I found range guards only on restore paths (interp.rs:10422, 4430 in image.rs), not on the dispatch/`id_name` path.
- **Firewall is textual, not binary.** The C1 acceptance bar ("object-code / disassembly firewall proof") is replaced by `size_of == 0` plus a source grep of meter.rs. Cargo feature unification is the realistic leak: any crate in a `cargo build` that enables `cost-calibration` flips ironhorse-vm for every consumer in that build; nothing (`compile_error!`, a CI artifact check) guards the consensus build. There is also no calibration CI job despite Cargo.toml saying there is, so the `on_tests` module is unexercised.
- **`HashMap` in the on-side recorder** (cost.rs:92) is iterated only in `report()`, which sorts — fine. `default_keys: HashSet<&'static str>` is membership-only — fine. No HashMap iteration order leaks in this region.
- **Hot-path allocation.** `tick_property_create` (interp.rs:10639–10645) calls `id_name(id)` which `clone()`s a `String` per new own property purely to do a `HashSet<&str>::contains`. Correctness-neutral, but it is on every property creation and the metering doctrine forbids fast paths that change the count — so it can only be fixed by a borrow, which is easy.
- **API-boundary porosity.** `pub mod interp` makes every `pub` item in the 45k-line file crate-public API (including the 207 calibration constants); lib.rs re-exports ~50 side-table Row/Snapshot types whose only consumer is ironhorse-snapshot. The snapshot crate is effectively a friend module of `Interp`; the crate boundary is not the abstraction boundary. `run_program` is a public, unmetered, non-total entry point (documented as such).
- **`Meter::reset` is dead API** (no callers in any engine crate); its doc refers to an oracle-shim use that lives outside the Rust workspace.
- **METR decode** (image.rs:88–111) is fail-closed on length/UTF-8 and exact-consumption, but accepts any `(index, interval, count)` triple — e.g. `count < index` with `interval != 0` makes the first check fire immediately. Harmless (host-visible only), but the meter has no `MeterState::validate`.

## Candidate findings

1. **[metering, high] The "frozen cost table" named by `COST_TABLE_VERSION` has no reified form, so a weight change without a version bump is undetectable by construction.**
   `ironhorse-vm/src/meter.rs:26` — Claim: no artifact (manifest, digest, or test) binds `"ironhorse-meter-1"` to the set of metering constants and tick sites; only scattered exact-computron assertions catch a drift.
   Evidence: meter.rs:25 `/// Bump the trailing number whenever any metering weight or check point changes.`; grep `pub const *_METERING|_COMPUTRONS|_RESIDUAL` → 6 in meter.rs, 207 in interp.rs; PR-CI is `cargo test -p ironhorse-vm -p ironhorse-snapshot` with ~17 exact computron asserts in tests + 33 in-file.
   Why: the design (§ Metering) makes "same release ⇒ same frozen table" the *entire* consensus argument and promises old tables stay addressable by version. Without a datum, "the table" is a git SHA and a hope.

2. **[docs-drift/metering, medium] The meter's own documentation contradicts the doctrine it labels: every weight is XS's constant, "calibrated raw-exact against the pin", while the version string and design claim an Ironhorse-own instrumentation-derived table.**
   `ironhorse-vm/src/meter.rs:3` — Claim: no weight in the current cost table was derived from the cost-calibration instrumentation (design "Not Started"; cost.rs is histogram-only).
   Evidence: meter.rs:3–4 `incremented at exactly XS's points with exactly XS's weights`; meter.rs:19–20 `Ironhorse's meter is its **own** frozen cost table, not a back-fit of the oracle's`; interp.rs:21 `Computrons are bit-exact`.
   Why: consensus consumers must know what a version *means*; "ironhorse-meter-1" currently means "XS 8.2.3 parity as measured at 48ee02d8", and the code's inline docs say so while the exported symbol's doc says the opposite.

3. **[metering/api-boundary, medium] Two independent meter versions share the `ironhorse-meter-N` namespace, and the snapshot records only one.**
   `ironhorse-vm/src/meter.rs:26` — Claim: `COST_TABLE_VERSION="ironhorse-meter-1"` (run meter) and `PARSE_METER_RELEASE="ironhorse-meter-0"` (parse meter, ironhorse-compile/src/meter.rs:22) can diverge with no single release id covering both.
   Evidence: meter.rs:26 `pub const COST_TABLE_VERSION: &str = "ironhorse-meter-1";`; ironhorse-compile/src/meter.rs:22 `pub const PARSE_METER_RELEASE: &str = "ironhorse-meter-0";`; image.rs:54 stores only `COST_TABLE_VERSION`.
   Why: the design defines one `ironhorse-meter-N` per release; a machine whose `eval`/`Compartment.evaluate` parse charges changed would resume under a matching `METR` and meter differently.

4. **[robustness/determinism, medium] `parse_symbols` is not the CESU-8 decoder its contract states, and the compiler emits UTF-8, so astral names in the SYMB atom are mangled from an XS atom and cannot be byte-identical to XS from ironhorse-compile.**
   `ironhorse-vm/src/symbols.rs:37` — Claim: an XS-produced SYMB entry containing a surrogate-pair-encoded astral character decodes to U+FFFD replacement characters while the same name in a STRING payload decodes correctly via `cesu8_to_units`.
   Evidence: symbols.rs:35–37 `// Strings are CESU-8; \`from_utf8_lossy\` matches how the oracle shim renders names` / `String::from_utf8_lossy(&atom[start..i])`; ironhorse-compile/src/coder.rs:301 `body.extend_from_slice(e.string.as_bytes());`; interp.rs:41424 `fn cesu8_to_units`.
   Why: property-key identity is result-observable; the differential harness's `SYMB` byte-identity claim (README crate table) is false for any astral identifier; tests are ASCII-only.

5. **[robustness, medium] Out-of-range symbol ids silently alias onto the empty-string default key instead of failing closed.**
   `ironhorse-vm/src/symbols.rs:24` — Claim: a bytecode id beyond the parsed name table (lenient count-less parse + dropped unterminated tail) reaches `id_name` → `""`, which is a `DEFAULT_KEYS` member, so the property is created uncharged under `""` rather than halting.
   Evidence: symbols.rs:25–26 `we read strings to the buffer end rather than trusting the count`; interp.rs:23167–23171 `self.symbol_names.get((id as usize).saturating_sub(1)).cloned().unwrap_or_default()`; default_keys.rs:478 `"",`.
   Why: untrusted bytecode/SYMB pairs (snapshots, buggy compiler) should be refused, not reinterpreted; the range guards I found (interp.rs:10422, image.rs:4430) are on restore paths only. Confidence medium — another region may guard at the decoder.

6. **[modularity/verification, medium] The opcode numbering is duplicated across crates with no equality test.**
   `ironhorse-vm/src/opcode.rs:7` — Claim: `ironhorse-compile/src/opcodes.rs` (253 lines, "generated from ironhorse-vm/src/opcode.rs") can drift from `Opcode` and no test compares them, although ironhorse-vm dev-depends on ironhorse-compile.
   Evidence: opcodes.rs:1 `//! XS opcode byte values, generated from \`ironhorse-vm/src/opcode.rs\``; opcode.rs:1–2 `GENERATED … Do not edit by hand.`; opcode.rs:496–510 hand-patched PROFILE size.
   Why: an encoder/decoder disagreement on one byte is a silent miscompile of every program; "generated" files that are hand-patched with no checked-in generator are the classic path to that.

7. **[docs-drift, medium] Pin provenance is inconsistent: generated tables and calibration constants cite `48ee02d8cfe0` (8.2.3) while README says the oracle pin is `23b4d6b0a65f` (8.3.1).**

## What is done well

- `instruction_len`/`remap_ids` are a genuinely total, fail-closed decoder seam: every read is `get()`/`checked_add`, truncation is refused at the whole-instruction level (W6-22), and the ID-sentinel set is locked in both directions by test (opcode.rs:1150–1212, 1223–1246). The dispatch loop uses the same walker before any raw operand indexing (interp.rs:11379).
- The cost-calibration firewall is well-conceived: ZST when off, one-directional data flow, a source-level grep test that runs in both configurations, deterministic `report()` ordering despite a `HashMap`.
- `Meter::check` faithfully reproduces `fxCheckMetering` including the overflow-wrap guard, with explicit `wrapping_add` and a unit test that forces the wrap; the resume forms (`rearm` vs `reattach_meter_host`) are carefully distinguished and documented against prior review findings.
- `COST_TABLE_VERSION` *is* enforced fail-closed at every snapshot admission path (image.rs:4444, store.rs:2010/3051/3152) and a real 0→1 bump exists with a migration fixture test — the version discipline works at the granularity it has.
- Exact-pinned `icu_normalizer`/`icu_segmenter = "=2.2.0"` fixes the Unicode data version that `normalize()`/`Intl.Segmenter` results depend on — a determinism detail easy to miss.
- `#![forbid(unsafe_code)]` at the crate root, and `run_program_bounded` with its documented rationale, show the safety/fuzzability requirements being taken seriously at the API surface.
