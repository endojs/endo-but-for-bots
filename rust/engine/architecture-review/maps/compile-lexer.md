## Purpose and responsibilities

`ironhorse-compile` is the stage-5 pure-Rust port of XS's compiler pipeline (lexer -> parser -> scoper
-> coder), held to a byte-identical-bytecode bar against the XS oracle (lib.rs:1-14). This region is the
first stratum:

- `lexer.rs` — a statement-for-statement transliteration of `fxGetNextTokenAux` and friends
  (`xsLexical.c`), pull-driven by the parser with two re-entry points (`next_template_part`,
  `read_regexp`) mirroring `fxGetNextTokenTemplate`/`fxGetNextRegExp`.
- `token.rs` — the `Token` enum with XS's exact `txToken` discriminants (0..=171), plus the sorted
  keyword tables and `classify_word` (= `fxGetNextKeyword`).
- `token_flags.rs` — `gxTokenFlags`, the 172-entry grammar-class bitset indexed by `Token` ordinal.
- `error.rs` — `LexError { line, kind }`; every XS `fxReportParserError` site in the lexer is meant to
  surface as data, never a panic (error.rs:1-5).
- `meter.rs` — the parse meter: a 16.16 fixed-point monotone counter bumped once per token,
  stamped `PARSE_METER_RELEASE = "ironhorse-meter-0"`.
- `lib.rs` — crate root: `#![forbid(unsafe_code)]`, module re-exports, `parse_computrons()` and
  `tokenize()` conveniences, and `pub use ironhorse_regexp::unicode` for ID_Start/ID_Continue.

## Invariants and contracts claimed (from doc comments) — and whether the code upholds each

1. **`#![forbid(unsafe_code)]`** (lib.rs:13-16; design § unsafe budget). **Upheld.**
2. **"no byte sequence can panic the lexer … a lex error is a `Result::Err`, never an `unwrap`"**
   (error.rs:3-5; tests.rs:2-3; fuzz lib.rs:1869-1873). **Violated** at one site: `self.line: u32` is
   incremented unchecked (lexer.rs:308, 633, 934, …) after `//@line N` sets it to `N-1` (lexer.rs:684),
   so `//@line 4294967295\n\n\nx` panics `attempt to add with overflow` at lexer.rs:308 under
   overflow-checks (verified) and wraps to `line = 0` in an unchecked release build. Every
   `char::from_u32(..).unwrap()` (738, 793, 873, 956, 974, 987, 993, 1195, 1210, 1250, 1264) is
   guarded by a preceding predicate that excludes `EOF`; I checked `is_identifier_first/next(0xFFFF_FFFF)`
   returns `false` (unicode.rs:208-251: cumulative sums never reach `u32::MAX`), so those are sound.
3. **Parse meter: "one counter bump per scanned token", monotone, deterministic** (meter.rs:13-18,
   28-30; lib.rs:8-10). **Partially.** Monotone and deterministic: upheld (pure integer counter, no
   HashMap, no host input). Per-token: **violated** for regexp literals — `next()` charges once for the
   `Divide`/`DivideAssign` it returns (lexer.rs:290), then the parser re-enters `read_regexp`
   (parser.rs:1052-1054) which charges again (lexer.rs:1232). Verified: `/a/g` = 3 computrons for
   2 tokens (Regexp, Eof). Templates are charged correctly (one per part).
4. **Design § Metering table: "Parse unit … `fxMeterSome` from the parser … cost-table entry"**
   (designs/ironhorse-engine.md:398). **Violated in practice**: the meter exists but nothing consumes it.
   `Parser::meter()` (parser.rs:187) and `parse_computrons` (lib.rs:52) are read only by tests
   (`tests/parse_meter_determinism.rs`, `parser/tests.rs:369`, `lexer/tests.rs:351`). The VM's
   compiler seam `SourceCompiler::compile_source -> CompiledSource { bytecode, symbols }`
   (interp.rs:55-61, 96-100) carries no cost, the production adapter discards it
   (ironhorse-262/src/lib.rs:57-61), and `ironhorse-vm/src/meter.rs:11-12` says parse metering "is not
   modeled here".
5. **Determinism per release of parse computrons** (tests/parse_meter_determinism.rs:4-12). **Upheld.**
6. **`Token` discriminants equal XS's `txToken` at the pin** (token.rs:1-15). **Unclear** — the
   `c/moddable` submodule is absent so I could not diff against `xsScript.h`; internally consistent
   (`TOKEN_FLAGS` has exactly 172 entries = `Yield(171)+1`, token_flags.rs:47; spot-check test
   tests.rs:356-362).
7. **`Lexeme.line` is the "1-based source line, as XS's `state.line` counts it"** (lexer.rs:46-47).
   **Partially**: wraps to 0 after the `@line` overflow (release), and the
   `LineTerminatorInString` error is reported one line late because `self.line += 1` precedes the
   `return Err` (lexer.rs:933-939; verified `'a\nb'` -> "line 2").
8. **Source decoded as UTF-8 scalar values; astral chars are single `char`s** (lexer.rs:11-16).
   **Upheld inside the crate**, but the contract forces a lossy boundary: `Lexer::new(&str)` cannot
   carry a lone surrogate, so the VM's eval bridge hands the compiler
   `String::from_utf16_lossy` output (interp.rs:17522 -> `str_text` -> interp.rs:10892). The design's
   fuzz target 4 ("unpaired-surrogate handling … at the source boundary", design:710-715) is not met
   by this shape.
9. **`LexErrorKind` "kinds mirror XS's report sites"** (error.rs:15, 19-20). **Partially**:
   `InvalidCharacter` and `Overflow` are never constructed (grep of lexer.rs); a stray control or
   non-identifier Unicode char falls into `scan_identifier`'s `else { ok = false }` (lexer.rs:1258-1259)
   and is reported as `InvalidEscape` (lexer.rs:1298-1299). Verified `"\u{1}"` -> "invalid escape".
10. **262 adapter: "Carry the bare diagnostic (`e.message`, no `line N:` prefix) so the SyntaxError
    renders with XS's exact wording"** (ironhorse-262/src/lib.rs:68-73). **Violated for lexer
    errors**: `From<LexError> for ParseError` sets `message: e.to_string()` (parser.rs:76), and
    `LexError::Display` writes `"line {}: "` (error.rs:61), so `e.message` is `"line 1: invalid number"`
    and `ParseError::Display` doubles it: `"line 1: line 1: invalid number"` (verified).
11. **"converts with correctly-rounded `f64` parsing"** (lexer.rs:840-842). **Upheld for decimal**
    (`str::parse::<f64>`, lexer.rs:904); the radix path accumulates `n = n*radix + d` in f64 per digit
    (lexer.rs:830-834), which double-rounds: `0x1000000000000081` -> 2^60 where the spec MV rounds to
    2^60+256 (verified in Rust and Python). Plausibly XS-faithful (XS accumulates per digit too), but
    then it is a shared spec divergence, not a fidelity win.
12. **Layering: design diagram `CC --> VM`** (design:284). The real seam is inverted and better: the VM
    owns a `SourceCompiler` trait (interp.rs:89-101), `ironhorse-compile` is only a dev-dependency of
    the VM (ironhorse-vm/Cargo.toml:22-29), and `ironhorse-262` supplies the production adapter. The
    diagram is stale (docs-drift), the code is right.

## Architectural observations

- **Clean, small, well-partitioned front stratum.** Seven files, one `impl Lexer`, no side tables, no
  GC interaction, no snapshot surface (a `Lexer` never outlives a compile). None of the headline
  GC-root / snapshot-ledger bug classes apply here.
- **Determinism**: no `HashMap`/`HashSet`, no host time/locale/env, integer arithmetic throughout
  except two f64 sites: `str::parse::<f64>` (core dec2flt, correctly rounded and platform-independent)
  and the per-digit radix accumulation (IEEE-deterministic, but not correctly rounded — see claim 11).
  `n as i32` (lexer.rs:914) saturates in Rust where C is UB; for non-negative literals both yield
  NUMBER for anything >= 2^31 so the INTEGER/NUMBER split matches.
- **Metering-doctrine drift (the region's most significant finding)**: the parse meter is instrumented
  and tested for determinism but is a dead instrument — no path adds parse cost to the VM's crank
  meter. `eval`/`Function` of an arbitrarily large source therefore costs zero computrons for
  lexing, parsing, scoping, coding *and* the eager regexp compile at lexer.rs:1223. The doctrine
  ("best available deterministic proxy for real execution cost") and the design's own table
  (design:398) both say parse cost is metered.
- **Hidden state / coupling**: `Lexer` keeps private copies of `strict/async/generator` that the parser
  must resync before every scan (`sync_lexer_flags`, parser.rs:245-249). Tokens buffered in the
  parser's `ahead`/`ahead2` window keep the classification current when they were lexed; a later flag
  flip (e.g. a `"use strict"` directive) does not reclassify them. This mirrors XS's `states[]` so it
  is probably faithful, but it is an invariant carried by convention, not by type.
  `prev_token` (lexer.rs:134) is lexer-owned state feeding the `.default`/`?.default` rule.
- **Error-model shape**: `LexError` is data (good), but `Display` bakes the `"line N: "` prefix into
  the message, and `ParseError` stores the rendered `LexError` as its `message`, so the two error
  types disagree on where location lives. That leaks into the eval bridge's `SyntaxError.message`
  (claim 10). Two `LexErrorKind` variants are dead; `UnexpectedCharacter(u32)` can carry the
  `0xFFFF_FFFF` EOF sentinel (`..` at EOF -> "invalid character 4294967295").
- **Robustness on untrusted input**: total except the `u32` line counter (claim 2). Escapes are
  bounds-checked with `chars.get`. `read_identifier_escape`'s `\u{…}` loop uses `wrapping_mul` with
  no `< 0x110000` bound (lexer.rs:1317-1318) while the string path bounds it (lexer.rs:1413): the
  identifier path silently accepts `\u{100000041}bc` as `Abc` (verified). Also: `0.x` lexes as
  `Number(0)` then `Identifier` (no identifier-abuts-number check on the `0.` path, lexer.rs:703-706)
  while `1.x` is a lex error; both reject downstream, so accept/reject agrees, but the error kind
  differs.
- **Eager regexp compile inside the lexer** (lexer.rs:1223): faithful to XS, but it means a
  source-controlled recursion depth (the census notes the regexp suites need `RUST_MIN_STACK=16 MiB`
  in debug CI) is reachable from `eval` through the lexer, unmetered. A Rust stack overflow is a
  process abort, not a catchable panic, so it would not be "a crashed crank" — it would be a dead
  worker. I did not read the regexp compiler; this is a seam observation for the regexp reader.
- **Performance architecture**: `Lexer::new` materializes `Vec<char>` + `Vec<usize>` (12 bytes per
  source char, 3-12x the source) up front; `cook_string` re-collects each escaped body into a
  `Vec<char>`; `Lexeme` is ~170 bytes with five owning heap fields and the parser clones
  `string`/`modifier`/`bigint` out of it (parser.rs:1048, 1056-1057, 1064). Fine for stage-5
  correctness; a cost for large `eval` sources and for the parse meter if it is ever wired in (the
  materialization is unmetered).
- **API surface**: `Lexeme` exposes all fields `pub` (reasonable for a data record) including the
  never-read `start`/`end`. `Lexer` fields are private with setters — good. `KEYWORDS` /
  `STRICT_KEYWORDS` are `pub static` and rely on sorted order for `binary_search_by` (token.rs:265,
  269) with no test or `const` assertion guarding the order; a future insertion (e.g. `using`) in the
  wrong place would silently misclassify.
- **Docs drift**: lexer.rs:11-18 still describes the crate's "child 1" bar; design:284 draws
  `CC --> VM`; design:398 lists parse metering as a cost-table entry; README:22 calls the compiler the
  "dual-run default" — all true-ish but none mention that parse cost is not charged at runtime.

## Candidate findings (most architecturally significant first)

1. **Parse meter is a dead instrument; eval/Function compile cost is never charged** — metering, high.
   `rust/engine/ironhorse-compile/src/lib.rs:52` (`parse_computrons`), consumers: none outside tests.
   Claim: no runtime path adds `ParseMeter` computrons to the VM meter, so compiling an eval'd
   source of any size costs 0 computrons.
   Evidence: interp.rs:55-61 `pub struct CompiledSource { pub bytecode: Vec<u8>, pub symbols: Vec<u8> }`
   (no cost field); ironhorse-262/src/lib.rs:57-61 `compile_atoms_with(&source, strict)` -> `Ok(CompiledSource { bytecode, symbols })`;
   ironhorse-vm/src/meter.rs:11-12 "parse metering is out of the interpreter-parity window, so it is not modeled here".
   Why it matters: the doctrine's proxy-for-real-cost property has a hole proportional to source size,
   and design:398 says the parse unit *is* a cost-table entry. Confidence: high (grep-complete).

2. **Compiler input is `&str`, so the eval boundary lossy-converts UTF-16 source and lone surrogates
   become U+FFFD** — api-boundary, medium. `lexer.rs:142`.
   Claim: `eval` of a source string containing a raw lone surrogate inside a string literal yields a
   string containing U+FFFD instead of that code unit.
   Evidence: lexer.rs:142 `pub fn new(source: &str) -> Lexer`; interp.rs:17521-17522 `let text = match source.value { Payload::String(off) => self.str_text(off)`;
   interp.rs:10892 `String::from_utf16_lossy(&self.str_units(off))`.
   Why: a result divergence vs XS (CESU-8 preserves lone surrogates) and the spec; design fuzz
   target 4 explicitly names unpaired-surrogate handling at the source boundary. Confidence: high on
   the mechanism; the observable divergence is inferred from spec, not oracle-run here.

3. **`u32` line counter overflows after a `//@line` pragma: panic under overflow-checks, `line = 0`
   in release** — robustness, medium. `lexer.rs:308` (also 633, 934, 944, 955, 973, 978).
   Claim: `//@line 4294967295\n\n\nx` panics the lexer in overflow-checked builds (verified) and
   wraps to a 0-based line in unchecked builds, contradicting error.rs:3-5 and lexer.rs:46-47.
   Evidence: lexer.rs:684 `self.line = n.saturating_sub(1);` lexer.rs:308 `self.line += 1;`.
   Why: the lexer's totality is the invariant the fuzz target and the coder's `catch_unwind` firewall
   lean on; cargo-fuzz builds enable overflow checks, so this is a real crash finding; and a
   crashed crank on a comment line is a cheap DoS. Confidence: high (reproduced).

4. **Lex-originating `ParseError.message` carries a `"line N: "` prefix (and `Display` doubles it),
   leaking location into eval's `SyntaxError.message`** — error-model, medium.
   `rust/engine/ironhorse-compile/src/parser.rs:76`.
   Claim: `eval("0x")` throws a SyntaxError whose message is `"line 1: invalid number"` while
   grammar errors are bare (`"missing identifier"`), contrary to the adapter's stated intent.
   Evidence: error.rs:61 `write!(f, "line {}: ", self.line)?;` parser.rs:76 `message: e.to_string()`;
   ironhorse-262/src/lib.rs:68-73 "Carry the bare diagnostic (`e.message`, no `line N:` prefix) … XS's exact wording".
   Why: observable (`e.message`) and compared "as the whole string" by the differential harness;
   also an internal inconsistency between the two error types. Confidence: high (reproduced:
   display = "line 1: line 1: invalid number").

5. **Regexp literals are double-charged by the parse meter, contradicting the "one bump per token"
   contract** — metering, low. `lexer.rs:1232`.
   Claim: a regexp literal costs 2 x `PARSE_TOKEN_METERING`.
   Evidence: lexer.rs:290 `self.meter.charge_token();` (for the `Divide` returned first);
   parser.rs:1054 `let rx = self.lexer.read_regexp(divide_assign)?;` lexer.rs:1232 `self.meter.charge_token();`.
   Why: deterministic so not a consensus bug, but the frozen table's stated shape is wrong and a
   future calibration inherits an accidental unit. Confidence: high (verified 3 computrons for `/a/g`).

6. **Identifier `\u{…}` escape uses wrapping arithmetic without the `0x10FFFF` bound the string path
   enforces** — robustness, low-medium. `lexer.rs:1318`.
   Claim: `\u{100000041}bc` lexes as identifier `Abc` (spec: SyntaxError).
   Evidence: lexer.rs:1318 `value = value.wrapping_mul(16).wrapping_add(d);` vs lexer.rs:1413 `while value < 0x0011_0000 {`.
   Why: accept/reject divergence vs spec; vs XS depends on whether `fxGetNextIdentiferX` bounds
   (C `txU4` also wraps) — unverified. Confidence: high on behavior (reproduced), unclear on parity.

7. **Hex/octal/binary literal values are double-rounded (per-digit f64 accumulation)** — other
   (spec correctness), low. `lexer.rs:833`.
   Claim: `0x1000000000000081` lexes to 2^60 where the correctly rounded MV is 2^60+256.
   Evidence: lexer.rs:832-833 `let d = c.to_digit(radix as u32).unwrap_or(0) as f64; n = n * radix as f64 + d;`
   lexer.rs:840-842 doc: "converts with correctly-rounded `f64` parsing" (decimal only).
   Why: a spec divergence baked into bytecode constants; plausibly XS-faithful (byte-identity bar
   would then forbid the fix without an exceptions-ledger entry). Confidence: high on arithmetic
   (reproduced in Rust and Python), unverified vs the pin.

8. **`LexErrorKind::InvalidCharacter` and `Overflow` are dead; stray characters are misreported as
   `InvalidEscape`** — error-model, low. `lexer.rs:1299`.
   Claim: no code path constructs `InvalidCharacter`; `"\u{1}"` and `"\u{FFFD}"` report "invalid escape".
   Evidence: lexer.rs:1258-1259 `} else { ok = false }` … lexer.rs:1298-1299 `if !ok { return Err(self.err(LexErrorKind::InvalidEscape)); }`;
   error.rs:23-25 documents `InvalidCharacter` as the `fxGetNextCode` "invalid character" site.
   Why: wording divergence from XS in eval-thrown messages; dead public variants mislead consumers.
   Confidence: high (reproduced).

9. **Eager regexp compilation inside the lexer exposes source-controlled recursion and unmetered work
   through `eval`** — robustness, low-medium (medium confidence). `lexer.rs:1223`.
   Claim: every regexp literal in an eval'd source runs the full regexp compiler at lex time with no
   meter charge and with recursion depth chosen by the guest.
   Evidence: lexer.rs:1223 `match ironhorse_regexp::compile::compile(&body, &flags) {` … `Ok(_) | Err(…Unsupported(_)) => {}`;
   census: regexp suites need `RUST_MIN_STACK=16777216` in CI ("recursion depth is an engine property").
   Why: a stack overflow is a process abort, not a crashed crank. I did not read the regexp compiler;
   the regexp reader should confirm whether its depth is bounded.

10. **`LineTerminatorInString` is reported one line late** — error-model, low. `lexer.rs:934`.
    Claim: `'a\nb'` reports `line 2`.
    Evidence: lexer.rs:933-939 `10 => { self.line += 1; if c == b'\`' as u32 { … } else { return Err(self.err(LexErrorKind::LineTerminatorInString)); }`.
    Why: `LexError.line` is documented as XS's `state.line`; probably diverges from XS's report line.
    Confidence: high on behavior, unverified vs XS.

11. **`Lexeme.start`/`end` byte offsets are computed for every token and never read** — other, low.
    `lexer.rs:48-51`.
    Evidence: set at lexer.rs:301, 621, 1127, 1135, 1151, 1231; no reader in `parser.rs`, `parser/stmt.rs`,
    `scoper.rs`, `coder.rs` (grep `\.(start|end)\b` in src matches only lexer.rs).
    Why: dead API plus the `offsets: Vec<usize>` (8 bytes/char) exists only to serve them.

12. **Keyword tables' sortedness is a silent precondition of `binary_search_by`** — robustness, low.
    `token.rs:265`.
    Evidence: token.rs:203 "(kept sorted; XS binary-searches it)"; token.rs:265 `KEYWORDS.binary_search_by(|(k, _)| (*k).cmp(word))`.
    Why: no test/const-assert; an unsorted insertion misclassifies keywords deterministically but
    wrongly. Confidence: high (tables are currently sorted — I checked by eye).

## What is done well

- The lexer is genuinely total on untrusted input apart from the one `u32` overflow: every
  `char::from_u32(..).unwrap()` sits behind a predicate that excludes the EOF sentinel, every escape
  decoder uses `chars.get`, `advance()` cannot run past EOF, and errors are data (`LexError`).
- Cooked strings are carried as UTF-16 code units (`Vec<u16>`) so `\uD800`-style lone surrogates from
  escapes survive to the coder exactly as XS stores them (`push_unit`, lexer.rs:1374-1382); the
  raw/cooked split and template CR/CRLF normalization are handled carefully.
- The parse meter is exactly what the doctrine asks for internally: a pure integer counter with a
  named release (`ironhorse-meter-0`), `saturating_add`, no host input, and a dedicated determinism
  test that repeats each program 64 times.
- The VM/compiler seam is well layered: the VM defines `SourceCompiler`, takes `ironhorse-compile` only
  as a dev-dependency, and the harness supplies the adapter — the dependency inversion the design
  diagram does not yet show.
- `Token` discriminants and `TOKEN_FLAGS` are kept in lockstep by construction (172 entries indexed by
  a `#[repr(u16)]` enum), so the table lookups are in-bounds without runtime checks.
- Tests are focused and readable; `no_panic_on_arbitrary_bytes` and the classification fixtures pin
  the shape the parser depends on rather than snapshotting streams.
