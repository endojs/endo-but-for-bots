## Purpose and responsibilities

Three loosely related leaf modules of `ironhorse-vm`:

1. **`compartment.rs`** — the "host-side Rust realm API": `Machine` (an `Rc<Intrinsics>` + `Rc<Cell<usize>>` counter), `Compartment` (id, name, two global maps, a `ModuleGraph`, two hook flags), `CompartmentOptions`, `CompartmentId`, `CompartmentSkip`. Its evaluators (`evaluate`, `evaluate_with_symbols`) build a **fresh `Interp`** per call, seed id-keyed globals in sorted id order, and run bytecode. It is the surface `rust/endo`'s `ironhorse_engine::engine::Machine::evaluate` and `ironhorse-262`'s `compartment_dual_run` call.
2. **`module.rs`** — a standalone, arena-free model of ECMA-262 CyclicModuleRecord linking/evaluation (`ModuleGraph`, `ModuleRecord`, `ImportEntry`/`ExportEntry`, `BodyOp`, `Namespace`, `ModuleSource`). Bodies are `BodyOp::{InitLocal, ReadLocal}` — not bytecode. `Interp` never sees a `ModuleGraph`; `XS_CODE_MODULE` has no dispatch arm in `interp.rs` (falls to `other => Halt::Unsupported(other.name())` at interp.rs:15850-15852) and `XS_CODE_IMPORT`/`IMPORT_META` self-name skips (interp.rs:15843-15848).
3. **`intl_number.rs`** — the `Intl.NumberFormat` value engine: `NfResolved` option record → `partition_number`/`format_to_string`. Exact decimal expansion of the double via `format!("{x:.1100}")`, nine rounding modes, fraction/significant/increment rounding, hand-rolled locale data (decimal/group separators, en-IN grouping, 8 numbering systems). Called from interp.rs:25540, 25581, 25591 after `nf_resolved` (interp.rs:19830-19903) converts string-typed `NumberFormatData` to enums.

## Architectural observations

- **Two disjoint "Machine" concepts.** `ironhorse_vm::Machine` (compartment.rs:342) is a two-`Rc` holder with no `eval`/metering/snapshot verbs; the design's `Machine` API (design §Metering 460-467, §Endor integration 723-736) is realized as an extension trait on `Interp` in `ironhorse-snapshot/src/machine.rs` (19-28) plus the endo wrapper (`ironhorse_engine.rs:137`). The compartment `Machine` is on the *non-persistent* path only.
- **Compartment ≠ realm.** Because each evaluation constructs a fresh `Interp`, a `Compartment` cannot: hold guest state across cranks, share intrinsics with a sibling (mutating `Object.prototype` in A is invisible in B only because B is a different heap), be snapshotted, or be metered across calls. It is a `(globals_by_id, bytecode) → RunOutcome` pure function with a counter-minted id. The `Rc<Intrinsics>` and `Rc<Cell<usize>>` exist to make `Rc::ptr_eq`-style tests pass, not to share anything.
- **Verification that cannot fail.** `compartments_share_one_intrinsics_graph` (compartment.rs:434-442), lib.rs:203-210, and `CompartmentDualRun.shared_intrinsics` (262/lib.rs:821) assert identity of a marker with no content. The dual-run does certify evaluator faithfulness (same bytecode → same result as oracle), which is real.
- **Write-only state.** `Compartment.globals` (name-keyed), `CompartmentOptions.endowments`, `name`, `has_*_hook` are recorded and read back by Rust-side getters only; none influence evaluation. `Intrinsics.locked_down` is never set.
- **Module machinery is a model, not the engine's.** Everything in module.rs is exercised only by its own tests and compartment.rs tests. The engine's module bytecode path does not exist (no `XS_CODE_MODULE` arm). The design's acceptance bar ("endor daemon's actual boot sequence … runs identically", design 574-579) is therefore unreachable today; the store-seam ledger (designs/ironhorse-snapshot-store-seam.md:1373-1380) already names `Modules` as a Pending prerequisite for deliver.
- **Error-path state in module.rs.** `inner_link`/`inner_eval` mutate status before recursing and never roll back on `Err`; `instantiate` and `evaluate` then early-return `Ok` for the same root. Spec requires Link to reset to `unlinked` and Evaluate to record `[[EvaluationError]]`.
- **`Slot` crosses arena boundaries.** `Slot` is `Copy` with a `Reference(SlotIndex)` payload; `endowments_by_id`, `ModuleValue::Value`, `BodyOp::InitLocal` accept any `Slot`, and `create_global_property` stores `(kind, payload)` unchecked (interp.rs:10603-10611) into a *fresh* arena. Only primitives are used in-tree, so no live bug, but the seam is not type-safe: a reference endowment would be a dangling index (bounds-checked → panic, or kind confusion → logic error). `ModuleGraph` cells are visited by no GC (not an `Interp` field) — moot today, a trap once modules hold heap references.
- **Panics/unwraps on untrusted data.** module.rs indexes `modules[id.0]` with a `pub`-constructible `ModuleId` (host input, not guest). intl_number.rs: `from_utf8(...).unwrap()` on ASCII digit runs (762, 767) is sound; `debug_assert!` in `from_f64` (242) is guarded by callers; the **u128 overflow** in `apply_rounding_increment` (518-530) is guest-reachable (see candidate 6). Release wraps silently (no `overflow-checks` per census), debug panics.
- **Determinism.** No host time/locale anywhere in the region; default locale is the constant `"en"` (interp.rs:18926). `format!("{x:.1100}")` is Rust-std exact formatting (no libm). `HashMap` in compartment.rs is sorted before any observable use (301-303, 327-329, 213-215). module.rs uses `BTreeMap`/`BTreeSet` throughout. The f64 percent multiply is deterministic (IEEE) but spec-divergent.
- **Metering-doctrine drift (adjacent).** `RunOutcome.computrons` doc (interp.rs:3597-3598) still says "comparable bit-for-bit with the oracle's run-only count" — parity language the 2026-07-04 doctrine retired. Compartment seeding is unmetered "matching XS" (interp.rs:8223-8225) — acceptable, but the justification is parity-framed.
- **Duplication.** `requested_modules` (module.rs:500-522) and `ModuleSource::requested_specifiers` (893-912) are the same algorithm; `group_separator`'s two branches are identical (696-700); the seeding block is duplicated verbatim in `evaluate`/`evaluate_with_symbols` (296-306 / 322-333).
- **Lint gate.** `cargo clippy` fails deny-by-default on intl_number.rs:779 (`int_digit_count > 3 || notation == Notation::Standard && int_digit_count > 3`); census records that no clippy job exists in CI — this line is why one cannot be added without a fix.
- **Precision-priority heuristic.** `render_magnitude` (856-864) picks between ToRawFixed and ToRawPrecision by comparing *trimmed* fraction-string lengths; ECMA-402 compares `[[RoundingMagnitude]]` before trailing-zero handling. Likely divergent at edges (e.g. when one result trims to an integer). Low confidence on a concrete counterexample; flagged as an observation, not a candidate.
- **Performance shape.** `from_f64` allocates a ~1.1 KB string per `format` call and `Vec<u8>` of up to ~1,100 digits; `namespace()` is O(exports × resolve) and `Namespace::get` is a linear scan. None are hot for the engine's purpose.

## Candidate findings

Ordered most architecturally significant first. Confidence is stated per item.

1. **`Compartment` is a stateless per-call evaluator, and "shared intrinsics" is a one-bool marker** — `compartment.rs:295` / `:320` / `:64-68`. Claim: every `Compartment::evaluate*` call constructs `Interp::new()`, so no intrinsic graph is shared between compartments or between two evaluations of one compartment, and `Intrinsics` contains no intrinsics. Evidence: `let mut interp = Interp::new();` (295, 320); `pub struct Intrinsics { pub locked_down: bool }` (64-68); `locked_down` has no writer in the workspace. Why: violates design §Hardened JS ("intrinsics are created once per machine and referenced per-realm", design 571-574); the endo `Machine::evaluate` built on it (ironhorse_engine.rs:161-166) cannot carry state across `eval` calls, so it is not the xsnap `Machine` surface the design promises. Confidence: high.

2. **Shared-intrinsics "certification" cannot fail** — `compartment.rs:440-441`, `ironhorse-262/src/lib.rs:821`. Claim: `Rc::ptr_eq(a.intrinsics(), b.intrinsics())` is the only evidence of shared intrinsics and it compares a content-free marker. Evidence: `assert!(Rc::ptr_eq(a.intrinsics(), b.intrinsics()));` (440); `let shared_intrinsics = std::rc::Rc::ptr_eq(a.intrinsics(), b.intrinsics());` (262/lib.rs:821). Why: the README/design cite this dual-run as certifying "shared-intrinsics identity" (compartment.rs:45-47); the property named is not the property tested. Confidence: high.

3. **`Intl.NumberFormat` `roundingIncrement` path overflows a `u128` for large finite inputs** — `intl_number.rs:518-530`. Claim: with `roundingIncrement ≠ 1` and `maximumFractionDigits = 2`, any |x| ≥ ~3.4e36 makes `n = n * 10 + d` exceed `u128::MAX` (39 digits); debug builds panic, release builds wrap and print garbage. Evidence: `let mut n: u128 = 0; for &d in &integer.digits { n = n * 10 + d as u128; }` (518-521); comment "(values in these tests stay well within range)" (517); constructor admits `roundingIncrement` 1…5000 (interp.rs:19503-19512). Verified: exact 1e40 has 41 significant digits → 43 with two fraction places. Why: guest-reachable panic through a *valid* option set (`new Intl.NumberFormat('en',{minimumFractionDigits:2,maximumFractionDigits:2,roundingIncrement:5}).format(1e40)`); in release a silent wrong value (no `overflow-checks` profile, census). Confidence: high (arithmetic verified; not executed in-tree).

4. **Currency/unit styles and compact notation are accepted and then formatted wrongly, not skipped** — `intl_number.rs:887-918`, `:877`, `:638-643`; `interp.rs:19644`, `:19713`, `:25540`. Claim: `style:'currency'|'unit'` and `notation:'compact'` pass the constructor but `partition_number` never emits `Currency`/`Unit`/`Compact` parts and `compute_notation_exponent` returns 0 for `Compact`, so `format(1)` with `currency:'USD'` yields `"1.00"` and compact `format(1234567)` yields `"1,234,567"`. Evidence: `Notation::Standard | Notation::Compact => 0,` (877); `#[allow(dead_code)] struct Compact` "Reserved for the compact-notation follow-up child" (637-639); doc "affixes for currency/unit are layered by the caller" (884) vs. callers `format_to_string(&resolved, n)` with no layering (interp.rs:25540, 25581, 25591). Why: contradicts the region's own doctrine "an honest named skip, never a wrong value" (which `formatRange` follows at interp.rs:25602); the XS oracle cannot catch it (no Intl), and `intl_numberformat.rs:11-12` lists these as follow-ups while leaving the surface live. Confidence: high.

5. **Module link/evaluate errors leave records stuck and a retry reports success** — `module.rs:435-441`, `:463-479`, `:641-644`. Claim: when `inner_link` returns `Err` (unresolved specifier, missing/ambiguous export) the root and every module on the DFS stack stay `Linking`, so a second `instantiate(root)` returns `Ok(())` without binding anything; likewise a `Tdz` error in `evaluate` leaves modules `Evaluating` and a re-`evaluate` returns `Ok(vec![])`. Evidence: `ModuleStatus::Linking | ModuleStatus::Linked | … => return Ok(()),` (436-439); `let dep = self.resolve(spec)?; self.inner_link(dep, stack)?;` (463-464) with no unwind; `ModuleStatus::Evaluating | ModuleStatus::Evaluated => return Ok(()),` (642). Why: ECMA-262 Link resets the stack to `unlinked` on abrupt completion and Evaluate records `[[EvaluationError]]` for rethrow; the model the Compartment API exposes silently converts a failed graph into a "linked" one. Confidence: high (by reading; no test exercises a retry).

6. **Percent style rounds an f64 product, contradicting the module's exactness contract** — `intl_number.rs:931-934` vs `:11-15`. Claim: `value *= 100.0` happens in binary floating point before `Decimal::from_f64`, so the value rounded is neither the spec's exact mathematical `100 × x` nor ICU's shortest-repr product. Evidence: `let mut value = x.abs(); if opts.style == Style::Percent { value *= 100.0; }` (931-934); header: "The rounding operates on the **exact** decimal expansion of the double" (11). Verified with Python: 825 of 20,000 inputs `i/1000` round differently (e.g. `0.015` → f64 `1.5` → `"2%"`, exact `1.49999…` → `"1%"`). Why: deterministic but spec-divergent; the fix is `dec.scale_pow10(2)` on the exact `Decimal`, which already exists (282-287). Confidence: high.

7. **The module graph is disconnected from the interpreter; the Compartment "module map" is a model the engine cannot execute** — `module.rs:8-10, 17-19`; `compartment.rs:255-260`; `interp.rs:15850-15852`. Claim: `XS_CODE_MODULE` has no dispatch arm (falls to the generic `Unsupported`), `Interp` holds no `ModuleGraph`, and `import_static` runs `BodyOp`s, so no compiled module can run on ironhorse. Evidence: "this crate does not yet execute `XS_CODE_MODULE`/`XS_CODE_IMPORT` bytecode" (module.rs:17-19); `other => { return Halt::Unsupported(other.name()); }` (interp.rs:15850-15852); `SideTable::Modules => ("module::ModuleGraph", Pending)` (sidetable.rs:586). Why: honest in docs, but the crate-root API (`lib.rs:53-56`) and the endo re-exports (`ironhorse_engine.rs:38`) present `ModuleGraph`/`ModuleSource` as engine surface; the design's acceptance bar (boot bundles are modules) is unreachable and the store-seam ledger (1373-1380) depends on it. Confidence: high.

8. **Name-keyed endowments and `define_global` never reach the evaluator** — `compartment.rs:171`, `:193-195`, `:301-306`, `:327-333`. Claim: only `globals_by_id` is seeded; `Compartment.globals` (populated by `endowments` and `define_global`) is write-only with respect to evaluation, even in `evaluate_with_symbols` where the `names` table needed to resolve them is in hand. Evidence: `globals: options.endowments,` (171); `self.globals_by_id.iter().map(|(&i, &v)| (i, v)).collect();` (302, 328); doc "resolves ids once the symbol table lands" (199-200) while `let names = crate::symbols::parse_symbols(symbols);` (319) is unused for that. Why: a `new Compartment({ endowments })` caller gets a silent no-op; docs are stale relative to the compiler landing. Confidence: high.

9. **Hand-rolled locale data is wrong for accepted locales and the "exact CLDR" claim overstates it** — `intl_number.rs:690-710`, `:780`, `:4-5`. Claim: every comma-decimal locale gets `"."` as group separator (CLDR: fr/ru → narrow/no-break space, de-CH → `'`), `es` is unconditionally comma-decimal (es-MX/es-US use `.`), and `Grouping::Auto` ignores `minimumGroupingDigits` (es: `1000` → `"1000"`, here `"1.000"`). Evidence: `if locale_uses_comma_decimal(locale) { "." }` (692-695) with comment "a few with the narrow no-break space, not exercised by the corpus"; `"de" | "fr" | "es" | "it" | "nl" | "pt" | "ru" | "tr"` (708); `Grouping::Auto => notation == Notation::Standard && int_digit_count > 3,` (780). `intl_resolve_locale` accepts any canonical tag and keeps it (interp.rs:18921-18924). Why: deterministic but not CLDR-exact for locales the engine does not reject; the oracle cannot catch it. Confidence: high on the divergences; medium on how much the corpus cares.

10. **`Slot` values cross machine boundaries with no arena anchor** — `compartment.rs:116`, `:305/:331`; `module.rs:89`, `:146`; `interp.rs:10603-10611`. Claim: `endowments_by_id: HashMap<u16, Slot>`, `ModuleValue::Value(Slot)`, and `BodyOp::InitLocal { value: Slot }` accept a `Reference` slot that is meaningless in the fresh `Interp` the evaluator builds, and `create_global_property` installs `(kind, payload)` without validation; `ModuleGraph` cells are visited by no GC. Evidence: `pub endowments_by_id: HashMap<u16, Slot>,` (116); `interp.define_global_id(id, value);` (305); `prop.kind = value.0;` (interp.rs:10604). Why: not memory-unsafe (bounds-checked arena) but a kind-confusion/panic trap the type system does not prevent; becomes a GC-root omission the moment modules hold heap values. Only primitives are used in-tree today. Confidence: medium (latent).

11. **`ironhorse_vm::Machine` collides with the design's `Machine` API and sits off the persistent path** — `compartment.rs:342-345`; `rust/endo/src/ironhorse_engine.rs:35, 137-139, 161-166, 408`; `ironhorse-snapshot/src/machine.rs:19-28`. Claim: the design's `Machine` (metering, snapshot, `run_promise_jobs`) is realized as an extension trait on `Interp` plus `begin_store_session(Interp::new(), …)`, while `VmMachine` offers none of those verbs and is used only by the stateless `evaluate` path. Evidence: `pub use ironhorse_vm::Machine as VmMachine;` (35); `let comp = self.inner.new_compartment(); Ok(comp.evaluate_with_symbols(...))` (164-165); `begin_store_session(ironhorse_vm::Interp::new(), &signature, &mut store)` (408). Why: two things named `Machine` with disjoint capabilities in one embedding is an API-boundary hazard for `rust/endo`; the compartment `Machine` cannot grow the design's verbs without first becoming stateful (finding 1). Confidence: high.

12. **`ModuleGraph::insert` replaces a linked record in place, orphaning cells other modules already bound** — `module.rs:268-273`. Claim: re-inserting a specifier that has been linked swaps the record for a `New` one with an empty `env`, while importers keep `CellId`s into the old cells (stale, never updated), and `by_specifier` still points at the same `ModuleId`. Evidence: `if let Some(&id) = self.by_specifier.get(&spec) { self.modules[id.0] = record; return id; }` (270-273); doc "A duplicate specifier replaces the record, matching a host loader" (266-267). Why: spec module maps are append-only; replacement produces silently dead live bindings. Confidence: high on mechanism; low on in-tree reachability (no caller re-inserts).

13. **Clippy deny-level error blocks a lint gate** — `intl_number.rs:779`. Claim: `int_digit_count > 3 || notation == Notation::Standard && int_digit_count > 3` is `clippy::overly_complex_bool_expr` (deny by default), so `cargo clippy -p ironhorse-vm` fails; the census records no clippy job in CI. Evidence: `Grouping::Always => int_digit_count > 3 || notation == Notation::Standard && int_digit_count > 3,` (779); identical `if/else` branches at 696-700 add a warning. Why: semantically harmless (reduces to `int_digit_count > 3`) but it is the concrete reason a clippy gate cannot be enabled today. Confidence: high (census observation).

14. **Namespace key order is byte order, not UTF-16 code-unit order** — `module.rs:749-751`. Claim: `entries.sort_by(|a, b| a.0.cmp(&b.0))` orders non-BMP export names (UTF-8 lead `F0`) after U+E000–U+FFFF names (lead `EE`/`EF`), whereas spec code-unit order (`D800`–`DBFF` < `E000`) puts them before. Evidence: comment "Rust's `String` order is byte order, == code-unit order for the corpus" (749-750). Why: XS's `c_strcmp` shares the byte-order behavior, so oracle parity holds while both deviate from ECMA-262; low impact, but the comment should say "matches XS, not the spec". Confidence: high on the ordering fact; low severity.

## What is done well

- **Determinism discipline in the evaluator seam is real and locked**: the W6-8 fix sorts `HashMap` endowments by id before seeding (compartment.rs:296-306) and `tests/endowment_order.rs` proves enumeration order is a function of ids alone; module.rs uses `BTreeMap`/`BTreeSet` exclusively; intl_number.rs has zero host-locale/time dependence and a constant default locale (interp.rs:18926).
- **Exact decimal arithmetic for NumberFormat**: `Decimal::from_f64` via `{:.1100}` is a correct, allocation-simple way to get the exact dyadic expansion, and `decide_round_up`/`round_to_significant` implement all nine ECMA-402 rounding modes cleanly with a compact carry (300-414).
- **Honest named skips where they exist**: dynamic import, `import.meta`, `formatRange`, and the `Compartment` intrinsic all self-name (`compartment:dynamic-import`, `module:*`, `Intl.NumberFormat:formatRange`) rather than fabricate results, and the README/doc comments state the scope folds plainly (compartment.rs:34-49; module.rs:12-20).
- **Module model is spec-shaped**: `resolve_export`/`get_exported_names` follow ECMA-262 §16.2.1.5.1-2 including star-ambiguity, `default` exclusion, and cycle guards; `allocate_local_cells` before recursion is the right move for cyclic SCCs; the 14-case corpus covers diamond, cycle, TDZ, ambiguity, and live bindings.
- **Snapshot ledger honesty**: `SideTable::Modules` is declared `Pending` (sidetable.rs:586) rather than omitted, and the exhaustiveness test forces every table to declare coverage.
- **Small, pure, testable Intl core**: `intl_number.rs` depends on nothing in the VM; the `NfResolved` record decouples it from slot representation, which is the right seam for a future CLDR data table.
