# Lens review: Security, sandboxing, and Hardened JavaScript

Reviewer note on method: every claim below was verified by reading the cited
lines in the current tree, and most were additionally executed as probes linked
against the already-built `libironhorse_vm` / `libironhorse_compile` rlibs
(sources under `scratchpad/sec/p1.rs … pc.rs`; no repo file was modified).
Probe output is quoted verbatim as `[probe]`.

## 1. Assessment

The engine's *memory* safety story is strong and its *ambient authority* story
is unusually clean: `#![forbid(unsafe_code)]`, index arenas, no host clock
(`Date.now` is 0, `Temporal.Now` is the epoch — interp.rs:25111), no host
locale, no randomness, no `WeakRef`/`FinalizationRegistry` (probe:
`typeof WeakRef` → `"undefined"`), and `Function.prototype.toString` that never
reveals source text (interp.rs:26036). The thirteen proxy traps are a faithful
10.5.x port with realm-local catchable errors. Those are the ingredients of a
confinement story.

What is missing is the confinement itself. Requirement 5 ("per-compartment
globals over shared frozen intrinsics", design:565-579) has no implementation
seam in this tree, and the three primitives it rests on are each broken in a way
that is not a gap but a wrong answer:

**Compartment isolates nothing.** `Compartment::evaluate*` constructs a brand-new
`Interp` per call (compartment.rs:295, :320) and `Intrinsics` is
`struct { locked_down: bool }` (compartment.rs:64) with no writer anywhere in
the workspace. Two compartments share no object; two evaluations of one
compartment share no object; name-keyed endowments are never read. The
certification of "shared intrinsics" is `Rc::ptr_eq` on that bool. There is no
realm abstraction below `Interp`, so "shared frozen intrinsics with
per-compartment globals" cannot be expressed on today's seams at all — and the
production (store-backed) path in `rust/endo` bypasses `Compartment` entirely,
running one realm per worker.

**Freezing does not freeze.** Integrity flags live only on slot-chain property
records, so no array, `Map`, `Set`, typed array, buffer, or proxy can be frozen
or hardened — `Object.freeze([])` and `harden({a:[1]})` *halt* the crank
(interp.rs:26866, :35776) — and functions harden incompletely (`name` stays
redefinable). More seriously, bare-identifier assignment writes the global
property slot raw, with no flag check (interp.rs:38498-38501): after
`Object.freeze(globalThis)`, `Object.isFrozen(globalThis)` is `true` and `g = 2`
still succeeds, in strict mode, without throwing [probe p8]. Frozen globals are
the first invariant a hardened realm buys.

**`harden` can lie.** The visited mark is stamped at enqueue (interp.rs:35754)
but the walk can abort mid-way on an exotic object; the marked-but-unfrozen
objects survive, and a later `harden(x)` short-circuits on the mark
(interp.rs:35727) and returns `x` *successfully* while `x` is still mutable
[probe p9: `inner.secret = 99` succeeds, `Object.isFrozen(inner)` is `false`].
That is silent wrong state in the SES primitive itself. (In the store-backed
daemon a halted crank rewinds, which masks it there; `Interp::run`, the public
API `ironhorse-262` uses, does not.)

Around those, the MOP has several read/write paths and the ones outside the
`mop_*` seam bypass proxies and accessors: `with (proxy)` throws
`ReferenceError` where the `has`/`get` traps should answer; `Object.defineProperty(o,'k',proxyDescriptor)`
reads through the proxy silently and defines `undefined`; `String.prototype`
accessors are invisible to a primitive-string receiver; and `Reflect.ownKeys`
gives *different* answers for a function and for a trap-less `Proxy` of it
(`prototype,caller` vs `length,name,caller,prototype`) — a violation of the
one proxy invariant that makes membranes composable.

Finally, the "honest named skip, never a wrong value" doctrine — which is
genuinely well applied in many places — fails at exactly the seams a sandbox
depends on (Intl currency renders `"1.00"`, `arr.length = 1.5` silently becomes
`0`, a detached typed array still reports `length 8`), and untrusted input can
kill the *process*, not the crank: three separate one-line guest programs
produced `fatal runtime error: stack overflow, aborting` (SIGABRT, uncatchable,
not a `Halt`, not a panic) — a self-referential array as the completion value, a
20k-deep object through `JSON.stringify`, and a spec-legal prototype cycle
through a `Proxy`; 500 nested parentheses do the same to the compiler on the
host's own thread.

The verdict along this lens: the *shape* is right (arena-based, no unsafe, no
ambient authority, named skips, spec-faithful traps) and the *doctrine* is
right, but the Hardened-JavaScript layer is not yet a security boundary — it is a
set of primitives that report success without delivering the invariant. Nothing
here is unfixable; several items (globals, id space, harden mark) are small
changes. But the compartment/realm seam is a genuine architectural hole that
should be closed before more surface accretes on top of `Interp`-as-realm.

### F1. Untrusted guest code aborts the host process via native stack overflow (three independent sites)
**Severity: critical · Confidence: high · Category: robustness/security · Novelty: partially-known** (reported per-region as separate leads by interp-05, interp-13, compile-parser; never merged, and the JSON site is new)

**Claim.** Several Rust-side recursive walks over guest-controlled structures
have no depth budget, so ordinary JavaScript terminates the whole process with
`SIGABRT` rather than producing a `Halt`.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
10945:  out.push_str(&self.render(item));                      // render() over array elements
30336:  fn json_serialize(&mut self, value: Slot, visited: &mut Vec<..>, cost: &mut u64)
36207:  return self.proxy_get(code, owner, id, receiver);      // ordinary_get -> proxy_get -> ordinary_get
```
Probes (release-of-record debug build, 8 MiB main thread):
```
[render-cycle]  var a=[]; a[0]=a; a            -> fatal runtime error: stack overflow, aborting (exit 134)
[proto-cycle]   Object.setPrototypeOf(t, new Proxy(t,{})); t.x -> exit 134
[stringify]     20,000-deep plain object, JSON.stringify(o)    -> exit 134
[compile]       500 nested "(" via compile_atoms_with          -> exit 134
```
By contrast, JS→JS recursion is handled correctly: `function f(n){return f(n+1)}`
returns `Halt::StackOverflow(4064)`.

**Impact.** In a consensus worker this is a liveness break that a single message
can trigger, and the threshold is a *host* property (thread stack size, build
profile), so replicas with different stack limits diverge on where it happens.
The design's memory-safety claim ("a panic is a crashed crank, not a compromised
daemon") does not hold: an abort is not a crashed crank, it is a dead process,
and `catch_unwind` cannot contain it.

**Recommendation.** Introduce one engine-wide recursion budget threaded through
every Rust-side recursive walk (render, `json_serialize`, `ordinary_get`/`mop_*`
proxy chains, `to_primitive`, the compiler's `parser`/`scoper`/`coder`
descents), charged like `DISPATCH_REENTRY_LIMIT` and surfacing as
`Halt::StackOverflow`. Making it a *counter* rather than a stack probe keeps it
deterministic across hosts, which a stack-size check would not be. Additionally,
`render` needs a cycle guard (it is a `join(",")` emulation and the spec's
`Array.prototype.join` has one).

### F2. `harden()` can return successfully while leaving the object unhardened
**Severity: critical · Confidence: high · Category: security · Novelty: new**

**Claim.** Because the visited mark is stamped at *enqueue* and the walk can
abort part-way on an exotic object, objects reached but not yet frozen stay
marked; a subsequent `harden(x)` short-circuits on the mark and returns `x`
without freezing it.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
35727:  if self.slots.get(inst).flag & XS_DONT_MARSHALL_FLAG != 0 { return Ok(arg0); }   // do_harden
35754:  if self.slots.get(inst).flag & XS_DONT_MARSHALL_FLAG != 0 { return; }
35756:  self.slots.get_mut(inst).flag |= XS_DONT_MARSHALL_FLAG;                          // mark at ENQUEUE
35776:  return Err(Halt::Unsupported("harden:exotic-object"));                           // mid-walk abort
```
Probe (`sec/p9.rs`, two cranks on one `Interp`):
```
crank1: var inner={secret:1}; var o={b:[], a:inner}; globalThis.inner=inner; try{harden(o)}catch(e){}
        -> completed=false halt=Unsupported("harden:exotic-object")
crank2: harden(inner); inner.secret = 99; inner.secret + ':' + Object.isFrozen(inner)
        -> "99:false"
```
The code's own comment acknowledges the equivalence argument
("marking at enqueue is behaviorally identical … the mark is only a visited
set") — which is true only if the walk always completes.

**Impact.** The SES primitive reports success on a mutable object. Any tamper-
proofing built on `harden` (Endo's `Far`/`harden` discipline) is silently void
for the affected subgraph. In the store-backed daemon a halted crank rewinds, so
exposure there depends on rewind succeeding; `Interp::run` (used directly by
`ironhorse-262` and by any future embedder) has no such protection.

**Recommendation.** Mark on *completion* of `harden_freeze_and_traverse`, not on
enqueue (use a separate `HashSet` for the worklist-dedup role), or make
`do_harden` transactional: collect the whole reachable set first, refuse before
mutating anything if it contains an object the model cannot freeze, and only
then stamp. The second form also removes the "partially frozen graph" state
entirely.

### F3. Frozen (and hardened) global bindings remain writable through bare assignment
**Severity: high · Confidence: high · Category: security · Novelty: partially-known** (interp-13 candidate 6 asserted the sloppy-mode case; the strict-mode no-throw and the `globalThis.g` asymmetry are new)

**Claim.** `resolve_set` writes the global property slot's kind/value directly
with no `XS_DONT_SET_FLAG` / accessor check, so a frozen global is writable by
name even though it is not writable through `globalThis.x`.

**Evidence** (`ironhorse-vm/src/interp.rs:38495-38502`):
```rust
} else if let Some(&idx) = self.global_props.get(&name) {
    let p = self.slots.get_mut(idx);
    p.kind = value.kind;
    p.value = value.value;
}
```
`resolve_get` (:38470-38473) likewise reads the raw slot, so a global accessor
would never invoke its getter. Probes:
```
[member-assign-frozen]      var g=1; Object.freeze(globalThis); globalThis.g = 2; g   -> "1"   (correctly blocked)
[bare-assign-frozen]        var g=1; Object.freeze(globalThis); g = 2; g              -> "2"   (bypass)
[strict-bare-assign-frozen] 'use strict'; ... g = 2 in try/catch                       -> "no-throw:2"
[harden-global-assign]      var g=1; harden(globalThis); g = 2; g                      -> "2"
[isfrozen-global]           Object.isFrozen(globalThis)                                -> "true"
```

**Impact.** The most basic hardened-realm invariant — a frozen `globalThis` — is
reported as held and is not. Two paths to the same property disagree, which is
also a plain spec divergence (strict assignment to a non-writable property must
throw `TypeError`).

**Recommendation.** Route the global arm of `resolve_get`/`resolve_set` through
`ordinary_get`/`ordinary_set` on the global object (or at minimum test
`XS_DONT_SET_FLAG` / `XS_GETTER_FLAG|XS_SETTER_FLAG` and raise
`catchable_type_error` in strict mode). The `global_props` index can stay as the
fast lookup; only the read/write must go through the ordinary seam.

### F4. The integrity model covers only slot-chain properties, so nothing exotic can be frozen or hardened
**Severity: high · Confidence: high · Category: security · Novelty: known-open** (interp-13 candidate 3)

**Claim.** `is_ordinary_object` excludes arrays, collections, typed arrays,
buffers, views, wrappers, regexps and proxies, and every integrity operation
refuses on them; functions pass the gate but their synthesized `length`/`name`
remain configurable.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
35673:  fn is_ordinary_object(&self, inst) -> bool { !(self.arrays.contains_key(&inst) || ... ) }
35776:  return Err(Halt::Unsupported("harden:exotic-object"));
26866:  "freeze:exotic-object"
26910:  "isFrozen:exotic-object"
35906:  configurable: Some(true),        // function_meta_own_descriptor, always
```
Probes:
```
[freeze-array]    var a=[1]; Object.freeze(a)             -> halt Unsupported("freeze:exotic-object")
[isfrozen-array]  Object.isFrozen([])                     -> halt Unsupported("isFrozen:exotic-object")
[harden-map]      harden(new Map())                       -> halt Unsupported("harden:exotic-object")
[harden-fn-name]  function f(){}; harden(f);
                  Object.defineProperty(f,'name',{value:'evil'}); f.name+':'+Object.isFrozen(f)
                                                          -> "evil:false"
```

**Impact.** No realistic object graph can be hardened — every SES-hardened API
surface contains arrays and functions. Requirement 5's acceptance bar ("the
endor daemon's boot sequence … runs identically") is unreachable, and this is
structural, not a missing method: integrity is modeled as a flag on property
records, while exotic own state lives in side tables that carry no flags.

**Recommendation.** Give exotic side-table state an integrity representation —
either a per-instance `frozen`/`sealed` bit consulted by every exotic write path
(`array_item_set`, typed-array element set, collection mutators,
`function_meta_own_descriptor`), or a materialization step that converts
exotic own state to chain slots on freeze. The first is far cheaper and is what
XS effectively does with `XS_DONT_SET_FLAG` on internal data slots (the
`do_petrify` doc at :35818 already names that XS behavior as unmodeled).

### F5. `Compartment` is a stateless per-call evaluator; the "shared frozen intrinsics" seam does not exist
**Severity: high · Confidence: high · Category: api-boundary · Novelty: known-open** (vm-compartment map candidates 1, 2, 8; interp-03 candidate 8)

**Claim.** Every `Compartment::evaluate*` boots a fresh `Interp`, `Intrinsics`
carries no intrinsics, name-keyed endowments are never read, and no primordial
is shared between compartments or between two evaluations of one compartment.

**Evidence** (`ironhorse-vm/src/compartment.rs`):
```
 64: pub struct Intrinsics { pub locked_down: bool }   // no writer anywhere in the workspace
295: let mut interp = Interp::new();                    // evaluate
320: let mut interp = Interp::new();                    // evaluate_with_symbols
171: globals: options.endowments,                       // never read by either evaluator
440: assert!(Rc::ptr_eq(a.intrinsics(), b.intrinsics()));  // the "shared intrinsics" certification
```
Module doc (:4-6) states the opposite: "intrinsics are created **once per
machine** and referenced per realm". `rust/endo/src/ironhorse_engine.rs:161-165`
builds a new compartment per `eval`; the store-backed `PersistentMachine` path
(:408) does not use `Compartment` at all.

**Impact.** There is no realm object below `Interp`, so the design's
architecture for requirement 5 cannot be built incrementally on this seam — the
per-compartment global object, the per-compartment evaluator, and the shared
frozen primordial graph all require a realm/intrinsics split inside `Interp`
that does not exist. The "isolation" the compartment tests certify is the
isolation of two unrelated heaps, which is trivially true and proves nothing
about the property SES needs.

**Recommendation.** Decide explicitly whether a compartment is (a) a realm
inside one `Interp` — which means factoring the global object, the property-id
space and the evaluator out of `Interp` into a `Realm`, with intrinsics
reference-counted across realms — or (b) a separate `Interp` per compartment,
in which case `Intrinsics`/`Machine`/`Rc::ptr_eq` should be deleted rather than
left as a marker that documents a property the code does not have. Either way,
delete or implement `Compartment.globals` and `locked_down`; a write-only
option bag is a trap for the embedder.

### F6. Relink re-installs `%Error.prototype%.stack` on every partial pass, silently reverting guest/SES taming
**Severity: high · Confidence: high · Category: security · Novelty: partially-known** (interp-03 candidates 2/3 traced the code path; empirical confirmation is new)

**Claim.** Two branches of `install_intrinsic_bindings` sit above the
`if !full { return; }` gate with no `keep`, no `full`, and no create-only
`find_property` guard, so a later crank's partial install overwrites a guest
redefinition of `Error.prototype.stack` and `%AsyncGeneratorPrototype%.constructor`.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
7625: if let Some(cid) = self.constructor_id { self.set_own_unmetered_with_flag(self.async_generator_proto, cid, ...) }
7699:     let sid = self.intern_key_unmetered("stack");
7700:     self.set_own_accessor_unmetered(proto, sid, Some(getter), Some(setter));
7735: if !full { return; }          // the gate both branches are ABOVE
7425: self.installed_names_len = names.len();   // floor set before the pass that appends names
```
Probe (`sec/p6.rs`, two cranks on one `Interp`, using the real `relink_crank`):
```
crank1: Object.defineProperty(Error.prototype,'stack',{get:function(){return 'TAMED'},configurable:true});
        new Error('x').stack                     -> "TAMED"
crank2: var q=1; new Error('y').stack            -> "Error: y\n at ()"   (boot accessor restored)
```
Note the create-only contract *does* hold for ordinary intrinsics — probed
`delete Math.PI` and `Object = 5` both survive a relink — which makes these two
branches an isolated, fixable defect rather than a systemic one.

**Impact.** SES's `lockdown` tames `Error.prototype.stack`; here the taming is
undone at the next crank boundary without any signal. The function doc claims
this class is "locked by `relink_preserves_guest_intrinsic_edits`" — no test of
that name exists (`tests/relink_preserves_guest_edits.rs` covers only the
symbol-keyed branches).

**Recommendation.** Move both branches below the `!full` gate (they depend on no
program name, which is the stated criterion for that gate), or give them the
same `find_property` create-only guard the `proto_data` branch uses. Add the
regression test the doc already names, covering `stack`, the async-generator
`constructor`, and a guest deletion (not only a redefinition). Separately,
setting `installed_names_len` *before* the pass that appends names (:7425)
guarantees a partial pass on the very next crank for almost every program — that
is what makes these branches fire; setting the floor after the pass would
confine partial passes to genuinely new names.

### F7. Property operations outside the `mop_*` seam bypass proxy traps and accessors
**Severity: high · Confidence: high · Category: api-boundary · Novelty: known-open** (interp-13 candidate 1; the trap-less-forward `ownKeys` divergence is new)

**Claim.** The doc's contract "all ordinary/`Object.*`/`Reflect.*`/syntax
property operations route through the same `mop_*` seam so a trap cannot be
bypassed" (interp.rs:36348-36350) is false at four sites, and a trap-less
`Proxy` does not forward `ownKeys` identically to its target.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
37847:  if !self.instance_has(descriptor, id).0 { continue; }     // descriptor_from_object: chain-only
37851:  let value = self.ordinary_get(code, descriptor, id, receiver)?;
38216:  let (present, recursions) = self.instance_has(obj, id);   // is_scopable_slot (with-statement)
38228:  let blocklist = self.instance_get(obj, unscopables_id);
38105:  ... string_property_get -> instance_get                    // primitive-string receiver
```
Probes:
```
[with-proxy]            with(new Proxy({x:42},{has:()=>true,get:()=>42})) { x }   -> "caught:ReferenceError"
[desc-of-proxy]         Object.defineProperty(o,'k', new Proxy({},{get:()=>7})); o.k -> "undefined" (spec: 7)
[string-proto-getter]   defineProperty(String.prototype,'g',{get:...}); ''.g       -> "undefined" (spec: "G")
[ownkeys-fn]            Reflect.ownKeys(f)                 -> "prototype,caller"
[ownkeys-proxy-fn]      Reflect.ownKeys(new Proxy(f,{}))   -> "length,name,caller,prototype"
```

**Impact.** A membrane's whole job is that a proxy is indistinguishable from its
target at the meta level. Here `with`, `ToPropertyDescriptor` and primitive-
string reads see through the proxy, and `Reflect.ownKeys` of a trap-less proxy
differs from that of the target — the invariant that lets proxies compose. The
`defineProperty` case is the worst shape: no throw, no skip, a wrong property.

**Impact is structural, not local**: there are four layered read paths
(`instance_get` / `ordinary_get` / `mop_get` / `property_at_get`), three presence
paths, five own-property insertion primitives and two ValidateAndApply
implementations; which layer a caller uses is historical.

**Recommendation.** Make `instance_get`/`instance_has`/`instance_put` private to
the boot/restore code that genuinely needs raw chain access, rename them to say
so (`boot_chain_get`, …), and convert every guest-reachable caller to `mop_*`.
Then add a mechanical test — for a representative object, assert that
`Reflect.ownKeys`, `getOwnPropertyDescriptor`, `get`, `set`, `has` and `delete`
agree between `x` and `new Proxy(x, {})` — which would have caught the `ownKeys`
divergence above.

### F8. Silent wrong values at confinement-relevant seams, contradicting the named-skip doctrine
**Severity: high · Confidence: high · Category: error-model · Novelty: partially-known** (individual instances flagged by vm-compartment map 4 and interp-13 candidate 8; the detached-buffer case is new)

**Claim.** The engine's stated rule — "an honest named skip, never a wrong
value" — is violated at several places where guest-observable state is silently
fabricated instead of refused.

**Evidence + probes:**
```
interp.rs:35517   _ => 0,        // to_length_u32; checked_array_length (:35524) exists and is unused
  [arr-len-frac]  var a=[1,2,3]; a.length=1.5; a.length+':'+a[0]  -> "0:undefined"   (spec: RangeError)
  [arr-len-str]   a.length='2'                                     -> 0              (spec: 2)
intl_number.rs:877 Notation::Standard | Notation::Compact => 0,
  [intl-currency] Intl.NumberFormat('en',{style:'currency',currency:'USD'}).format(1) -> "1.00"
  [intl-compact]  Intl.NumberFormat('en',{notation:'compact'}).format(1234567)        -> "1234567"
interp.rs:26951   NativeMethod::Test262DetachArrayBuffer => { ... self.detached_buffers.insert(buffer); }
  [detached-ta]   b=new ArrayBuffer(8); t=new Uint8Array(b); $262.detachArrayBuffer(b);
                  t.length+':'+t[0]+':'+t.byteLength  -> "8:0:8"   (spec: 0:undefined:0)
```

**Impact.** Wrong values are worse than refusals in a consensus engine: a
refusal is a visible coverage gap, a wrong value is a divergence that reaches
the guest and, through a snapshot, the durable state. The Intl surface is
additionally oracle-blind by construction (XS ships no Intl), so no differential
test can catch it.

**Recommendation.** Convert each to a named skip until it is modeled:
`array_set_length` should call the already-written `checked_array_length` and
raise a catchable `RangeError` on `None`; `partition_number` should refuse
`style: 'currency' | 'unit'` and `notation: 'compact'` at the constructor rather
than at format time; the detach hook should mark the dependent typed arrays (or
be removed entirely — see F9). A grep-able invariant would help: every
`_ => 0`-shaped fallback in a guest-visible coercion is a bug until proven a
spec default.

### F9. The test262 host object (`$262`, with a live `detachArrayBuffer`) is built into every production machine
**Severity: medium · Confidence: high · Category: security · Novelty: new**

**Claim.** `create_test262_host` runs unconditionally in `create_intrinsics`, so
any guest program that names `$262` receives a working buffer-detach capability
in the shipped engine.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
6339:  self.create_test262_host();          // inside create_intrinsics, no cfg, no flag
6858:  fn create_test262_host(&mut self) { ... self.intrinsics.insert("$262", host); }
```
Probes: `typeof $262` → `"object"`; `$262.detachArrayBuffer(b)` succeeds and
leaves `t.length === 8` (see F8).

**Impact.** A hardened realm is supposed to have an enumerable, auditable global
surface; an unexpected host object with a memory-detach primitive is exactly the
kind of thing `lockdown` exists to reject. The capability itself is currently
low-power (it detaches a buffer the guest already holds) but its semantics are
only half-modeled, so it is also a wrong-value generator.

**Recommendation.** Put `create_test262_host` behind a Cargo feature (or an
explicit `Interp::install_test262_host()` the 262 harness calls), so the
production boot cannot mint it. This is a two-line change and removes a
permanent audit item.

### F10. No attenuation seam: a program gets every intrinsic it names, and endowments can only add
**Severity: medium · Confidence: high · Category: api-boundary · Novelty: new**

**Claim.** `install_intrinsic_bindings` binds a global for every name in the
program's symbol table that matches an intrinsic, and the only host control is
`CompartmentOptions.endowments_by_id`, which adds bindings. There is no deny
list, no attenuation, no "start with an empty global object" mode.

**Evidence** (`ironhorse-vm/src/interp.rs:7416-7477`, `compartment.rs:108-127`):
`install_intrinsic_bindings(names, full, keep)` — `keep` is an *id floor* used
for create-only relinking, never as a host policy; `link_intrinsics`
(:7373-7382) calls it with `|_| true`. The option bag has `endowments` and
`endowments_by_id` and no removal or replacement channel.

**Impact.** The embedder cannot express "this compartment gets no `eval`, no
`Function`, no `Intl`, no `$262`" — the standard first move when hosting
untrusted code. Combined with F5 (no realm object), there is nowhere to *put*
such a policy today.

**Recommendation.** When the realm split of F5 is done, make the intrinsic
binding set an explicit per-realm input (a permit set, as SES's `whitelist.js`
is), with `link_intrinsics` consulting it. In the interim, an
`Interp::set_intrinsic_permit(&[&str])` consulted by the global-binding arm at
:7427-7436 would be small and would make the surface auditable.

### F11. Property-key ids are a durable, non-reclaimable, guest-writable 16-bit resource
**Severity: medium · Confidence: high · Category: robustness · Novelty: partially-known** (the single-crank exhaustion is a landed wave-6 item with a test; the *durable, cross-crank* accumulation is new)

**Claim.** Novel string property keys are appended to `symbol_names`
permanently — no GC sweep or crank boundary reclaims them — and the table is
part of the persisted machine state, so a guest can durably consume the id space
across successful cranks until the machine can no longer accept new code.

**Evidence** (`ironhorse-vm/src/interp.rs:35006-35033`): `append_name_key`
pushes onto `symbol_names` and inserts into `symbol_ids`; grep finds no
`retain`/`remove`/`clear` of `symbol_names` in the sweep. `relink_crank`
(:8356-8360) returns `RelinkError::TableFull` once the table reaches the
symbol-key floor, and `rust/endo/src/ironhorse_engine.rs:556-570` maps that to a
hard `SymbolMismatch` refusal for the crank.

Probe (`sec/pa.rs`):
```
crank1: var o={}; for(i=0;i<500;i++){ o['zz'+i]=1 }   -> completed=true, names=503
crank2: o = 0;                                        -> completed=true, names=503   (nothing reclaimed)
```

**Impact.** ~65,000 distinct property names over the *lifetime* of a worker —
easily produced by dictionary-shaped guest data across many small, individually
harmless, committed cranks — permanently bricks that worker for any crank
introducing a new name. The state is checkpointed, so it survives restart, and
the meter (which does charge for novel interns) is not armed by the daemon at
all, so nothing bounds the rate.

**Recommendation.** Either (a) reclaim ids at GC (a compacting rename requires
rewriting persisted bytecode ids — expensive, but the ledger already contemplates
row moves), or (b) stop routing ordinary dictionary keys through the global id
space: index-like and dynamically-computed string keys on non-exotic objects can
live in a per-instance table as XS does for array indices, or (c) at minimum,
document the id space as a per-machine quota, expose it (`program_symbol_names().len()`)
to the supervisor, and refuse *before* the floor with a distinguishable error so
a vat can be migrated rather than discovered dead.

### F12. Descriptor helpers throw uncatchable host escapes where the spec throws a catchable TypeError
**Severity: medium · Confidence: high · Category: error-model · Novelty: known-open** (interp-13 candidate 9)

**Claim.** `descriptor_from_object`, `to_property_id` and
`define_properties_from_object` return `Err(Halt::Throw(String))` instead of
`catchable_type_error()`, so guest `try`/`catch` cannot observe the error and
the crank dies.

**Evidence** (`ironhorse-vm/src/interp.rs:37861`, `:37869`, `:37877`,
`:37886/37893/37899`, `:37952`) versus the `raise_js` doc (:34633-34636):
"Native semantic failures must use this path so `try`/`catch`/`finally` can
observe the realm-correct Error object instead of seeing an uncatchable
host-side `Unsupported` halt." Probe:
```
try { Object.defineProperty({}, 'x', {get: 1}) } catch (e) { 'caught' }
  -> completed=false halt=Throw("TypeError: getter is not callable")
```

**Impact.** Guest-visible error semantics depend on which helper a path happens
to use; a guest cannot defensively wrap reflective code, and every such throw
costs a whole crank (a rewind in the daemon).

**Recommendation.** Mechanical: replace those `Err(Halt::Throw(...))` sites with
`Err(self.catchable_type_error())` (adding a message-carrying variant as
`catchable_syntax_error_msg` already does). A grep gate — no
`Halt::Throw(` literal constructed outside `raise_js`/`render_uncaught` — would
keep the rule enforced.

### F13. Guest code runs at the host boundary after the halt is decided, and a meter abort there is swallowed
**Severity: medium · Confidence: high · Category: metering/reentrancy · Novelty: known-open** (interp-05 candidate)

**Claim.** `render_uncaught` invokes the guest's `toString`/`valueOf` *after*
`meter_host_escape()` has already accounted for the escape, and discards any
`Halt` the nested dispatch returns — including `Halt::MeterAbort`.

**Evidence** (`ironhorse-vm/src/interp.rs`):
```
11072: fn render_uncaught(&mut self, code: &[u8], v: Slot) -> String {
11076:     if let Ok(prim) = self.to_primitive(code, v, true) {     // Err (incl. MeterAbort) dropped
15715:     self.meter_host_escape();
15716:     let text = self.render_uncaught(code, v);
```

**Impact.** Ticks accrued by that guest code land in `RunOutcome.computrons`
after the boundary constant, and a crank that actually exceeded its meter inside
the rendering is reported as `Halt::Throw` rather than `Halt::MeterAbort` — a
misclassification a supervisor may act on. It is deterministic, so not a
divergence, but it is a metering/typing hole in the exact place where guest code
is least expected to run.

**Recommendation.** Propagate the nested halt: if `to_primitive` returns
`Err(Halt::MeterAbort | Halt::StackOverflow | Halt::Unsupported(..))`, return
that halt from the dispatch loop instead of falling back to the static render.

### F14. Intrinsic globals are enumerable, configurable and writable
**Severity: low · Confidence: high · Category: security · Novelty: known-open** (interp-03 candidate 6)

**Claim.** `create_global_property` yields flag 0, so `Object`, `Math`,
`globalThis` &c. are enumerable/configurable/writable, unlike XS
(`XS_DONT_ENUM_FLAG`) and the spec.

**Evidence** (`ironhorse-vm/src/interp.rs:7442`):
```rust
self.create_global_property(id, (Kind::Reference, Payload::Reference(func)));
```
`Slot::property` sets `flag: 0` (`value.rs:349-363`). Probe:
```
Object.getOwnPropertyDescriptor(globalThis,'Object')  -> enumerable:true configurable:true writable:true
Object.keys(globalThis).length                        -> 2
```

**Impact.** A hardened realm inspects global descriptors; SES's global-permit
checks would trip. Also a plain result divergence from XS, currently unobserved
because the 262 baseline lacks the top-level `prop-desc` cases.

**Recommendation.** Set `XS_DONT_ENUM_FLAG` on intrinsic global bindings and add
the corresponding `built-ins/*/prop-desc` cases to the corpus.

## 3. Strengths

These are real and worth preserving:

- **No ambient authority.** No host clock (`Date.now` is 0; `Temporal.Now` is
  the Unix epoch with a UTC zone, interp.rs:25111-25120), no host locale
  (default `"en"`, interp.rs:18926), no randomness anywhere in `ironhorse-vm`,
  and **no `WeakRef`/`FinalizationRegistry`** (probe: both `undefined`) — which
  removes the classic GC-observability covert channel and non-determinism source
  in one stroke. This is a better starting position than any production JS
  engine.
- **`#![forbid(unsafe_code)]` with index arenas**, so the memory-safety class of
  sandbox escape is genuinely absent; the only `unsafe` is in the dev-only
  oracle.
- **Function source text is never exposed**: `Function.prototype.toString`
  renders `function ["name"] (){[native code]}` for user and native functions
  alike (interp.rs:26026-26038), and `f.caller`/`f.arguments` read `undefined`
  (probe) — no caller leak, no source leak.
- **The thirteen proxy traps are complete and invariant-checking**
  (interp.rs:37098-37554): revocation check, `GetMethod`, trap-absent forwarding
  through `mop_*` so proxies compose, and every 10.5.x target-consistency check
  present with realm-local *catchable* errors and correct `SameValue`.
- **The create-only relink contract works** for the ordinary intrinsic surface:
  probed `delete Math.PI` and `Object = 5` both survive a relink, and
  `Object.freeze(Object.prototype)` blocks a later property add — the two
  ungated branches in F6 are the exception, not the rule.
- **`harden` is an iterative, cycle-safe, metered worklist** that walks
  prototypes and accessor getters/setters (interp.rs:35718-35810) — the
  algorithm is right; only the mark timing (F2) and the exotic gap (F4) are
  wrong.
- **Named-skip discipline is widely and honestly applied**: `defineProperty` on
  the global object, dynamic `import`, `Intl.NumberFormat.formatRange`, direct
  eval in a function frame, and the whole module bytecode path all self-name
  rather than guess. `SideTable::Modules` is declared `Pending` rather than
  omitted.
- **Determinism discipline at the boundaries**: endowments seeded in id order
  (compartment.rs:296-306, locked by `tests/endowment_order.rs`), GC roots
  sorted and deduped, `BTreeMap`/`BTreeSet` throughout `module.rs`, boot
  allocation from fixed-order literals.
- **The id-space meet is a named refusal, not an alias** (interp.rs:35008-35018
  plus `tests/id_space_exhaustion.rs`) — the right instinct, applied to a hazard
  most engines get wrong; F11 is about the resource being unreclaimable, not
  about the latch.

## 4. Recommended architectural direction

**First, make untrusted input unable to kill the process.** F1 is the only
finding here that is fatal *by construction* rather than by a policy gap, and it
is cheap to fix: one recursion budget, decremented in every Rust-side recursive
descent (render, JSON, MOP/proxy chains, `to_primitive`, and the compiler's
parser/scoper/coder), surfacing as `Halt::StackOverflow`. Making it a counter
rather than a stack-headroom probe is what makes it deterministic across hosts,
which matters more here than in a normal engine. Until that lands, no amount of
`forbid(unsafe_code)` supports the claim that "untrusted JS cannot take down the
process".

**Second, decide what a realm is, before more surface accretes on `Interp`.**
Today `Interp` *is* the realm: it owns the global object, the property-id space,
the intrinsics, the symbol registry, the meter and the heap, and `Compartment`
is a wrapper that creates a new one per call. Requirement 5 needs the opposite
factoring — one intrinsics graph, many globals — and that factoring gets more
expensive with every side table added to the 165-field struct. The concrete step
is to extract a `Realm { global_obj, global_props, symbol_ids/symbol_names,
installed_names_len, source_compiler }` and let `Interp` hold a vector of them
with the intrinsic slots shared, then re-point `Compartment` at it. That also
gives F10 (attenuation) a place to live and turns the `Rc<Intrinsics>` marker
into the real thing. If the project instead decides one worker == one realm
forever, then `Compartment`, `Machine`, `Intrinsics` and `ModuleGraph` should be
removed from the public surface rather than left as a seam that certifies a
property it does not have — the current state misleads both embedders and
reviewers.

**Third, treat "integrity" as a property of the whole own-state model, not of
the property chain.** F2, F3 and F4 are three faces of the same design gap:
integrity is a flag byte on slot-chain records, while own state also lives in
`arrays`, `collections`, `typed_arrays`, `wrapper_data`, `FuncInfo` and the
global fast index — each of which has a write path that never consults the flag.
The fix that scales is a single per-instance integrity level (`extensible /
sealed / frozen`, plus the `hardened` mark) checked by *every* own-state write,
with the property-chain flags kept only as the descriptor-level detail; the
alternative (teaching each exotic write path about flags) is the same number of
edits with no invariant to test against. Once that exists, `harden` should be
made transactional (collect the reachable set, refuse before mutating, stamp on
completion) so it can never report success on a partially frozen graph, and
`lockdown` becomes implementable. A cheap mechanical guard for the whole class:
a test that, for each of ~20 representative object shapes, asserts
`Object.freeze(x)` ⟹ every write path leaves `x` unchanged and `Object.isFrozen(x)`
agrees — run over ordinary objects, arrays, functions, collections, typed
arrays, proxies, and `globalThis`.
