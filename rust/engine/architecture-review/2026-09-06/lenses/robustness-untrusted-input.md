# Lens: Robustness on untrusted input and resource exhaustion

HEAD 97d8de25, branch claude/ironhorse-architecture-review-bimf34. Every citation below
was read by me in the current tree.

## Assessment

IronHorse's safety story is built around one sentence in the design — "a panic is a
crashed crank, not a compromised daemon" (designs/ironhorse-engine.md:616-618) — and
`#![forbid(unsafe_code)]` makes that sentence true *for panics*. The problem is that the
two failure modes that actually matter for a shared-process supervisor are not panics.
A native Rust stack overflow is `SIGSEGV`/abort, and `handle_alloc_error` on a failed
`Vec` reservation is an abort; neither unwinds, neither is containable by
`catch_unwind`, and both kill the whole daemon. The engine has a *deterministic* budget
for the JS value stack (`STACK_SLOT_COUNT = 4096`, checked in `enter_call`) and one
native-recursion counter (`DISPATCH_REENTRY_LIMIT = 64`, interp.rs:11281) that covers
exactly one recursion family — re-entry through `dispatch_at`. Everything else recurses
on the native stack with no counter at all.

I confirmed at least seven distinct guest-reachable unbounded native recursions:
proxy-mediated prototype cycles in the MOP (`ordinary_get` ↔ `proxy_get`, and the cycle
is *deliberately permitted* by `prototype_chain_would_cycle` returning `false` at a
proxy, interp.rs:36623); `JSON.parse`; `JSON.stringify`; `Interp::render` over a cyclic
array — which runs at the host boundary, outside any crank, on the daemon's only result
path; the async-generator request drain (`kick_async_generator` ↔
`finish_async_generator_request`); the entire compile front end (parser, scoper, coder)
which a guest reaches through `eval`; and the regexp pattern compiler, which a guest
reaches through `new RegExp(s)` *and* which the lexer runs eagerly on every regexp
literal in eval'd source. None of these has a depth guard; `grep` for `depth|recursion`
across ironhorse-compile/src and ironhorse-regexp/src returns only unrelated hits. The
project already knows: CI sets `RUST_MIN_STACK=16777216` for the oracle lane with the
comment "the recursion depth is an engine property, not this lane's" (ci.yml:826-832),
and ironhorse-262 spawns a fresh large-stack thread per case because "a deeply-nested
source ... would overflow and SIGSEGV the whole batch (uncatchable by `catch_unwind`)"
(xst.rs:1371-1374). The hazard is documented and worked around at the harness, never
fixed at the engine. That also breaks the design's own consensus requirement that
"deterministic stack overflow is consensus-relevant" (design:886-887): the abort depth
is a function of host thread stack and build profile, not of a modelled budget.

The second structural failure is that the meter cannot bound anything in production.
`check_meter` returns `Continue` whenever `meter_host` is `None` (interp.rs:10752), and
nothing in `rust/endo` ever arms it — the seam calls `session.machine_mut().run(&bytecode)`
(ironhorse_engine.rs:572) with `step_limit == u64::MAX`. The dispatch loop's own comment
states the dependency plainly: the memory-wedge guard is "bounded mode ONLY (`step_limit`
is `u64::MAX` in production, which relies on the computron meter to bound allocation)"
(interp.rs:11326-11338). Production relies on a meter that production never arms. And
even a fully armed meter would not help inside a native: charges are *post-hoc* —
`build_regexp` runs `ironhorse_regexp::compile` to completion and then ticks
(interp.rs:20089-20107); `regexp_exec` runs the whole backtracking match and then ticks
`outcome.match_meter_raw` (interp.rs:20189-20191); `String.prototype.repeat` calls
`Vec::with_capacity(content.len() * count)` with `count` up to 2^31 (interp.rs:31218).
Metering check points exist only at the dispatch loop's closing points, so any single
native operation is unbounded in both time and memory.

Third: there is no GC pressure trigger and no heap ceiling. `collect_garbage` has zero
callers inside `ironhorse-vm/src` and zero in `rust/endo` — the only callers are two
snapshot tests. The design's GC-roots contract explicitly requires "collection fires on
allocation pressure at fixed thresholds" (design:918-921); that stage never landed. A
crank's arena growth is therefore O(total allocated), not O(live), while
`ChunkArena::alloc` narrows to `u32` (value.rs:1479-1483) with no ceiling.

There is real hardening here, and it is unevenly applied: the bytecode operand decoder is
genuinely total, the snapshot decoders are cursor-based with `checked_add`, strict
owner-ordering and cross-table typed-array geometry validation, `harden` is worklist-based
rather than recursive, arrays are sparse `BTreeMap`s so `new Array(1e9)` costs nothing,
and the typed-array-from-source path was rewritten to bound-and-charge *before*
allocating, with a comment that names the exact hazard ("`handle_alloc_error` ABORTS THE
PROCESS, which no `catch_unwind` can contain", interp.rs:18355-18361) and a deadline test
that locks the order. That fix is the model. It was never generalized into a rule, so the
same class remains open in `repeat`, `padStart`, `ArrayBuffer`, JSON and regexp.

Finally, the workspace sets no `[profile]` overflow-checks anywhere (verified: no
`[profile]` section in either `Cargo.toml`), so every guest-reachable integer overflow is
a debug panic in CI and a *silent wrap* in the shipped build — the worst split for a
consensus engine, because tests see the loud failure and validators see the quiet
divergence.

## Findings

### F1 (critical) — No engine-wide native recursion budget; `Halt::StackOverflow` covers one recursion family out of eight

**File:** rust/engine/ironhorse-vm/src/interp.rs:11281
**Other sites:** interp.rs:36206 (`ordinary_get`), interp.rs:37352 (`proxy_get`),
interp.rs:30548/30761/30804 (JSON parse), interp.rs:30336/30435/30474 (JSON stringify),
interp.rs:10945 (`render`), interp.rs:16886/16971 (async-generator drain),
ironhorse-compile/src/parser.rs:626, ironhorse-compile/src/scoper.rs:1130,
ironhorse-regexp/src/compile.rs:1531

**Claim:** `DISPATCH_REENTRY_LIMIT` bounds only recursion that passes through
`dispatch_at`, so at least seven other guest-reachable native recursions have no depth
counter and terminate by overflowing the thread stack (an uncatchable process abort),
at a depth that depends on host stack size and build profile.

**Evidence:**
```
pub const DISPATCH_REENTRY_LIMIT: usize = 64;
...
        if self.dispatch_depth >= DISPATCH_REENTRY_LIMIT {
            return Halt::StackOverflow(self.stack_slots_in_use());
        }
```
and CI's own admission (.github/workflows/ci.yml:826-832):
```
        # The regexp parity and unicode-sets suites recurse deeply in
        # debug builds ... overflowing the 2 MiB default test-thread stack.
        # ... the recursion depth is an engine property, not this lane's.
          RUST_MIN_STACK: '16777216'
```

**Impact:** A process-killing DoS lever from guest code in any deployment where the
engine shares a process with the supervisor — the design's stated target
(design:742). Also a determinism defect: design:886-887 requires stack-exhaustion
aborts to be bit-exact, and a native SIGSEGV depth is not a modelled quantity.

**Recommendation:** Introduce one `Interp`-level `native_depth` counter (and a
compile-crate/regexp-crate equivalent), incremented by a guard object at every
self-recursive entry — MOP get/set/has/delete/own-keys, JSON parse/serialize, `render`,
the async-generator drain, parser/scoper/coder dispatch, and regexp
`disjunction_parse`/`sequence_parse`. Exceed it ⇒ `Halt::StackOverflow` (VM) or
`Err(ParseErrorKind::…)` (compiler), never a native frame. Add a CI test per family that
drives the guard at the default 2 MiB stack, and delete `RUST_MIN_STACK` from ci.yml so
the guard, not the runner's stack, defines the bound.

**Novelty:** new (partially-known as an operational workaround at ci.yml:826 and
xst.rs:1371; never attributed as an engine defect; not in the store-seam ledger).

### F2 (critical) — A spec-legal proxy prototype cycle drives unbounded MOP recursion with zero JS frames

**File:** rust/engine/ironhorse-vm/src/interp.rs:36623
**Other sites:** interp.rs:36203-36220 (`ordinary_get` loop), interp.rs:37352 (`proxy_get`
trapless fallback)

**Claim:** `const t = {}; const p = new Proxy(t, {}); Object.setPrototypeOf(t, p); p.x;`
is accepted by the cycle check and then recurses `proxy_get → mop_get → ordinary_get →
proxy_get …` forever on the native stack, with `dispatch_depth` never incremented
because no JS frame is entered.

**Evidence:**
```rust
    fn prototype_chain_would_cycle(&self, inst: …, new_proto: …) -> bool {
        let mut p = new_proto;
        while !p.is_null() {
            if p == inst { return true; }
            if self.proxies.contains_key(&p) { return false; }   // cycle permitted
```
```rust
        let trap = match self.proxy_trap(code, handler, "get")? {
            Some(t) => t,
            None => return self.mop_get(code, target, id, receiver),   // recurse
        };
```
```rust
            if owner != inst && self.proxies.contains_key(&owner) {
                return self.proxy_get(code, owner, id, receiver);       // recurse
            }
```

**Impact:** Four lines of ordinary, spec-legal JavaScript abort the process. Reachable
from any untrusted guest that can build a Proxy — i.e. every SES compartment.

**Recommendation:** Bound the MOP with the F1 depth counter (the spec's own answer is
that the recursion terminates only because real engines have a stack-overflow
RangeError; IronHorse must produce a deterministic catchable RangeError or a
`Halt::StackOverflow` instead). Cover `[[Get]]`, `[[Set]]`, `[[HasProperty]]`,
`[[Delete]]`, `[[GetPrototypeOf]]` and `[[OwnPropertyKeys]]` — every one of them has the
same trapless-forwarding shape.

**Novelty:** new.

### F3 (critical) — Metering is fail-open at the deployment seam; the guard that would bound memory is documented as depending on it

**File:** rust/engine/ironhorse-vm/src/interp.rs:11326
**Other sites:** interp.rs:10748-10754 (`check_meter`), rust/endo/src/ironhorse_engine.rs:572

**Claim:** The daemon seam runs guest bytecode with no meter host and no step limit, so
`while(true){}` never terminates and every allocation guard that defers to the meter is
inert.

**Evidence:**
```rust
    fn check_meter(&mut self) -> MeterCheck {
        match self.meter_host.as_mut() {
            Some(host) => self.meter.check(host),
            None => MeterCheck::Continue,
        }
    }
```
```rust
            // Memory wedge guard, bounded mode ONLY (`step_limit` is
            // `u64::MAX` in production, which relies on the computron
            // meter to bound allocation). …
            if self.step_limit != u64::MAX
                && self.slots.live_count() >= BOUNDED_RUN_SLOT_CEILING
```
and the only production call site:
```rust
                let outcome = session.machine_mut().run(&bytecode);
```
(`grep -rn "arm_meter|rearm_meter|reattach_meter" rust/endo/src` → no hits.)

**Impact:** No time bound and no memory bound on a crank in the shipped engine binding.
The engine's entire resource-exhaustion story is delegated to a mechanism the embedder
never enables, and the code says so in its own comment.

**Recommendation:** Make the unmetered configuration opt-in and loud: have `Interp::run`
require either a meter host or an explicit `run_unmetered()` entry, and have
`PersistentMachine::eval`/`Machine::evaluate` arm a meter and a step ceiling by default
(the seam already surfaces `Halt::MeterAbort`, ironhorse_engine.rs:89, it just can never
be produced). Extend `BOUNDED_RUN_SLOT_CEILING` to a configurable production heap
ceiling rather than a fuzz-only guard.

**Novelty:** partially-known (digest lead "Daemon runs cranks with no meter limit";
the loop-comment dependency and the `check_meter` fail-open half are new here).

### F4 (high) — Guest-sized allocations are made before any bound or charge; `handle_alloc_error` aborts the process

**File:** rust/engine/ironhorse-vm/src/interp.rs:31218
**Other sites:** interp.rs:31367-31372 (`padStart`/`padEnd`), interp.rs:34411
(`alloc_array_buffer`), ironhorse-vm/src/value.rs:1479 (`ChunkArena::alloc`)

**Claim:** `"abcdefgh".repeat(2**30)` reserves a 16 GiB `Vec<u16>` and `"".padStart(2**40)`
reserves a ~2 TiB `Vec<u16>` with no maximum-string-length check and no `RangeError`, so
the allocation failure aborts the process instead of throwing.

**Evidence:**
```rust
                let mut out = Vec::with_capacity(content.len() * count as usize);
                for _ in 0..count { out.extend_from_slice(&content); }
```
```rust
                        } else if n.is_infinite() || n > usize::MAX as f64 {
                            return Err(self.catchable_range_error());
                        } else { n.floor() as usize }
                        …
                        let mut out = Vec::with_capacity(target);
```
The codebase names this exact hazard elsewhere (interp.rs:18355-18361):
```
                        // What that costs depends on the host and both outcomes are bad:
                        // where the reservation fails, `handle_alloc_error` ABORTS THE
                        // PROCESS, which no `catch_unwind` can contain; where
                        // overcommit lets it succeed, the worker stalls filling
                        // slots the meter never sees (measured: 132 seconds and
                        // 8.6 GB for a two-call program — review wave 5).
```

**Impact:** Process-killing DoS from a one-line guest program; under overcommit, a
multi-minute unmetered stall instead. This is a doctrine/implementation gap: the rule was
discovered and written down for one call site (typed-array-from-source) and never applied
to its siblings.

**Recommendation:** Introduce a single `Interp::reserve_units(n) -> Result<(), Halt>`
helper that (a) enforces a maximum string/buffer length (XS's 0x7FFFFFFF chunk ceiling is
already the constant used at interp.rs:34397) with a catchable `RangeError`, (b) charges
`tick_chunk_new` *before* the reservation, and (c) is the only way any built-in sizes a
buffer from guest input. Route `repeat`, `padStart`/`padEnd`, `join`, `String.raw`,
`Array.prototype.flat`, `alloc_array_buffer` and the JSON serializer through it. Add a
grep-style lint or a test-time audit forbidding raw `Vec::with_capacity` on a
guest-derived length in interp.rs.

**Novelty:** known-fixed-regressed in kind (the identical hazard was fixed at
interp.rs:18340 in review wave 5 and locked by tests/typed_array_source_length.rs);
new at these sites.

### F5 (high) — Regexp compile and match are unmetered until after they finish; catastrophic backtracking and case-fold expansion are unbounded

**File:** rust/engine/ironhorse-vm/src/interp.rs:20191
**Other sites:** interp.rs:20089-20107 (`build_regexp`), ironhorse-regexp/src/compile.rs:880-897
(case-insensitive range fold), ironhorse-regexp/src/matcher.rs:310/373/395 (state pushes),
ironhorse-compile/src/lexer.rs:1223 (eager compile of every regexp literal)

**Claim:** The meter is charged after `match_regexp` and after `compile` return, so
`/(a+)+$/.test("a".repeat(40)+"b")` runs to exhaustion with no abort point, and
`/[\u{0}-\u{10FFFF}]/i` performs 1,114,112 fold iterations each allocating two retained
AST nodes, all before a single computron is charged.

**Evidence:**
```rust
            ironhorse_regexp::match_regexp(program, subject, start_i)
        };
        self.meter.tick_raw(outcome.match_meter_raw);
```
```rust
        let program = match ironhorse_regexp::compile(&pattern, &flags) { … };
        …
        self.meter.tick_raw(program.compile_meter_raw);
```
```rust
            let mut ch = begin;
            while ch <= end {
                let canon = crate::charcase::canonicalize(ch as i64, fold) as i32;
                let single = self.add_node(Kind::CharSet { chars: vec![2, canon, canon + 1], … });
                result = self.charset_combine(result, single, MX_CHARSET_UNION_OP)?;
                ch += 1;
            }
```
and each backtrack state clones the capture vector:
```rust
                        states.push(State { step: sequel, offset, flags, captures: captures.clone() });
```

**Impact:** ReDoS is a full-process hang plus unbounded `Vec<State>` growth, not a metered
abort. The compile-side charge is proportional to the *output* code size, so a pattern
whose fold collapses to a small charset pays almost nothing for a million iterations of
work. Reachable from `new RegExp(untrusted)` and, via lexer.rs:1223, from any regexp
literal in `eval`'d source.

**Recommendation:** Thread a `&mut Meter` (or a step budget with an abort callback) into
`ironhorse_regexp::compile` and `match_regexp` so both can charge and check incrementally,
and give the matcher a hard state-stack ceiling. Charge the fold loop per code point, not
per output byte.

**Novelty:** new (the digest flagged the fold cost; the post-hoc-charge architecture and
the matcher's unbounded state stack are added here).

### F6 (high) — The u16 property-key id space is a monotone machine-lifetime budget; exhausting it permanently bricks the machine, and untrusted JSON exhausts it

**File:** rust/engine/ironhorse-vm/src/interp.rs:35006
**Other sites:** interp.rs:30829 (`JSON.parse` interns every distinct key),
interp.rs:32809 (`array_generic_index_id`), interp.rs:11351 (permanent halt latch),
interp.rs:10742 (`is_quiescent` refuses persistence forever)

**Claim:** `symbol_names` is append-only and never reclaimed by GC, so ~65,535 distinct
string property keys over a machine's entire lifetime — e.g. one
`JSON.parse` of an object with 65k distinct keys — sets `id_space_exhausted`, and every
subsequent crank halts with `Halt::Unsupported("property-key:id-space-exhausted")`
forever with no way to snapshot out.

**Evidence:**
```rust
    fn append_name_key(&mut self, name: &str) -> u16 {
        let next = self.symbol_names.len().saturating_add(1);
        if next >= self.next_symbol_key_id as usize {
            self.id_space_exhausted = true;
```
```rust
            if self.id_space_exhausted {
                return Halt::Unsupported("property-key:id-space-exhausted");
            }
```
```rust
            let id = self.intern_key(&key);      // json_parse_object, per distinct key
```
(`grep -n symbol_names interp.rs` shows only `push`, `resize`, `clone` — no removal; the
sweep never prunes it.)

**Impact:** A single untrusted message payload permanently and irrecoverably disables a
vat. The latch is correctly fail-closed (no id aliasing, no wrong answer), but the
availability consequence is total and the budget is a *lifetime* budget, not a
working-set one, so even benign long-running vats that mint distinct keys (uuids, per-
message ids) will eventually hit it.

**Recommendation:** Either (a) reclaim key ids at GC — walk live property ids, compact
`symbol_names`, and remap — which requires the id→name table to be a snapshot-versioned
mapping rather than a positional one; or (b) widen the runtime key space beyond u16 with
a distinct id representation for runtime-interned keys, keeping the compiler's u16 space
for bytecode operands only; or (c) at minimum, refuse the *offending operation* with a
catchable `RangeError` at a soft threshold instead of poisoning the machine, so the vat
survives a hostile payload. Add a fuzz/regression case that feeds 100k-key JSON through
the seam.

**Novelty:** partially-known (the latch itself is a wave-6 item and
tests/id_space_exhaustion.rs exists); the JSON.parse reachability and the
never-reclaimed-lifetime-budget framing are new.

### F7 (high) — No allocation-pressure GC and no heap ceiling anywhere in the VM; chunk offsets narrow to u32 without a bound

**File:** rust/engine/ironhorse-vm/src/value.rs:1479
**Other sites:** interp.rs:43707 (`collect_garbage`, no in-crate caller),
designs/ironhorse-engine.md:913-921 (the unmet contract)

**Claim:** `collect_garbage` has zero callers in `ironhorse-vm/src` and zero in
`rust/endo`, so arena growth within a crank is O(total allocated) rather than O(live),
and `ChunkArena::alloc` writes a `u32` length header and a `u32` offset with no arena
ceiling.

**Evidence:**
```rust
        let v = self.bytes_mut();
        v.extend_from_slice(&(data.len() as u32).to_le_bytes());
        let off = v.len() as u32;
```
Design contract (designs/ironhorse-engine.md:918-921):
```
The trigger points must also be deterministic (collection fires on
allocation pressure at fixed thresholds), so that within an Ironhorse
release collection scheduling cannot perturb the meter
```

**Impact:** A crank that allocates and discards (string concatenation in a loop, repeated
`JSON.parse`) grows the process without bound until the OS OOM-kills the daemon. Past
2^32 arena bytes, offsets and length headers wrap and the heap is silently corrupt.

**Recommendation:** Land the deferred stage: fire `collect_garbage` from `alloc` at fixed
deterministic thresholds (the design already requires the thresholds be a pure function
of the release so the meter is not perturbed), and refuse an allocation that would take
the arena past a configured ceiling with a catchable `RangeError`. Add a `debug_assert`
plus a hard check that `v.len()` stays below `u32::MAX` in `ChunkArena::alloc`.

**Novelty:** partially-known (the design records it as a deliberate stage-2 deferral with
a MUST for whichever stage wires it; still open at graduation).

### F8 (high) — Guest-triggerable panics from `&str` slicing at non-char boundaries in the date/duration parsers

**File:** rust/engine/ironhorse-vm/src/interp.rs:39623
**Other sites:** interp.rs:40802 (`parse_temporal_duration`)

**Claim:** `Date.parse("2020-01-01T00:00:00.éé")` panics with "byte index 3 is not a char
boundary" and `Temporal.Duration.from("P1é")` panics with "byte index 2 is not a char
boundary", because both slice guest text at byte offsets derived from ASCII assumptions.

**Evidence:**
```rust
        if !fraction.is_empty() {
            let digits = &fraction[..fraction.len().min(3)];
```
(`fraction` is whatever followed `.` in the guest string; `"éé"` is 4 bytes and index 3
is mid-character.)
```rust
        let end = rest.find(|c: char| !(c.is_ascii_digit() || c == '.'))?;
        …
        let designator = rest.as_bytes().get(end).copied()? as char;
        rest = &rest[end + 1..];
```
(`end` is a char boundary but `end + 1` is not when the designator is multi-byte.)

**Impact:** A crashed crank from a one-argument built-in call on an attacker-supplied
string. Tolerable in isolation but it is the loud half of a class: everywhere the code
reasons about a guest string in bytes while holding a `&str`.

**Recommendation:** Parse both on `&[u8]` (or `char_indices`) rather than mixing. For the
fraction, take `fraction.chars().take(3)` and reject a non-digit; for the designator,
advance by `designator.len_utf8()`. Add a fuzz target for `Date.parse` /
`Temporal.*.from` over arbitrary UTF-8 — the design's fuzz target 4 (UTF-8⇄UTF-16
boundary) is absent and every existing generator is ASCII-only, which is exactly why this
survived.

**Novelty:** new.

### F9 (high) — A wrapped numeric backreference yields a negative capture index that indexes `names[usize::MAX]` in the matcher




```rust
                        if e < 0 {
```

**Impact:** A crashed crank from `new RegExp(untrustedPattern)` plus one `.test()`. In the

### F10 (high) — No `overflow-checks` profile: every guest-reachable integer overflow is a debug panic and a release silent wrap

**File:** rust/engine/Cargo.toml:1 (no `[profile]` section anywhere in the repo)
**Other sites:** interp.rs:40866 (`era * 146097` in `days_from_civil`),
ironhorse-vm/src/intl_number.rs:518-529, ironhorse-vm/src/meter.rs (unchecked
`untick_code`/`untick_raw`), ironhorse-compile/src/lexer.rs:308

**Claim:** `new Date(1e17, 0)` and
`new Intl.NumberFormat('en',{roundingIncrement:5,minimumFractionDigits:2,maximumFractionDigits:2}).format(1e300)`
panic in debug and produce silently wrong values in release, because neither profile sets
`overflow-checks` and neither site uses checked arithmetic.

**Evidence:** (`grep -rn "overflow-checks|\[profile" --include=Cargo.toml` → no matches.)
```rust
    let era = if y >= 0 { y } else { y - 399 } / 400;
    …
    Some((era * 146097 + doe - 719468) as i128)
```
`date_from_components` bounds `year` only by `i64::MIN..=i64::MAX` (interp.rs:39587-39589),
so `era` reaches ~2.3e16 and `era * 146097` exceeds `i64::MAX`.
```rust
    let mut n: u128 = 0;
    for &d in &integer.digits { n = n * 10 + d as u128; }
    …
        for _ in 0..extra.max(0) { n *= 10; }
```
with the comment `// Turn integer into a u128 (values in these tests stay well within range).`

**Impact:** The split is the worst case for a consensus engine: CI (debug) sees a loud
panic and validators (release) see a quiet wrong answer. Two IronHorse nodes built with
different profiles would disagree on `new Date(1e17,0)`.

**Recommendation:** Set `overflow-checks = true` for `[profile.release]` in
`rust/engine/Cargo.toml` and in the root workspace for the engine crates — this is a
consensus engine, and the cost of a checked add is small against a divergence. Then fix
the sites so the check is a *deterministic refusal* (`NaN`/`RangeError`) rather than a
panic: bound `norm_year` to the proleptic-Gregorian range representable in i64 days
before calling `days_from_civil`, and do the `intl_number` digit accumulation in a
big-decimal path or bound `extra`.

**Novelty:** new as a profile-level claim; the individual overflow sites are digest
leads I confirmed.

### F11 (high) — Symbol-id truncation at 65,535 in both the compiler and the linker yields a silently wrong program instead of a refusal

**File:** rust/engine/ironhorse-compile/src/coder.rs:298
**Other sites:** coder.rs:307 (`count = used.wrapping_add(1)`), coder.rs:5787
(`symbol_id(c, sym_ids) as u16`), ironhorse-vm/src/interp.rs:7310
(`let id = (k + 1) as u16`), ironhorse-vm/src/symbols.rs:23 (count field ignored)

**Claim:** A source with more than 65,535 emitted symbols — reachable through `eval` of a
few hundred KB of generated JS — compiles "successfully" to bytecode whose 2-byte symbol
operands collide, and the VM binds the resulting SYMB table with `(k + 1) as u16` so id
65,536 becomes 0 (`XS_NO_ID`), with no refusal at either end.

**Evidence:**
```rust
                if e.usage {
                    used = used.wrapping_add(1);
```
```rust
        let count = used.wrapping_add(1);
```
```rust
        for (k, name) in names.iter().enumerate() {
            let id = (k + 1) as u16;
            self.symbol_ids.entry(name.clone()).or_insert(id);
        }
```
and the decoder deliberately ignores the count:
```rust
    // The leading 2-byte count is `distinct + 1` … we read strings to the
    // buffer end rather than trusting the count, so a short or malformed
    // buffer degrades to fewer names rather than panicking.
```

**Impact:** Not a DoS but worse for this engine's purpose: a silently wrong program.
Guest-reachable via `eval`, and the AGENTS.md numeric-domain rule ("narrowing a wider
domain must fail, not truncate") is violated in the consensus-critical direction.

**Recommendation:** Make both narrowings fallible: `u16::try_from(next)` in the coder with
a `ParseErrorKind` on overflow, and a refusal (not a wrap) in `bind_program_symbols` when
`names.len() >= u16::MAX as usize`. Have `parse_symbols` validate the count field against
the number of strings decoded and return `Err` on disagreement rather than degrading.

**Novelty:** partially-known (digest leads at coder.rs:298 and interp.rs:7310); the
end-to-end compiler→linker chain and the `parse_symbols` count-ignoring half are joined
here.

### F12 (medium) — The bytecode dispatch loop is fail-open on value-stack underflow

**File:** rust/engine/ironhorse-vm/src/interp.rs:10853

**Claim:** `pop()` on an empty stack returns `undefined` instead of halting, so malformed
or mis-compiled bytecode keeps executing with fabricated operands and can complete with a
rendered result, even though every *operand-length* error is a `Halt::Decode`.

**Evidence:**
```rust
    fn pop(&mut self) -> Slot {
        self.stack.pop().unwrap_or_else(Slot::undefined)
    }
```
Contrast the operand decoder immediately above the match (interp.rs:11390):
```rust
            if pc + ilen > len {
                return Halt::Decode(format!("opcode {} at {} needs {} bytes, {} left", …));
            }
```

**Impact:** The design names "the bytecode loader/decoder must never panic on corrupt
input" (fuzz target 2) as a bar; the loop meets it by being total, but totality here is
achieved by *inventing* a value, which converts a corrupt-bytecode detection into a wrong
answer. For store-resumed bytecode this is a silent-wrong-state path.

**Recommendation:** Return `Halt::Decode("stack underflow at pc N")`. Where XS genuinely
tolerates an under-full stack (if anywhere), name the opcode explicitly rather than making
underflow the global default. There is currently no test in `ironhorse-vm/tests` that
feeds malformed or truncated bytecode to the decoder — the target lives in
`ironhorse-fuzz`, which cannot build without the C oracle, so this surface has no
oracle-free regression in PR CI.

**Novelty:** partially-known (digest lead at interp.rs:10855).

### F13 (medium) — Async-generator request drain is unbounded mutual recursion

**File:** rust/engine/ironhorse-vm/src/interp.rs:16971

**Claim:** `kick_async_generator` and `finish_async_generator_request` call each other once
per queued request with no depth counter, so queuing N `.next()` calls on an
already-completed async generator produces N native frames.

**Evidence:**
```rust
        self.settle_via_function(…)?;
        self.kick_async_generator(code, gen)
    }
```
and, in `kick_async_generator`:
```rust
            AsyncGeneratorState::Completed => match request.status {
                GenStatus::Next => {
                    let result = self.new_generator_result(Slot::undefined(), true);
                    self.finish_async_generator_request(code, gen, result, false)
                }
```
Neither function touches `dispatch_depth`, so `DISPATCH_REENTRY_LIMIT` does not apply.

**Impact:** `for (let i = 0; i < 1e6; i++) g.next();` on a completed async generator is a
guest-controlled native stack depth. The frames are small (unlike `dispatch_at`), so the
depth needed is large but well within a loop's reach; whether LLVM turns the tail call
into a jump is build-dependent, which is itself the determinism problem from F1.

**Recommendation:** Rewrite the drain as an explicit `while let Some(request) =
…requests.pop_front()` loop rather than a tail call, and count it under the F1 native
depth budget.

**Novelty:** new (digest lead confirmed in code; not in the ledger).

### F14 (medium) — `render()` is an unguarded recursive walk on the host boundary, outside any crank, meter or halt

**File:** rust/engine/ironhorse-vm/src/interp.rs:10945

**Claim:** `Interp::run`'s result renderer recurses over array elements with no depth or
cycle guard, so a crank whose completion value is a self-containing array
(`var a=[]; a[0]=a; a`) overflows the native stack after the crank has already halted.

**Evidence:**
```rust
                    for i in 0..a.length {
                        if i > 0 { out.push(','); }
                        if let Some(item) = a.items().get(&i) {
                            if item.kind != Kind::Undefined && item.kind != Kind::Null {
                                out.push_str(&self.render(item));
```

**Impact:** Worse than an in-crank abort: the failure happens on the path that produces
`RunOutcome`, after the meter has stopped mattering, and it is the only result path the
daemon seam uses (`ironhorse_engine.rs:572`). Also a memory amplification — a
`String` proportional to the rendered graph is built with no cap.

**Recommendation:** Give `render` a visited set (the spec's `Array.prototype.join` cycle
behaviour that real engines implement) and a depth + output-size cap, returning a
truncated marker rather than recursing. Better: stop rendering guest values to a `String`
at the engine boundary at all — the oracle-shim coercion baked into `run` is separately
flagged by other lenses.

**Novelty:** partially-known (digest lead at interp.rs:10945; confirmed).

### F15 (medium) — Snapshot `ABUF` length is validated against the arena, not against the chunk's own header, and `slice_mut` is arena-bounded

**File:** rust/engine/ironhorse-snapshot/src/image.rs:3583
**Other sites:** ironhorse-snapshot/src/image.rs:1372-1400 (`decode_buffers` does not see
the arena), ironhorse-vm/src/value.rs:1529 (`ChunkArena::slice_mut`)

**Claim:** A crafted image can declare an `ArrayBuffer` whose `length` exceeds the stored
chunk header at its `data` offset; the bounds gate only checks `data + length <=
chunk_len`, so restore succeeds and typed-array writes deterministically overwrite
neighbouring chunks (other strings, BigInts, buffers).

**Evidence:**
```rust
    for b in buffers {
        owned(b.owner)?;
        if b.data == u32::MAX
            || (b.data as usize) < CHUNK_HEADER
            || b.data as u64 + b.length as u64 > chunk_len as u64
        { return Err(OOC); }
    }
```
(no comparison to `ChunkArena::len_of(b.data)`), and:
```rust
    pub fn slice_mut(&mut self, off: ChunkOffset, len: usize) -> &mut [u8] {
        let start = off.0 as usize;
        …
        &mut self.bytes_mut()[start..start + len]
    }
```

**Impact:** Not memory-unsafe (Rust bounds-checks the arena), but it is silent cross-object
state corruption on resume from an image the host does not fully trust, and it breaks
`ChunkArena::compact`'s assumption that live blocks do not overlap.

**Recommendation:** Validate `b.length == chunk_len_of(b.data)` (or `<=`) at the gate, and
add a whole-arena chunk-chain walk that proves the header lengths tile the arena without
overlap — the gate already walks the arena for offsets, so this is one more pass. Add a
`debug_assert` in `slice_mut` that `off + len <= off + len_of(off)`.

**Novelty:** partially-known (the ledger records "BLOC block lengths are never validated
at the gate" as an open limitation for string/BigInt chunks; the ABUF/`slice_mut`
write-side consequence is new).

## Strengths

- **`#![forbid(unsafe_code)]` is real and universal** across every engine crate
  (ironhorse-vm/src/lib.rs:1, ironhorse-compile:16, ironhorse-snapshot:1,
  ironhorse-regexp, ironhorse-262, ironhorse-fuzz), with the FFI oracle explicitly and
  honestly excluded. Every one of the index errors above is a bounded panic rather than
  memory corruption. That is exactly what the design bought, and it delivered it.
- **The bytecode operand decoder is genuinely total.** `instruction_len` bounds the whole
  instruction, the loop re-checks `pc + ilen > len` before every operand read
  (interp.rs:11390), and an unknown opcode byte is a named `Halt::Decode`. This is
  careful work.
- **The one native-recursion guard that exists is deterministic and well-argued.**
  `DISPATCH_REENTRY_LIMIT`'s 20-line doc comment (interp.rs:186-205) reasons correctly
  about `dispatch_at`'s activation size and cites the issue that produced it. The problem
  is scope, not quality.
- **The typed-array-from-source fix is the right pattern, fully executed**: read the
  length, bound it, charge for it, *then* allocate — with the hazard named in the comment
  and a deadline test (`tests/typed_array_source_length.rs`) that locks the ordering
  (interp.rs:18340-18375). If generalized, it closes F4 entirely.
- **`harden` is worklist-based, not recursive** (interp.rs:35746-35760), with the visited
  mark applied at enqueue so a cyclic object graph terminates. A deeply nested object
  graph does not blow the stack here.
- **Arrays are sparse `BTreeMap`s** (bulk.rs:121), so `new Array(2**31-1)` and
  `a.length = 1e9` cost nothing — the obvious length-amplification attack is structurally
  absent.
- **The id-space exhaustion path is fail-closed, not aliasing**: `append_name_key`
  latches, the dispatch loop halts before the next instruction, and `is_quiescent` keeps
  the poisoned machine out of the persist gate. The availability consequence (F6) is
  severe, but the *correctness* choice is the right one.
- **The snapshot decoders are the best-hardened code in the tree**: cursor-based with
  `checked_add`, strictly-ascending owner enforcement, non-canonical flag-bit refusal,
  free-slot ownership refusal, and cross-table typed-array geometry validation done "here
  where all three tables are in hand". The reviewers' prior waves clearly landed.
- **The team knows this failure class.** ci.yml:826-832, xst.rs:1371-1374,
  interp.rs:18355-18361 and interp.rs:11326-11338 are all accurate, self-aware
  descriptions of exactly the hazards above. The gap is between diagnosis and
  generalization, which is a much easier gap to close than an unrecognized one.

## Recommended architectural direction

**1. Make "no uncatchable termination" an engine invariant with a mechanism, not a
doctrine.** The design's safety sentence ("a panic is a crashed crank") should be
restated as: *no guest input may terminate the process by any means other than a
`Halt`.* That has two mechanisms. First, a single `native_depth` budget threaded through
every self-recursive function in the VM and mirrored in the compile and regexp crates —
one RAII guard type, incremented at ~10 entry points, yielding `Halt::StackOverflow` or a
`SyntaxError`. Second, an `Interp::reserve(n)` chokepoint that is the only way a built-in
sizes a buffer from guest input, enforcing a length ceiling and charging before
allocating. Both are small, mechanical, and testable at the *default* 2 MiB stack —
deleting `RUST_MIN_STACK` from ci.yml should become the acceptance test for the first,
and a `Vec::with_capacity`-on-guest-length audit the acceptance test for the second.
Until then, `#![forbid(unsafe_code)]` buys memory safety but not availability, and the
design's own "consensus-relevant deterministic stack overflow" claim (design:886) is
false: the abort depth is a property of the runner, not the release.

**2. Close the loop between the meter and the seam, and move check points inside the
natives.** Today the meter is armed by nobody, and where it is charged it is charged
after the work. The fix has an ordering: make an unmetered `Interp` an explicit,
awkward-to-reach configuration (rename `run` to `run_unmetered` and require a meter host
or a step ceiling for the ordinary entry); arm it in `PersistentMachine`/`Machine`; then
push abort points into the three natives where a single call can dominate a crank —
regexp match (per-step budget), regexp compile (per-fold-iteration budget), and the
buffer-sizing chokepoint from (1). `BOUNDED_RUN_SLOT_CEILING` should stop being
fuzz-only and become a configured production heap ceiling; and the deferred
allocation-pressure GC (design:913-921) needs to land, because without it the meter
bounds *work* but not *residency*, and residency is what OOM-kills a daemon.

**3. Set `overflow-checks = true` in release and turn the fuzz corpus toward the
untrusted-input boundaries that have no coverage.** A consensus engine that wraps
silently in the shipped profile while panicking loudly in CI has inverted its own
verification. Beyond the profile, the coverage gaps are specific and match the findings
exactly: no fuzz target ever emits a non-ASCII code unit (which is why F8 survived), no
target feeds malformed bytecode from a crate that builds without the C oracle (F12), no
target feeds a hostile regexp *pattern* to the compiler with a bounded stack (F5, F9),
and no target drives an untrusted JSON payload through the id-space budget (F6). Each of
those is a small pure-Rust target that can run in PR CI without the oracle — which
matters, because the oracle submodule is the reason four of nine existing targets are
unreachable in this environment at all.
