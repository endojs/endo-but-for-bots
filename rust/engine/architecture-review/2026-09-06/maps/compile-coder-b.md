## Purpose and responsibilities

This half of `coder.rs` is the back end of the pure-Rust XS compiler port
(`ironhorse-compile`): it walks the scoper's annotated AST (`ScopeTree`) and appends
`Code` records (opcode id, stack delta, payload) in exactly the order XS's `xsCode.c`
does, then `serialize_atoms` (5454) runs `fxCoderOptimize` (5357) and `fxParserCode`'s
three passes (size-widest / choose-widths / emit) to produce the `codeBuffer` bytes and
the `SYMB` atom. Its only contract is **byte identity with the XS oracle** (Design
Decision 4): node shapes, operand widths, branch displacements, temporary-slot numbering
and symbol-id order all leak into the bytes, so every function here is a transliteration
of a named XS function, cited in its doc comment.

The tests in scope are (a) the curated byte-identity fixture file (~110 `#[test]`s, each a
list of programs compiled on both engines), (b) two whole-corpus smoke tests (parser
accept/reject agreement, scoper totality) over the 1,711 programs recovered from the
`test/ironhorse/` test262 tree, and (c) a parse-meter determinism test.

## Architectural observations

**Error model / API boundary.** The coder has a structured code-time error channel
(`Coder::error`, 434–442, surfaced at 954/992) and the parser has a
`ParseErrorKind::Unsupported` variant (262 lib.rs:65), yet every "deferred" (unported)
construct in this range is a `panic!`/`assert!`: 2958–2961 and 2997 (`static { }` block
with lexical declarations — valid ES2022), 3149–3153 (function-scope declare kinds),
3503–3506 / 3510–3513 (parameter declare kinds), 3938–3945 (parameter patterns), 3130,
3817, 4364, 4958, 4960, 4973. The consequence is that *panic-safety is outsourced to the
caller*: three separate consumers independently wrap `compile` in `catch_unwind`
(262 lib.rs:56, compile_diff.rs:24/323–329, fuzz lib.rs:1952), README 2201–2204 and
2884–2885 document this as the norm, and the VM's runtime `eval`/`Function` path is only
panic-safe if whoever implements `SourceCompiler` remembers to do the same. Under the
design's own error model (interp.rs:63–76) these should be `SourceCompileError::
Unsupported` returned, not panics caught.

**Determinism.** This range is clean: no `HashMap`/`HashSet` iteration (the `HashSet` at
3390 and the `brand_slot` map at 2900 are used via membership/`entry` only), no float
formatting (the `NUMBER` payload is written as raw `to_le_bytes` at 5749), no host time,
env, or randomness. The tagged-template cache symbol counter (`generate_tag` 493) is a
plain in-order `i32`. Symbol-id order comes from `symbols.assign_ids()` (region A).

**Hidden state / implicit protocol.** Six "staged hint" registers on `self` are set by
one method and consumed by a later, structurally unrelated dispatch: `pending_name`
(set 2409/2464/2564/4772/4947, consumed 3181 and in `code_class`), `pending_accessor`
(set 2747/2789/4348/4358, consumed by `mem::take` at 3197), `tail` (set 4113/4155,
consumed at 1021), `no_value`, `chain_target`, `class_instance_init` (3252). The
regression pinned by `named_class_with_heritage_names_constructor` (test 2014–2033: a
heritage `function(){}` consumed the class's pending name) is exactly the failure mode of
this design; XS avoids it by writing the name into the node before coding. Correctness
depends on every intermediate node either not consuming or explicitly saving/restoring
the register (as `code_chain` does at 4142–4147).

**AST identity by address.** `node_key` is a raw pointer cast. `scope_of` `expect`s a
registration (700–701), but `resolution_of` (501–503) returns `None` for an unregistered
address — i.e. a cloned or re-materialized node would silently take the *symbol path*
(`GET_VARIABLE`/`SET_VARIABLE`) and emit different bytes rather than panic. The comment at
5114–5115 ("cloning would miss registrations") shows the authors know the seam is fragile;
nothing enforces it.

**Panics/unwraps on untrusted-adjacent data.** The coder consumes the parser's AST, not
raw source, so most `expect`s encode parser/scoper invariants (4157/4183 Option-in-Chain,
4207 private resolution, 3388 alias target, 3261 instanceInit alias). The
externally-reachable panics are the deferred-construct folds above. `bigint_limbs_le`'s
`expect` (5839) is safe because the lexer strips separators (lexer.rs:29, 744–746).
`code_object_binding_assign` indexes `items[regular_end]` (3822) on the strength of
`flags::SPREAD ⇔ a trailing RestBinding` — a parser invariant, unchecked here.

**Silent truncation in emit.** `emit_step` casts every operand to its chosen width
without asserting fit: branch displacements `as i8`/`as i16` (5711, 5718), fixed 1-byte
operands `index_value(c) as u8` (5733) for `ARGUMENT`/`ARGUMENTS*`/`BEGIN_*`/`MODULE`,
string lengths (5754, 5760). Pass 2's `delta` bookkeeping (5634–5645) is a faithful port,
but if it ever disagreed with XS the result would be a wrong branch target handed to the
VM decoder, not a compile error; there is no `debug_assert!` anywhere in the serializer.

**Performance architecture.** `optimize` (5357–5437) does a linear `target_pos` scan
(5440–5444) per `BRANCH_1` and `Vec::remove` (5395, 5413, 5429) per rewrite, so the
peephole passes are O(n²) in records for a large function body; XS runs the same passes
over a doubly-linked list with direct `txTargetCode*` pointers in O(n). For SES/endo
bundles compiled in-worker (hundreds of KB of one program) this is a compile-latency
risk that the byte-identity tests cannot see.

**Duplication (inherited from XS).** The iterator-close protocol is hand-unrolled four
times in this range alone (array pattern 3595–3641, array-literal spread 4393–4422,
call spread 4620–4647, plus `code_for_in_of` in region A), and the try/finally
selector/alias/finalize/jump machinery is instantiated twice (3575–3739, 5196–5280).
`count_parameters` (2600) and `count_binding_items` (3907) compute two different
parameter counts for two opcodes. `scope_code_using` returns a bare `(i32, i32, usize)`
context tuple threaded through `code_body` 3981–3983, `code_switch` 5102–5147, and
`code_catch` 5163–5186.

**Stale stub.** `node_code_name` (5992–5998) is hard-coded `false` with a comment saying
function/class nodes "are not in the ported surface" — they have been ported for many
stages. It gates the `XS_CODE_NAME` emission for `x ||= function(){}` /
`x ??= class {}` (4832–4839); no fixture exercises a function/class value on the right of
a short-circuit assignment (tests cover only `x&&=1`, `x||=2`, `x??=3`, `a.b||=c` at 619).

**Dead code.** `serialize_atoms` pass 1 has a `match` whose only arm is a no-op
(5461–5468) immediately before the real `size1_step` call.

**Test methodology.**
- Byte identity is hand-curated fixtures (≈700 programs) whose oracle side *executes*
  the program (`xs_oracle::run`), so every script fixture must terminate (test 513–517);
  module fixtures are compile-only via `xs_oracle::compile_module` (1762–1812). Scripts
  compile as an *eval program* (`flags::EVAL` forced at 941–943), so the oracle shim's
  goal is what is pinned, not the plain Script goal.
- Only bytecode is compared here (`compile`, not `compile_atoms`); the SYMB atom's
  identity is locked in ironhorse-262 (`corpora_symbols_atom_byte_identity`,
  compile_diff.rs:734). Fine, but the compile crate's own tests would pass with a broken
  atom.
- Coder *totality over the corpus* is not locked in this crate (parse and scope smokes
  exist; there is no `corpus_code_smoke`). It is covered by 262's `compile_diff`, where a
  coder panic is a bar-violating `IronhorseRejected` (compile_diff.rs:38–41, 269–275).
- Oracle rejection is inferred by substring-matching `"SyntaxError"` in the runtime error
  string (test 164–167; smoke 42–44). compile_diff.rs:232–254 had to add a byte-identity
  recovery for the runtime-`SyntaxError`-from-`eval` false positive; the two in-crate
  tests did not.
- Width-family coverage: `wide_operands_and_branch_widths` (1310–1320) forces
  `INTEGER_2/4` and one `BRANCH_2`; nothing forces `BRANCH_4`, `STRING_2/4`,
  `RESERVE_2`/`GET_LOCAL_2`/`STORE_2` (>255 slots), `BIGINT_2`, or `RUN_2`.
- `parse_meter_determinism` asserts the release string and intra-process repeatability
  only; no golden computron values, so the "frozen table" can drift silently within
  `ironhorse-meter-0`.
- All compile-crate tests need the oracle and therefore run only in the oracle CI job
  (census: `RUST_MIN_STACK=16777216 cargo test -p ironhorse-compile …`), not in the
  PR-default `test-ironhorse` job.

## Candidate findings

Ordered most architecturally significant first. Confidence noted where I could not run
the oracle.

1. **Deferred constructs panic instead of returning a structured `Unsupported` error**
   — `rust/engine/ironhorse-compile/src/coder.rs:2997` (also 2958–2961, 3149–3153,
   3503–3506, 3510–3513, 3938–3945). Claim: `ironhorse_compile::compile("class C {
   static { let x = 1; } }")` panics rather than returning `Err`, so panic-safety of the
   VM's runtime `eval`/`Function` path depends on each `SourceCompiler` implementer
   wrapping the call in `catch_unwind`. Evidence:
   `panic!("static block with lexical declarations deferred");` (2997);
   `/// … ironhorse's coder is infallible, so it records the first here` (435–436);
   `let compiled = std::panic::catch_unwind(std::panic::AssertUnwindSafe(move || {`
   (ironhorse-262/src/lib.rs:56). Why it matters: the design's own seam already defines
   `SourceCompileError::Unsupported` for "an unported-but-valid construct, or a coder
   panic" (interp.rs:73–75); pushing the classification to the boundary by returning it
   would make the crate total, remove three duplicated `catch_unwind` wrappers, and stop
   a guest-supplied valid program from being able to unwind through whatever production
   host eventually implements the trait. Category: error-model. Severity: high.
   Confidence: high (panic sites read; `static {}` with `let` is valid ES2022).

2. **Parse-smoke treats "ironhorse accepts, oracle rejects" as benign, contradicting the
   design and the 262 bar** — `rust/engine/ironhorse-compile/tests/corpus_parse_smoke.rs:63`
   (also 83–85, 107–109, 114–118). Claim: the test cannot fail when the ironhorse parser
   accepts a program XS rejects. Evidence: `// The benign direction (we accept, oracle
   rejects) — recorded, not fatal.` (63); `(true, false) =>
   ironhorse_accepted_oracle_rejected.push(...)` (83–85) with no assertion on it. Why:
   design § test262 says a case Ironhorse passes that XS fails "is a semantic divergence …
   never a silent improvement", and ironhorse-262's `CompileReport::met_bar` counts the same
   direction as a bar violation (compile_diff.rs:42–44, 76–78); the two harnesses disagree
   on what the bar is. Category: verification. Severity: medium.

3. **Peephole optimizer is quadratic in code size** — `coder.rs:5440` (`target_pos`),
   used per `BRANCH_1` at 5368; `Vec::remove` at 5395, 5413, 5429. Claim: `optimize()` runs
   in O(records × branches) time, so compile time of a single large function body grows
   superlinearly, unlike XS's O(n) linked-list passes. Evidence:
   `fn target_pos(&self, tid: usize) -> Option<usize> { self.codes.iter().position(…)`
   (5440–5444); `self.codes.remove(i); continue;` (5395). Why: the engine compiles SES
   bundles and eval'd sources inside a metered worker; a compile-latency cliff on large
   inputs is a performance-envelope risk invisible to byte-identity tests. Category:
   performance. Severity: medium. Confidence: high on the complexity, unmeasured on
   impact.

4. **Emit-time operand casts wrap silently; no fit assertion after width selection** —
   `coder.rs:5711` (also 5718, 5733, 5754). Claim: if pass 2 ever chose a too-narrow
   branch width, `emit_step` would emit a wrapped displacement and the VM would receive
   a wrong-target branch instead of the compiler failing. Evidence:
   `out.push(offset as i8 as u8);` (5711); `out.extend_from_slice(&(offset as i16).to_le_bytes());`
   (5718); no `debug_assert!` in 5699–5796. Why: the `delta` bookkeeping at 5634–5645 is
   the single most intricate piece of the port and is fixture-tested only at `BRANCH_2`
   (test 1314–1319); a cheap `debug_assert!(i8::try_from(offset).is_ok())` would convert
   a latent miscompile into a deterministic panic. Category: robustness. Severity:
   medium. Confidence: high that the guard is absent; no evidence of an actual
   miscompile.

5. **`node_code_name` is a hard-coded `false` stub with a stale comment; `x ||=

6. **Parse-meter "frozen per release" is not actually locked — no golden values** —
   `rust/engine/ironhorse-compile/tests/parse_meter_determinism.rs:44` (also 49–63).

## What is done well

- **Faithful, well-cited transliteration.** Every coder method names the XS function it
  ports and the fixture that pinned it (e.g. 3018–3026, 3854–3879, 3964–3969,
  3987–3998); the doc comments record *why* XS behaves as it does, not just what, which
  is unusually good for a byte-identity port.
- **Determinism hygiene in this range is clean.** No collection iteration order, float
  formatting, host time, or randomness reaches the byte stream; the two hash containers
  are used for membership only (3390, 2900).
- **Regression fixtures are named after the bug class they closed** (Class α/β/γ/ε, the
  `tco-call-args` fold, `binding-tests-3.js`, `10.5-1-s.js`) and each fixture block
  explains the divergence it locks (test 303–312, 331–338, 2086–2095). This is a durable
  triage record.
- **The oracle-classification pitfalls are reasoned about explicitly** where they were
  noticed (compile_diff.rs:232–254; test 159–163), and the reject-agreement lock
  (`assert_both_reject`, test 155–177) pins both sides of the accept/reject boundary.
- **Layering is real, not aspirational:** `ironhorse-compile` is only a dev-dependency of
  `ironhorse-vm` (Cargo.toml:22–29) and the runtime `SourceCompiler` seam has an honest
  `Unsupported` channel (interp.rs:63–76) — the pieces needed to fix finding 1 already exist.
- **`forbid(unsafe_code)`** is present (lib.rs:16) and the whole serializer is plain
  index arithmetic over `Vec`s; there is no place for memory unsafety to hide.
