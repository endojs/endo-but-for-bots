## Purpose and responsibilities

`ironhorse-262` is the design's "dual-run harness" (ironhorse-engine.md §test262 conformance, requirement 6),
grown into `endot-ih`, an `xst`-shaped test262 runner with a differential XS oracle. Responsibilities:

1. **Differential primitive** (`lib.rs`): compile a source with the selected compiler (default: ironhorse-compile;
   the XS oracle's bytes as a selectable reference), run it on `ironhorse-vm`, run the same source on the
   XS oracle (`xs_oracle::run`), and produce a `DualRun` with the four-valued `Agreement`, result/error/computron
   comparisons, ironhorse's verbatim `Halt`, and the ironhorse-compile reaction (`IronhorseCompile`).
   Variants: `dual_run_cranks` (multi-crank on one machine per engine), `dual_run_async` (retains the interp to
   read the `$DONE` latch), `compartment_dual_run`, `boot_bundle_verdict`, `ironhorse_only_run` (hang attribution).
2. **Runtime eval bridge** (`IronhorseSourceCompiler`, lib.rs:47–81): installs ironhorse-compile as the VM's
   `SourceCompiler` so `eval`/`Function` compile in-realm; panics in the compiler are caught and surfaced as
   `SourceCompileError::Unsupported`.
3. **xst-shaped runner** (`xst.rs`): YAML frontmatter → feature pre-skip list → structural pre-skips →
   sloppy+strict mode selection → assembly (`sta.js`, `assert.js`, includes, body) → dual-run → verdict
   (`Covered | PreSkip | RunSkip | Fail`) with positive/negative/early-error/async/module arms →
   `XstReport` (YAML `mode:/skip:/skip-detail:/fail:/advisory:` + per-case `CaseRecord`s + `observed` map).
   Also the per-case wall-clock bound with oracle-vs-ironhorse hang attribution.
4. **Expectation lists and ratchet** (`expectations.rs`): a flat committed list `path mode outcome`, a
   `BTreeMap<(path, Mode), Outcome>` model, and `compare()` producing six `Ratchet` event kinds, all gating
   except `SkipReasonChanged` (soft unless `--strict-skip-reasons`).
5. **Legacy `language/` walker** (`test262.rs`): the older classifier (`Class::{Covered, Divergent, Skipped}`)
   plus file discovery helpers (`collect_js*`, `locate_test262`, `ses_xs_parity_files`) still used by `endot-ih`
   and by three in-crate `cargo test` bars.
6. **Frontmatter** (`frontmatter.rs`): yaml-rust2 parse of the `/*--- … ---*/` block into
   `Frontmatter {description, flags, includes, negative{phase,ty}, features, info, present}`.

## Architectural observations

- **Verdict semantics are asymmetric by construction.** The positive arm treats every ironhorse-side abort where the oracle completed as one bucket (`ironhorse-aborted`) without inspecting `Halt` (xst.rs:559–560). The negative arm *does* inspect halts (xst.rs:619–623, 360–366) and distinguishes limit aborts from throws. The result is that the harness can only ever produce a `Fail` for (a) a differing *completion value* on BothComplete, (b) over-acceptance, (c) an armed meter gate, (d) a hang/worker panic, (e) computron nondeterminism. A test262 positive test's actual pass signal — "no `Test262Error` thrown" — is not a Fail-producing signal when ironhorse alone throws it.
- **Substring heuristics on source text decide verdicts.** `oracle_missing_temporal` (`source.contains("Temporal")`, xst.rs:604), the multi-agent pre-skip (`src.contains("$262.agent") || …Atomics.wait…`, xst.rs:823–826), `looks_like_overflow` (xst.rs:325–328). The first is placed before the agreement match and so applies to all four agreements.
- **Two verdict engines, two assemblers, two combiners.** `test262.rs::classify` (bit-exact required) vs `xst.rs::evaluate_positive` (advisory computrons); `test262.rs::assemble` vs `xst.rs::assemble`; `run_case` inline combiner (912–930) vs `combine_mode_results` (1127–1151). lib.rs:16–23 describes the legacy path as "retired", yet test262.rs carries three oracle-backed `cargo test` bars and is what `endot-ih` uses for discovery.
- **The ratchet is a library without a caller.** `expectations.rs` and `--expectations/--update-expectations` are complete and tested, but no list is committed anywhere (grep: the only `# engine=ironhorse` string in the repo is inside `designs/test262-fixture-consolidation.md`), `scripts/README.md` never mentions expectations, hardened262 does not pass `--expectations`, and CI runs `cargo test -p ironhorse-262` (ci.yml:833). `baseline/baseline.json` is an immutable JSON snapshot (README says "Do not edit") with no code consumer in `rust/engine` (grep: only the two READMEs reference it). So the design's own listed defect — skip↔covered flips silently absorbed (fixture-consolidation.md:82–87) — is still the live behavior.
- **Ratchet model drift.** `observed` is keyed `(path, Mode)` but is populated one-entry-per-file under `Sloppy` (strict verdict folded into a `strict:` reason prefix); `(path, Strict)` only appears as `skip:strict-unimplemented` when the meter-exact policy suppressed strict; the `only_strict` branch (xst.rs:1252–1256) matches a reason prefix no code emits (report.rs:153 also still classifies the phantom `onlyStrict:strict-mode-unimplemented`). A committed list would therefore label an `onlyStrict` case's strict run as `sloppy`.
- **Quarantine semantics.** `compare()` treats expected `fail` == observed `fail` as green (expectations.rs:293); `Fail→Skip` is `SkipReasonChanged` (soft) (346–351); `Fail` detail is not serialized (xst.rs:1249), so a Fail whose *reason* changes is invisible. The design's open question 1 (fixture-consolidation.md:289–293) leans toward never committing a `fail`; the code chose quarantine.
- **`Halt::Unsupported` is the VM's runtime bail channel** (269 distinct literal labels + `op.name()` sites in interp.rs; e.g. `reduce:concurrent-mutation`, `JSON.parse:astral`, `toCase:non-ascii`, `to_numeric:mixed-bigint`, `bind:bound-callback`, and the hostile-bytecode guards `eval:frame-underflow` 13513, `end:frame-underflow` 15247, `yield:stack-underflow` 15341). The harness maps all to `RunSkip("unsupported-opcode:<label>")` → `Category::Unsupported` ("genuine language gaps, the actionable backlog"). Two consequences: the "opcode" vocabulary is a misnomer; and an internal-invariant violation reached from ironhorse-compile's *own* output on the default path is reported as a coverage gap rather than a compiler/VM integrity failure. The doctrine ("honest named skip, never a wrong value") is honored; what is lost is the ability to audit, from harness output alone, whether a bail replaced a wrong value.
- **Compiler-fold labels are dropped on the positive path.** `compile_for` returns empty bytecode for `Unsupported`/`Panicked` (lib.rs:325, 331–335); the VM decodes it as `Halt::Decode`; `evaluate_positive` names that `parse-or-decode` (xst.rs:451) and never reads `run.ironhorse_compile` — only `evaluate_negative_early` does (695). The eval-bridge does the same one level down: `SourceCompileError::Unsupported(msg)` → `Halt::Unsupported("eval:compiler-unimplemented")` (interp.rs:8010–8012), discarding `msg`.
- **Over-rejection is a skip.** A positive test where ironhorse-compile `Rejected` valid JS the oracle ran: `dual_run_with` synthesizes `Halt::Throw("SyntaxError")` (lib.rs:395–402) → `OracleOnlyComplete` → `ironhorse-aborted`. Parser over-acceptance is a `Fail`; parser over-rejection is not.
- **`catch_unwind` use** is confined to compiler calls (lib.rs:56, 306, 617; xst.rs:962) with `AssertUnwindSafe` over a stateless compiler — sound. VM panics are deliberately *not* caught in-process: in the CLI's bounded path they become `Fail("ironhorse-worker-panic")` (xst.rs:1438–1447); in the unbounded library default they propagate and abort the run (loud, acceptable). No custom panic hook, so each caught compiler panic still prints to stderr (noise, not a correctness issue). The workspace sets no `panic = "abort"` profile (checked `Cargo.toml`), so `catch_unwind` is effective.
- **Determinism hazards in the harness itself:** none found. `HashSet` used only for membership; `BTreeMap` for everything serialized; file lists sorted; the report is a pure function of `(outcome, reason)`. Host time is used only for the wall-clock bound (CLI policy, off in the library). The timeout value is embedded in a skip reason (`oracle-nontermination: … within {N}s`), which makes lists non-portable across `--case-timeout` values (a soft `SkipReasonChanged`).
- **Panics/unwraps on untrusted input:** none reachable from test files. `constructor_name` slices at an ASCII `:` (xst.rs:319–322), `extract_block` at ASCII markers (frontmatter.rs:85–88); yaml-rust2 indexing returns `BadValue`; `unwrap_or_default` throughout. `unreachable!` at expectations.rs:306 and xst.rs:929/1149 are genuinely unreachable by construction. The two `Path::new(".")`/nonexistent harness-dir unit tests confirm assembly errors are `Err`, not panics.
- **Metering-doctrine drift:** `DualRun::is_bit_exact`/`Summary::met_bar` (lib.rs:223–251, 852) and `test262.rs::classify` (145–147) define acceptance as computron equality with XS; `--gate-meter-exact` (xst.rs:462–467, 473, 497) fails a case on `oracle_computrons != ironhorse_computrons`, i.e. XS parity — which ironhorse-engine.md:441–458 says is never an acceptance gate. `xst.rs`'s default path is doctrine-compliant (advisory). Meanwhile lib.rs:1501–1545 pins ironhorse's *own* frozen UTF-16 costs — the doctrine-correct shape.
- **API-boundary leaks:** `RunOutcome` is built as a struct literal in three places (lib.rs:395, 442, 460); `DualRun` in three test helpers. `SesMode::prelude` splices `{body}` into a `function(){…}` wrapper (xst.rs:141–144) which would change top-level `var`/function-declaration semantics vs `new Compartment().evaluate(<string>)` — unreached today (`unimplemented_skip` always `Some`), flagged so it is not switched on as-is.
- **Performance-architecture:** oracle is run before compile for every case and again on every `--repeat`; the hang path leaks one XS machine per hang (bounded by hang count). `run_files` parses frontmatter twice per case. None consensus-relevant.

## Candidate findings (most architecturally significant first)

1. **`xst.rs:560` — an ironhorse-only test failure is a skip, never a Fail.** Claim: a positive test262 case where ironhorse throws `Test262Error` (its own assertion failed) while XS completes is recorded `RunSkip("ironhorse-aborted")` → `Category::Unsupported`, and `met_bar()`/`bar-met: true` stay green. Evidence: `Agreement::OracleOnlyComplete => Verdict::RunSkip("ironhorse-aborted".into()),` (xst.rs:560; identical at test262.rs:173); `|| reason.starts_with("ironhorse-aborted")` → `Category::Unsupported` (report.rs:197–209). The arm never inspects `run.ironhorse_halt`, unlike the negative arm (xst.rs:360–366, 619–623). Why it matters: the design's bar is pass-vector *and* fail-vector parity (ironhorse-engine.md:627–639); this arm makes the harness structurally unable to fail on "ironhorse fails a test XS passes", so `fail:` empty ≠ conformance, and the published "unsupported = genuine language gaps" count mixes wrong-value assertion failures with unimplemented surfaces. ## What is done well

- The `oracle_parsed` / `bytecode` split (lib.rs:207–217; xst.rs:575–579) fixed a previously vacuous host-abort conjunct and is documented with the exact reasoning; the early-error verdict is decided at the parse phase (xst.rs:659–666) with the `$DONOTEVALUATE()` insight that made the over-acceptance arm reachable, and `Rejected` / `Unsupported` / `Panicked` are kept distinct so a refusal to parse is never counted as a correct rejection (lib.rs:135–162; xst.rs:695–697, tests 1932–1992).
- Over-acceptance — the one direction the harness does fail on — is guarded by tests that pin the non-masking of the host-abort and Intl/Temporal exclusions (xst.rs:1814–1899).
- Hang handling is careful: thread-per-case with an explicit 32 MiB stack, attribution by re-running ironhorse alone with per-mode reassembly including strict and the async prelude (xst.rs:1463–1508), a regression test for the `onlyStrict` attribution bug (2060–2090), and worker panics kept in the bar-forbidden category (1438–1447). The oracle shim's lifecycle mutex covers only create/delete, so a leaked hung machine cannot deadlock later cases.
- Harness output is deterministic by construction (`BTreeMap` everywhere serialized, sorted discovery, `HashSet` only for membership), and `panic_message` is bounded to one line / 200 chars so a panic payload cannot flood `report.json`.
- `catch_unwind` is used narrowly and soundly (stateless compiler calls only, `AssertUnwindSafe` justified), VM panics are deliberately loud, and `#![forbid(unsafe_code)]` holds.
- The expectation-list machinery itself (`compare`, six event kinds, deterministic serialization, loud parse failures) is small, correct on read, and well tested — the gap is deployment, not implementation.
