## Purpose and responsibilities

`ironhorse-regexp` is the `#![forbid(unsafe_code)]` transliteration of XS's `xsre.c`: the pattern compiler
(`fxCompileRegExp` = recursive-descent parse → `measure` → `code`) and the backtracking match VM
(`fxMatchRegExp`). It has no JavaScript surface; `ironhorse-vm` (interp.rs, "child 9") owns `RegExp`,
`exec`/`test`/`replace`/`split`, `lastIndex`, `.groups`, `.indices`, and the UTF-16 ⇄ UTF-8 subject boundary.
The crate additionally hosts (a) the XS `ID_Start`/`ID_Continue` tables (`unicode.rs`) which `ironhorse-compile`
re-exports for its lexer, (b) the XS case-fold tables (`charcase.rs`), (c) a port of XS's UTF-8 helpers
(`encoding.rs`), and (d) ~12k lines of vendored Unicode property endpoint tables.

Output of `compile` is a `Program { code: Vec<i32>, capture_count, name_count, assertion_count, quantifier_count,
compile_meter_raw, capture_group_names }` whose `code` is the exact XS integer step stream (byte offsets kept in
bytes, `sizeof(txInteger)==4`). Output of `match_regexp` is `MatchOutcome { matched, captures: Vec<(i32,i32)>
(UTF-8 byte offsets), names: Vec<i32>, match_meter_raw }`.

## Architectural observations

- **Coupling / layering.** The XS meter *weights* live in this leaf crate (opcode.rs:34,38) and the crate returns
  pre-weighted raw units, so the VM's `COST_TABLE_VERSION = "ironhorse-meter-1"` (meter.rs:26) cannot re-weight
  regexp steps without editing the regexp crate. A step *count* (and a compile-work count) would be the right
  export; the weight belongs in the VM's cost table. `ironhorse-compile` depends on the whole regexp engine (16k
  lines incl. 12k of tables) to get two ~200-line identifier tables; an `ironhorse-unicode` leaf would be the
  cleaner seam. The lexer's parse-time `compile()` is a second full compile of every literal (the runtime `new
  RegExp` path compiles again) and its compile meter is dropped.
- **Recursion shape = XS's.** Parse, measure and emit are all recursive by construction (see table above). Flat
  sequences survive in release only because LLVM tail-calls the last `measure(right)`/`emit(right)`
  (PROBE: `a`×100 000 OK at 2 MiB) — fragile; alternation chains and group nesting do not. Untrusted inputs reach
  this recursion from three places: source text (lexer), runtime `new RegExp`, and snapshot resume
  (`restore_regexps`). A resume on a host with a smaller stack than the snapshotting host can abort where the
  original succeeded.
- **Hidden state.** None in the crate (no globals, no HashMap, no floats, no host time). `Compiler` is per-call.
  Determinism inside the crate is good. `sort_strings` is a total order.
- **Panics/unwraps on untrusted data.** `compile()` has one `.expect` (306) justified by the preceding check;
  `measure`/`emit`/`charset_combine` `unreachable!`s are on internal kinds. The one real panic path is the
  negative capture index (compile.rs:1688 → matcher.rs:211/247). `matcher.rs` otherwise indexes only compiler-
  produced words; `captures[e as usize]` (216/252) is safe because `e` was range-checked at 281-287 when
  non-negative.
- **Integer arithmetic.** `size: i64` but every `step`/`completion`/`loop_off` is `self.size as i32` (1885 etc.)
  — silently wrong for a >2 GiB program (unreachable in practice, unchecked). `decimal()` wraps `u32`
  deliberately to mirror XS (`a{4294967297}` → `{1}`; PROBE confirms `min=1,max=1`; `(a)\4294967297` →
  `\1`, matched). Both are XS-parity spec deviations, not divergences.
- **Metering-doctrine drift.** The crate is built and tested to XS-computron parity (Cargo.toml:3 "Metering-exact
  and bit-exact"; parity.rs:92-98) although the design's binding doctrine is accuracy over parity. The per-step
  weight ignores real work: each backtrack point clones the captures Vec (matcher.rs:163,310,373,395 — O(captures)
  heap alloc), a backreference compare is O(len) at one step's price (225-232, 261-268), and compile charges
  `size*1024` by *emitted* bytes while `charset_range` under `i` performs O(range × result) work
  (PROBE: `[\u{0}-\u{FFFF}]`/iu → 0.73 s, 365 MB RSS, 1245 emitted words; `[\u{0}-\u{1FFFF}]` → 4.7 s, 900 MB).
- **Error-handling shape.** Two-variant `CompileError`; `Syntax(String)` messages are short reasons (never
  surfaced to JS). `Unsupported` is a compile-time-only notion but the VM converts it to `Halt::Unsupported`
  (interp.rs:20096, 20799), i.e. a crank abort for ordinary JS such as `/😀/` (non-u astral literal,
  compile.rs:374-376) — a stage-bar "honest skip" that is production-fatal.
- **API-boundary leaks.** The crate's NUL-terminated-pattern contract (compile.rs:153,228; encoding.rs:83-85)
  leaks: the VM spells NUL as `C0 80` for the *subject* (interp.rs:20219-20233) but not for the *pattern*
  (18597-18601), so `new RegExp("a b")` compiles as `/a/`. Lone surrogates in either pattern or subject
  are replaced by U+FFFD before reaching the crate (10891-10893, 18601, 30878-30881). Capture offsets are UTF-8
  byte offsets; the VM converts to code units only for the NUL spelling (20255-20267, 20311-20312) and refuses
  non-ASCII subjects only when `g`/`y` (20169-20171), so a non-global match over a non-ASCII subject reports
  `index`/`.indices` in bytes.
- **Snapshot coverage.** `Program` is re-derived from `(source, flags)` on restore; `compile` is deterministic
  so this is sound, but restore re-runs the unbounded compile work (recursion, quadratic fold) at resume time.
  `regexp_last_names` (interp.rs:4392) is transient exec→replace scratch; not a snapshot concern at quiescence.
- **Performance architecture.** `charset_parts` clones both endpoint Vecs on every combine (908-913); `Compiler.nodes`
  never frees intermediate charsets (each `charset_range` iteration retains a singleton and a growing union node —
  the source of the 900 MB); `State.captures` is a fresh `Vec` per backtrack point. All are XS-shaped but Rust
  pays allocator cost XS's bump arena did not.

## Candidate findings (most architecturally significant first)

1. **Backtracking is not bounded by the crank meter (ReDoS is uninterruptible).** — `matcher.rs:108,130`;
   `interp.rs:20189-20191`. Claim: a metered crank cannot abort a catastrophic regexp match because the matcher
   meters into a local `u64` and the VM charges/checks only after `match_regexp` returns.
   Evidence: `let mut meter: u64 = 0;` (108) … `meter += XS_REGEXP_METERING;` (130); interp.rs:20189-20191
   `ironhorse_regexp::match_regexp(program, subject, start_i)` then `self.meter.tick_raw(outcome.match_meter_raw)`.
   PROBE: `(a*)*b`/"aac" ran >10 s without terminating; `(a+)+b` over 28 a's >20 s (24 a's = 2.4 s). Why: a
   consensus engine's liveness depends on the meter; XS's matcher is subject to `fxCheckMetering` when the
   interval is armed (parity.rs:254-257, 263-269 attribute the unbounded run to the *unarmed* shim). Severity
   critical; confidence high (reproduced).
2. **Recursive compile overflows the native stack on hostile patterns — a process abort, host-dependent.** —
   `compile.rs:1539` (also 1713-1867 group recursion, 1337, 1880-1952, 1956-2193). Claim: a pattern with ~20k
   alternatives or ~10k nested groups aborts the process on a 2 MiB thread in release, and the threshold varies
   with embedder stack size and build profile. Evidence: `let right = self.disjunction_parse(character)?;`
   (1539); ci.yml:826-832 "recurse deeply … overflowing the 2 MiB default … RUST_MIN_STACK: '16777216' … the
   recursion depth is an engine property". PROBE: `a|a|…`×20 000 and `(`×10 000 → "fatal runtime error: stack
   overflow, aborting". Why: reachable from source text (lexer.rs:1223), `new RegExp` (interp.rs:20088) and
   snapshot resume (9155); an abort cannot be caught at the crank boundary and its host-dependence breaks
   "identical inputs produce identical outcomes on every host". Severity critical; confidence high.
3. **`charset_range` under `i` is O(range × result) time and memory, unmetered, at parse time.** — `compile.rs:880-898`
   (+ 908-913, 1885). Claim: a ≤24-byte `iu` class range makes the compiler allocate hundreds of MB before any
   meter is charged. Evidence: `while ch <= end { … let single = self.add_node(…); result = self.charset_combine(result,
   single, MX_CHARSET_UNION_OP)?; ch += 1; }` with `charset_parts` cloning both Vecs and every intermediate node
   retained in `nodes`. PROBE: `[\u{0}-\u{FFFF}]`/iu 0.73 s, 365 MB; `[\u{0}-\u{1FFFF}]` 4.7 s, 900 MB (full
   range extrapolates to multi-GB). Compile meter is `size*1024` over 1245 emitted words. Why: memory DoS from a
   literal in source (lexer) or `new RegExp`, and the accuracy doctrine says compile cost should track real
   work. XS likely shares the time shape; the retained-arena memory is the port's. Severity high; confidence high.
4. **Negative capture index → matcher panic on `\2147483648`.** — `compile.rs:1688`, `matcher.rs:247` (and 211).
   Claim: a numeric backreference whose u32 value is ≥ 2^31 becomes a negative `capture_index`, skips the range
   check (283 `*capture_index >= 0 &&`), is emitted with `name_slot = -1`, and the matcher indexes
   `names[(-1) as usize]`. Evidence: `capture_index: value as i32,` (1688); `let f = code[p + 1]; e = names[f as
   usize];` (246-247). PROBE: `compile(r"\2147483648","")` Ok; `match_regexp` → `panic_bounds_check`. Why: a
   crashed crank from a 12-byte pattern the lexer accepts as valid; XS's C reads out of bounds here (UB), so
   this is also a likely result divergence. Severity high; confidence high.
5. **Embedded NUL silently truncates the pattern (wrong value, not an honest skip).** — `encoding.rs:83-85`,
   `compile.rs:228`, `interp.rs:18600-18601`. Claim: `new RegExp("a b")` compiles as `/a/`. Evidence:
   `if first == 0 { return (C_EOF, p); }` (encoding.rs:83-85); `pattern_bytes.push(0);` (228); the VM builds the
   pattern with `String::from_utf8_lossy(&bytes)` and no `C0 80` spelling, unlike the subject path at
   20219-20233. PROBE: `run("a\0b","","ab")` → matched (0,1), program 11 words. Why: XS stores U+0000 as `C0 80`
   so its pattern keeps the NUL; result divergence and a broken `.source`↔program relation. Severity high;
   confidence high.
6. **Lone surrogates are destroyed at the regexp boundary (pattern and subject).** — `interp.rs:10891-10893`
   (`str_text`), 20284, 18601, 30878-30881; contract in `encoding.rs:12-19`. Claim: `/\uD800/.test("\uD800")` and

   surrogate as its own sequence and `fxUTF8Decode` yields 0xD800). Evidence: `String::from_utf16_lossy(&self.str_units(off))`
   (10892); encoding.rs:14-16 "differs … only when the bytes encode a surrogate … which a well-formed UTF-8 subject

## What is done well

- Genuinely zero `unsafe`, zero `HashMap`, zero floats, zero host-time in the crate; all lookups are `match` or
  binary search on sorted static data — determinism inside the crate is by construction.
- The XS byte-offset layout (`measure`/`emit`) is reproduced exactly enough that the differential harness pins
  the entire step stream's behaviour (result, every capture, per-step meter) against the pin, and six
  `finding_*_regexp_meter_overflow` regressions in `ironhorse-vm/tests` guard the full-width `u64` meter with
  oracle-free fixtures.
- Named-capture semantics (ES2025 duplicate names across alternatives, forward `\k<name>`, runtime `names[]`)
  and the Annex-B-vs-XS strictness decisions are documented case by case in lib.rs tests (337-567) with
  the *reason* XS differs from the spec spelled out.
- The `Unsupported`-after-accept/reject ordering (compile.rs:312-320) is a careful design: the lexer gets the
  correct syntax verdict even for features whose matcher is unported.
- The two-pass named-capture reparse, the participate-list "pointer surgery" and the inline-modifier flag
  threading are faithful to `xsre.c` with the XS function names cited at each site, which makes auditing against
  the pin tractable.
- The string-property generator checksums the pin (`fnv1a64` assert) before emitting, a good pattern that
  simply needs extending to the other tables and wiring into CI.
