## Purpose and responsibilities

This region is the daemon-side embedding of the Rust engine — the "endor integration" seam of `designs/ironhorse-engine.md` § Endor integration (requirement 8) and the "supervisor wiring" of `designs/ironhorse-snapshot-store-seam.md`. It consists of:

1. **`endo::ironhorse_engine::engine`** (`rust/endo/src/ironhorse_engine.rs`), feature-gated on `ironhorse-engine` (default-on, `rust/endo/Cargo.toml:30-31`). Two engine handles:
   - `Machine` (:137-199): a thin wrapper over `ironhorse_vm::Machine` + `Compartment`; compiles JS with `ironhorse_compile::compile_atoms_with` and evaluates in a fresh compartment. Used only by `run_script` (`endor run -e ironhorse <file.js>`, :208-223).
   - `PersistentMachine` (:325-812): the store-backed worker-heap lifecycle — open/resume from a SQLite heap store, compile+relink+run one crank, checkpoint per cadence, rewind on halt/failed checkpoint, durable partial collection, flush, close. This is the part the design calls "fully landed".
   - `run_worker` (:820-839): a named-gap stub — `endor worker -e ironhorse` exits 1.
2. **`ironhorse-store-sqlite`** (`rust/endo/ironhorse-store-sqlite/src/lib.rs`): the daemon-side `HeapStore` backend (SQLite via bundled rusqlite) implementing the trait from `ironhorse_snapshot::store`. Lives in the ROOT workspace (not `rust/engine`) so the engine workspace stays zero-C.
3. **Supervisor touch points** (`supervisor.rs:15-31, 145-218`): `SuspendedWorker.heap_store: Option<PathBuf>`, `mark_suspended_store`, `put_suspended`. `endo.rs:712-750` `handle_resume` refuses to resume a store-backed worker (named gap).
4. **CLI dispatch** (`endor.rs:62-153, 425-441`): `-e xs|ironhorse` string match per subcommand.
5. **test262 host** (`run-ironhorse-host.js`): builds and runs the engine workspace's `endot-ih` binary as the third `ses-xs-parity` host (`yarn test262:ironhorse`).
6. **The two-workspace split**: root `Cargo.toml:6` `exclude = ["rust/engine"]`; `rust/endo/Cargo.toml:7-21` and `ironhorse-store-sqlite/Cargo.toml:15-16` depend by path into the excluded workspace.

## Architectural observations

**Coupling and abstraction shape.** The design's engine seam is stated as "the same `Machine` surface behind an engine selection". What exists is: (a) a CLI string switch in `endor.rs`; (b) an `Engine` enum in `engine.rs` whose variants are transport shapes (`Separate`/`Shared`) with an XS-specific `&'static xsnap::ffi::XsCreation` baked into `Shared` — no ironhorse variant, no engine axis in the spawn payload; (c) two unrelated ironhorse handles (`Machine`, `PersistentMachine`) with no common trait and with `xsnap::Machine`. The seam is therefore a fork of call sites, not a seam. The sentinel encoding of the store-backed suspend record (`sha256 == ""` ⇔ store-backed; supervisor.rs:160; test :113) is the visible cost of bolting a second engine onto an XS-shaped record instead of an enum.

**Duplication with xsnap.** `xsnap::Machine` carries `begin_metering/end_metering/current_meter/current_computrons/set_meter/run_promise_jobs_metered` plus the thread-local `CRANK_LIMIT`/`set_crank_limit`/`take_metering_aborted` (xsnap lib.rs:326-369, 1217-1240) and the meter-report envelope (`send_meter_report`, :1243). The ironhorse seam duplicates none of it and provides no equivalent: `Interp` HAS the primitives (`arm_meter`, `rearm_meter`, `reattach_meter_host`, `meter_state`) but the seam never calls them. So the "duplication" question inverts: the two engines share no abstraction AND the second one has a hole where the first one's metering contract is.

**Hidden state / two meanings of one type.** `EvalOutcome.computrons` means "this eval's fresh-Interp count" from `Machine::evaluate` (compartment.rs:320 boots `Interp::new()` per call) but "machine-lifetime cumulative count, persisted across suspend" from `PersistentMachine::eval` (interp.rs:11252 `self.meter.computrons()`; `run` never resets; sqlite test :1435-1438 asserts continuation). The supervisor's `process_meter_report(steps)` expects per-crank steps; no delta is computed anywhere.

**Error-handling shape.** `MachineError` is five variants, four of them `String`. `store_err` uses `{e:?}` (Debug) so even the string is the Rust Debug form of an enum, not a message. The supervisor-relevant distinctions the code's own comments enumerate — "crank discarded, redeliverable" vs "session poisoned" vs "store fault" vs "this program's state is not persistable by this build" — are all `Store(String)`. The seam DOES have the right vocabulary for the last case (`Unavailable(what)`) and does not use it.

**Metering-doctrine drift.** Not the seam's own text, but what it re-exports: `RunOutcome.computrons` rustdoc says "comparable bit-for-bit with the oracle's run-only count" (interp.rs:3597-3598) and `run` says "directly comparable with the oracle" (:11251) — parity language under an accuracy-over-parity doctrine. The seam's `EvalOutcome` uses the correct "release-versioned count" wording (:109). Cross-region; noting only.

**Determinism hazards at this boundary.** (1) Two lockfiles: root `Cargo.lock` vs `rust/engine/Cargo.lock` disagree on `icu_locale_core` 2.2.0/2.3.0, `icu_provider` 2.2.0/2.3.0, `zerovec` 0.11.6/0.11.7, `tinystr`, `writeable`, `litemap`, `potential_utf`, `zerotrie`, `displaydoc`, `smallvec` (verified by grep over both files). The ICU DATA crates agree (2.2.0), so today's outputs likely coincide, but the "release" whose determinism is promised is not one dependency closure, and nothing in CI compares the two lockfiles. (2) No `[profile]` in either workspace root — release builds wrap on integer overflow (census). (3) No HashMap iteration in this region affects anything observable (`edge_pairs`/CTE results are sorted or BTreeSet; `externally_referenced` sorts, :587). (4) No host time/locale in the seam. (5) `SqliteHeapStore` numeric handling is fail-closed (`page_col`, contiguity checks) — no panics on DB content: the two `.unwrap()`s (:327, :800) are on `chunks_exact(4)` slices and cannot fail.

**GC-root / side-table / snapshot coverage hazards at this boundary.** The seam relies on `checkpoint_to_store`'s gates (`stored_unpersistable_row_at_checkpoint`, `is_quiescent`) to refuse un-persistable state rather than checking anything itself. That is the right layering, but it makes the seam's behavior on refusal (rewind + discard) the user-visible consequence of every still-Pending ledger row: any completed crank with a suspended `await` is unpersistable and therefore un-runnable through `PersistentMachine` (Candidate 4). The seam also relies on `is_quiescent` (interp.rs:10733-10743) — a list of 8 fields — rather than a structural guarantee; the census's headline bug class ("a side table missing from the ledger") surfaces here as a checkpoint refusal at best, or as a silently-wrong resume at worst (the design's own W6-9/P2 notes on `arr.length` reading `undefined` after resume, seam design :775-782).

**RefCell re-entrancy seam.** `checkpoint_to_store(session, &sig, &mut *self.store.borrow_mut())` (:574-578, :682, :762) holds the `RefMut` across the whole call while the lazily-resumed session's page source holds an `Rc<RefCell<S>>` clone to the SAME store (machine.rs:1578-1581). Any page fault during checkpoint would panic with `BorrowMutError`. The snapshot crate is aware (machine.rs:773-776: "the caller necessarily holds the RefCell's mutable borrow") and avoids probing; dirty pages are resident by construction. It works today by discipline, not by type — a deterministic panic (crashed crank), not corruption.

**Performance-architecture risks.** Every crank recompiles from source (`compile_atoms_with`, :496) and, on a divergent table, walks and rewrites the whole bytecode (`relink_crank`). Every `Machine::evaluate` boots a full `Interp::new()` (all intrinsics). Every `SqliteHeapStore::open` pays a full `edge_pairs` rebuild write transaction plus all-leaf-hash validation. None is wrong for the current stage, but "resume is O(working set)" oversells what `open` costs.

**Monolith symptoms.** `PersistentMachine::eval` is 165 lines with ~90 lines of comments narrating review waves inline (:499-655). The comments are accurate and valuable as history, but the function's control flow (cadence decision, link, relink, run, checkpoint, three rewind paths, scheduled collect with latched failure) would be clearer as a small state machine with the history moved to the type docs. `run_worker`'s error message is a 16-line paragraph inside a string literal (:822-836).

**CI shape.** The 5 unit tests in `ironhorse_engine.rs` (:841-899) never run: `build-xsnap` runs `--test ironhorse_store_worker` only (ci.yml:675) and `test-ironhorse` never builds `-p endo`. `test-ironhorse`'s PR path filter (:724) omits `rust/endo/src/` and `rust/endo/tests/`, so a seam-only PR runs the engine tests only via `build-xsnap` (which has no filter). No clippy/rustfmt anywhere (census).

**What `run-ironhorse-host.js` actually does.** It is a thin `spawnSync('cargo', ...)` wrapper in `rust/engine` (:51-84) running `endot-ih -l --feature-filter ses-xs-parity --features-include ses-xs-parity --test262-dir <pkg>/test262 built-ins language`. Its own header (:23-28) states every `ses-xs-parity` case currently reports an honest named skip, so `yarn test262:ironhorse` is green with zero assertions exercised. It requires `cargo` on PATH and, for the oracle, the `c/moddable` submodule — it builds `-p ironhorse-262`, which cannot build here (census). The flags all exist in `endot_ih.rs` (:84-120).

## Candidate findings (most architecturally significant first)

1. **The daemon runs cranks with no meter limit; `Halt::MeterAbort` is unreachable from the seam.** `rust/endo/src/ironhorse_engine.rs:572` and `:165`.
   Claim: no code path in the endo crate arms the engine meter, so a guest `while(true){}` in `PersistentMachine::eval` or `Machine::evaluate` never terminates.
   Evidence: `let outcome = session.machine_mut().run(&bytecode);` (:572); `Ok(comp.evaluate_with_symbols(&bytecode, &symbols).into())` (:165); `Interp::run` is "default-unbounded" and `StepLimit` is "Never produced by the default-unbounded `Interp::run`" (interp.rs:3532-3534); `arm_meter`/`rearm_meter`/`reattach_meter_host` (interp.rs:10667/10684/10697) have zero callers in `rust/endo` (grep).
   Why it matters: the engine is a metered, consensus-grade JS engine and the design promises the xsnap metering API "preserved verbatim" so the crank lifecycle and admission gate carry over "without supervisor changes" (ironhorse-engine.md:460-467). Also interp.rs:10681-10683: "every resume that wants metering MUST call one of the three arm forms" — `PersistentMachine::open`/`rewind_to_last_checkpoint` call none, so a resumed machine's persisted meter state is dead weight. Severity: high. Confidence: high.

2. **The seam's error type erases the distinctions a supervisor must act on.** `rust/endo/src/ironhorse_engine.rs:381-383`, `:591-596`, `:635-647`, `:773-778`.
   Claim: `MachineError::Store(String)` is returned for four operationally different outcomes — transient store I/O with the crank discarded (safe to redeliver), deterministic checkpoint refusal with the crank discarded (redelivery loops forever), a failed rewind (session poisoned; every later call fails), and a foreign-signature/schema refusal at open — distinguishable only by substring.
   Evidence: `fn store_err(e) -> MachineError { MachineError::Store(format!("{e:?}")) }` (:381-383); `return Err(MachineError::Store(format!("rewind failed after a failed checkpoint ({e:?}): {rewind_err}")))` (:642-644); test matches `e.contains("Signature")` (tests/ironhorse_store_worker.rs:143).
   Why it matters: the code's own comments (:608-616) argue at length that a supervisor "re-delivering would double-execute a committed crank" if two errors are indistinguishable — and then makes the redeliverable/poisoned/permanent cases indistinguishable by type. `StoreError` is a rich enum (Empty, MissingRow, EpochMismatch, BaselineMismatch, SummaryCount, PendingStateUnsupported, MachineNotQuiescent, Io, Snapshot) that is flattened at exactly the boundary where it is needed. Severity: high. Confidence: high.

3. **There is no engine axis in the supervisor; `-e ironhorse` is a CLI-only switch and the store-backed suspend record is sentinel-encoded.** `rust/endo/src/engine.rs:10-21, 25-55`; `rust/endo/src/supervisor.rs:159-161`.
   Claim: the daemon's `Engine` enum has no Ironhorse variant and `engine_for_spawn_request` dispatches only on `platform`, so no spawned worker can ever be an Ironhorse worker, and store-backed suspends are discriminated by empty strings.
   Evidence: `pub enum Engine { Separate {...}, Shared { bootstrap, creation: &'static xsnap::ffi::XsCreation, label } }` (engine.rs:10-21); `match platform { "separate" | "" => ..., "shared" => ..., "node" => ..., other => Err(...) }` (:31-54); `self.mark_suspended_inner(handle, String::new(), std::path::PathBuf::new(), Some(heap_store));` (supervisor.rs:160).
   Why it matters: ironhorse-engine.md:732-736 promises "an orthogonal engine axis" on the spawn verb; the `Engine` type that exists is XS-typed (`XsCreation`) and would need redesign, not extension. The sentinel encoding already produced one bug class the code guards against (`handle_resume` "would hand the machine an empty snapshot path", endo.rs:720-723). A `SuspendedState::{Cas{sha256,cas_dir}, Store{heap_store}}` enum would make the refusal a type error. Severity: medium (the worker gap is honestly named; the encoding is the finding). Confidence: high.

4. **A completed crank that leaves a suspended `await` is unpersistable, and the seam turns that into crank loss reported as a store fault.** `rust/endo/src/ironhorse_engine.rs:635-647`, `:749-780`; `rust/engine/ironhorse-snapshot/src/machine.rs:1059-1061`; `rust/engine/ironhorse-vm/src/interp.rs:8656-8668`.
   Claim: when `checkpoint_to_store` refuses with `PendingStateUnsupported` (any promise reaction of a non-User kind, i.e. an `await` resumption, or a live async generator), `eval` rewinds and returns `Err(Store(..))`, discarding a crank that completed; under `checkpoint_every > 1` the refusal surfaces at `flush_pending` and discards previously ACKNOWLEDGED cranks for a reason that is not an I/O failure.
   Evidence: `if let Some(row) = session.interp.stored_unpersistable_row_at_checkpoint() { return Err(StoreError::PendingStateUnsupported { row }); }` (machine.rs:1059-1061); `return Some("a promise reaction that would resume a non-persisted async frame");` (interp.rs:8667); `Some(Err(e)) => { if let Err(rewind_err) = self.rewind_to_last_checkpoint() {...} Err(store_err(e)) }` (:635-647).
   Why it matters: `CadencePolicy`'s rewind window is documented purely as an I/O trade ("Host I/O failures fork epoch history", :255-256); a deterministic program-shape refusal is a different contract and should be `Unavailable(named row)` refused BEFORE run (the seam already does exactly this for relink refusals, :556-568) or at least a distinct variant. Endo guest code is `await`-heavy, so today `PersistentMachine` can persist only cranks that fully settle. Severity: medium-high. Confidence: high on the mechanism; medium on how often real workloads hit it.

5. **Two Cargo workspaces, two lockfiles: the daemon links a different dependency closure than the engine CI tests.** `Cargo.toml:6`, `rust/endo/Cargo.toml:7-21`, `Cargo.lock` vs `rust/engine/Cargo.lock`.
   Claim: the same engine crates are compiled against different transitive versions in the two workspaces and nothing checks the lockfiles agree.
   Evidence: `exclude = ["rust/engine"]` (Cargo.toml:6); `icu_locale_core` 2.2.0 (root) vs 2.3.0 (engine), `icu_provider` 2.2.0 vs 2.3.0, `zerovec` 0.11.6 vs 0.11.7, `tinystr` 0.8.3 vs 0.8.4, `litemap` 0.8.2 vs 0.8.3, `zerotrie` 0.2.4 vs 0.2.5 (grep of both lockfiles); CI runs `cargo test -p ironhorse-vm -p ironhorse-snapshot` from `rust/engine` (ci.yml:745-746) but `cargo test -p ironhorse-store-sqlite` and `-p endo` from root (:750, :675).
   Why it matters: "Determinism per release ... on every host, architecture, and build" (ironhorse-engine.md:370-379) presumes a release is one artifact; here the tested engine and the shipped engine are different builds by construction. The ICU data crates coincide today (2.2.0), so this is a latent, not active, divergence — but a `cargo update` in either workspace changes it silently. The stated reason for the split ("builds in-repo from the first commit", README.md:5-6, root Cargo.toml:3-5) is historical now that root depends on the engine by path. Severity: medium. Confidence: high on the facts; medium on impact.

6. **`Machine` and `PersistentMachine` give `EvalOutcome.computrons` two different meanings, and `Machine::evaluate` shares no state across calls.** `rust/endo/src/ironhorse_engine.rs:161-166`, `:493-657`; `rust/engine/ironhorse-vm/src/compartment.rs:318-334`; `interp.rs:11252`.
   Claim: `Machine::evaluate` boots a fresh `Interp` per call (so globals do not persist between `eval`s and `computrons` is per-eval), while `PersistentMachine::eval` reports the machine-lifetime cumulative meter; both return the same `EvalOutcome`.
   Evidence: `let mut interp = Interp::new(); interp.link_intrinsics(&names); ... interp.run(bytecode)` (compartment.rs:320-333); `computrons: self.meter.computrons(),` with no reset in `run` (interp.rs:11252); sqlite test asserts "meter continued through the SQLite round-trip" (lib.rs:1435-1438).
   Why it matters: the supervisor's `process_meter_report(handle, steps, ...)` (supervisor.rs:234) expects per-crank steps; a consumer wiring `PersistentMachine` into it would double-count monotonically. And `Machine` is documented as mirroring `xsnap::Machine` (:134-136) whose `eval` runs in the persistent realm (xsnap lib.rs:136-160). `Machine::intrinsics()` (:190-192) returns a `struct Intrinsics { locked_down: bool }` (compartment.rs:64-68) that `evaluate_with_symbols` never reads. Severity: medium. Confidence: high.

7. **Internal engine types leak through the daemon's public API.** `rust/endo/src/ironhorse_engine.rs:35-39, 97, 113-116`.
   Claim: `Halt`'s internal control-transfer variants (`Resume(usize)`, `Yield(Slot)`, `Await(Slot)`, `AsyncYield(Slot)`) and raw arena `Slot`s are part of `EvalOutcome`, and eight re-exported types have no daemon-side user.
   Evidence: `pub use ironhorse_vm::{Compartment, GcStats, Halt, Heap, Intrinsics, Meter as VMeter, MeterCheck, MeterState, ModuleGraph, ModuleSource, RunOutcome, Slot};` (:36-39); `other => format!("halted: {other:?}")` (:97); `Halt::Yield(Slot)` is "never seen by the top-level `run`" (interp.rs:3554-3555).
   Why it matters: the daemon crate now has two unrelated `MeterState` types (`engine::MeterState` = VM counters; `types::MeterState` = supervisor budget). `EvalOutcome.meter_raw` ("Raw 16.16 fixed-point meter index", :113-114) exports a calibration diagnostic as API. Consumers matching on `Halt` must handle variants that cannot occur. Severity: low-medium. Confidence: high.

8. **The relink-refusal "machine unchanged" invariant is violated on the first named crank.** `rust/endo/src/ironhorse_engine.rs:525-568`.
   Claim: if `relink_crank` refuses on the first crank with a non-empty table, the live machine has already been mutated by `link_intrinsics` and marked `linked`, while the store has not, so a live replica and a reopened twin will build different `symbol_names` orders on the next crank (durable-bytes fork).
   Evidence: `session.machine_mut().link_intrinsics(&names); self.linked = true;` (:534-535) precedes `relink_crank` (:559); the comment claims "Nothing ran on refusal, so no rewind is needed and the epoch stands" (:555); `RelinkError` doc: "Every variant is fail-closed: nothing ran, the machine is unchanged" (interp.rs:3633-3634).
   Why it matters: it is the same replica-fork class review wave 5 hunted (identical results, different bytes). Reachable only via `RelinkError::TableFull` (table within reach of `u16::MAX`) or `MalformedBytecode` from our own compiler, so practically remote; the fix is to relink before linking or to rewind on refusal. Severity: low. Confidence: high on mechanism, low on reachability.

9. **`SqliteHeapStore::open` performs a write transaction on every open.** `rust/endo/ironhorse-store-sqlite/src/lib.rs:283, 308-335`.
   Claim: opening a store — including for read-only inspection — deletes and re-inserts the whole `edge_pairs` table, so a store on read-only media or with read-only permissions cannot be opened, and open cost is O(edges) writes regardless of need.
   Evidence: `Self::rebuild_edge_pairs(&conn)?;` (:283); `tx.execute("DELETE FROM edge_pairs", [])` then per-edge `INSERT OR REPLACE` (:310-331); the test helper `read_manifest` opens a store just to read its manifest (tests/ironhorse_store_worker.rs:507-511).
   Why it matters: the doc justifies it as "open never TRUSTS" the derived index (:295-307), which is sound, but the design also promises "resume is lazy (O(working set), not O(heap))" (ironhorse_engine.rs:230-232); a verify-then-rebuild-if-different or a read-only open mode would keep both. Severity: low. Confidence: high.

10. **The seam's own unit tests never run in CI.** `.github/workflows/ci.yml:675, 724`; `rust/endo/src/ironhorse_engine.rs:841-899`.

    Claim: only `close(self)` flushes pending cranks; dropping the machine (a panic in the supervisor thread, a forgotten `close`) silently loses up to N-1 cranks already reported `Ok`.
    Evidence: `pub fn close(mut self) -> Result<(), MachineError> { let flush = self.flush_pending(); ...` (:786-795); no `impl Drop for PersistentMachine` anywhere in the file; `CadencePolicy` doc: "the widened window exists only while the machine is live" (:269-270).
    Why it matters: the doc for the store says committed epochs survive drop (lib.rs:344-348) — true, but the acknowledged-but-pending cranks are exactly the ones a supervisor has already told the world about. A best-effort flush in `Drop` (ignoring errors) or a `#[must_use]` marker on the type would close the gap partly; the fully-correct answer is a supervisor rule that acknowledgement waits for durability. 13. **`RefCell` re-entrancy is prevented by discipline, not type, on the checkpoint path.** `rust/endo/src/ironhorse_engine.rs:574-578, 680-682, 762`; `rust/engine/ironhorse-snapshot/src/machine.rs:1578-1581`.
    Claim: `checkpoint_to_store(session, &sig, &mut *self.store.borrow_mut())` holds a `RefMut` on the same `Rc<RefCell<SqliteHeapStore>>` that the session's lazy page source reads through, so any page fault inside checkpoint is a deterministic `BorrowMutError` panic.
    Evidence: `checkpoint_to_store(session, &self.signature, &mut *self.store.borrow_mut())` (:574-578); `StorePageSource { store: store.clone(), pin: pin.clone() }` (machine.rs:1578-1581); the snapshot crate's own note: "during a same-store commit the caller necessarily holds the `RefCell`'s mutable borrow ... so any probe through the `RefCell` would re-enter it" (machine.rs:773-776).
    Why it matters: it holds today because dirty pages are resident and the checkpoint gates (`is_quiescent`, `stored_unpersistable_row_at_checkpoint`) walk side tables, not lazily-faulted arena pages — an invariant that lives in two crates and no test. A crashed crank, not corruption; but a `&dyn HeapStore` split (page reads through one handle, commit through another) would make it structural. Severity: low. Confidence: medium (I did not trace every read inside `checkpoint_to_store`).

## What is done well

- **The SQLite backend is genuinely fail-closed and panic-free on untrusted database content.** Every pragma that matters is read back (`locking_mode`, `journal_mode`, `synchronous`; lib.rs:161-199); foreign databases are refused by `application_id` (:120-143); every trait reader enforces contiguity and decodes with `try_into` errors rather than casts; the only `.unwrap()`s are on `chunks_exact(4)` slices. `commit` runs ALL verification before the first mutation and is locked by a rollback-after-mutation test (`sql_abort_after_row_mutation_rolls_back_and_forces_a_cold_retry`, :1267-1345).
- **The cadence policy is derived from durable, replica-visible state**, and the tests prove the property rather than assert bookkeeping (`the_collect_schedule_survives_a_suspend` compares manifest `root` and `free_len` across suspend histories, tests :488-504). The starvation fixes (`checkpoint_after_rewind`, absolute `durable_cranks`) are reasoned about in terms of replica agreement, which is the right frame for this engine.
- **Gaps are named, not simulated.** `run_worker` refuses; `handle_resume` refuses and answers a waiting sender; `run-ironhorse-host.js` states in its header that it is currently vacuous. This is exactly the honesty the design asks for.
- **The store-backed lifecycle is exercised end to end through the real `Supervisor`** (tests :102-134), including the put-back round-trip, WAL fold, reopen, and the signature gate — and the sqlite crate instantiates the engine's shared `store_suite` so backend parity is one instrument, not mirrored tests (tests/store_suite.rs header).
- **Rustdoc carries its review provenance.** Nearly every non-obvious branch in `PersistentMachine::eval` cites the wave and finding that motivated it; a future reader can find the regression lock for each. (The cost — a 165-line function that is mostly narrative — is noted above, but the discipline is real.)
- **Layering of the persistence gates is correct**: the seam does not re-implement quiescence or persistability checks; it defers to `checkpoint_to_store`'s gates and reacts (rewind) uniformly.
