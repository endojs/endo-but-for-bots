## Purpose and responsibilities

`xs-oracle` is the differential *reference* for the whole port: it compiles JavaScript on the
pinned Moddable XS engine and runs it, returning `(bytecode, symbols, completion string, error
string, run-only computrons)` so `ironhorse-262`, `ironhorse-fuzz`, `ironhorse-compile`'s
byte-identity tests and `ironhorse-regexp`'s parity tests can compare the Rust engine against XS.
It is the only crate in `rust/engine` that contains `unsafe` or links C (lib.rs:1-17;
README.md:18). It is dev/CI only: it is a **dev-dependency** of `ironhorse-regexp` and
`ironhorse-compile` and a normal dependency only of the two harness crates `ironhorse-262` and
`ironhorse-fuzz`; `ironhorse-vm` and `ironhorse-snapshot` have no path to it (Cargo.toml files
read above). The design's "never linked into a shipped engine" (design:592) therefore holds.

Five entry points, each creating and destroying a fresh XS machine per call (except the
multi-crank entry, which holds one machine across a sequence):

| Rust (lib.rs) | C (xs_shim.c) | What it measures |
|---|---|---|
| `run` :248 | `xs_oracle_run` :295 | Script goal; bytecode + symbols captured before run; `meterIndex` zeroed after parse, read after run + microtask drain |
| `run_cranks` :349 | `xs_oracle_run_cranks` :492 | Same, N sources sequentially on ONE machine, per-crank meter reset |
| `compile_module` :399 | `xs_oracle_compile_module` :643 | Module goal, parse+code only, no run, no meter |
| `run_module_dir` :500 | `xs_oracle_run_module` :773 | Link+evaluate a module graph from a directory via shim-supplied `fxFindModule`/`fxLoadModule` (:140, :218); result read from `globalThis.result` |
| `regexp` :171 | `xs_oracle_regexp` :964 | `fxCompileRegExp` + `fxMatchRegExp` directly; byte-offset captures; separate compile/match meters (u64) |

`build.rs` compiles the 44 XS sources plus xsnap's `xsnap-platform.c` and the shim into one
static library with xsnap's feature defines (build.rs:46-97), through a wrapper platform header
that flips `mxUseDefaultFindModule`/`mxUseDefaultLoadModule` off (xsoracle-platform.h:25-28).

## Architectural observations

- **Text decode at the seam is wrong for XS's own encoding.** XS is built with `mxCESU8`
  (build.rs:82; xsnap build.rs:139-144 explains: surrogate pairs stored as two 3-byte sequences),
  and XS strings are NUL-terminated C strings (the shim uses `c_strlen`/`strncpy`, :427-428), so
  U+0000 must be stored in an overlong form. The shim copies raw bytes and the Rust side applies
  `String::from_utf8_lossy` (lib.rs:525). Every astral character, lone surrogate, or NUL in a
  completion or error string is mangled on the oracle side only (finding 1). This is the
  reference value of a differential oracle, so it manufactures false divergences and, in the
  lone-surrogate case, a count mismatch (3 vs 1 U+FFFD) that contradicts interp.rs:10889.
- **Duplication → drift.** The Rust copy-out exists three times (lib.rs:264-296, 301-335,
  415-430); the C install block exists three times (:335-348, :514-527, :806-819) and the `$262`
  block twice (:351-368, :528-545; the module-run entry omits `$262`); the completion-value copy
  exists three times (:424-431, :593-599, :891-896) and only two set `result_len`. The one
  observed bug (finding 2) is exactly a drift between copies. A single `capture_completion(the,
  out)` helper in C and one `impl XsOracleResultRaw { fn take(&mut self) -> OracleOutcome }` in
  Rust would remove the class.
- **ABI by convention.** Two hand-mirrored `#[repr(C)]` structs with duplicated constants
  (`16384`, `256`, `64`) and no compile- or test-time layout check (finding 3). A drift here is
  not a test failure but a C write past a Rust stack struct.
- **Error model is a single `ok` bit.** JS throw, console-mode parse stub, `String()`-coercion
  failure of the completion value, and platform aborts (`XS_JAVASCRIPT_STACK_OVERFLOW_EXIT`,
  `XS_NOT_ENOUGH_MEMORY_EXIT`, … all longjmp with `the->exitStatus` set, xsnap-platform.c:355-368)
  arrive as `ok == 0` plus a best-effort string that is EMPTY when `mxException` is undefined
  (:109-110). The consumer is reduced to `oracle_parsed && oracle_error.is_empty()` to guess
  "host abort" and documents the follow-up itself (262 xst.rs:581-589). `exitStatus` is one
  `txU4` away from being surfaced (finding 4).
- **No cancellation or resource bound at the seam.** The shim never sets `meterInterval`/a crank
  limit and exposes no abort; a non-terminating guest (`for (const i=0; i<1; i++){}` on XS,
  xst.rs:1415-1416; catastrophic backtracking, fuzz regexp.rs:96-99) can only be abandoned by
  leaking the OS thread with its live machine (xst.rs:1409-1420: "Leak the worker"). That thread
  keeps a 32 MiB stack (xst.rs:222) plus the XS heap and burns a CPU until the batch exits. This
  is the most concrete in-tree mechanism for the README's "the XS oracle accumulates memory across
  a whole-tree walk" (README:170-171) (finding 5). A `the->meterInterval` + `fxAbort` path or a
  per-call meter ceiling argument would turn it into a normal `ok == 0` outcome.
- **Definite per-call leak in the compile-only path.** `xs_oracle_compile_module` parses to a
  malloc'd `txScript` and never runs or deletes it (:665-689). In the run paths `fxRunScript`
  consumes the script (XS API contract, memory of xsRun.c — medium-high confidence); here nothing
  does (finding 6).
- **Inconsistent NULL discipline.** `script` is NULL-checked in `fxLoadModule` (:237) and
  `xs_oracle_compile_module` (:667) but dereferenced blind in `xs_oracle_run` (:379) and
  `xs_oracle_run_cranks` (:563). Whether `fxParseScript` can return NULL at the pin (parser
  memory-exhaustion longjmp, or non-console mode) I could not verify (finding 7).
- **Safe API forwarding unchecked indices into C.** `pub fn regexp(.., start: i32)` (lib.rs:171)
  is a safe function; `start` is handed to `fxMatchRegExp` as a byte offset into a C string with
  no range check on either side (:1007-1008), and `subject_len` is deliberately unused
  (:1000-1004). The `// Safety:` comment (:180-181) does not mention `start`. Today's callers
  keep `0 <= start <= len` (fuzz regexp.rs:67-71; parity tests use fixed offsets), so the
  soundness of the seam depends on caller discipline (finding 8).
- **Width asymmetry after a real finding.** The regexp result struct was widened to `txU8`/`u64`
  after finding 5d122a6fc10babd9; the script/module structs still carry `computrons`/`meter_raw`
  as `txU4` (:43-44, :418-419, :588-589, :869-870). `meter_raw` wraps every 65536 computrons
  (documented "diagnostic", but `probe.rs:76` derives a fractional part from it and 262 stores it
  `as u64`, 262 lib.rs:547) (finding 9).
- **Error channel has no truncation signal.** `error[256]` (:47) with `strncpy … 255` (:115,
  :878, :988) and no `error_len`; 262 compares `oracle.error == ironhorse_error` byte-for-byte
  (262 lib.rs:533). Same class as 493390fc0397 (finding 10).
- **Observation is not side-effect-free in multi-crank mode.** Between crank i and i+1 the shim
  runs `fxToString` on crank i's completion value on the SAME machine (:592). That allocates
  (perturbing later allocation metering/GC timing the port may not mirror) and can execute guest
  `toString` code with side effects visible to crank i+1 — a result-relevant divergence source that
  is the harness's, not the engines' (finding 11). The single-crank entry is unaffected because
  the machine is discarded.
- **Build robustness.** `rerun-if-changed` covers 4 files but not the XS sources or
  `xsnap-platform.h`; a local pin bump keeps the stale static library until `cargo clean`
  (finding 12). CI is saved by fresh-checkout mtimes, not by the declaration. No sanitizer or
  Miri lane despite the design's promise (finding 13). `__thread`, `pthread`, `-Wno-*` and
  `realpath` make the crate POSIX/GCC-only (acceptable for dev/CI; undocumented).
- **Acceptance signal for module compile lives in the wrong layer.** Rust recognizes a module by
  a three-opcode trailer (`126 … 187 68`, lib.rs:439-441) because the C entry discards
  `parser->errorCount`; yet the shim already drives a raw `txParser` in `fxEndorLoadScript`
  (:183-212) and could report the count exactly (finding 14).
- **Hidden state:** `gEndorClusterReady` (:56), the lifecycle mutex (:72), the thread-local
  module latch (:716), the intentionally never-terminated shared cluster (:273-276). The
  `Option<T>` return type erases the negative `rc` (lib.rs:260-262 etc.).
- **Determinism hazards (harness-level only):** `run_module_dir` keys modules by `realpath` of a
  caller temp directory (:837-838, :850), so anything exposing module ids (`import.meta.url`) is
  per-run; the shim test avoids it with `typeof import.meta` (lib.rs:610). Test temp dirs under
  `std::env::temp_dir()` keyed by case name (lib.rs:554) collide across concurrent test binaries.
- **Geometry gap:** the oracle runs with `stackCount = 64Ki` (:256) vs production xsnap 4096
  (xsnap lib.rs:32); the shim argues computrons are geometry-independent (:249-250), but the
  overflow point is result-relevant for deep-recursion tests, and interp.rs:152 tunes the port to
  the shim's geometry, not production's. Deliberate and documented; worth remembering when a
  RangeError-vs-completion disagreement with production xsnap appears.
- **Examples** index bytecode with unchecked `code[pc + o]` (probe.rs:9-14, modprobe.rs:10-11)
  and can panic on truncated operands; dev tools, low.
- **Panics/unwraps in the crate:** none in library code; `unwrap`s only in tests and build.rs
  (`CARGO_MANIFEST_DIR`, :19).

## Candidate findings (most architecturally significant first)

1. **CESU-8 reference strings are mis-decoded at the seam** — `src/lib.rs:525` (`cstr_field`),
   `csrc/xs_shim.c:425-428`, `build.rs:82` (`mxCESU8`).
   Claim: any completion or error value containing an astral character, a lone surrogate, or
   U+0000 is rendered differently by the oracle than by the port, producing a false result
   divergence (astral: 6 × U+FFFD vs the character; lone surrogate: 3 × U+FFFD vs 1; NUL:
   2 × U+FFFD vs `"\0"`, the last assuming XS's overlong-NUL encoding).
   Evidence: `String::from_utf8_lossy(&buf[..end]).into_owned()` (lib.rs:525);
   `.define("mxCESU8", Some("1"))` (build.rs:82); "Lone surrogates render as U+FFFD, matching the
   oracle shim's lossy decode" (interp.rs:10889 — contradicted by the rustc check in this session).
   Why: the oracle's one job is to be the faithful reference string; a decode that is wrong for
   the engine's own encoding silently converts a whole class of correct port results into
   "divergences" and hides real ones behind U+FFFD collisions. Fix is local: decode CESU-8 to
   UTF-16 units and render with the same `from_utf16_lossy` the port uses (or compare units).
   Confidence: high on mechanism (empirical decode + in-repo `mxCESU8` doc); cannot execute the

## What is done well

- Ownership across the FFI is explicit and correct: C mallocs, Rust copies into owned `Vec`s,
  then frees through the C `xs_oracle_free` (never `libc::free`), which NULLs pointers so a
  double call is harmless (lib.rs:264-296; xs_shim.c:459-469). `Option` on the negative `rc`
  keeps "machine failed" separate from "guest threw".
- The catch-side stringification runs under a nested `mxTry` with a fixed fallback tag, closing a
  real `fxAbort`-with-empty-jump-chain hazard (xs_shim.c:97-124; commit 5f52705d).
- Thread-safety reasoning is written down where the bug was: the create/delete mutex + latch
  explains the unsynchronized cluster count and the observed glibc aborts, and keeps execution
  parallel (xs_shim.c:58-72, 267-287); the module reject latch is `__thread` for the same reason
  (:708-716).
- Past crash classes are locked by named tests with the mechanism explained (home-object stamping
  from the stack top, lib.rs:709-793; 64-bit regexp meter, :685-707; truncation, :540-548), so a
  regression fails a test instead of coring a sweep.
- `fxEndorLoadScript` improves on xst.c by marking setjmp-crossing locals `volatile` and
  closing the `FILE*` on the error path (xs_shim.c:183-212).
- build.rs states precisely why it does not depend on the xsnap crate and fails loudly with the
  exact recovery command when the submodule is absent (build.rs:6-13, 34-42).
