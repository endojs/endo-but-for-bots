# Lens: API surface and crate layering

Reviewer notes, HEAD 97d8de25. Every claim below was verified by reading the
cited lines in the current tree.

## 1. Assessment

The crate graph is sound where it was designed and accidental where it was
not. Two seams are genuinely well built. First, the compiler/VM seam is
correctly dependency-inverted: `ironhorse_vm::interp::SourceCompiler`
(interp.rs:89) lets the VM own linkage, realm identity and lifetime while the
compiler owns only source→bytecode, and `ironhorse-compile` is only a
*dev*-dependency of `ironhorse-vm` — the opposite of the `CC --> VM` edge the
design diagram draws, and better than it. Second, the persistence layer's
inner structure is disciplined: `ValidatedSnapshot` is a real proof token
whose constructor is `pub(crate)` (image.rs:424), the container and store
paths call the same decoders and the same bounds gate, and the store's
integrity stack (domain-separated leaves, per-class Merkle trees, seal chain)
is shared code rather than three copies.

Everything outside those two seams is a fork of call sites wearing the
vocabulary of a seam. Three findings carry that verdict.

**There is no engine abstraction anywhere.** The design says the `xsnap`
`Machine` API is "preserved verbatim … behind an engine selection, so the
supervisor, the worker platforms, the reactive pump, suspend and resume, and
the embedded JS bundles are engine-agnostic" (designs/ironhorse-engine.md:723,
727-731). In the tree, `rust/endo/src/engine.rs:10` `Engine` has exactly two
XS-typed variants; `engine_for_spawn_request` dispatches on *platform* only;
no trait in `rust/endo/src` abstracts an engine (the only two traits are
`HttpClient` and `GitCas`); `-e ironhorse` is a `match` on a string in
endor.rs:83/144. `ironhorse_engine::engine::Machine` (ironhorse_engine.rs:137)
has six methods against `xsnap::Machine`'s thirty, and none of the metering
(`begin_metering`/`set_meter`/`run_promise_jobs_metered`/`set_crank_limit`),
snapshot, or host-function verbs. Consequently the daemon runs Ironhorse
cranks with no meter armed and no step ceiling — `session.machine_mut()
.run(&bytecode)` at ironhorse_engine.rs:572 — while the XS path calls
`begin_metering(DEFAULT_METERING_INTERVAL)` (xsnap/src/lib.rs:1743). Every
downstream design promise that rides "engine-agnostic supervisor" is not
merely unimplemented; it has no place to attach.

**`ironhorse-vm`'s public surface is not an API, it is the absence of one.**
`lib.rs:28` declares `pub mod interp`, which publishes all 241 `pub const
*_METERING` values, 36 `pub struct`s, 6 `pub enum`s and 87 `pub fn`s of a
44,942-line file. Grepping the rest of the workspace and `rust/endo` for any
`*_METERING` identifier finds only *comments* — not one external use. Of the
87 public `Interp` methods, 21 are `restore_*` and ~24 are `*_snapshot`,
existing solely so `ironhorse-snapshot` can reach the machine's interior; and
`Interp` exposes `pub slots: SlotArena` / `pub chunks: ChunkArena`
(interp.rs:3723-3725), the raw heap, mutably, to every consumer including
`endo`. Because Rust has no friend visibility, this is the *only* way the
current split can work — which is the point: the vm/snapshot split is not a
module boundary, it is a compilation-unit boundary with the internals
published to make it compile. The compile crate does the same
(`pub mod ast/coder/lexer/parser/scoper/...` plus `pub use
ironhorse_regexp::unicode`, lib.rs:18-32).

**Version identifiers are five independent hand-strings with no compatibility
document.** `IRONHORSE_FORMAT_VERSION = 12` (format.rs:197, read range
1..=12), `STORE_SCHEMA_VERSION = 23` (store.rs:89, min 5, an 18-step ladder),
`COST_TABLE_VERSION = "ironhorse-meter-1"` (meter.rs:26),
`PARSE_METER_RELEASE = "ironhorse-meter-0"` (compile/meter.rs:22),
`INTL_DATA_VERSION = "ironhorse-intl-2026a"` (interp.rs:4422). Grepping all of
`designs/*.md` and `rust/engine/README.md` for any of those five identifiers
returns **nothing**. The two that have migration machinery (format, schema)
are bumped together in the seam design's changelog; the three that gate
*semantics* have none: the cost table is a bare equality gate that bricks
every persisted store on any recalibration (store.rs:3150, image.rs:4444), the
parse meter is not carried in `METR` at all, and `INTL_DATA_VERSION` is
published to guests as `Intl.__ironhorseDataVersion` (interp.rs:6603) while
the actual Unicode data comes from external `icu_*` crates it does not cover.

Two smaller structural notes. The safety obligations of the persistence traits
are prose or default-open: `HeapStore::commit` says "Must enforce the epoch
discipline via `check_epoch`" (store.rs:1776) and three hand-written
implementations each remember to; `MachineSnapshot::persist_gate` defaults to
`Ok(())` (machine.rs:139). And the one mechanism that ties the vm's side
tables to the snapshot ledger is a downstream test that reads
`../ironhorse-vm/src/interp.rs` as **text** (sidetable.rs:662-668) — the
layering invariant is enforced by a grep, not by a type.

## 2. Findings

### F1 — No engine abstraction: the Ironhorse `Machine` is a parallel type, not an implementation of xsnap's surface
- severity: high · confidence: high · category: api-boundary · novelty: partially-known (digest lead `integration-endo` @ engine.rs:10; docs-ci @ ironhorse_engine.rs:147)
- file: rust/endo/src/ironhorse_engine.rs:137 · other sites: rust/endo/src/engine.rs:10-21, rust/endo/src/bin/endor.rs:83, rust/endo/xsnap/src/lib.rs:326-378, designs/ironhorse-engine.md:723
- claim: No trait in `rust/endo` abstracts an engine, `Engine` has no Ironhorse variant, and `ironhorse_engine::engine::Machine` implements none of `xsnap::Machine`'s metering, snapshot, host-function or pump verbs — so the design's "same surface behind an engine selection" is a fork of call sites.
- evidence:
  - `pub enum Engine { Separate { platform, command, args }, Shared { bootstrap, creation: &'static xsnap::ffi::XsCreation, label } }` (engine.rs:10-21)
  - `impl Machine { pub fn new … evaluate … eval … eval_strict … intrinsics … vm_machine }` — six methods (ironhorse_engine.rs:147-199)
  - xsnap: `begin_metering`, `end_metering`, `current_meter`, `current_computrons`, `set_meter`, `run_promise_jobs_metered`, `write_snapshot`, `from_snapshot`, `suspend`, `resume`, `define_function`, `run_promise_jobs`, `quiesce` (lib.rs:218-487)
  - `grep '^pub trait ' rust/endo/src/*.rs` → only `HttpClient`, `GitCas`
- impact: The supervisor cannot spawn, meter, admission-gate, suspend or resume an Ironhorse worker at all; every reconciliation row in the design's table ("Machine API preserved", "crank lifecycle … unchanged") is unattached. The cost of retrofitting grows with each new call site added against the concrete `xsnap::Machine`.
- recommendation: Extract the surface the daemon actually calls into a `trait JsMachine` in `rust/endo/src/engine.rs`, implement it for `xsnap::Machine` first (a mechanical no-op change), then for the Ironhorse seam; add an `Engine::Ironhorse` variant and make `-e` select it in `engine_for_spawn_request`, not in `endor.rs`'s string match. Land the trait *before* more verbs.

### F2 — The daemon never arms the meter, and the pump/quiesce verbs the design names are private dead code
- severity: high · confidence: high · category: metering / api-boundary · novelty: partially-known (leads: integration-endo @ :572, interp-05 @ 10749, store-seam ledger @ interp.rs:21449)
- file: rust/endo/src/ironhorse_engine.rs:572 · other sites: ironhorse-vm/src/interp.rs:10667 (`arm_meter`), :21449 (`has_pending_jobs`), :21460 (`run_promise_jobs`), rust/endo/xsnap/src/lib.rs:1743
- claim: No code path in `rust/endo` calls `arm_meter`/`rearm_meter`/`reattach_meter_host` or `run_bounded`, so a guest `while(true){}` delivered through `PersistentMachine::eval` or `Machine::evaluate` never terminates; and the per-machine pending-jobs query the design promises is a private `fn` marked `#[allow(dead_code)]`.
- evidence:
  - `let outcome = session.machine_mut().run(&bytecode);` (ironhorse_engine.rs:572) — `run` is the default-unbounded entry
  - `grep -rn 'arm_meter\|rearm_meter\|reattach_meter_host\|run_bounded' rust/endo/src/` → no matches
  - `/// The design's daemon pump loop queries this per-machine … it is exposed for the embedding.` then `#[inline] #[allow(dead_code)] fn has_pending_jobs(&self) -> bool` (interp.rs:21444-21451) — `fn`, not `pub fn`
- impact: Process-killing DoS from guest code on the only production Ironhorse execution path, and the design's replacement for xsnap's global `fxHasPendingJobs` latch is unreachable from any embedder. `StoreSession::machine_mut()` (machine.rs:856) means the fix is available today; nothing consumes it.
- recommendation: Arm the meter in `PersistentMachine::open` and re-arm per crank with the same `DEFAULT_METERING_INTERVAL`/`CRANK_LIMIT` policy the XS path uses; make `has_pending_jobs`/`run_promise_jobs` `pub` and put them on the F1 trait. Add a test that a non-terminating crank returns `Halt::MeterAbort`.

### F3 — Two workspaces, two lockfiles: 21 of 48 shared dependencies resolve differently, and the shipped engine build is never tested
- severity: high · confidence: high · category: determinism / api-boundary · novelty: partially-known (integration-endo lead "two workspaces, two lockfiles"; the measurement and the CI consequence are new)
- file: Cargo.lock:1 · other sites: rust/engine/Cargo.lock:1, Cargo.toml:6, .github/workflows/ci.yml:746-750
- claim: `Cargo.lock` and `rust/engine/Cargo.lock` resolve different versions for 21 of the 48 crates they share — including the whole `icu`/`zerovec` stack that backs `String.prototype.normalize` and `Intl.Segmenter` — and no CI job builds or tests `ironhorse-vm`/`ironhorse-snapshot` in the root workspace, so the engine inside the shipped `endor` binary is a build nobody tests.
- evidence (computed by parsing both lockfiles):
  - `icu_locale_core: root=2.2.0 engine=2.3.0`, `icu_provider: root=2.2.0 engine=2.3.0`, `zerovec 0.11.6/0.11.7`, `zerotrie 0.2.4/0.2.5`, `tinystr 0.8.3/0.8.4`, `potential_utf 0.1.5/0.1.6`, `litemap 0.8.2/0.8.3`, `hashbrown 0.17.1/0.16.1`, `syn 2.0.117/3.0.3`, `serde 1.0.228/1.0.229`, … (21 total)
  - `interp.rs:39511 use icu_segmenter::…`, `interp.rs:40273 icu_normalizer::ComposingNormalizer::new_nfc()` — both guest-observable
  - ci.yml: engine lane is `working-directory: rust/engine … cargo test -p ironhorse-vm -p ironhorse-snapshot`; the root lane is `cargo test -p ironhorse-store-sqlite` only
  - no `--locked`/`--frozen` in any cargo invocation in ci.yml; no `rust-toolchain.toml` for either workspace (only `ironhorse-fuzz/fuzz/` and `rust/ocapn_noise/` have one); no `[profile]` overflow-checks setting in either root manifest
- impact: For an engine whose stated property is "identical inputs produce identical computrons on every host, architecture, and build", the artifact under test and the artifact under ship are different dependency graphs, drifting freely, on an unpinned toolchain, with overflow checks off in release. Any divergence introduced by a transitive bump lands in production without a failing test.
- recommendation: Either fold `rust/engine` into the root workspace (one lock, one resolution) or add a CI step that diffs the shared subset of the two lockfiles and fails on disagreement. Add `--locked` to every CI cargo invocation, a `rust-toolchain.toml` at both workspace roots, and an explicit `[profile.release] overflow-checks = true` for the consensus artifact.

### F4 — `Halt` conflates completion, internal control transfer, engine gaps, hostile-input refusals and internal invariant violations; every verification instrument therefore reads an engine bug as a coverage gap
- severity: high · confidence: high · category: error-model · novelty: partially-known (interp-01 lead @ :3517, fuzz lead @ lib.rs:1699, t262 lead @ xst.rs:450; the cross-instrument framing is new)
- file: ironhorse-vm/src/interp.rs:3517 · other sites: ironhorse-fuzz/src/lib.rs:1698-1701, ironhorse-262/src/xst.rs:449-452, rust/endo/src/ironhorse_engine.rs:91-97,116
- claim: `Halt::Unsupported(&'static str)` carries 269 distinct labels including 17 internal-invariant guards (`end:frame-underflow`, `yield:stack-underflow`, `async:non-boundary-return`, …), and both differential instruments discard *every* `Unsupported` unexamined, so an interpreter invariant violated on valid oracle-produced bytecode is reported as "unlanded feature" and can never redden a build.
- evidence:
  - `if let ironhorse_vm::Halt::Unsupported(_) = ironhorse.halt { return Ok(()); }` — "Out-of-subset opcode: not a divergence, just uncovered ground." (fuzz lib.rs:1698-1701)
  - `Halt::Unsupported(op) => return Verdict::RunSkip(format!("unsupported-opcode:{}", op))` (xst.rs:450)
  - `grep -o 'Halt::Unsupported("[^"]*")' interp.rs | sort -u | wc -l` → 269; among them `end:frame-underflow`, `eval:frame-underflow`, `yield:stack-underflow`, `private:missing-brand`, `function:missing-segment`
  - `Halt::Resume(usize)`, `Yield(Slot)`, `Await(Slot)`, `AsyncYield(Slot)` are documented "Consumed by the dispatch loop" / "never seen by the top-level run" yet share the type that `EvalOutcome.halt` (ironhorse_engine.rs:116) publishes from the daemon
- impact: A class of engine bug is structurally invisible to the two instruments the design leans on. `Throw(String)`/`Decode(String)` additionally discard the thrown value and the decode reason, so a host cannot act on either.
- recommendation: Split the type: a host-visible `Completion { Return, MeterAbort, StepLimit(u64), StackOverflow(usize), Throw(Value), Decode(DecodeError), NotImplemented(&'static str), Refused(&'static str) }` and a crate-private `Transfer { Resume, Yield, Await, AsyncYield }`. Make `EngineInvariant(&'static str)` its own variant, and make both the fuzz comparator and `evaluate_positive` treat it as a hard failure. `#[non_exhaustive]` the public one.

### F5 — The restore seam is 21 public, inconsistently-validating mutators on `Interp`, with the proof token stranded in the downstream crate
- severity: high · confidence: high · category: api-boundary · novelty: partially-known (interp-02 lead @ 9232 rated low; interp-04 @ 9444)
- file: ironhorse-vm/src/interp.rs:8273 · other sites: interp.rs:9181, :9205, :9120, :9666, ironhorse-snapshot/src/image.rs:419-437, ironhorse-snapshot/src/machine.rs:629
- claim: `Interp` exposes 21 `pub fn restore_*` verbs with three different failure disciplines — 5 return `()` and accept anything, 16 return `bool`, several `expect`/index internally — and the `ValidatedSnapshot` proof wrapper that is supposed to gate them lives in `ironhorse-snapshot`, so the engine cannot require it.
- evidence:
  - `pub fn restore_snapshot_state(&mut self, slots: SlotArena, chunks: ChunkArena, stack: Vec<Slot>, symbol_names: Vec<String>, meter: MeterState)` — returns `()` (interp.rs:8273-8280)
  - `pub fn restore_dates(&mut self, rows: Vec<(u32, u64)>) { for (owner, value_bits) in rows { self.dates.insert(SlotIndex(owner), f64::from_bits(value_bits)); } }` (interp.rs:9205) — no owner-kind, range or duplicate check
  - `pub fn restore_arguments_brands(&mut self, owners: Vec<u32>)` (interp.rs:9181) — same
  - vs. `pub fn restore_accessors(&mut self, rows: Vec<AccessorRow>) -> bool { … if !self.functions.contains_key(&function) { return false; } …}` (interp.rs:9502)
  - `impl ValidatedSnapshot { pub(crate) fn from_validated_image(image: MachineImage) -> ValidatedSnapshot }` (image.rs:424) — constructible only inside `ironhorse-snapshot`
- impact: The restore trust boundary is split across two crates by convention. The invariant "no unvalidated row reaches the engine" is not a property of the engine's type signatures; it is a property of the one caller that happens to be `image_to_interp`. Any second caller — a future backend, a tool, a test — gets no gate, and adding a 22nd side table adds a 22nd verb with a freely-chosen discipline.
- recommendation: Define the proof token in `ironhorse-vm` (e.g. `interp::RestoreToken`, constructible only via a vm-side `Interp::begin_restore()` that returns a `RestoreSession<'_>` owning all 21 verbs), and make every verb `Result<(), RestoreError>` so the discipline is uniform and the compiler enforces handling. Alternatively seal a `pub trait SnapshotAccess` on `Interp` whose supertrait is a private marker.

### F6 — `pub mod interp` publishes 241 metering constants and the raw arenas as external API with no consumer
- severity: medium · confidence: high · category: api-boundary / modularity · novelty: partially-known (vm-meter lead @ lib.rs:40)
- file: ironhorse-vm/src/lib.rs:28 · other sites: ironhorse-vm/src/interp.rs:3723-3725, :1839, ironhorse-compile/src/lib.rs:18-32
- claim: `ironhorse-vm`'s public surface is the interpreter's internals: `pub mod interp` exports 241 `pub const *_METERING`, 36 structs, 6 enums (including the ~280-variant `NativeMethod`) and 87 methods, none of the constants has a single non-comment consumer anywhere in the workspace or in `rust/endo`, and `Interp` publishes `pub slots` / `pub chunks` — the mutable heap.
- evidence:
  - `pub mod interp;` (lib.rs:28); `grep -c '^\s*pub const ' interp.rs` → 241, `pub fn` → 87 of 799 fns
  - `pub slots: SlotArena,` / `pub chunks: ChunkArena,` (interp.rs:3723,3725)
  - `grep -rn '_METERING' ironhorse-snapshot ironhorse-262 ironhorse-fuzz ironhorse-compile rust/endo` → matches only inside doc comments; `PROGRAM_INVOCATION_COMPUTRONS` (re-exported at lib.rs:50) has zero external uses
  - `ironhorse-compile` has the same shape: ten `pub mod`s plus `pub use ironhorse_regexp::unicode;` (lib.rs:18-32), re-publishing a leaf crate's module as its own API
- impact: Nothing distinguishes the surface `ironhorse-snapshot` needs from the surface that is an implementation detail, so refactoring the interpreter is a semver event and any consumer can bypass every invariant by writing to `interp.slots`. It also means the design's "unsafe budget"/API discussions have no artifact to point at.
- recommendation: Make `interp` private; keep a curated `pub use interp::{…}` list at the crate root (which already exists at lib.rs:40-51) and move the snapshot verbs behind the F5 restore session. Make `slots`/`chunks` private with `pub fn slots(&self) -> &SlotArena` accessors. Demote the metering constants to `pub(crate)` and expose a single versioned `cost_table()` datum (see F8).

### F7 — Persistence safety obligations are prose on a public trait, or default-open
- severity: medium · confidence: high · category: api-boundary · novelty: known-open (snapshot-store lead @ store.rs:1777)
- file: ironhorse-snapshot/src/store.rs:1776 · other sites: ironhorse-snapshot/src/machine.rs:139, ironhorse-snapshot/src/store.rs:3558, ironhorse-snapshot/src/store_file.rs:557, rust/endo/ironhorse-store-sqlite/src/lib.rs:857
- claim: `HeapStore::commit` states its admission obligation in a doc comment and three independently hand-written implementations each remember to call `check_succession` + `apply_batch`; `MachineSnapshot::persist_gate` defaults to `Ok(())`, so any implementor other than `Interp` gets no quiescence gate.
- evidence:
  - `/// Apply one checkpoint atomically. Must enforce the epoch discipline via [check_epoch] and drop rows beyond the new geometry.` `fn commit(&mut self, batch: &CheckpointBatch) -> Result<(), StoreError>;` (store.rs:1774-1777)
  - three call sites, each hand-rolled: MemoryStore store.rs:3559-3570, FileStore store_file.rs:573, SqliteHeapStore lib.rs:875/900/973
  - `/// The default is permissive for image-only implementors; [Interp] overrides it.` `fn persist_gate(&self) -> Result<(), MachineSnapshotError> { Ok(()) }` (machine.rs:137-141)
- impact: The single most consensus-critical invariant of the store — that no batch is admitted without succession and geometry checks — is enforced by three copies of a convention. A fourth backend, or one refactor of one copy, silently drops it and the store accepts a forged or replayed epoch.
- recommendation: Invert the trait: make `commit` a *provided* method that runs `check_succession` + `apply_batch` on cloned leaves and then calls a new required `fn commit_verified(&mut self, batch: &CheckpointBatch, leaves: &StoreLeaves) -> Result<(), StoreError>` that does only the medium-specific write. Make `persist_gate` a required method so a new implementor must decide.

### F8 — Five independent version identifiers, no compatibility document, and the one the doctrine says will change has no migration path
- severity: medium · confidence: high · category: api-boundary / docs-drift · novelty: partially-known (metering-version leads across interp-01/vm-meter/snapshot-tests; the "no single document" fact and the `INTL_DATA_VERSION` gap are new)
- file: ironhorse-vm/src/meter.rs:26 · other sites: ironhorse-compile/src/meter.rs:22, ironhorse-snapshot/src/format.rs:197, ironhorse-snapshot/src/store.rs:89, ironhorse-vm/src/interp.rs:4422, ironhorse-snapshot/src/store.rs:3150, ironhorse-snapshot/src/image.rs:4444
- claim: The engine carries five independently hand-maintained version identifiers; none of the five appears anywhere in `designs/*.md` or `rust/engine/README.md`; and unlike the container format (read range 1..=12) and the store schema (18-step ladder 5→23), `COST_TABLE_VERSION` is a bare equality gate with no registry, so any recalibration makes every persisted worker heap permanently unresumable.
- evidence:
  - `pub const COST_TABLE_VERSION: &str = "ironhorse-meter-1";` with `/// Bump the trailing number whenever any metering weight or check point changes.` (meter.rs:17-26) — over 241 constants in interp.rs, pre-weighted constants in `ironhorse-regexp/src/opcode.rs`, and `DEFAULT_KEYS` membership
  - `if meter.cost_table_version != COST_TABLE_VERSION { return Err(SnapshotError::CostTableMismatch{…}) }` (image.rs:4444) and the store twin (store.rs:3150-3155)
  - `pub const PARSE_METER_RELEASE: &str = "ironhorse-meter-0";` (compile/meter.rs:22) — same namespace, different number, never carried in `METR`
  - `const INTL_DATA_VERSION: &str = "ironhorse-intl-2026a";` (interp.rs:4422) published to guests at interp.rs:6603, never serialized, and does not cover the external `icu_*` data crates it describes
  - `grep -rn 'COST_TABLE_VERSION\|IRONHORSE_FORMAT_VERSION\|STORE_SCHEMA_VERSION\|PARSE_METER_RELEASE\|INTL_DATA_VERSION' designs/*.md rust/engine/README.md` → no output
- impact: There is no place a maintainer can look to answer "what does bumping X break?". The doctrine's central planned change (recalibrating the meter) is the one with no migration story; the parse meter can drift silently under a machine already suspended; and the Intl data version guests can read is decorative.
- recommendation: Add `designs/ironhorse-compatibility.md` (or a `versions.rs` module) that names all five, states which artifacts each gates, and states the bump rule and migration path for each. Reify the cost table as a single data structure with a derived digest so `COST_TABLE_VERSION` is *computed*, not remembered, and carry `PARSE_METER_RELEASE` in `METR` alongside it. Give the cost table the same registry-and-ladder treatment the store schema already has, or state explicitly that a bump requires draining every worker.

### F9 — Structured engine errors are collapsed to `String` at the daemon seam, erasing redeliverable vs. poisoned vs. permanent
- severity: medium · confidence: high · category: error-model · novelty: known-open (integration-endo lead @ ironhorse_engine.rs:381)
- file: rust/endo/src/ironhorse_engine.rs:381 · other sites: :591, :646, :560-568, ironhorse-snapshot/src/store.rs:101
- claim: `StoreError` implements neither `Display` nor `std::error::Error` anywhere in the workspace, so the seam flattens its 16 variants with `{e:?}` into `MachineError::Store(String)` — the same variant that also carries "rewind failed" (session poisoned) and the deterministic `PendingStateUnsupported` refusal — leaving a supervisor no way to decide whether to redeliver.
- evidence:
  - `fn store_err(e: ironhorse_snapshot::store::StoreError) -> MachineError { MachineError::Store(format!("{e:?}")) }` (ironhorse_engine.rs:381-383)
  - `grep -n 'impl .*StoreError' ironhorse-snapshot/src/*.rs` → only `impl From<SnapshotError> for StoreError` (store.rs:164)
  - `return Err(MachineError::Store(format!("rewind failed after a crank halt ({}): {rewind_err}", describe_halt(&halt))))` (:591-594) — a poisoned session and a transient I/O error share one variant
  - `RelinkError` is a clean two-variant enum (interp.rs:3636-3642) and is likewise stringified at :560-568
- impact: The three outcomes with opposite supervisor semantics — transient I/O (retry), deterministic refusal (never retry), poisoned session (tear down) — are indistinguishable at the only boundary that can act on them. The comment at :611-617 shows the authors already found one instance of this class the hard way.
- recommendation: `impl Display + std::error::Error` on `StoreError`; replace `MachineError::Store(String)` with `Store { kind: StoreFailure, source: StoreError }` where `StoreFailure ∈ {Transient, Refused, Poisoned}`, classified once from the variant. Mark both enums `#[non_exhaustive]`.

### F10 — The vm↔snapshot coverage contract is enforced by parsing the upstream crate's source text from a downstream test
- severity: medium · confidence: high · category: verification / modularity · novelty: new
- file: ironhorse-snapshot/src/sidetable.rs:662 · other sites: ironhorse-vm/tests/gc_visitation_registry.rs:34, ironhorse-snapshot/src/sidetable.rs:642
- claim: The only mechanism that fails when a new `Interp` side table is added without a ledger row is a `#[test]` in `ironhorse-snapshot` that `read_to_string`s `../ironhorse-vm/src/interp.rs` and string-matches its field list, so the layering invariant is checked by grep rather than by the type system and is blind to any field whose type is declared outside `interp.rs`.

## 3. Strengths

- **The compiler/VM seam is genuinely well designed and better than the design doc.** `SourceCompiler` (interp.rs:82-101) inverts the dependency with an explicit rationale — "Rather than couple `Interp` to a concrete front end (which would make the VM depend on `ironhorse-compile` and invert the layering), the host installs a compiler through this trait" — and the manifests honour it: `ironhorse-compile` is only a *dev*-dependency of `ironhorse-vm`, and the two error arms (`Syntax` → catchable realm `SyntaxError`; `Unsupported` → honest gap) are the right split.
- **The proof-token pattern is real where it fits in one crate.** `ValidatedSnapshot`'s constructor is `pub(crate)` (image.rs:424) and `image_to_interp` consumes it by value, so within `ironhorse-snapshot` you cannot restore an unvalidated image; and `read_machine` itself runs the semantic bounds gate (image.rs:4645), so even the lower-level public entry is not a bypass of bounds checking.
- **Store integrity is shared code, not copied code.** `check_succession`, `check_batch`, `apply_batch`, `leaf_hash`, `compute_root`, `RootLedger` are one implementation used by all three backends, and the two migration writers share `atomic_replace_and_reload`. The backend-parameterized `store_suite` (feature-gated out of production builds) is the right instrument for keeping backends honest.
- **The nested-workspace decision is documented with a real reason** (root `Cargo.toml:3-5`; `ironhorse-store-sqlite/Cargo.toml:1-8`): the engine crates are `forbid(unsafe_code)` and zero-C, the SQLite backend links C, and putting the backend outside the engine workspace keeps that budget honest. The layering of `HeapStore` (trait in snapshot) / backend (in `rust/endo`) is the correct direction.
- **Cross-crate error types are mostly well-shaped at the source.** `RelinkError` (interp.rs:3636) is a two-variant enum with no strings; `StoreError` (store.rs:101) has sixteen precise, data-carrying variants including `EpochMismatch`, `BaselineMismatch`, `SummaryMismatch`, `RowLength`; `SnapshotError` reuses one vocabulary across the container and store paths. The defect is only what happens at the daemon boundary (F9).
- **Determinism hazards at seams are named and fixed where they were found.** `Compartment::evaluate*` sorts endowments by id before seeding, with the reason in the comment ("iterating the HashMap seeds per-process SipHash order into the global object's property CHAIN … snapshot bytes would differ between replicas", compartment.rs:290-296) — exactly the kind of seam-level care this architecture needs more of.

## 4. Recommended architectural direction

**Draw the engine boundary once, in `rust/endo`, and make everything else
serve it.** The root cause of F1, F2, F11 and F12 is that no type in the tree
answers "what is a JS machine to this daemon?". Extract a `trait JsMachine`
from the ~15 `xsnap::Machine` verbs the daemon actually calls, implement it
for `xsnap::Machine` as a mechanical no-op, then implement it for an Ironhorse
type that owns an `Interp` directly (not the stateless `compartment::Machine`).
Give `Engine` an `Ironhorse` variant and route `-e` through
`engine_for_spawn_request`. Doing this first makes the metering gap (F2) a
compile error rather than an omission, gives `set_source_compiler` (F12) an
obvious home, and turns "the Machine API is preserved verbatim" from prose
into a type-checked claim.

**Turn the vm↔snapshot split from a compilation boundary into a designed
one.** `ironhorse-vm` should publish two surfaces: a small embedder API (run,
meter, jobs, quiesce, GC) and an explicitly-marked persistence surface behind
a proof-carrying `RestoreSession` whose token type lives in the vm (F5), with
`interp` itself private and the arenas behind accessors (F6). The 21 restore
verbs become uniform `Result<(), RestoreError>` methods on that session, and
the ledger that ties side tables to snapshot coverage moves into the vm as a
macro that *defines* the fields and *emits* the enum, so the downstream
crate consumes a type instead of re-parsing source text (F10). Applied
together, these convert three hand-maintained parallel enumerations (GC roots,
snapshot rows, persist-gate holders) into one declaration — which is the only
way the "add a side table, edit nine places" cost stops growing.

**Give the version story a single owner.** Five identifiers (F8) with
different bump rules, two of them sharing the `ironhorse-meter-N` namespace,
none of them mentioned in any design or in the 2,953-line README, is not a
versioning scheme. Reify the cost table as data with a derived digest so its
version is computed; carry the parse meter's version beside it in `METR`;
write one compatibility document that states, per identifier, what it gates,
what breaks on a bump, and whether a migration exists. Until the cost table
has a registry, a recalibration is a fleet-wide worker drain — a fact worth
writing down before it is discovered operationally. In the same pass, close
the build-identity gap (F3): one lockfile or a lockfile-diff gate, `--locked`
in CI, a pinned toolchain at both workspace roots, and `overflow-checks` on
for the consensus profile. For an engine whose whole value proposition is
determinism, the fact that the tested build and the shipped build differ in 21
dependency versions is the finding that should be fixed first.
