# Lens: Metering architecture and the doctrine gap

Reviewer: deep-architecture pass. Every claim below was verified by reading the cited
lines in the current tree (HEAD 97d8de25, `rust/engine`). Region-map leads that I could
not confirm are not reported.

## 1. Assessment

**Verdict: there is no cost table. There is a meter *primitive* — good, small, faithful,
tested — attached to 219 XS-parity residuals scattered across three crates under two
uncoordinated version strings, and the project's own CI makes the doctrine's central
mechanism (recalibration at an `ironhorse-meter-N` bump) unreachable.**

The design (§ Metering, revised 2026-07-04) promises four things: (a) a per-opcode /
per-builtin **cost table** derived from calibration instrumentation, (b) frozen and
stamped `ironhorse-meter-N`, with **previous tables addressable by version**, (c) a meter
that is "the best available deterministic proxy for real (wall-clock) execution cost",
and (d) XS-computron parity as an **explicit non-goal**, with the oracle result-only and
computron comparison advisory. The code delivers none of the four, and the gap is
structural rather than cosmetic.

*(a) No table.* `meter.rs` holds 6 primitive weights, all literally XS's
(`CODE_METERING = 1 << 16`, `SLOT_ALLOCATION_METERING = 1 << 8`, …). Everything else is
210 `pub const …_METERING: u64` in `interp.rs` (`ASYNC_INSTANCE_METERING = 414600`
:342, `DEFINE_PROPERTY_NEW_RESIDUAL_METERING = 622024` :452), each documented as
"calibrated raw-exact against the pin `48ee02d8cfe0`" — i.e. back-fitted residuals of a
2023-era C build. Some are explicitly C-build artifacts
(`RESUMED_HANDLER_THROW_METERING`, :135–139: "a property of the COMPUTED-GOTO dispatch
build … in a plain-`switch` build this surcharge would be WRONG"). Two more weights live
in `ironhorse-regexp/src/opcode.rs:34,38` as XS constants with **no version string at
all**, pre-weighted so the VM's table cannot re-weight regexp steps. One more lives in
`ironhorse-compile/src/meter.rs:26` under a *different* release id. Provenance is
heterogeneous inside one "frozen table": some entries are isolated-raw-gap
calibrations against XS, some are self-described "advisory … directional" hand picks
(:453–460). The design's per-opcode table does not exist at all: the loop charges a flat
`CODE_METERING` for every opcode (:11365), while `cost.rs:312` already *knows* that
`GET_PROPERTY` is `PropertyChain` and `OBJECT`/`ARRAY` are `AllocSize` — and feeds
nothing.

*(b) The version is a string nobody checks.* `COST_TABLE_VERSION = "ironhorse-meter-1"`
is enforced fail-closed at snapshot admission (`image.rs:4444`) and store migration
(`store.rs:2010`) — a genuinely good gate — but **no artifact binds that string to the
219 weights**. Change `ASYNC_INSTANCE_METERING` and every gate still passes; the 15
inline `assert_eq!(out.computrons, N)` locks cover programs of 6–87 computrons and touch
a small fraction of the table. And no prior table is retained: a bump does not make old
outcomes addressable, it *bricks every existing snapshot* (`CostTableMismatch`).

*(c) The meter models XS's data structures, not Ironhorse's.* `collection_find`
(:34435) is `entries().iter().position(…)` — a linear scan — while the metering around it
faithfully reproduces XS's hash geometry, `mxTableThreshold`, and the `fxNewChunk(len*8)`
rehash (`collection_table_resize` :34456–34490, including a "measured one-time `+8` raw"
:34486). `Map.get`/`has` charge *nothing* proportional to size. Building an n-entry Map
is O(n²) real work at O(n) metered cost. Memory is priced at 1 raw unit per byte:
`new ArrayBuffer(0x7FFFFFFF)` zero-fills 2 GiB for 32,768 computrons (:34411), and there
is no heap ceiling anywhere in `ironhorse-vm`. Runtime compilation costs **zero**:
`CompiledSource` (:55) has no meter channel, `eval_source` (:8005–8081) ticks nothing
between `compile_source` and dispatch, and `ParseMeter`/`parse_computrons` are referenced
only by tests. Meanwhile `check_meter` appears at 44 sites, **all** inside
`dispatch_at_inner` (11292–15870) — no native is interruptible, and the regexp matcher
accumulates into a local `u64` charged only after `match_regexp` returns
(`matcher.rs:130`, `interp.rs:20189`), so catastrophic backtracking cannot be aborted by
any crank limit.

*(d) Parity is the shipped acceptance bar.* 1,588 checked-in test262 cases carry the
`ironhorse-meter-exact` feature and two in-repo suites run them with
`gate_meter_exact: true` (`corpus_conversion_equivalence.rs:64`,
`regressions_dual_run.rs:64`), failing on `oracle_computrons != ironhorse_computrons`
(`xst.rs:473`). Every differential fuzz comparator returns `Err` on the same inequality
(`ironhorse-fuzz/src/lib.rs:1722`). `meter.rs`'s own first paragraph says the weights are
"exactly XS's weights" — nineteen lines above the paragraph asserting the opposite.
The practical consequence is the deepest finding here: **the recalibration mechanism the
doctrine rests on cannot be exercised.** Any weight change reddens ~1,600 CI gates, so
`ironhorse-meter-2` is not a version bump, it is a corpus regeneration. The engine is
frozen to XS 8.2.3's counts by its test suite while its design says XS parity is a
non-goal.

Finally, metering is **fail-open in three independent ways**: `check_meter` returns
`Continue` when no host closure is installed (:10749–10754) regardless of `interval`;
`Meter::begin`/`rearm` do `interval << 16` unchecked, so `arm_meter(1 << 48)` installs
`interval == 0` and silently disables metering entirely (`meter.rs:120`); and the
production embedder never arms at all — `arm_meter` has no caller in `rust/endo`.

## 2. Findings

### F1 — [critical] Regexp backtracking runs outside every meter check point; a metered crank cannot abort it
**file:** `rust/engine/ironhorse-regexp/src/matcher.rs:130`
**other sites:** `ironhorse-vm/src/interp.rs:20189`; `matcher.rs:491`; all 44 `check_meter` sites are in `interp.rs:11292–15870`
**confidence:** high · **novelty:** partially-known (regexp region map lead; not in the store-seam ledger)

**Claim.** An armed crank limit cannot interrupt a catastrophic regexp match, because the
matcher accumulates into a function-local `u64` and the VM charges the meter only after
`match_regexp` has already returned.

**Evidence.**
```rust
// matcher.rs:108,130
let mut meter: u64 = 0;
...
meter += XS_REGEXP_METERING;      // inside the step loop; no host, no check hook
```
```rust
// interp.rs:20188-20191
        let outcome = { let program = &self.regexps[&inst].program;
            ironhorse_regexp::match_regexp(program, subject, start_i) };
        self.meter.tick_raw(outcome.match_meter_raw);
```
`Meter::check` is reachable only through `Interp::check_meter` (interp.rs:10749), whose
44 call sites all lie inside `dispatch_at_inner`.

**Impact.** `/(a+)+b/.test("a".repeat(40))` is exponential wall-clock inside one native
call. For a consensus engine this is a validator-halt vector that the meter — the
mechanism whose entire purpose is bounding a crank — structurally cannot see. Design
§ Metering "Check points and abort" is violated for the whole regexp surface.

**Recommendation.** Give `match_regexp` a step budget and an abort return
(`MatchOutcome::Aborted`), passed in from the VM as `remaining_raw` derived from
`meter.interval`/`count`; the VM maps an abort to `Halt::MeterAbort`. This is the same
shape the dispatch loop already has and requires no new determinism surface (the budget
is a pure function of the frozen meter state).

### F2 — [critical] `arm_meter` silently disables metering for large budgets: `interval << 16` drops the high bits
**file:** `rust/engine/ironhorse-vm/src/meter.rs:120`
**other sites:** `meter.rs:137` (`rearm`); `interp.rs:10667` (`arm_meter`), `10684`
**confidence:** high · **novelty:** partially-known (interp-05 map flagged the shift; the *fail-open at interval 0* consequence is new)

**Claim.** `arm_meter(n)` for any `n` that is a multiple of 2^48 installs `interval == 0`,
which `Meter::check` treats as "metering disabled", so a host asking for a very large but
finite computron budget gets **no metering at all** rather than a large budget.

**Evidence.**
```rust
// meter.rs:119-124
    pub fn begin(&mut self, interval: u64) {
        let scaled = interval << 16;
        self.interval = scaled;
        self.count = scaled;
        self.index = 0;
    }
```
```rust
// meter.rs:285
        if self.interval != 0 && self.index > self.count {
```
Rust's `<<` on `u64` checks only the shift *amount*, never the lost bits, in both debug
and release. `(1u64 << 48) << 16 == 0`.

**Impact.** A supervisor that expresses "effectively unlimited but bounded" as a large
computron number gets an unmetered machine and no diagnostic. The failure is silent and
non-monotone (`arm_meter(2^48)` = no limit; `arm_meter(2^48 + 1)` = a 1-computron window).

**Recommendation.** `let scaled = interval.checked_shl(16).unwrap_or(u64::MAX);` — or
better, make `arm_meter` return `Result` and reject an interval above `u64::MAX >> 16`.
Add a unit test at the boundary.

### F3 — [critical] Metering is fail-open and the production embedder never arms it
**file:** `rust/engine/ironhorse-vm/src/interp.rs:10749`
**other sites:** `rust/endo/src/ironhorse_engine.rs:161` (`Machine::evaluate`), `:89` (`Halt::MeterAbort` mapped but unreachable); only callers of `arm_meter` are `ironhorse-262/src/lib.rs:1192`, `interp.rs:42161`, `interp.rs:42756`, `ironhorse-snapshot` tests
**confidence:** high · **novelty:** partially-known (interp-05 and integration-endo maps; not in the store-seam ledger)

**Claim.** A machine whose meter carries a non-zero `interval` but whose host callback was
never installed (or was lost across a restore) runs unbounded, and no path in the shipped
`rust/endo` embedding arms a meter, so a guest `while(true){}` delivered through
`Machine::evaluate` or `PersistentMachine::eval` never terminates.

**Evidence.**
```rust
// interp.rs:10749-10754
    fn check_meter(&mut self) -> MeterCheck {
        match self.meter_host.as_mut() {
            Some(host) => self.meter.check(host),
            None => MeterCheck::Continue,
        }
    }
```
`grep -rn "arm_meter" rust/` returns no hit in `rust/endo`. The restore path notes the
hazard in prose only (interp.rs:10681–10683: "a restored machine that skips them reports
armed state but never consults a host").

**Impact.** The one property the design calls unconditional and consensus-critical is not
enforced at the only production seam. `Halt::MeterAbort` is dead code there.

**Recommendation.** Make the fail-open case impossible in the type: an armed meter
(`interval != 0`) with `meter_host == None` should abort, not continue. Give
`Interp::restore_snapshot_state` no way to yield a machine that reports armed state
without a host — take the host as a parameter of the resume verb. Wire `set_crank_limit`
through `rust/endo` per design § Metering's "`Machine` metering API … preserved verbatim"
(none of `begin_metering`/`end_metering`/`current_meter`/`current_computrons`/`set_meter`/
`run_promise_jobs_metered`/`set_crank_limit` exists there).

### F4 — [high] The doctrine's recalibration mechanism is blocked by ~1,600 XS-parity CI gates
**file:** `rust/engine/ironhorse-262/tests/corpus_conversion_equivalence.rs:64`
**other sites:** `ironhorse-262/tests/regressions_dual_run.rs:64`; `ironhorse-262/src/xst.rs:473,497`; `ironhorse-fuzz/src/lib.rs:1722`; 15 `assert_eq!(out.computrons, N, "bit-exact computrons vs XS")` in `interp.rs:42233–42725`; 1,588 `.js` files under `packages/test262-runner/test262/test/ironhorse/` carrying `ironhorse-meter-exact`
**confidence:** high · **novelty:** partially-known — sharpens store-seam-design-ledger item 10 ("metering doctrine drift … the constants are XS-derived"); the *blocking* consequence and the case count are new

**Claim.** XS computron equality is an enforced acceptance gate in CI for 1,588 test262
cases and in every wired differential fuzz comparator, so recalibrating any weight —
the only mechanism the accuracy-over-parity doctrine provides — cannot be done without
regenerating the corpus, which makes `ironhorse-meter-2` unreachable in practice.

**Evidence.**
```rust
// corpus_conversion_equivalence.rs:62-66
    let cfg = Config { gate_meter_exact: true, ..Config::default() };
```
```rust
// xst.rs:473
                if meter_exact_gate && run.oracle_computrons != run.ironhorse_computrons {
```
```rust
// ironhorse-fuzz/src/lib.rs:1722
        if oracle.computrons != ironhorse.computrons {
            return Err(Divergence { ... "computrons: oracle={} ironhorse={}" ... });
```
Design § Metering:441–458 — "computron **equality** with XS is never an acceptance gate."

**Impact.** The design's whole safety argument for consensus ("accuracy bought at release
boundaries") depends on being able to bump the table. Today the table is pinned to a 2023
XS fork by the test suite while the design says that parity is a non-goal. This is not
documentation drift: it is a build-system constraint on the engine's evolution.

**Recommendation.** Decide, and make the code say it. Either (i) demote the meter-exact
gate to an advisory report with a drift threshold (the design's stated position), keeping
the parity data as the allocation-faithfulness canary it was meant to be; or (ii) amend
the design to say XS parity *is* the current acceptance bar for this release and that
`ironhorse-meter-1` means "XS 8.2.3-equivalent", making the future divergence an explicit
`ironhorse-meter-2` project. Option (ii) is honest and cheap; the present state is neither.

### F5 — [high] `COST_TABLE_VERSION` names a table that has no reified form; the snapshot gate trusts a hand-typed string
**file:** `rust/engine/ironhorse-vm/src/meter.rs:26`
**other sites:** `interp.rs:342,452,267` (210 `pub const *_METERING` in `interp.rs`); `ironhorse-regexp/src/opcode.rs:34,38`; `ironhorse-compile/src/meter.rs:22`; `ironhorse-snapshot/src/image.rs:4444`; `store.rs:2010`
**confidence:** high · **novelty:** partially-known (vm-meter-opcode-tables lead); the cross-crate namespace split and the "no prior table addressable" consequence are sharpened here

**Claim.** No manifest, digest, or test binds `"ironhorse-meter-1"` to the 219 weights it
names, so any weight edit that does not also edit the string produces a machine that a
prior snapshot still resumes into — continuing a meter under changed weights, precisely
the failure the `CostTableMismatch` gate exists to prevent.

**Evidence.**
```rust
// meter.rs:17-26
/// ... a resume under a **different** cost-table version fails closed
/// rather than silently continuing a meter whose weights changed ...
/// Bump the trailing number whenever any metering weight or check point changes.
pub const COST_TABLE_VERSION: &str = "ironhorse-meter-1";
```
`grep -rn COST_TABLE_VERSION` finds 17 uses; none reads a weight. The 15 inline computron
locks cover programs of 6–87 computrons; 210 constants are unlocked.

**Impact.** The one fail-closed metering gate the engine has is only as strong as a human
remembering to edit a string. Additionally, the design's "the previous table remains
addressable by its version so old metered outcomes stay reproducible" is not implemented
at all: there is one table, and a mismatch is a refusal, not a table selection — so a
bump does not preserve old outcomes, it bricks every existing snapshot and store.

**Recommendation.** Reify the table: move every weight into a single
`meter_table.rs` (or a checked-in TOML compiled by `build.rs`) as one `CostTable` value,
and add a test asserting `sha256(table) == KNOWN_DIGEST_FOR_ironhorse_meter_1`, so a
weight change without a version bump is a red build. Then make version selection real:
`CostTable::for_version(&str) -> Option<&'static CostTable>` with the meter holding a
`&'static CostTable`, and let restore pick the snapshot's table rather than refuse it.
That single change turns "bump the string" into the versioning discipline the design
describes, and unblocks F4 (a new table can coexist with the old parity corpus).

### F6 — [high] There is no per-opcode cost table: every dispatch charges one flat constant, and the calibration model that knows better feeds nothing

**Claim.** Design § Metering's table row 1 ("Bytecode dispatch → cost-table entry, **per
opcode**") is unimplemented: the loop charges `CODE_METERING` for every opcode

### F7 — [high] Map/Set are linear scans metered as hash tables: O(n²) real work at O(n) metered cost
**file:** `rust/engine/ironhorse-vm/src/interp.rs:34435`
**other sites:** `interp.rs:34456` (`collection_table_resize` charging XS's `fxNewChunk(len*8)` rehash and a measured `+8`), `29620,29640,29653,29660,29664,29671` (Map/Set set/add/get/has/delete), `31986–32203` (ES2025 Set methods)
**confidence:** high · **novelty:** new (interp-12 map flagged the linear scan; the *hash-geometry metering of a structure that is not a hash table* is the sharper framing)

**Claim.** `Map.prototype.get`/`has` charge no size-proportional meter and perform a full
linear scan of the physical entry list, while the surrounding metering faithfully models
XS's hash-table rehash costs — so a program that builds an n-entry Map does Θ(n²)
comparisons for Θ(n) metered cost.

**Evidence.**
```rust
// interp.rs:34435-34440
    fn collection_find(&self, inst: crate::value::SlotIndex, key: &Slot) -> Option<usize> {
        let data = self.collections.get(&inst)?;
        data.entries().iter()
            .position(|entry| entry.is_some_and(|(k, _)| self.same_value_zero(&k, key)))
    }
```
```rust
// interp.rs:34484-34491
            self.meter.tick_chunk_new(current as u64 * 8);
            // The first grow away from the minimum-length (1) address array
            // carries a measured one-time `+8` raw ... Raw-exact against the pin.
```
`MapGet`/`MapHas`/`SetHas` arms (29650–29665) contain no `self.meter.` call.

**Impact.** Directly falsifies "the best available deterministic proxy for real
(wall-clock) execution cost". With a computron budget L, an attacker obtains ~(L/k)²
wall-clock work — a metered-but-slow crank, which for a consensus fleet is a block-time
attack that the meter reports as cheap. It is also the clearest instance of the general
disease: the cost model describes XS's data structures, not Ironhorse's.

**Recommendation.** Either give collections a real hash index (making the XS-shaped
metering honest), or meter `collection_find` proportional to the scan length. The first
is correct; the second is a one-line stopgap. Add a metering invariant test: for a family
of workloads, assert metered computrons grow at least as fast as a measured op count.

### F8 — [high] Runtime compilation is entirely unmetered, and straight-line bytecode has no check points
**file:** `rust/engine/ironhorse-vm/src/interp.rs:55`
**other sites:** `interp.rs:8005–8081` (`eval_source`: `compile_source` → `parse_symbols` → `relink_program_symbols` → `install_intrinsic_bindings` → dispatch, with no `self.meter.` call); `ironhorse-compile/src/lib.rs:52` (`parse_computrons`, test-only); `ironhorse-compile/src/meter.rs:22`; `ironhorse-compile/src/lexer.rs:1223` (eager regexp compile per literal)
**confidence:** high · **novelty:** partially-known (compile-lexer / interp-01 leads); the compound "unmetered compile + no check point in straight-line code" vector is new

**Claim.** `eval(src)` performs O(|src|) lexing, parsing, scoping, coding, symbol
relinking and intrinsic installation at zero computron cost, and the resulting
straight-line program then executes with no meter check point at all (checks fire only at
backward branches, calls, returns and catch landings).

**Evidence.**
```rust
// interp.rs:55-61
pub struct CompiledSource {
    pub bytecode: Vec<u8>,
    pub symbols: Vec<u8>,
}
```
```rust
// interp.rs:8006-8014  (the whole compile→run bridge; no meter tick)
        let compiled = match compiler.compile_source(source, strict) { ... };
        let eval_names = crate::symbols::parse_symbols(&compiled.symbols);
        let code = match self.relink_program_symbols(&compiled.bytecode, &eval_names) { ... };
```
The compile-side meter exists and is dead: `grep parse_computrons` finds only
`lib.rs`, `parser.rs`, and two test files. The 262 harness's own test
`no_meter_check_when_program_returns_to_c` (`ironhorse-262/src/lib.rs`) documents that a
straight-line program is never checked.

**Impact.** A guest with a modest computron budget can spend unbounded host time and
memory in the front end (the scoper has quadratic shapes; the lexer eagerly runs the full
recursive regexp compiler per literal), then run a multi-megabyte straight-line program
that no check point can interrupt. Design § Metering table row 4 ("Parse unit →
cost-table entry") is unimplemented end to end.

**Recommendation.** Add `parse_meter_raw: u64` to `CompiledSource`, charge it via
`meter.tick_raw` in `eval_source` and `create_dynamic_function` *before* dispatch, and
give `SourceCompiler::compile_source` a `budget: u64` so the compiler can abort. Fold
`PARSE_METER_RELEASE` into `COST_TABLE_VERSION` (see F5/F10). Separately, add a periodic
check point (e.g. every N dispatches) so straight-line code is interruptible; the design
already concedes the abort point is release-defined, so this costs no parity.

### F9 — [high] Memory is priced at 1 raw unit per byte and there is no allocation ceiling anywhere
**file:** `rust/engine/ironhorse-vm/src/interp.rs:34411`
**other sites:** `interp.rs:18197,18234,18380,18463` (ArrayBuffer / TypedArray constructors); `interp.rs:31219` (`String.prototype.repeat`); `meter.rs:49` (`CHUNK_ALLOCATION_METERING = 1`)
**confidence:** high · **novelty:** partially-known (interp-12 lead "memory is unmetered in practice"); confirmed and priced here

**Claim.** One computron buys 64 KiB of zeroed heap: `new ArrayBuffer(0x7FFFFFFF)`
allocates and zero-fills 2 GiB for 32,768 computrons, and no heap ceiling exists in
`ironhorse-vm`.

**Evidence.**
```rust
// interp.rs:34410-34413
    fn alloc_array_buffer(&mut self, byte_length: u32) -> crate::value::SlotIndex {
        self.meter.tick_chunk_new(byte_length as u64);
        let data = self.chunks.alloc(&vec![0u8; byte_length as usize]);
```
`CHUNK_ALLOCATION_METERING: u64 = 1` (meter.rs:49) against `CODE_METERING = 1 << 16`.
`grep -E "heap_limit|memory_limit|max_heap|arena_limit"` over `ironhorse-vm/src` returns
nothing.

**Impact.** A worker with a small computron budget can OOM the host process. Under the
accuracy doctrine memory pressure is real cost the meter is meant to proxy; under XS
parity this weight is simply inherited. Either way the deployed engine has no memory
admission control.

**Recommendation.** Add a machine-level byte ceiling (`chunks` + `slots` high-water)
checked in `ChunkArena::alloc` and `SlotArena::alloc`, surfacing as a catchable
`RangeError` or `Halt::MeterAbort`. Separately, raise the chunk weight in the next table
so a byte of heap is not 1/65536 of an opcode.

### F10 — [medium] Three weight namespaces, two version strings, one unversioned; the snapshot records only the VM's

### F14 — [medium] Meter arithmetic has no overflow/underflow discipline, and no `[profile]` sets `overflow-checks`
**file:** `rust/engine/ironhorse-vm/src/meter.rs:153`
**other sites:** `meter.rs:164` (`untick_code`), `172`, `178`, `184`, `193`, `200`, `215`, `228`, `238` (`untick_raw`); `interp.rs:16079`, `17444`, `34699`, `34713` (the credit sites); `rust/engine/Cargo.toml` (no `[profile]` section)
**confidence:** high · **novelty:** known-open (vm-meter-opcode-tables lead), confirmed

**Claim.** Every `Meter` mutator uses unchecked `+=`/`-=`/`*`, and the workspace sets no

architecture, **and build**".

**Evidence.**

`rust/engine/Cargo.toml` has `[workspace]`/`[workspace.package]` only.

## 3. Strengths

These are real and should not be lost in a rewrite.

- **The meter primitive is well built.** `Meter` (meter.rs, 371 lines) is a small,
  auditable, pure-integer type with no HashMap iteration, no host input, and no floats. It
  reproduces `fxCheckMetering` faithfully *including* the overflow-wrap guard
  (meter.rs:291–299) and has unit tests for the disabled case, the `begin` scaling, the
  wrap guard, and the ordinary window advance. Determinism-by-construction genuinely holds
  for the meter arithmetic itself.
- **Meter state across suspend is designed, implemented, and tested.** `MeterState`
  carries exactly the three counters that matter, and the three resume forms are
  distinguished with correct and clearly documented semantics: `begin` (fresh, zeroes the
  index), `rearm` (interval change, preserves the index, moves the deadline), and
  `reattach_meter_host` (pure resume, touches nothing). `ironhorse-snapshot/tests/persist_gates.rs:139–235`
  locks all three, and `machine.rs:1780–1840` proves an interrupted run's final computron
  count equals the uninterrupted run's. This is the best-executed part of the whole
  metering story.
- **The snapshot cost-table gate is fail-closed and consistently applied** at container
  decode (`image.rs:4444`), store open/validate (`store.rs:2010`), and migration
  (`store.rs:2861,3051,3152`), with a dedicated `SnapshotError::CostTableMismatch`. The
  mechanism is right; only its input (a hand-typed string, F5) is weak.
- **The cost-calibration determinism firewall is genuinely engineered.** `CostRecorder` is
  a ZST with `#[inline(always)]` empty bodies when the feature is off (cost.rs:37–60), the
  data flow is one-directional by construction (the recorder never holds `&mut Meter`),
  and there are two mechanical proofs: a size assertion and a source-grep invariant test
  (`interp.rs:42767`, asserting `meter.rs` names no cost type). Few projects firewall
  instrumentation this carefully.
- **The 2026-07-06 UTF-16 re-basing did land where it matters most:**
  `new_string_units`/`new_string_metered` meter by code-unit length (interp.rs:30899–30906),
  which is the correct cost shape for the chosen representation.
- **Check-point placement mirrors XS's loop-closing set faithfully**, and the deliberate
  consequence (a straight-line program is never checked) is *tested* rather than assumed
  (`ironhorse-262/src/lib.rs`, `no_meter_check_when_program_returns_to_c`). The
  `MeterAbort` path is locked with the exact XS consultation cadence at `interp.rs:42150–42188`.
- **`harden`/`petrify` are metered per queue item and per key** (interp.rs:35758, 35778,
  35782, 35837, 35841) — the SES-critical transitive walk is not an unmetered hole, which
  is more than can be said for the Proxy seam next to it.
- **The constants are extraordinarily well documented.** Each of the 210 carries a
  derivation, a pin reference, and often a caveat about what would invalidate it
  (interp.rs:135–139 on the computed-goto build is a model of honest engineering notes).
  That documentation is what makes this review possible and would make a real
  recalibration tractable.

## 4. Recommended architectural direction

**Reify the table, then decide what it is.** The single highest-leverage change is to
turn the meter's weights into a *value*: one `CostTable` struct in one module, holding the
6 primitive weights, the 210 residuals, the 2 regexp weights, the parse-token weight, and
`DEFAULT_KEYS`, with `Meter` holding a `&'static CostTable` rather than reading module
constants. Add a digest test (`sha256(table) == …`) so a weight edit without a version
bump is a red build, and a `CostTable::for_version(&str)` registry so the *previous* table
stays addressable — which is what the design promises, what historic-block replay needs,
and what turns a meter bump from "brick every snapshot" into "resume under the table that
produced these computrons". This is mechanical, testable, and unblocks everything else. It
also fixes the version-namespace fracture: the compiler and regexp crates should receive
their weights as parameters from the VM's table rather than compiling in their own.

**Then resolve the doctrine, in code, one way.** The present state is the worst of both:
the design forbids XS parity, the tests enforce it on 1,588 cases, and the module doc
endorses it. My recommendation is to be honest about the current release —
`ironhorse-meter-1` *is* the XS-8.2.3-equivalent table, and the meter-exact corpus is its
specification — and to schedule divergence as `ironhorse-meter-2`, the first table whose
weights come from the (still Not Started) cost instrumentation. Under the registry above,
the two can coexist: keep the parity corpus gating `meter-1`, run the new table's
determinism-only bar for `meter-2`, and let consumers adopt at a coordinated upgrade
exactly as the design's decision (b) already describes. That converts an unresolvable
contradiction into a shipping plan.

**Finally, close the three metering holes that are security properties, not accuracy
properties.** (i) Make fail-open impossible: an armed meter with no host must abort, not
continue; `arm_meter` must reject or saturate an over-wide interval; and `rust/endo` must
arm — a shipped engine whose only production embedding cannot stop a `while(true){}` has
no metering at all, whatever the table says. (ii) Make long natives interruptible: pass a
remaining-budget into `match_regexp` (and, over time, into the other guest-sized native
loops — JSON, string builders, collection bulk ops) and return an abort, plus a periodic
check point in the dispatch loop so straight-line bytecode is not a blind spot. (iii)
Price what actually costs: charge parse work at the compiler seam, charge collection
lookups proportional to the scan they perform (or give collections a real hash index), and
add an absolute heap ceiling — because a meter that lets a guest buy 64 KiB of zeroed
memory per computron and Θ(n²) comparisons for Θ(n) computrons is not a proxy for
wall-clock cost, which is the one thing the doctrine says it must be.
