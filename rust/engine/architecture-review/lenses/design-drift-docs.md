# Lens: Design-document drift and documentation architecture

Reviewer note: every line cited below was read in the current tree (HEAD on
`claude/ironhorse-architecture-review-bimf34`). Leads taken from the region maps
were re-verified; three were dropped or narrowed.

## 1. Assessment

IronHorse has three governance documents and no reference. `designs/ironhorse-engine.md`
is the approved architecture, but its *content* is frozen: the last substantive
amendment is dated 2026-07-29 (`design:1111`), its "landed-stage records" stop at
stage 3 (`design:842, 863`), and it has no `## Status` section even though
`designs/AGENTS.md:57-61` prescribes one ("lists what has been built, file paths,
and any deviations from the original design"). `designs/README.md:355` shows
`Updated | —` for it. Everything the engine actually became between 2026-08-06 and
2026-09-01 — the store seam, schema v5→v23, container format v1→v12, Intl,
Temporal, six numbered review waves — is recorded in `designs/ironhorse-snapshot-store-seam.md`
(4,474 lines, three documents in one: design, per-phase changelog, and review
ledger) and in `rust/engine/README.md` (2,952 lines, last touched 2026-08-14,
86% of it in two headings). Neither is a reference. There is no ARCHITECTURE.md,
no format spec, no per-crate design note, and the crate-root rustdoc — the
`cargo doc` landing page — is stage-frozen at each crate's first child
(`ironhorse-vm/src/lib.rs:6-11` still describes "the arithmetic / logic /
bitwise / comparison / branch / stack opcode subset" for a 246-opcode engine).
A new maintainer's honest answer to "what is the current design of the meter?"
is: read 45k lines of `interp.rs`.

The drift is not uniformly in one direction, which is what makes it structural
rather than cosmetic. Three distinct failure modes are present:

**(a) The design says something the code contradicts, and the code is right.**
The architecture diagram (`design:264-293`) names `ironhorse-ses` and
`ironhorse-debug`, neither of which exists; the `unsafe`-budget roster
(`design:584-585`) enumerates those two and omits `ironhorse-regexp`,
`ironhorse-snapshot`, and `ironhorse-fuzz`, which do exist and do carry
`forbid`. The diagram's integration edges are backwards: `XSNAP --> VM` and
`ENDO --> XSNAP`, but `rust/endo/xsnap/Cargo.toml` has no ironhorse dependency
at all and `rust/endo/Cargo.toml:7-20` depends on `ironhorse-vm`/`-compile`/
`-snapshot` directly, by default feature. Requirement 8's whole premise —
"Ironhorse implements the same surface behind an engine selection, so the
supervisor … are engine-agnostic" (`design:724-731`) — rests on a topology the
implementation declined.

**(b) The design says something the code contradicts, and the design is right
but nobody noticed.** The 2026-07-04 metering doctrine made XS-computron parity
an explicit non-goal and made the weights "calibration constants derived from
the cost-calibration instrumentation … not hand-copied from XS"
(`design:400-411`). `ironhorse-vm/src/meter.rs:3-4` opens: "incremented at
exactly XS's points with exactly XS's weights"; sixteen lines later the same
file says "Ironhorse's meter is its **own** frozen cost table, not a back-fit of
the oracle's" (`meter.rs:19-20`). `interp.rs` carries 206 `pub const
*_METERING` constants documented as "calibrated raw-exact against the pin";
README uses "bit-exact" 37 times. The instrumentation that was supposed to
produce the weights is `Status | Not Started` — while its stage C1 *has landed*
(`ironhorse-vm/src/cost.rs:1-31`), so the design's status is wrong in both
directions at once.

**(c) The docs record a gap as closed that is open.** `README:118` marks
upstream delta item 7 **"Already mirrored"** because "the parser carries its own
stack checks". `grep` over `parser.rs`, `parser/stmt.rs`, and `scoper.rs` finds
no depth counter, margin, or recursion guard of any kind; the compile-parser and
compile-scoper region readers measured a *process abort* (uncatchable native
stack overflow) on nested source. A verdict table is the mechanism by which a
real robustness gap became invisible.

Two claims that the design makes as *enforcement* do not exist at all: Miri and
ASAN/UBSAN in CI (`design:612-615`; zero matches for `miri|sanitizer|ASAN|UBSAN`
across `.github/workflows/`), and the stage-8 performance envelope
(`design:753-770`) — there is no benchmark harness in the tree (no `criterion`,
no `[[bench]]`, no "four-variant benchmark"; the only bench-shaped code is four
`#[ignore]`d snapshot instruments). Kill criterion 3 of the program is
unmeasurable by construction.

What is genuinely good: `ironhorse-snapshot/src/format.rs` is a real format
specification — atom roster, canonical order, per-version change log, the
refusal rules and why each exists — and it is accurate. It is simply not
reachable from any document a reader would open first.

## 2. Findings

### F1. Metering doctrine inverted, and `ironhorse-meter-1` names a cost table with no reified form
**Severity** high · **Confidence** high · **Category** metering / docs-drift ·
**Novelty** known-open (docs-ci-process cand 1; vm-meter-opcode-tables cand 1;
store-seam-ledger invariant 10)

`rust/engine/ironhorse-vm/src/meter.rs:3` and `:19`:
```
//! A `u64` in 16.16 fixed point, incremented at exactly XS's points
//! with exactly XS's weights, and checked only at loop-closing points.
...
/// version. Ironhorse's meter is its **own** frozen cost table, not a
/// back-fit of the oracle's;
```
`designs/ironhorse-meter-opcode-cost-instrumentation.md:7` `| **Status** | Not Started`,
and `:69-72`: "They are currently XS's constants, carried because the landed
stages predate the doctrine flip … they were never calibrated against real
Ironhorse execution cost."

Claim: the shipped cost table is XS's weights (parity), the design says it is a
calibrated Ironhorse table (accuracy), and no artifact anywhere binds the string
`"ironhorse-meter-1"` to the set of weights that produced a computron count.

Verified: `grep -c '^pub const [A-Z_]*METERING' interp.rs` → 206, every one
documented as calibrated raw-exact against the XS pin; `meter.rs:29-54` are XS's
literal `1<<16`/`1<<14`/`1<<8`/`1`. `COST_TABLE_VERSION` has 17 references
(`lib.rs:52`, `image.rs:32/54/4444`, `store.rs:55/2010/2861/3051/3152`,
`machine.rs:1657/1860`, `format.rs:393`, `migration.rs:193`) — every one a
*comparison*, none a *definition*: no manifest, digest, golden vector, or test
ties the version string to the 212 constants.

Impact: the version is the consensus gate a resumed snapshot is refused on
(`image.rs:4444`, `store.rs:2010`). A weight edit without a version bump is
undetectable by any check in the tree, and produces two machines that agree on
`METR` and disagree on computrons. Separately, the "accuracy" half of
accuracy-over-parity has no evidence and no instrument, and a maintainer cannot
tell whether an XS-mismatched constant is a defect or a recalibration.

Recommendation: (1) reify the cost table as a single data artifact — a
`meter/ironhorse-meter-1.rs` table (or a `const` array with a checked-in
SHA-256) that `meter.rs` and `interp.rs` read from — and add a test asserting
`digest(table) == PINNED_DIGEST_FOR("ironhorse-meter-1")` so a weight change
without a bump is a red test. (2) Correct `meter.rs:3-4` to say what is true
today: the table is XS-derived and awaits calibration. (3) Either amend
`design:400-411` to record that the first release ships XS-derived weights, or
flip the instrumentation design's Status and land a calibration lane.

### F2. The approved design is content-frozen at 2026-07-29; no document describes the current architecture
**Severity** high · **Confidence** high · **Category** docs-drift / modularity ·
**Novelty** partially-known (docs-ci-process cands 10, 14)

`designs/ironhorse-engine.md` headings: `## Feasibility Verdict`, `## Ground
Truth`, `## Architecture`, `## Staged Roadmap`, `## Dependencies`, `## Design
Decisions`, `## Resolved Questions`, `## Prompt`. There is no `## Status`
section, contrary to `designs/AGENTS.md:57-61`. The latest dated amendment in
the body is `design:1111` "*Amended 2026-07-29 by maintainer directive*" (a
crate-renaming directive). `designs/README.md:355`:
```
| [ironhorse-engine](ironhorse-engine.md) | 2026-07-02 | — | Approved |
```
— `Updated` is `—` despite `Revised 2026-07-04` and `Revised 2026-07-06` in the
document's own metadata table (`design:8-9`).

Claim: no document in the repository describes IronHorse as it exists today; the
current state is reconstructable only from a 4,474-line changelog-design plus a
2,952-line README, neither of which has a current-state section.

Evidence of the gap's size: `git log -1` on `rust/engine/README.md` → 2026-08-14;
on `interp.rs` → 2026-09-01. Everything in between (store schema v5→v23,
container format v1→v12, the language-completion rebase, Intl, Temporal, six
review waves) exists only in `designs/ironhorse-snapshot-store-seam.md` and in
`designs/README.md:1274` — a **23,138-byte single table cell**, one paragraph,
in the design index.

Impact: the design's own instruction is that "the verification-ledger
blockquotes in `rust/engine/README.md`" are the record (`design:1152-1155`); that
record is 18 days stale and internally contradictory (F7). Review, onboarding,
and any future amendment all have to re-derive the design from source. This is
the mechanism that produces F3–F13: there is no process step that re-reads a
design when reality moves.

Recommendation: split the documentation along the axis of *rate of change*.
(a) `designs/ironhorse-engine.md` gains a `## Status` section, maintained, that
says per roadmap stage: landed / partial / not started, with a one-line deviation
note and a pointer. (b) `rust/engine/ARCHITECTURE.md` (new, ~300 lines): crate
roster with real names and real edges, the seams (SourceCompiler, HeapStore,
GcHooks, side-table ledger), and where each invariant is enforced. (c) Per-crate
`ARCHITECTURE.md` for `ironhorse-vm` and `ironhorse-snapshot` only. (d) The
README's stage narrative moves to `rust/engine/CHANGELOG.md` verbatim, leaving a
~150-line README that is a map. (e) `designs/ironhorse-snapshot-store-seam.md`
splits into design / CHANGELOG / open-ledger, since it is already three
documents.

### F3. Requirement 8: the `Machine` API the design says is "preserved verbatim" does not exist, and the daemon never arms the meter
**Severity** high · **Confidence** high · **Category** api-boundary ·
**Novelty** known-open (docs-ci-process cand 4; integration-endo cand 1)

`designs/ironhorse-engine.md:460-465`:
```
The `Machine` metering API (`begin_metering`, `end_metering`,
`current_meter`, `current_computrons`, `set_meter`,
`run_promise_jobs_metered`, `set_crank_limit`) is preserved
verbatim, so the crank lifecycle, admission gate, and meter-report
envelopes ... carry over without supervisor changes;
```
`rust/endo/src/ironhorse_engine.rs:146-198` is the complete `impl Machine`:
`new`, `evaluate`, `eval`, `eval_strict`, `intrinsics`, `vm_machine`. The VM's
actual metering API is `arm_meter(&mut self, interval: u64, host: Box<dyn FnMut(u64) -> bool>)`
(`interp.rs:10667`), `rearm_meter` (`:10684`), `reattach_meter_host` (`:10697`).

Claim: none of the seven named methods exists on the Ironhorse seam, and no code
path under `rust/endo/src/` calls `arm_meter`/`rearm_meter`/`set_crank_limit`.

Verified by grep across `rust/`: the only `arm_meter` callers are
`ironhorse-262/src/lib.rs:1192`, `ironhorse-snapshot/src/machine.rs:1837`, and
`ironhorse-snapshot/tests/persist_gates.rs:147/163` — tests and the harness.
`set_crank_limit` exists only in `rust/endo/xsnap/src/lib.rs` (the C engine).

Impact: two things, one documentary and one operational. Documentary: the
reconciliation table (`design:740-748`) declares five sibling designs
"unchanged" on the strength of a seam that does not exist, so those
reconciliations are unverified. Operational: on the `-e ironhorse` path a guest
`while(true){}` delivered through `Machine::evaluate` or
`PersistentMachine::eval` runs unbounded — `Halt::MeterAbort` is unreachable
from the daemon. (The seam is honest about being unwired at
`ironhorse_engine.rs:19-21`; the drift is in the design, the operational
consequence is real either way.)

Recommendation: amend `design:460-467` and the reconciliation table to state the
actual seam shape (`arm_meter` with a boxed host closure, not a thread-local
crank limit) and enumerate the supervisor changes that will be needed; and, as
the integration lens recommends independently, arm the meter in
`PersistentMachine::eval` before any production use of `-e ironhorse`.

### F4. Design-promised Miri and ASAN/UBSAN CI enforcement does not exist; four tests are named `*_is_miri_clean` and run as ordinary tests
**Severity** high · **Confidence** high · **Category** verification ·
**Novelty** known-open (docs-ci-process cand 2; vm-heap-gc "violated" row)

`designs/ironhorse-engine.md:612-615`:
```
CI enforcement:
Miri on the arena and GC test suites, ASAN/UBSAN on the oracle
harness (the remaining C), and the fuzz targets below.
```
`design:782` (stage-2 acceptance bar): "GC test suite under Miri".

Verified: `grep -rn "miri|Miri|sanitizer|ASAN|UBSAN|asan" .github/workflows/` →
**no matches**. The four tests named as the evidence —
`harden_transitive_freeze_is_miri_clean` (`interp.rs:42664`),
`generator_suspend_resume_is_miri_clean` (`:42819`),
`promise_thenable_adoption_is_miri_clean` (`:42857`),
`async_await_suspend_resume_is_miri_clean` (`:42900`) — carry no `cfg(miri)`
and there is no `cfg(miri)`/`cfg!(miri)` anywhere in `rust/engine`. README cites
them as Miri evidence in five places.

Impact: the memory-safety confidence claim (requirement 3, the program's
headline) rests on `forbid(unsafe_code)` alone. `forbid` does not cover
`xs-oracle` — the C process that compiles and executes hostile test262 input in
CI — which the design specifically says ASAN/UBSAN covers. A test whose *name*
asserts a property no job checks is worse than no test: it reads as verified.

Recommendation: either add the two jobs (a Miri lane over
`ironhorse-vm --lib gc/value/bulk` and `RUSTFLAGS=-Zsanitizer=address` on the
oracle job), or rename the four tests (they are ordinary behavioral tests) and
amend `design:612-615` to say the enforcement is `forbid` + fuzzing. Do not
leave the names.

### F8. `README:118` records the parser stack-margin gap as "Already mirrored"; no such check exists
**Severity** medium · **Confidence** high · **Category** docs-drift ·
**Novelty** partially-known (compile-parser map "violated" row; the doc-mechanism
framing is new)

`rust/engine/README.md:118`, upstream delta item 7:
```
| 7 | Native stack overflow reported natively, not as JS (#1635) + parser stack
margin — ... | `ironhorse-vm` already models overflow as `Halt::StackOverflow`
... — and the parser carries its own stack checks. | **Already mirrored.**
Oracle-covered; margin/overhead tuning is behavior-neutral. |
```
Verified: no `depth`, `recursion`, `nesting`, `margin`, or stack-probe guard
exists in `ironhorse-compile/src/parser.rs`, `parser/stmt.rs`, or `scoper.rs`
(the only `depth(` in the front end is `scoper.rs:2583`, a debug-dump indent
helper). `ironhorse-vm`'s half of the row *is* true (`Halt::StackOverflow`);
the parser half is not.

Impact: two independent region readers measured an uncatchable native stack
overflow (process abort, not a `panic!`, so `catch_unwind` cannot contain it) at
a host- and build-dependent nesting depth in the compiler front end. That is a
robustness gap on the eval path; the delta table records it as closed, which is
precisely how it stays unfixed. Note the verdict is also *load-bearing* — the
table is the mechanism by which upstream XS fixes are triaged.

Recommendation: flip item 7 to **Follow-up** with the measured depths, and add a
nesting counter to `Parser`/`Scoper`/`Coder` that returns
`ParseErrorKind::Syntax` ("too much recursion", XS's own message) past a fixed
bound, so the failure is a `Result` the eval bridge can render.

### F9. The performance envelope has no instrument: no benchmark harness, no fourth benchmark variant, no gate
**Severity** medium · **Confidence** high · **Category** verification · **Novelty** new

`designs/ironhorse-engine.md:753-770` sets the stage-8 envelope (throughput
"geometric mean within 2.0x of XS on the four-variant daemon benchmark plus a
microbenchmark corpus", footprint 1.1x heap / 2x code size, latency
no-regression) and `design:56-58` makes exceeding it by 2x a **kill criterion**
for the program. `design:742` promises "The three-variant benchmark gains a
fourth variant (Rust supervisor + Ironhorse engine) and is the
performance-envelope harness".

Verified: no `benches/` directory under `rust/engine/*`; no `criterion` and no
`[[bench]]` in any `rust/engine/*/Cargo.toml`; `grep -rn "four-variant|fourth
variant"` across `.rs`, `.toml`, `.yml` → **no matches**. The only
benchmark-shaped code is four `#[ignore]`d snapshot instruments
(`ironhorse-snapshot/tests/{gc,dispatch,attached,wake_latency}_bench.rs`), each
documented as an instrument for the store seam, not an engine envelope, and each
requiring a manual `--release --ignored` run.

Impact: a named kill criterion of the program cannot be evaluated, and there is
no regression floor at all — the design's "no optimization that perturbs
metering observability is admissible" has no counterpart check on the

## 3. Strengths

- **`ironhorse-snapshot/src/format.rs` is a real format specification, and it is
  accurate.** `CANONICAL_ATOM_ORDER` (`:164`), the per-atom doc comments
  (`:22-158`), `IRONHORSE_MAGIC` and the reason it exists (`:172-178`), and the
  version log at `:181-197` — which names, version by version, exactly which
  state-bearing atom each bump added and what a stale reader would have silently
  dropped ("a version-1 reader — which skips unknown atoms and would silently
  drop arrays, collections, RegExps, Intl records and iterator cursors — refuses
  a version-2 container outright instead of resuming a degraded machine"). This
  is the standard the rest of the documentation should be held to.
- **Fail-closed meter versioning at the persistence boundary is mechanically
  real.** `COST_TABLE_VERSION` is stamped into `METR` and checked before any
  mutation on both resume paths (`image.rs:4444`, `store.rs:2010/3051/3152`),
  with `tests/migration.rs:185-204` locking it and a fixture that panics if a
  refused store is touched. This is the one place the "release-versioned meter"
  claim is enforced rather than asserted, and it is done correctly.
- **Honest named skips are a genuine, consistently-applied doctrine.** The
  boot-bundle ledger (`README:990-1012`) says plainly that the bar is not met and
  names the exact stopping opcode for each bundle;
  `ironhorse-262/src/lib.rs:654-660` explains why `ses_boot.js` cannot be
  dual-run rather than quietly dropping it; `ironhorse_engine.rs:19-21` says the
  worker protocol is unwired. Across a large LLM-authored codebase this
  discipline held.
- **The determinism firewall around cost calibration is designed, not bolted
  on.** `cost.rs:4-23`: feature off by default, zero-sized recorder, one-way data
  flow, a grep-invariant test that `meter.rs` names no type in the module, and a
  `size_of::<CostRecorder>() == 0` structural proof. The design's rule was
  implemented faithfully even though the design that specifies it is marked Not
  Started.
- **CI probes are defensively written** (`ci.yml:715-729`): fail-open on an
  unexpected merge-commit shape, and a deliberate avoidance of the
  `grep -q`/SIGPIPE false-miss with the reason in a comment. The path-filter gap
  in F14 is an omission, not carelessness — the same probe was correctly extended
  when `ironhorse-store-sqlite` moved.
- **Measurement-process corrections are recorded rather than rewritten.** The
  "a whole-tree claim requires the whole-tree enumeration" rule (README:1774-1783)
  was adopted after an over-claim and is visibly applied afterward; earlier wrong
  verdicts are kept as dated history. The instinct is right; only the
  presentation (F7) defeats it.
- **The store-seam design's review ledger is an unusual and valuable artifact.**
  Six numbered waves with per-finding fix records and bite-checks is a level of
  review provenance most projects never produce. Its problem is packaging, not
  substance.

## 4. Recommended architectural direction

**Separate the three genres that are currently mixed.** IronHorse's
documentation collapses *design* (what we intend and why), *changelog* (what
landed when, and what was measured), and *reference* (what is true now) into
documents that are structurally changelogs. Every drift in this report follows
from that: a changelog is append-only, so nothing in it is ever wrong, so nothing
in it is ever corrected — which is exactly the wrong property for the document a
maintainer opens first. The fix is mechanical. `designs/ironhorse-engine.md`
keeps design and gains a maintained `## Status` section per `designs/AGENTS.md`.
`rust/engine/CHANGELOG.md` absorbs the README's stage narrative verbatim (it is
good material, wrongly filed) and the store-seam design's phase history. A new
`rust/engine/ARCHITECTURE.md` of ~300 lines carries the reference: the real crate
graph, the seams (`SourceCompiler`, `HeapStore`, `GcHooks`, the side-table
ledger), and a "where is X specified" index pointing at `format.rs` for the
container, `meter.rs` + the cost table for the meter, `sidetable.rs` for the
ledger. Per-crate `ARCHITECTURE.md` for `ironhorse-vm` and `ironhorse-snapshot`
only; for the others, an honest crate-root rustdoc is enough (F15).

**Give each consensus artifact one authoritative, machine-checkable home.** Today
the answer to "what is the meter?" is 206 constants in a 45k-line file plus six in
`meter.rs`, versioned by a string nothing binds to them (F1); the answer to "what
is the snapshot format?" is `format.rs`, which is excellent but unreachable; the
answer to "what is the side-table ledger?" is a table inside a 4,474-line design
plus `sidetable.rs`, which already parses `interp.rs`'s source text to stay
honest. The pattern that works here is already in the tree twice —
`gc_visitation_registry.rs` derives GC ground truth from the `Interp` struct, and
`sidetable.rs:896` reconciles the ledger enum against source — so extend it: a
cost-table digest test, an atom-roster length test, and a `Cargo.toml`-derived
crate-graph check would make F1, F6, and F15 impossible to reintroduce. Prose
that a test cannot contradict will drift; prose that a test does contradict gets
fixed on the next run.

**Close the loop between the design and the code with one cheap process step.**
The single highest-leverage change is a rule that landing a stage requires
updating the parent design's `## Status` section and its roadmap row in the same
change — the same discipline the repo already applies to `yarn.lock`. Three of
this report's findings (F5's Intl and Temporal, F13's gitlink bump, F11's C1) are
cases where a binding resolved question or a status field was overtaken by work
and nobody was obliged to notice. Everything else — the missing Miri/sanitizer
lanes (F4), the absent performance instrument (F9), the phantom fuzz targets
(F10) — is the same shape at the level of CI: a claim made in a document with no
job behind it. Either land the job or amend the document; leaving the claim
standing is the only option that costs something.
