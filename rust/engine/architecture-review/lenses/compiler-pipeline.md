# Lens: Compiler pipeline (lexer → parser → scoper → coder)

Reviewer notes: every finding below was verified by me in the current tree (HEAD 97d8de25).
Behavioural claims were reproduced with a throwaway probe crate outside the repo
(`scratchpad/probe2`, own target dir) linking the *unmodified* `ironhorse-compile` and
`ironhorse-vm` libs. No repo file was modified. The XS oracle cannot build here (submodule
absent), so every claim about *what XS does* is marked as unverified where it matters.

## 1. Assessment

`ironhorse-compile` is an unusually legible transliteration. Every method names its `xsCode.c` /
`xsSyntaxical.c` / `xsScope.c` / `xsLexical.c` counterpart, the flag bits and token discriminants are
XS's exact values, the three-pass serializer and the symbol bucket-walk are ported as algorithms
rather than approximated, and the determinism hygiene inside the crate is genuinely clean: no
`HashMap` iteration reaches the byte stream, `f64` is emitted as raw bits, BigInt limbs are
canonicalized, address-keyed maps are lookup-only, and there is no host time, locale, or randomness.
The layering is also better than the design diagram: the VM owns a `SourceCompiler` trait and takes
`ironhorse-compile` only as a dev-dependency, so the compiler is genuinely swappable.

The architecture nonetheless has a coherent defect, and it is a single one seen from four sides:
**the compiler's contract with everything around it is enforced by convention rather than by a
type, an assertion, or a test — and where the convention fails, the failure is silent or fatal
rather than a `Result`.** Four instances, all confirmed:

*Representation.* The AST symbol slot is a Rust `String` (`ast::Item::Symbol`), and string property
keys reach it through `String::from_utf16_lossy` (`ast.rs:442`, called from `parser.rs:1481,1532`).
A Rust `String` cannot represent a lone surrogate, which XS's CESU-8 symbols can. The consequence is
not a diagnostic: `Object.keys({"\uD800":1,"\uD801":2}).length` compiles and runs to **1** on the
production path, and `o["\uD801"]` reads the value stored under `"\uD800"`. That is a silent wrong
answer from valid JavaScript — the one outcome the design says must never happen — and it is
simultaneously a byte-identity violation that no fixture reaches.

*Totality.* `compile() -> Result<_, ParseError>` is not total. `ParseErrorKind::Unsupported` exists
for exactly the "valid but unported" case, but only the *parser* ever produces it; the scoper and
coder encode the same condition as 33 `panic!`s. `class C { static { let x = 1; } }` (valid ES2022)
and `({a = 1});` (a spec early error) both panic. The panic firewall is `catch_unwind` — and it
lives only in the test harness (`ironhorse-262/src/lib.rs:56`). Production (`rust/endo`) calls
`compile_atoms_with` at `ironhorse_engine.rs:162` and `:496` with no `catch_unwind` anywhere in the
crate. Worse, the harness's classification maps *every* panic to `Unsupported` — a coverage gap —
so a genuine coder invariant violation and a deliberate fold are indistinguishable in the dual-run
report.

*Bounds.* Nothing in the crate bounds recursion (grep: no depth counter, no stack check), and a
stack overflow is a process **abort**, not a panic, so `catch_unwind` cannot contain it. Measured
here: 4,000 nested parens (~8 KB of source) abort a release build on the 8 MiB main thread; a debug
build aborts between 200 and 300. The accept/reject boundary is therefore a function of the host
thread's stack size and the build profile, not of the source — in a consensus engine that is a
divergence axis, and CI papers over it with `RUST_MIN_STACK=16777216` while calling the depth "an
engine property".

*Cost.* The only cost instrument, `ParseMeter`, is charged per token, is never read by
`compile_atoms_with`, never crosses `CompiledSource`, and is versioned `ironhorse-meter-0`
independently of the VM's `ironhorse-meter-1`. Meanwhile compilation is *quadratic*: I measured
1 MB of ordinary JS at **12.8 s** and localized it to `Coder::optimize`'s per-branch linear
`target_pos` scan (parse and scope stay linear). So the meter is linear where the work is quadratic,
and it is not charged at all.

Finally, verification: `cargo test -p ironhorse-compile` cannot *build* without the C submodule
(xs-oracle is an unconditional dev-dependency), so the four oracle-free unit-test modules and two
oracle-free integration tests are unreachable too, and the PR-default `test-ironhorse` job runs none
of them. The byte-identity bar is real but lives entirely in one path-filtered, submodule-fetching
CI lane on one OS/arch.

## 2. Findings

### F1 — Lone-surrogate property keys silently alias to U+FFFD (silent wrong answer)
- **Severity** critical · **Confidence** high · **Category** compiler · **Novelty** new
- **Site** `rust/engine/ironhorse-compile/src/ast.rs:442`; also `src/parser.rs:1481`, `src/parser.rs:1532`, `src/parser/stmt.rs:922`
- **Claim** A source object literal with two distinct lone-surrogate string keys compiles to a single property, and a lookup with a *different* lone surrogate finds it.
- **Evidence**
  ```
  ast.rs:440  /// surrogates fold to U+FFFD (`from_utf16_lossy`); every well-formed key —
  ast.rs:441  /// which is all the corpus interns — round-trips exactly.
  ast.rs:442  pub fn units_to_string(u: &[u16]) -> String { String::from_utf16_lossy(u) }
  parser.rs:1481  let s = crate::ast::units_to_string(&self.cur.string.clone().unwrap_or_default());
  ```
  Probe (`compile_atoms` + `ironhorse_vm::run_program_with_symbols`, release):
  - `var o = {"\uD800": 1, "\uD801": 2}; Object.keys(o).length;` → `"1"` (spec/XS: `2`)
  - `var o = {"\uD800": 1}; o["\uD801"];` → `"1"` (spec: `undefined`)
  - `Object.keys(o)[0].charCodeAt(0)` → `65533` (spec: `55296`)
  - symbols atom for the two-key program: `[03 00 6f 00 ef bf bd 00]` — one U+FFFD symbol, not two CESU-8 surrogate symbols.
  - control: `"\uD800".charCodeAt(0)` → `55296` (string *values* are fine); astral keys are fine.
- **Impact** A guest-triggerable, deterministic, silent wrong result on the production path (`Machine::evaluate` / `PersistentMachine::eval`), with no halt and no diagnostic — the exact failure mode `ironhorse_engine.rs:15-17` says cannot happen ("Ironhorse declines a program it cannot run rather than returning a wrong answer"). It is also a byte-identity violation vs XS (which interns CESU-8 `ed a0 80`), invisible because no fixture covers it. The same aliasing makes two distinct source keys collide in the persisted `KEYS`/symbol space.
- **Root cause** `ast::Item::Symbol(String)` — the AST/coder symbol representation is well-formed UTF-8 and structurally cannot carry the surrogate XS stores.
- **Recommendation** Make the symbol slot a byte string in the CESU-8 encoding the coder already emits (`units_to_cesu8`, `coder.rs:98`), or `Vec<u16>`, and intern on those bytes; keep `String` only for diagnostics. Failing that, refuse a key containing an unpaired surrogate with `ParseErrorKind::Unsupported` rather than folding it. Add a byte-identity fixture with lone-surrogate keys and a `Object.keys().length` conformance case; check whether `ironhorse_vm::symbols::parse_symbols`' `from_utf8_lossy` (symbols.rs:37) has the mirror-image problem at relink.

### F2 — Unbounded recursion: a few KB of source aborts the process, at a depth set by host stack and build profile
- **Severity** critical · **Confidence** high · **Category** robustness (and determinism) · **Novelty** new (facets flagged by the parser/scoper/regexp readers; merged, measured, and re-framed here)
- **Site** `rust/engine/ironhorse-compile/src/coder.rs:934` (pipeline entry); recursion in `parser.rs:626`, `parser/stmt.rs:266`, `scoper.rs:1130`, `scoper.rs:2016`, `coder.rs:547` (`intern_tree`), `coder.rs:1004`; plus `lexer.rs:1223` into `ironhorse-regexp`'s recursive compiler
- **Claim** No depth or stack guard exists anywhere in `ironhorse-compile`, so a bounded-size source aborts the process (SIGABRT, not a panic), and the accept/reject boundary depends on the host thread's stack size and the build profile rather than on the source.
- **Evidence** `grep -i 'depth|recursion|nesting|stack'` over `ironhorse-compile/src` finds no guard. Probe (my `catch_unwind` did **not** contain it):
  - release, 8 MiB main thread: 1000 parens OK, 2000 OK, **4000 → `fatal runtime error: stack overflow, aborting`**
  - debug, 8 MiB main thread: 200 OK, **300 → abort** (a ~20x profile-dependent swing on the same source)
  - release, 2 MiB spawned thread (Rust's default): `var r = /(((…a…)))/;` at 10,000 groups and `/a|a|…/` at 20,000 alternatives (~20–40 KB source) → abort, *from inside the lexer's eager regexp compile*
  Design: "a panic is a crashed crank, not a compromised daemon" (`designs/ironhorse-engine.md:617-618`). CI works around it: `RUST_MIN_STACK: '16777216'` with the comment "the recursion depth is an engine property, not this lane's" (`.github/workflows/ci.yml:826-832`). The 262 harness works around it again: `.stack_size(CASE_THREAD_STACK_BYTES)` "…would overflow and SIGSEGV the whole batch (uncatchable by `catch_unwind`)" (`ironhorse-262/src/xst.rs:1369-1374`). `rust/endo` has no `catch_unwind` at all (grep).
- **Impact** (a) Process-killing DoS from ~8 KB of guest source, taking down every co-hosted machine in the worker, not one crank. (b) Consensus: two validators built with different profiles or running the compiler on threads with different stacks disagree on whether the *same* source compiles. (c) The design's whole safety story ("panic = crashed crank") does not cover the actual failure mode. (d) Reachable at snapshot **restore** too, via `restore_regexps` re-running the same recursive compiler outside any crank (`interp.rs:9155`, per the interp-04 map).
- **Recommendation** Own the budget in the engine, not in the embedder: a monotone `depth` counter threaded through `Parser`, `Scoper`, `Coder` and `ironhorse_regexp::compile`, with a single crate-level constant, returning `Err(ParseError{kind: Syntax, message: "too much recursion"})` — XS's `fxCheckParserStack` behaviour, but as a *counter* (deterministic) rather than a stack-address margin (host-dependent). Add depth fixtures at `LIMIT-1`/`LIMIT+1` so the boundary is pinned, and delete `RUST_MIN_STACK` from CI once it holds.

### F3 — Panic-as-control-flow: the coder/scoper are not total, and the only firewall lives in the test harness
- **Severity** high · **Confidence** high · **Category** error-model · **Novelty** partially-known (coder-a #3, coder-b #1, scoper #3; production-path and classification-erasure framing new)
- **Site** `rust/engine/ironhorse-compile/src/coder.rs:2997`; also `coder.rs:2403`, `:2958`, `:3149`, `:3503`, `:3921`, `:1150`, `:4958`, `scoper.rs:651`; firewall at `ironhorse-262/src/lib.rs:56,76`; unprotected production callers at `rust/endo/src/ironhorse_engine.rs:162,496`
- **Claim** `ironhorse_compile::compile*` panics on valid ES2022 and on a spec early error, `ParseErrorKind::Unsupported` is never produced outside the parser, and the production embedder calls it without `catch_unwind`.
- **Evidence**
  ```
  coder.rs:2997  panic!("static block with lexical declarations deferred");
  coder.rs:2403  panic!("coder: invalid initializer");
  coder.rs:435   /// longjmps out on the first; ironhorse's coder is infallible, so it
  262/lib.rs:56  let compiled = std::panic::catch_unwind(std::panic::AssertUnwindSafe(move || {
  262/lib.rs:76  Err(payload) => Err(ironhorse_vm::SourceCompileError::Unsupported(panic_message(...)))
  endo/ironhorse_engine.rs:162  let (bytecode, symbols) = compile_atoms_with(source, strict)
  ```
  Probe: `class C { static { let x = 1; } }` → `PANIC static block with lexical declarations deferred`; same for `var`, `const`, `function` in a static block; `({a = 1});` and `({a: {b = 1}});` → `PANIC coder: invalid initializer`. `grep Unsupported ironhorse-compile/src` → only `parser.rs:63,207` (3 raise sites). `grep catch_unwind rust/endo/src` → none.
- **Impact** In the harness a guest-triggerable panic is laundered into "coverage gap", so a *real* coder invariant violation reads as "not yet ported" in the dual-run report — the report cannot tell "unimplemented" from "we may have miscompiled", which is precisely the distinction a consensus engine needs. In production the panic unwinds through the daemon crank with no firewall; if any embedder ever sets `panic = "abort"` the harness's firewall stops working too. Semantically, `({a = 1})` is a *catchable* `SyntaxError` under `eval` in XS; Ironhorse turns it into `Halt::Unsupported("eval:compiler-unimplemented")` (`interp.rs:8010`) or a process-level unwind.
- **Recommendation** Make the crate total: give the coder and scoper the same `Result` channel the parser has, return `ParseErrorKind::Unsupported` for the deliberate folds (`static {}` with declarations, unported declare kinds, unported parameter patterns) and `ParseErrorKind::Syntax` for the reachable early errors (`CoverInitializedName` as an expression — the parser should record the refinement obligation at `parser.rs:1397` and rule on it). Reserve `panic!` for invariants no input can reach, and keep `catch_unwind` only as belt-and-braces. This deletes three duplicated `catch_unwind` wrappers and makes the harness's `Unsupported` count mean what it says.

### F4 — Symbol ids silently wrap at 65,536; the SYMB count wraps too and the VM's decoder ignores it
- **Severity** high · **Confidence** high · **Category** compiler · **Novelty** new (coder-a #2; independently reproduced and traced to the VM decoder here)
- **Site** `rust/engine/ironhorse-compile/src/coder.rs:292`, `:298`, `:307`, `:5787`; `rust/engine/ironhorse-vm/src/symbols.rs:26`
- **Claim** A program with more than 65,535 emitted symbols compiles "successfully" to bytecode whose 2-byte symbol operands collide and whose SYMB count field is wrapped, with no diagnostic in either crate.
- **Evidence**
  ```
  coder.rs:292   let mut used: u16 = 0;
  coder.rs:298   used = used.wrapping_add(1);
  coder.rs:307   let count = used.wrapping_add(1);
  coder.rs:5787  out.extend_from_slice(&(symbol_id(c, sym_ids) as u16).to_le_bytes());
  symbols.rs:25  // read strings to the buffer end rather than trusting the count
  ```
  `assign_ids` (`coder.rs:246-262`) increments an `i32` with no bound. Probe: 70,000 `var vN;` declarations → `OK bytecode=550821 symbols=478892 count_le=[113, 17]` (0x1171 = 4465 = 70,001 mod 65,536).
- **Impact** Deterministic, so not a consensus split between replicas, but a silently *wrong program*: two distinct names share one 16-bit operand, so the VM relinks the wrong intrinsic/global. `AGENTS.md` § Numeric domain names exactly this anti-pattern ("silently truncates … rather than failing"). Reachable from one large machine-generated bundle.
- **Recommendation** Fail closed at the boundary: in `assign_ids`/`symbols_atom`, refuse when `id > u16::MAX` with `ParseErrorKind::Syntax`/`Unsupported` ("too many symbols"), mirroring the scoper's existing "too many arguments" refusal at `scoper.rs:2432`. Use `u16::try_from` at `coder.rs:5787` rather than `as u16`. Optionally have `parse_symbols` cross-check the count instead of ignoring it.

### F5 — Compilation is quadratic in source size and entirely unmetered; measured 12.8 s for 1 MB
- **Severity** high · **Confidence** high · **Category** performance (metering) · **Novelty** new (coder-b #3 guessed the complexity; measurement and localization are mine)
- **Site** `rust/engine/ironhorse-compile/src/coder.rs:5440` (`target_pos`), used per `BRANCH_1` at `:5368`; `Vec::remove` at `:5395`, `:5413`, `:5429`; entry `coder.rs:934`
- **Claim** `Coder::optimize` is O(records × branches), so compile time grows quadratically in source size, while the parse meter grows linearly and is charged to nothing.
- **Evidence** `fn target_pos(&self, tid: usize) -> Option<usize> { self.codes.iter().position(…) }` (`coder.rs:5440-5444`) inside the `while i < self.codes.len()` scan at `:5364`. Measured (release, `if(aN){bN;}else{cN;}` × n):
  | n | source | full compile | parse | parse+scope | parse computrons |
  |---|---|---|---|---|---|
  | 4,000 | 117 KB | 143 ms | 16 ms | 20 ms | 52,001 |
  | 8,000 | 237 KB | 773 ms | 29 ms | 40 ms | 104,001 |
  | 16,000 | 495 KB | 3.52 s | 62 ms | 84 ms | 208,001 |
  | 32,000 | 1.00 MB | **12.81 s** | — | — | — |
  Parse and scope are linear; the coder/serializer is the quadratic stage. The scoper's `Eval`-root prepend (`scoper.rs:704` `sc.declares.insert(0, decl)`) is separately quadratic: 2,000→8,000 top-level `var`s is 18.6 ms→343 ms.
- **Impact** `rust/endo/src/inproc.rs:225` records that the daemon's own manager bundle is ~1.2 MB; extrapolating, that is ~18 s of unmetered, unpreemptible host CPU inside a crank, with no check point and no abort path (F6). A guest that can submit source gets an n² CPU amplifier for free. The design's own doctrine — "the best available deterministic proxy for real (wall-clock) execution cost" (`ironhorse-engine.md:362-364`) — is contradicted by a linear meter over quadratic work.
- **Recommendation** Build a `tid → position` index once per `optimize` pass (or keep XS's linked-list shape with an index side table) and replace `Vec::remove` with a retain/compaction pass, restoring O(n). Replace `Vec::insert(0)` in `scope_add_declare` with a push-then-reverse for `Eval` scopes. Then charge the compile cost (F6) so the residual is bounded rather than merely faster.

### F6 — The parse meter is a dead instrument, separately versioned, and its "frozen release" test is inverted
- **Severity** high · **Confidence** high · **Category** metering · **Novelty** partially-known (lexer #1, coder-b #6, docs-ci); the inverted gate is new
- **Site** `rust/engine/ironhorse-compile/src/meter.rs:22`; `src/lib.rs:52`; `coder.rs:934`; `ironhorse-vm/src/interp.rs:56-61`; `ironhorse-vm/src/meter.rs:26`; `tests/parse_meter_determinism.rs:44`
- **Claim** No path charges parse cost to the VM meter; the compiler and VM carry two independently versioned meter releases; and the determinism test fails when the release is *correctly* bumped while passing when the weights change silently.
- **Evidence**
  ```
  compile/meter.rs:22  pub const PARSE_METER_RELEASE: &str = "ironhorse-meter-0";
  vm/meter.rs:26       pub const COST_TABLE_VERSION: &str = "ironhorse-meter-1";
  vm/meter.rs:11-12    the parser adds XS_PARSE_CODE_METERING … (parse metering is out
                       of the interpreter-parity window, so it is not modeled here)
  interp.rs:58-61      pub struct CompiledSource { pub bytecode: Vec<u8>, pub symbols: Vec<u8> }
  parse_meter_determinism.rs:44  assert_eq!(PARSE_METER_RELEASE, "ironhorse-meter-0", …)
  ```
  `compile_atoms_with` (`coder.rs:930-958`) never reads `parser.meter()`. `grep parse_computrons` → only `tests/parse_meter_determinism.rs`. The design lists "Parse unit | `fxMeterSome` calls from the parser | cost-table entry" (`ironhorse-engine.md:398`) and promises "one release-versioned meter … the previous table remains addressable by its version" (`:383-410`). The snapshot `METR` atom records only `COST_TABLE_VERSION`, so a parse-table change is undetectable at resume.
- **Impact** Compilation of arbitrary guest source (top-level program, `eval`, `Function`) costs zero computrons and cannot be aborted — F5 gives that hole an n² shape. The versioning gate is worse than absent: it is an inverted ratchet (bumping the release breaks the test; changing `PARSE_TOKEN_METERING` or the charge sites does not). The test's own name, `parse_computrons_are_deterministic_per_build`, admits it checks a weaker property than the design's per-release-across-hosts requirement.
- **Recommendation** Add `parse_computrons: u64` to `CompiledSource`, charge it on the VM meter in `eval_source`/`create_dynamic_function` and in the `rust/endo` evaluate path, and add a compile-time check point so a quadratic compile can meter-abort. Unify the two version strings behind one constant (or record both in `METR` and gate resume on both). Replace the tautological assertion with golden `(program, computrons)` pairs, as `ironhorse-262/src/lib.rs:1501-1545` already does for the VM's frozen UTF-16 costs.

### F7 — Two valid programs are rejected, and over-rejection is structurally invisible to the test suite
- **Severity** high · **Confidence** high (behaviour reproduced; XS side unverified) · **Category** compiler · **Novelty** partially-known (parser #3, scoper #6; merged with the verification hole)
- **Site** `rust/engine/ironhorse-compile/src/parser/stmt.rs:704`; `src/scoper.rs:1393`; verification gap at `tests/corpus_parse_smoke.rs:63,83`
- **Claim** `for (/a/;;) {}` and `try {} catch (e) { var e; }` — both valid ECMAScript — are rejected with a `SyntaxError`, and neither the compile crate's corpus smoke test nor the 262 positive arm can fail on an over-rejection.
- **Evidence** `stmt.rs:703-705`: `self.match_token(Token::LeftParenthesis)?; self.look_ahead_once()?;` runs *unconditionally* before the header dispatch, so a `/`-initial init has its next token lexed in operator mode and the later `read_regexp` re-entry replays a stale lookahead. `scoper.rs:1393-1395`: `if matches!(dtok, Token::Const | Token::Let | Token::Using | Token::Define) { conflict = Some(id); break; }` — the catch parameter is a `Let` declare, so Annex B.3.4's exemption is not applied. Probe: `for (/a/;;) { break; }` → `ParseError { line: 1, kind: Syntax, message: "missing ?" }`; `try {} catch (e) { var e; }` → `"duplicate variable"`. Verification: `corpus_parse_smoke.rs:63` `// The benign direction (we accept, oracle rejects) — recorded, not fatal.`; the only assertion is on `ironhorse_rejected_oracle_accepted` and on `agree_accept > 0` (`:113-122`).
- **Impact** Deterministic rejection of spec-valid programs — result-parity defects in the shipped path. The verification asymmetry matters more than the two bugs: the compile crate's smoke test asserts nothing on over-*acceptance*, and `xst.rs:560` maps over-*rejection* to `RunSkip("ironhorse-aborted")` (see t262 map finding 1), so neither direction of a parser accept/reject defect can turn CI red. The design says the fail vector matters as much as the pass vector (`ironhorse-engine.md:637-639`).
- **Recommendation** Move the `for`-header lookahead into the three arms that need it (`let`/`using`/`await`), matching XS's `fxForStatement`. Exempt a simple catch parameter from `hoist_var`'s intermediate-scope conflict walk. Make `corpus_parse_smoke` assert on **both** disagreement directions (an intentional divergence belongs on an exceptions ledger with a named entry, not in an `eprintln!`).

### F8 — Operand widths are defined twice with no cross-check, and `emit_step`'s default arm silently drops an unclassified operand
- **Severity** medium · **Confidence** high · **Category** verification (compiler) · **Novelty** new (coder-a #7 named the convention; the table cross-check is mine)
- **Site** `rust/engine/ironhorse-compile/src/coder.rs:5790-5796` (default arm), class predicates `:5866`, `:5895`, `:5926`, `:5934`; `rust/engine/ironhorse-compile/src/opcodes.rs:1-6`; ground truth `rust/engine/ironhorse-vm/src/opcode.rs:258` (`CODE_SIZES`), `:1064` (`instruction_len`)
- **Claim** `opcodes.rs` claims to be generated from `ironhorse-vm/src/opcode.rs` but no generator or agreement test exists; the emitted operand width for each opcode is expressed a second time as three hand-written class predicates plus a `match`, whose default arm emits **zero** operand bytes for any opcode it does not enumerate.
- **Evidence**
  ```
  opcodes.rs:1-5  //! XS opcode byte values, generated from `ironhorse-vm/src/opcode.rs`
                  //! … Do not edit by hand.
  coder.rs:5790   } else if is_index_2_fixed(c.id) { … }
  coder.rs:5794   // else: a plain 1-byte opcode, already pushed
  ```
  `grep -rn "opcodes.rs" rust/engine` finds only that doc comment; there is no script, `build.rs`, or test. I diffed the two tables mechanically: all 246 name→value pairs are identical today. I also cross-checked the coder's static per-opcode emitted width against the VM's `CODE_SIZES` for all 246 opcodes: the only mismatches are `CODE_ARCHIVE_1/2/4` and `STRING_ARCHIVE_1/2/4`, which the coder never emits. So the classes are *not total* — they simply happen not to be exercised.
- **Impact** A new or reclassified opcode (an upstream XS bump, or a fold being implemented) produces bytecode that is short by its operand, with no compile-time error; the VM's `instruction_len` walk then mis-frames every subsequent instruction. This is the one bug class byte-identity testing catches only where the oracle corpus reaches, and it is a silent-wrong-bytecode class, not a crash class.
- **Recommendation** Add a cross-crate test in `ironhorse-262` (which already depends on both): for every opcode, assert the coder's emitted record length equals `ironhorse_vm::opcode::CODE_SIZES`'s resolution, and assert `opcodes.rs` name/value agreement — the two checks I ran by hand, mechanized. Additionally, walk the output of every byte-identity fixture with `ironhorse_vm::instruction_len` and assert the walk lands exactly on `bytecode.len()`; that is a cheap total-coverage net for the whole serializer. Make the default arm `unreachable!()` with the opcode name rather than a silent no-op, or generate `opcodes.rs` for real.

### F9 — The scoper→coder contract is raw-address hash maps with three inconsistent miss behaviours, one silent
- **Severity** medium · **Confidence** high · **Category** modularity · **Novelty** known-open (scoper map #1, coder-b #8) — confirmed still open
- **Site** `rust/engine/ironhorse-compile/src/scoper.rs:361`; consumed at `coder.rs:502`, `coder.rs:701`, `coder.rs:1194`

  ```
  coder.rs:502   self.tree.resolutions.get(&node_key(node)).copied().flatten()   // None → global symbol path
  coder.rs:1194  *self.tree.scope_counts.get(&scope).unwrap_or(&0)               // → 0 frame slots
  ```

### F13 — Lex-originating error messages carry a `line N:` prefix into the guest-observable `SyntaxError`
- **Severity** medium · **Confidence** high · **Category** error-model · **Novelty** partially-known (lexer #4) — reproduced
- **Site** `rust/engine/ironhorse-compile/src/parser.rs:76`; `src/error.rs:61`; consumed at `ironhorse-262/src/lib.rs:73`, `ironhorse-vm/src/interp.rs:8007`
- **Claim** `ParseError.message` is bare for grammar errors but prefixed with `"line N: "` for lexer errors, and `ParseError::Display` doubles the prefix.
- **Evidence** Probe:
  ```
  "0x"      -> kind=Lex   message="line 1: invalid number"    display="line 1: line 1: invalid number"

  "'a\nb'"  -> kind=Lex   message="line 2: end of line in string"   (reported one line late)
  ```

  **Impact** `eval("0x")` throws `SyntaxError: line 1: invalid number` where XS throws `SyntaxError: invalid number`; the message is guest-observable and is compared as a whole string by the dual-run harness, so this is a result divergence for every lexer-originating early error under `eval`/`Function`, plus an internal inconsistency between the two error types. `LineTerminatorInString` is additionally reported one line late (`lexer.rs:933-939`).
- **Recommendation** Keep location in the `line` field only: build `ParseError` from `LexError` with `message: e.kind.to_string()` and let `Display` add the prefix once. Move `self.line += 1` after the `Err` return at `lexer.rs:933-939`.

### F14 — Eager regexp compilation inside the lexer: work discarded, duplicated at runtime, and it imports unbounded recursion
- **Severity** medium · **Confidence** high · **Category** modularity · **Novelty** partially-known (lexer #9, regexp map) — confirmed and reproduced
- **Site** `rust/engine/ironhorse-compile/src/lexer.rs:1223`; `src/lib.rs:32` (`pub use ironhorse_regexp::unicode`)
- **Claim** Every regexp literal runs the full `ironhorse-regexp` compiler at lex time, discards the result, and re-imports that crate's unbounded recursion into the compile pipeline; the pattern is compiled again at runtime.
- **Evidence**
  ```

  lexer.rs:1224      Ok(_) | Err(…CompileError::Unsupported(_)) => {}
  ```

## 3. Strengths

- **The transliteration is auditable without the oracle.** Every coder/parser/scoper method names its XS
  counterpart and, unusually, explains *why* XS behaves as it does — `scoper.rs:2237-2241` reproduces a
  known XS frame-accounting bug **on purpose** and says so, and `coder.rs:936-940` states exactly which
  shim flags the Script goal inherits. A reader can distinguish a design choice from an accident, which
  is rare in a port this size.
- **Determinism inside the crate is genuinely clean.** I re-checked: no `HashMap`/`HashSet` iteration
  reaches output anywhere in `coder.rs` or `scoper.rs` (the two hash containers at `coder.rs:3390` and
  `:2900` are membership/entry only), `NUMBER` is emitted as `to_le_bytes` of the raw `f64`, BigInt limbs
  are canonicalized, `Sym::Anon` and declare ids are sequential, address keys are lookup-only, and there
  is no host time, locale, env, or libm use. Given how many of this repo's other regions have
  iteration-order hazards, this is a real achievement.
- **The dependency inversion is real, not aspirational.** The VM defines `SourceCompiler`
  (`interp.rs:89-101`), takes `ironhorse-compile` only as a dev-dependency, and carries an honest
  `SourceCompileError::Unsupported` channel. Every piece needed to fix F3 already exists in the design.
- **Regression fixtures are named after the bug class they closed** (`named_class_with_heritage_names_constructor`,
  the Class α/β/γ/ε blocks) and each explains the divergence it locks — a durable triage record rather
  than an opaque snapshot.
- **The code-time `SyntaxError`s XS raises in the coder are handled correctly** for the three sites that
  exist (`invalid break/continue`, `invalid const/using`, duplicate labels): structured `Err(Syntax)`
  with XS's wording via `Coder::error`, not a panic. The right pattern is present; F3 is about the
  other twelve sites.
- **`#![forbid(unsafe_code)]` holds** and the whole serializer is plain index arithmetic over `Vec`s; the
  scoper's arena + `(scope, id)` addressing is a clean, index-based replacement for XS's pointer graph
  that survives the eval-prepend and block-placeholder removal without remapping.
- **`corpus_scope_smoke` gives the scoper a totality bar over 1,711 programs** and `CORPUS_PROGRAM_COUNT`
  is asserted in two places so a dropped program is caught — the right instinct, undermined only by F11.

## 4. Recommended architectural direction

**Make the crate total, and make it own its own bounds.** The single highest-leverage change is to
finish the error model the design already sketched: the scoper and coder get the parser's `Result`
channel, deliberate folds return `ParseErrorKind::Unsupported`, reachable early errors return
`Syntax`, and `panic!` is reserved for invariants no input can reach. Pair that with a monotone
recursion counter threaded through parser/scoper/coder and the regexp validator, tripping a
crate-level constant into a `Syntax` error. Together these turn today's two uncontainable failure
modes — an abort that `catch_unwind` cannot catch, and a panic classified as a coverage gap — into
ordinary compile errors, and they make accept/reject a function of the source alone, which is what a
consensus engine has to promise. Only then does the harness's `catch_unwind` become belt-and-braces
rather than the load-bearing firewall it is now (and which production does not have at all).

**Fix the representation at the symbol boundary, and stop trusting width conventions.** F1 is not a
bug in a function; it is `Item::Symbol(String)` being the wrong type for a CESU-8 symbol space, and
it produces silent wrong answers today. Carry symbols as the bytes the coder already emits. In the
same spirit, replace the three implicit contracts that carry the rest of the pipeline with checkable
ones: node identity by a parser-stamped `u32` instead of a heap address (F9); a `u16::try_from` at
the symbol-id boundary instead of `as u16` (F4); and a cross-crate test — `ironhorse-262` depends on
both crates — that walks every fixture's bytecode with `ironhorse_vm::instruction_len` and asserts
the walk lands exactly on the end, plus a mechanical `opcodes.rs`/`CODE_SIZES` agreement check (F8).
That last test is cheap, total over the serializer, and would have caught the entire "silent short
emit" class before any oracle was needed.

**Close the cost and verification holes together.** Add `parse_computrons` to `CompiledSource`,
charge it, and add a compile-time meter check point; then fix `Coder::optimize`'s quadratic scan so
the charged cost is a defensible model rather than a tax (F5, F6). Unify the two meter release
strings and lock the parse table with golden values instead of the currently inverted assertion.
Finally, make the compiler's own tests runnable without the C oracle by putting `xs-oracle` behind a
feature and gating only the oracle-dependent targets — a contributor should not need a C submodule to
run the parser's shape fixtures — and make both directions of accept/reject disagreement fail
(F7, F11, F12). The byte-identity bar is a strong instrument; today it is the *only* instrument, it
runs in one path-filtered lane on one architecture, and it is blind to over-acceptance, to
over-rejection, to the SYMB atom in-crate, to the `_2`/`_4` width families, and to every construct
that panics before it can be compared.
