# Lens review: Determinism and consensus safety

Reviewer: deep-architecture lens 4 (determinism / consensus).
Tree: /home/user/endo-but-for-bots @ HEAD on `claude/ironhorse-architecture-review-bimf34`.
Every finding below was verified by reading the cited lines in the current tree; the
behavioural claims marked "probe" were executed against the live engine from an
out-of-tree cargo project that path-depends on `ironhorse-vm` + `ironhorse-compile`
(no repo file was modified).

## 1. Assessment

IronHorse's *internal* determinism discipline is genuinely good, and better than the
census's raw HashMap counts suggest. Every snapshot emitter I sampled sorts before it
encodes (`array_buffers_snapshot` interp.rs:8984, `typed_arrays_snapshot` :8999,
`wrappers_snapshot` :9114, `symbol_registry_snapshot` :10511); `gc_roots` sorts and
dedups (:43692–43693); array elements are a `BTreeMap`; the compiler's address-keyed
side tables are lookup-only and never iterated; boot allocates from fixed-order `Vec`
literals; `Date.now()` returns 0 and `Temporal.Now` is pinned to epoch 0
(interp.rs:25112 `const NOW_EPOCH_NS: i128 = 0`); the number↔string codecs are pure
Rust and correctly rounded; the snapshot wire format never serialises a `usize`. The
one XS platform artefact that *would* have leaked — C's signed `char` in the parser's
symbol hash — is frozen deliberately into `b as i8 as i32` (coder.rs:221). Where a
code-unit↔byte hazard was recognised, the engine fails closed loudly
(`RegExp:non-ascii-stateful-lastIndex`, interp.rs:20169). This is the work of people
who understood the problem.

What is missing is not discipline inside the interpreter; it is **the boundary**. The
design states determinism as unconditional — "identical inputs produce identical
computrons on every host, architecture, and build" (designs/ironhorse-engine.md:373–375),
and "cross-platform CI verify computron stability across runs and platforms" (:455–456)
— and nothing in the repository holds that line. Concretely, four independent leaks
put two honestly-built validators on different answers:

1. **Platform libm.** 22 `Math` transcendentals call `f64::sin`/`powf`/`ln`… directly
   (interp.rs:29879–29930). The code says so, in a 15-line DECISION-OF-RECORD that
   rescopes determinism to "PER RELEASE BINARY PER PLATFORM" (:29829–29843). That
   rescoping lives only in a private Rust doc comment; the design and README still make
   the unconditional claim, and no consumer-facing document states the narrower one.
2. **NaN payloads.** There is no canonicalisation anywhere. `Slot::number` stores raw
   bits (value.rs:332), the Float64 typed-array store is `n.to_le_bytes()`
   (interp.rs:40344), and the snapshot codec has a test *asserting* payload
   preservation (slot_codec.rs:189–203). Probe: `d.setFloat64(0, Math.sqrt(-1));
   d.getUint8(0)` → **255** on this x86-64 host; on AArch64 the default NaN is
   `0x7FF8…` and the same program yields 127. The design says the opposite
   (":336 NaN canonicalization follows `mxCanonicalNaN`"), and the oracle *is* built
   with `mxCanonicalNaN=1` (xs-oracle/build.rs:81) — so the differential harness, which
   compares completions rendered through `String()`, is structurally blind to it.
3. **Two builds.** `rust/engine` is an excluded nested workspace with its own lockfile.
   The shipped daemon (root workspace) and the CI-tested engine resolve *different*
   ICU graphs: `icu_provider` 2.2.0 vs 2.3.0, `icu_locale_core` 2.2.0 vs 2.3.0,
   `zerovec` 0.11.6 vs 0.11.7, `zerotrie` 0.2.4 vs 0.2.5, plus tinystr/potential_utf/
   writeable/displaydoc. There is no `rust-toolchain.toml` for the engine and no
   `rust-version`. And `Intl.Segmenter`/`Collator` are live (probe: a word-segment loop
   over `'hi there'` returns 3), so ICU data is on the consensus path.
4. **No enforcement.** Every IronHorse CI lane is `runs-on: ubuntu-latest`
   (ci.yml:698, :766; full-test262.yml:52; deep-fuzz.yml:47) while the same workflow
   uses `matrix.platform` for six JS jobs. The determinism gate that exists —
   `--repeat N` (ironhorse-262/src/xst.rs:744) — defaults to 1 (:229) and is invoked by
   no workflow. There is no golden-computron corpus anywhere, so `COST_TABLE_VERSION`
   ("ironhorse-meter-1", meter.rs:26) can drift silently; the snapshot-carry tests
   compare computrons *relatively* (snapshot vs continuous), never against a frozen
   number.

Underneath the determinism story sits a second class of defect that this lens keeps
tripping over: **a Rust `String` seam that violates the engine's own UTF-16 value
model**, and **byte-vs-code-unit offset leakage from the same seam**. Probes:
`new Error('\uD800').message.charCodeAt(0)` → 65533 while `'\uD800'.charCodeAt(0)` →
55296; `/b/.exec('äb').index` → 2 (spec: 1); `'äb'.search(/b/)` → 2. These
are silent wrong answers, not aborts, on a shipped path — and they are *deterministic*
wrong answers, which is worse for a consensus engine: every validator agrees on the
wrong value and it persists into snapshots.

Finally, the meter itself is not yet a safety mechanism in production. All 43
`check_meter()` sites live inside the dispatch loop (interp.rs:11741–15733); no
built-in checks, so `String.prototype.repeat` charges `count * 2^14` raw units and
*then* calls `Vec::with_capacity(len * count)` (:31219) — an `handle_alloc_error`
process abort no `catch_unwind` contains, exactly the failure the tree already
diagnosed and fixed at one other site (:18350–18360). And `rust/endo/src/
ironhorse_engine.rs` never calls `arm_meter`/`rearm_meter`/`reattach_meter_host` at
all, so in the only shipped integration the meter accumulates and never aborts.

Verdict: the engine is *reproducible on one binary on one host* and the internal
plumbing supports more than that. It is not yet a cross-host consensus engine, and —
more importantly — nothing in CI or the docs would tell you when it stopped being one.

## 2. Findings

### F1. Platform libm in 22 `Math` built-ins defeats cross-host consensus; the narrowed scope is documented only in a private comment
- severity **high**, confidence **high**, category determinism
- `rust/engine/ironhorse-vm/src/interp.rs:29829` (decision), `:29879–29930` (sites)
- Claim: `Math.sin/cos/exp/pow/log/atan2/hypot/cbrt/…` return the host libm's result
  bit-for-bit, so two validators on glibc and musl (or x86-64 and AArch64) can differ
  in the last ulp, and because results feed guest branches the computron counts diverge
  transitively.
- Evidence:
  ```
  /// LIBM DECISION-OF-RECORD (wave-6 W6-23): the transcendental bodies
  /// call the platform libm (via `f64::sin`/`powf`/…), the engine's one
  /// genuine host-environment dependence …
  /// The recorded stance: determinism
  /// is scoped PER RELEASE BINARY PER PLATFORM
              Sin => unary(f64::sin, arg(0))?,
  ```
  vs designs/ironhorse-engine.md:373–375 "identical computrons on every host,
  architecture, and build".
- Impact: heterogeneous-validator consensus break; a chain halt.
- Recommendation: the pure-Rust `libm` crate is **already in the engine lockfile**
  (rust/engine/Cargo.lock:258, pulled by `core_maths` under `icu_segmenter`), so
  vendoring costs no new supply-chain surface. Land it together with an oracle built
  against the same library, as the comment itself prescribes. Until then, move the
  narrowed scope out of the source comment into designs/ironhorse-engine.md § Metering
  and the README's consumer-facing statement — a consensus scope that only the
  implementer can read is not a scope.
- Novelty: **known-open** — store-seam ledger item **W6-23** (maps/store-seam-design-ledger.md:83);
  still open, and the parent design still carries the stronger claim.

### F2. No NaN canonicalization: the host CPU's default-NaN sign/payload is guest-observable and persisted, and the differential oracle is structurally blind to it
- severity **high**, confidence **high**, category determinism
- `rust/engine/ironhorse-vm/src/value.rs:332`; other sites
  `ironhorse-vm/src/interp.rs:40344`, `ironhorse-snapshot/src/slot_codec.rs:77` and the
  test at `:189`, `xs-oracle/build.rs:81`
- Claim: a NaN produced by arithmetic carries the host CPU's default-NaN bit pattern
  (x86-64 SSE `0xFFF8…`, AArch64 `0x7FF8…`), is readable through a `DataView`/
  `Float64Array` byte view, and is written verbatim into the snapshot — so the same
  program on two architectures produces different guest values and different snapshot
  bytes.
- Evidence (code):
  ```rust
  pub fn number(n: f64) -> Slot { Slot::of(Kind::Number, Payload::Number(n)) }   // value.rs:332
  3 => n.to_le_bytes().to_vec(),                                                  // interp.rs:40344 (Float64 store)
  Payload::Number(n) => { d[0..8].copy_from_slice(&n.to_bits().to_be_bytes()); }  // slot_codec.rs:77
  fn nan_bits_preserved() { … assert_eq!(n.to_bits(), raw) }                      // slot_codec.rs:189
  .define("mxCanonicalNaN", Some("1"))                                            // xs-oracle/build.rs:81
  ```
  Probe (this x86-64 host):
  `var d=new DataView(new ArrayBuffer(8)); d.setFloat64(0, Math.sqrt(-1)); d.getUint8(0)` → **255**.
  Same for `0/0`. On AArch64 the same programs yield 127.
- Impact: cross-architecture consensus divergence in both guest results and persisted
  state. The design explicitly promised the opposite ("NaN canonicalization follows
  `mxCanonicalNaN`", designs/ironhorse-engine.md:336), and because the oracle *is*
  built with `mxCanonicalNaN=1` while `results_agree` compares `String()`-rendered
  completions, the differential harness can never observe the divergence.
- Recommendation: canonicalize on ingress to a `Slot` — make `Slot::number` map any NaN
  to a single chosen bit pattern (XS's `mxCanonicalNaN` value), and make
  `slot_codec::encode_slot` refuse or canonicalize a non-canonical NaN. Replace
  `nan_bits_preserved` with `nan_is_canonicalized`. Add a fuzz/262 case that reads NaN
  bytes through `DataView`.
- Novelty: **new** (the mapper for interp-11 raised it as a lead; not in the store-seam
  ledger, and the design records the opposite as done).

### F3. The design's cross-platform / repeat determinism CI does not exist, and no golden computron corpus pins the cost table
- severity **high**, confidence **high**, category verification
- `.github/workflows/ci.yml:698`; other sites `.github/workflows/ci.yml:766`,
  `.github/workflows/ironhorse-full-test262.yml:52`,
  `.github/workflows/ironhorse-deep-fuzz.yml:47`, `ironhorse-262/src/xst.rs:229`
- Claim: no workflow runs any IronHorse job on a second OS or architecture, no workflow
  passes `--repeat N`, and no test asserts an absolute computron value — so every
  determinism claim in the design is unenforced and a silent cost-table drift under an
  unchanged `COST_TABLE_VERSION` passes CI.
- Evidence: `runs-on: ubuntu-latest` at all four cited lines while the same ci.yml uses
  `runs-on: ${{ matrix.platform }}` for six JS jobs (:162, :273, :328, :370, :476);
  `repeat: 1,` (xst.rs:229) with `if cfg.repeat > 1 && determinism_violation(...)`
  (:878, :1105) as the only gate; `grep -rn repeat .github/workflows/*.yml` → no match;
  the snapshot `*_carry.rs` suites compare snapshot-vs-continuous computrons, never a
  frozen number.
- Impact: the property Agoric consensus depends on ("same release ⇒ same frozen cost
  table ⇒ identical computrons", design:475–478) has no test. F1 and F2 would both be
  caught by a two-platform lane; neither is.
- Recommendation: (a) add `runs-on: ${{ matrix.platform }}` with
  `[ubuntu-latest, macos-latest]` (and ideally an aarch64 runner) to `test-ironhorse`;
  (b) add a checked-in golden corpus `program → (result, computrons)` asserted by
  `cargo test -p ironhorse-vm`, so any weight change forces an explicit
  `COST_TABLE_VERSION` bump and a golden re-pin; (c) wire `--repeat 3` into the oracle
  lane.
- Novelty: **partially-known** — docs-ci mapper raised the single-platform half;
  the golden-computron gap is new.

### F4. The shipped build and the CI-tested build are different dependency graphs, with no toolchain pin and an ICU version skew on a live consensus surface
- severity **high**, confidence **high**, category determinism
- `Cargo.toml:6` (`exclude = ["rust/engine"]`); other sites `Cargo.lock` vs
  `rust/engine/Cargo.lock`, `rust/engine/ironhorse-vm/Cargo.toml:16–18`,
  `rust/engine/ironhorse-vm/src/interp.rs:4422`
- Claim: `cargo build` at the repo root (which is how the daemon links the engine, via
  `rust/endo/Cargo.toml:7–17`) resolves a different ICU dependency graph than
  `cd rust/engine && cargo test` (the CI job), and `Intl.Segmenter`/`Intl.Collator` are
  reachable guest surfaces that consume that data.
- Evidence: root vs engine lockfiles resolve `icu_provider` **2.2.0 / 2.3.0**,
  `icu_locale_core` **2.2.0 / 2.3.0**, `zerovec` **0.11.6 / 0.11.7**, `zerotrie`
  **0.2.4 / 0.2.5**, `tinystr` 0.8.3/0.8.4, `potential_utf` 0.1.5/0.1.6, `writeable`
  0.6.3/0.6.4, `displaydoc` 0.2.5/0.2.7. `find . -name rust-toolchain*` finds none for
  the engine; `grep rust-version rust/engine/Cargo.toml` → none.
  `const INTL_DATA_VERSION: &str = "ironhorse-intl-2026a";` (interp.rs:4422) is a
  hand-stamped string with no derivation from the ICU crate versions, and unlike
  `COST_TABLE_VERSION` (gated at `image.rs:4444`, `store.rs:2010`) it is gated nowhere —
  a snapshot written under one ICU data set resumes silently under another.
  Probe: `new Intl.Segmenter('en',{granularity:'word'}).segment('hi there')` iterates 3
  segments; `new Intl.Collator('de',{sensitivity:'base'}).compare('ä','a')` → 1.
- Impact: two validators that both "build from source" can differ; and an ICU bump
  changes Intl/normalisation results with no version gate and no fail-closed resume.
- Recommendation: add a `rust-toolchain.toml` at `rust/engine/` (and pin the same
  channel at the root), add a CI step that asserts the two lockfiles agree on every
  shared package version, and either fold `INTL_DATA_VERSION` into the snapshot
  signature/`METR`-style gate or derive it mechanically from the pinned ICU versions
  (`env!("CARGO_PKG_VERSION")`-style build script) instead of hand-stamping it.
- Novelty: **partially-known** (an integration mapper noted "two workspaces, two
  lockfiles"; the concrete ICU skew, the missing toolchain pin, and the ungated
  `INTL_DATA_VERSION` are new).

### F5. Guest-triggerable unbounded allocation inside a built-in aborts the process; and the shipped integration never arms the meter at all
- severity **critical**, confidence **high**, category metering
- `rust/engine/ironhorse-vm/src/interp.rs:31219`; other sites
  `ironhorse-vm/src/interp.rs:11741–15733` (all 43 `check_meter()` sites),
  `rust/endo/src/ironhorse_engine.rs:147`
- Claim: no meter check point exists inside any built-in, so
  `'x'.repeat(2**31-1)` charges its computrons and *then* calls
  `Vec::with_capacity(content.len() * count)`, which on failure calls
  `handle_alloc_error` — a process abort `catch_unwind` cannot contain; and in the only
  shipped integration the meter is never armed, so even the dispatch-loop check never
  fires.
- Evidence:
  ```rust
  self.meter.tick_builtin_some(count as u64);
  let mut out = Vec::with_capacity(content.len() * count as usize);   // interp.rs:31219
  ```
  `grep -n "check_meter()" interp.rs` → 43 hits, all between :11741 and :15733 (the
  dispatch loop). `grep -n "arm_meter\|rearm_meter\|reattach_meter_host"
  rust/endo/src/ironhorse_engine.rs` → no match, although the API exists
  (interp.rs:10667, :10684, :10697). The tree already diagnosed this exact class at
  another site: "where the reservation fails, `handle_alloc_error` ABORTS THE PROCESS,
  which no `catch_unwind` can contain … measured: 132 seconds and 8.6 GB" (:18350–18360).
- Impact: one line of guest JS kills the worker process (and, in a shared-platform
  process, every other worker in it). With the meter unarmed there is no crank limit
  at all in production.
- Recommendation: apply the :18350 remedy uniformly — bound-and-charge *before*
  materialising, at every built-in whose output size is a guest-chosen scalar
  (`repeat`, `padStart/padEnd`, `Array.prototype.fill/copyWithin`, `join`,
  `TypedArray` constructors, `Iterator.prototype.toArray`) — and give `Meter` a
  `try_reserve`-style admission call (`charge_and_check(n)`) that built-ins use instead
  of bare `tick_*`. Separately, wire `arm_meter`/`set_crank_limit` through
  `ironhorse_engine.rs` before anything metered ships.
- Novelty: **partially-known** — the class is ledgered (review wave 5, fixed at the
  TypedArray-from-source site) and the unarmed-meter half was raised by the
  integration-endo mapper; the `repeat` site and the uniform-gap framing are new.

### F6. `RegExp.prototype.exec().index` and `String.prototype.search` return UTF-8 byte offsets for non-ASCII subjects — the sibling `lastIndex` path is guarded, these are not
- severity **high**, confidence **high**, category correctness (silent wrong state)
- `rust/engine/ironhorse-vm/src/interp.rs:20284`; other sites `:20311–20312`, `:20169`,
  `:20255` (`regexp_nul_pairs_before`)
- Claim: the matcher runs over UTF-8 bytes and the only offset correction applied is for
  the `C0 80` NUL spelling, so any multi-byte code point before a match inflates the
  reported index by the extra byte count.
- Evidence:
  ```rust
  Payload::String(off) => Self::regexp_subject_bytes(&self.str_text(off)),         // :20284
  let match_start = captures[0].0 - Self::regexp_nul_pairs_before(&subject, …);    // :20311
  // the code-unit↔byte `lastIndex` remap … is identity only for an ASCII subject;
  // a multi-byte subject under a stateful flag self-names.
  if advance && !subject.is_ascii() { return Err(Halt::Unsupported("RegExp:non-ascii-stateful-lastIndex")); }  // :20166–20170
  ```
  Probes: `/b/.exec('äb').index` → **2** (spec: 1); `'äb'.search(/b/)` → **2**;
  `/b/.exec('ab').index` → 1 (ASCII correct).
- Impact: a deterministic wrong answer on a shipped path, and one every validator
  agrees on; it flows into slicing logic in guest code and into persisted state. The
  guard at :20169 proves the hazard was understood, which makes the unguarded siblings a
  gap rather than an oversight.
- Recommendation: either (a) carry the code-unit↔byte remap the guard's own comment
  names (`fxCacheUTF8ToUnicodeOffset`) and apply it to *every* reported offset —
  `index`, `.indices`, `search`, `matchAll` — or (b) extend the `!subject.is_ascii()`
  refusal to the whole regexp surface until the remap lands. Silent wrong offsets are
  worse than an honest `Unsupported`.
- Novelty: **new** (no map reports it; the interp-09 mapper covered the lossy-String
  half but not the offset half).

### F7. A lossy Rust-`String` ToString seam turns lone surrogates into U+FFFD in guest-observable values, next to a lossless helper that exists and is not used
- severity **high**, confidence **high**, category api-boundary
- `rust/engine/ironhorse-vm/src/interp.rs:10892`; other sites `:38979`
  (`to_string_bytes_metered`), `:24061` (`value_to_string`), `:23080`+`:23104`
  (Error constructor), `:30880` (`string_receiver_text`), `:11010` (RegExp source)
- Claim: values that pass through `str_text` (`String::from_utf16_lossy`) lose lone
  surrogates, contradicting the 2026-07-06 UTF-16 storage decision, even though the
  lossless `to_string_units` exists in the same file and documents exactly this hazard.
- Evidence:
  ```rust
  fn str_text(&self, off: ChunkOffset) -> String { String::from_utf16_lossy(&self.str_units(off)) }   // :10892
  Payload::String(off) => self.str_text(off).into_bytes(),                                             // :38979
  Some(String::from_utf8_lossy(&bytes).into_owned())                                                   // :23080 (Error message)
  let off = self.alloc_str_text(text.as_bytes());                                                      // :23104 (own `message`)
  /// ECMAScript `ToString`, retaining UTF-16 code units … (so lone surrogates never
  /// pass through Rust's scalar-value `String`)                                                       // :30910 to_string_units
  ```
  Probe: `new Error('\uD800').message.charCodeAt(0)` → **65533**, while
  `'\uD800'.charCodeAt(0)` → 55296 and `new Error('𐀀').message.length` → 2.
- Impact: silent string corruption on a shipped path, persisted into snapshots; 83
  `str_text` call sites make this a class, not a site. It also blocks the store-seam's
  "the stored form is exactly what the specification defines a string to be"
  (design:318–336).
- Recommendation: make `str_text` `#[deprecated]`-in-spirit — rename it
  `str_text_lossy_for_diagnostics`, restrict it to `Debug`/diagnostic paths, and route
  every value-producing path through `to_string_units`/`new_string_units`. Store
  `ErrorInfo.message` as `Vec<u16>`. Add fuzz target 4 (UTF-8⇄UTF-16 boundary), which
  the design specifies and which does not exist.
- Novelty: **partially-known** — the interp-09 and compile-lexer mappers both flagged
  the seam; the Error-constructor round trip is confirmed here by probe.

### F8. Array `length` above 2^31 is reported to the guest as a negative number, and above 2^32-1 silently becomes 0
- severity **high**, confidence **high**, category correctness
- `rust/engine/ironhorse-vm/src/interp.rs:12696`; other sites `:35516–35518`
  (`to_length_u32`), `:36965–36971` (`array_own_descriptor`)
- Claim: `ArrayData.length` is a `u32` rendered to the guest with `as i32`, and the
  length setter's fallback arm silently stores 0 instead of throwing `RangeError`.
- Evidence:
  ```rust
  Slot::integer(self.arrays[&inst].length as i32)                              // :12696 (arr.length get)
  Payload::Number(n) if n >= 0.0 && n.fract()==0.0 && n <= 4294967295.0 => n as u32,
  _ => 0,                                                                       // :35516–35518
  value: Some(Slot::integer(a.length as i32)),                                  // :36970
  ```
  Probes: `a.length = 4294967295; a.length` → **-1**;
  `a.length = 3000000000; a.length` → **-1294967296**;
  `a.length = 2147483648; a.length` → **-2147483648**;
  `a.length = 5000000000; a.length` → **0** (spec: `RangeError`).
- Impact: a deterministic wrong value observable from one line of ordinary JS, which
  then feeds every length-driven loop and is persisted (`ARRY` rows carry the raw u32,
  interp.rs:9311 ff.). Because it is deterministic it will not be caught by any
  determinism gate — only by conformance.
- Recommendation: render length through `Slot::number(a.length as f64)` whenever it
  exceeds `i32::MAX`, and make `to_length_u32` return `Result` so the out-of-range arm
  raises `RangeError` (`checked_array_length` at :35524 already has the right shape —
  the setter just does not use it).
- Novelty: **new**.

### F9. Snapshot boot-layout compatibility rests on a caller-supplied opaque string; nothing in the engine binds it to the actual boot layout
- severity **high**, confidence **high**, category snapshot-coverage
- `rust/engine/ironhorse-snapshot/src/format.rs:326`; other sites
  `ironhorse-vm/src/interp.rs:5377`, `rust/endo/src/ironhorse_engine.rs:394`
- Claim: adoption boots a fresh machine and replaces its arenas, so every boot-derived
  map keyed by `SlotIndex` survives from the *current* build; the only guard is a
  `Signature` string the host passes in, with no derivation from `create_intrinsics`.
- Evidence:
  ```
  ///    written under a different boot layout would therefore attach this
  ///    build's boot metadata to the image's unrelated slots — silently.
  ///    Nothing else catches it: `boot_slot_count` is not serialized      // format.rs:333–336
  interp.boot_slot_count = interp.slots.capacity();                        // interp.rs:5377 (never serialized)
  let signature = ironhorse_snapshot::Signature::new(&options.signature);  // ironhorse_engine.rs:394
  ```
- Impact: a validator that rebuilds the engine with one reordered `alloc_method`
  restores a peer's snapshot into a machine whose `functions`/`*_proto` maps point at
  unrelated slots — silent wrong state across the whole fleet, with no refusal. The
  doc's own mitigation ("at release the signature must move with it") is a human
  process step.
- Recommendation: derive the signature mechanically — hash the boot region
  (`boot_slot_count` plus the ordered `(SlotIndex, NativeMethod)` list
  `create_intrinsics` produces) at machine construction, serialize it, and refuse on
  mismatch, exactly as `COST_TABLE_VERSION` is refused at image.rs:4444. A build-derived
  fingerprint cannot be forgotten; a hand-stamped string will be.
- Novelty: **known-open** (interp-03 mapper finding 5); reported here because it is the
  determinism-lens twin of F4 and remains open.

### F10. No `[profile]` overflow-checks setting: CI validates the panic-on-overflow build while production ships the silent-wrap build
- severity **medium**, confidence **high**, category determinism
- `Cargo.toml` (root, no `[profile]` section); other sites
  `rust/engine/Cargo.toml` (no `[profile]`), `ironhorse-compile/src/lexer.rs:308`
- Claim: `cargo test -p ironhorse-vm -p ironhorse-snapshot` (the CI job, ci.yml:698)
  runs the dev profile, where a guest-reachable integer overflow is a deterministic
  panic (a "crashed crank"), while a release daemon wraps silently and continues with a
  wrong value — so CI and production disagree about the *class* of every overflow bug.
- Evidence: `grep -rn "overflow-checks\|debug-assertions" rust/engine .github` → no
  match; neither `Cargo.toml` has a `[profile]` section; the confirmed instance is
  `//@line 4294967295\n\n\nx`, which panics `attempt to add with overflow` in the
  checked build and yields `Lexeme.line == 0` in release (lexer.rs:308).
- Impact: the design's memory-safety doctrine ("a panic is a crashed crank, not a
  compromised daemon") is a statement about the *tested* build only; in production the
  same defect is silent wrong state, which for a consensus engine is strictly worse.
- Recommendation: set `overflow-checks = true` in `[profile.release]` for both
  workspaces. The engine is already spending on safety (`forbid(unsafe_code)`, index
  arenas); making the release profile fail loudly rather than wrap is consistent with
  that and eliminates a whole CI-vs-production behavioural delta. Where a hot path
  genuinely cannot afford it, use `wrapping_*` explicitly at that site.
- Novelty: **new** as a framing (the lexer instance is a compile-lexer mapper lead).

### F11. `Intl` and `Temporal` ship inside the consensus engine against a resolved design decision, with no oracle and an unversioned data seam
- severity **medium**, confidence **high**, category verification
- `rust/engine/ironhorse-vm/src/interp.rs:6409`; other sites `:3269–3283`,
  `:4422`, `:39511`, `:40273`, `designs/ironhorse-engine.md:1181–1185`
- Claim: five ECMA-402 constructors plus the whole Temporal family are live guest
  surfaces whose results depend on `icu_normalizer`/`icu_segmenter` data, and which by
  construction cannot be differentially checked because the pinned XS oracle has
  neither.
- Evidence: `use icu_segmenter::{GraphemeClusterSegmenter, SentenceSegmenter,
  WordSegmenter};` (:39511); `let normalizer = icu_normalizer::ComposingNormalizer::
  new_nfc();` (:40273); probes show `Intl.Segmenter`, `Intl.Collator`,
  `Intl.NumberFormat` all returning results. The design says "Intl is omitted, matching
  the oracle".
- Impact: the largest oracle-blind surface in a consensus engine, sitting on external
  data crates (see F4). Every other guest-visible behaviour has a differential check;
  this one has none.
- Recommendation: amend the design (this is a real, arguably good, scope change — but
  it must be recorded), and give the Intl surface its own frozen golden corpus
  (`input → output` fixtures regenerated only on a deliberate `INTL_DATA_VERSION` bump)
  so the missing oracle is replaced by a pinned expectation rather than by nothing.
- Novelty: **partially-known** (docs-ci and interp-02 mappers); reported here because
  the ICU-skew evidence in F4 turns a docs-drift item into a determinism item.

### F12. `HashMap::iter().find()` scans whose determinism relies on an un-asserted uniqueness invariant
- severity **low**, confidence **high**, category determinism
- `rust/engine/ironhorse-vm/src/interp.rs:29746`; other sites `:37906`, `:37913`
- Claim: three lookups select an entry by scanning a `HashMap` with `RandomState` and
  taking the first match; each is deterministic today only because the predicate
  happens to match exactly one entry, and nothing asserts that.
- Evidence:
  ```rust
  if let Some((&function, _)) = self.functions.iter().find(|(_, info)| info.method == Some(expected))  // :29746
  if let Some((&descriptor, _)) = self.symbol_key_ids.iter().find(|(_, property_id)| **property_id == id) // :37906
  .find_map(|(name, property_id)| (*property_id == id).then(|| name.clone()))                            // :37913
  ```
- Impact: none today (I traced each: `expected` is one of four distinct `NativeMethod`s
  each allocated once in `create_intrinsics`; `symbol_ids` maps name→position so ids are
  unique). But `property_key_slot` feeds `Reflect.ownKeys`, so a future duplicate would
  make property enumeration ASLR-dependent — an intra-process nondeterminism the
  `--repeat` gate is designed to catch and which is not run (F3).
- Recommendation: build the reverse indexes once (`symbol_names[id-1]` already exists
  and is used at :30508) instead of scanning, and add a debug assertion that the match
  is unique where a scan must remain. Cheap, and it converts an accident into an
  invariant.
- Novelty: **new** (interp-11 mapper noted the performance half).

## 3. Strengths

- **Snapshot emission is canonically ordered everywhere I checked.** Every
  `*_snapshot` view collects from a `HashMap` and then `sort_unstable_by_key(owner)`
  before returning (interp.rs:8984, :8999, :9114, :10511 and ~40 siblings). This is
  the discipline that makes an index-arena heap snapshot-able at all, and it is applied
  without exception rather than case by case.
- **The collector is order-independent by construction, not by luck.** `gc_roots`
  sorts and dedups (:43692–43693), the sweep runs in index order, compaction sorts
  `seen`, arena compaction uses `BTreeSet`, and array elements live in a `BTreeMap`.
  The one `HashMap` walk in the ephemeron worklist affects visit order but not the
  resulting mark set.
- **Host non-determinism is genuinely closed off.** `Date.now()` returns 0
  (interp.rs:25164), `Temporal.Now` is pinned to `NOW_EPOCH_NS = 0` and the `UTC`
  zone (:25111–25112), there is no `Math.random`, no `SystemTime`, no `std::env` in the
  VM, and the Intl profile explicitly refuses the host locale ("Intl never consults the
  host locale, libc, environment variables, or a dynamically-updated database",
  :4420–4421). Most engines get this wrong; this one closed it deliberately.
- **The number↔string axis is sound.** `number_to_ecma_string` reformats Rust's
  correctly-rounded shortest representation to the spec's thresholds (value.rs:1759 ff.)
  and parsing uses `str::parse::<f64>` behind explicit ECMAScript grammars — so the
  classic dtoa/strtod determinism trap is simply absent.
- **The wire format is platform-width-free.** No `usize` is ever serialized; every
  snapshot field is an explicit `u8`/`u16`/`u32`/`i128` in big-endian
  (`image.rs`, 127 fixed-width writes). `tick_chunk_new` even hardcodes the 16-byte
  64-bit chunk header rather than reading `size_of::<usize>()`, so the meter is
  width-independent by construction.
- **XS's C-platform artefacts were frozen rather than inherited.** The parser symbol
  hash pins signed-char promotion explicitly (`(b as i8 as i32) as u32`,
  coder.rs:221) instead of depending on the build platform's `char` signedness. That is
  exactly the right instinct, and it is the instinct F1 and F2 are missing.
- **Where the code knows about a determinism scope it says so, in detail.** The 15-line
  libm DECISION-OF-RECORD (:29829–29843) names the hazard, the remedy, the coupling to
  the oracle, and the reason a unilateral fix would be wrong. Reviewing this codebase is
  easy precisely because of comments like that; the problem is that the design document
  never learned what the comment knows.
- **`COST_TABLE_VERSION` is a real fail-closed gate.** A snapshot whose `METR` atom
  carries a different table refuses to resume (image.rs:4444, store.rs:2010, :3152).
  The mechanism F9 needs for the boot layout already exists, one file away.

## 4. Recommended architectural direction

**Make the determinism boundary an artifact, not a promise.** Today "deterministic per
release" is a sentence in a design document; it should be a *manifest* the engine emits
and the store enforces. Concretely: one `EngineFingerprint` computed at build time from
(a) `COST_TABLE_VERSION`, (b) a hash of the boot layout `create_intrinsics` produces,
(c) `INTL_DATA_VERSION` derived from the resolved ICU crate versions, (d) the libm
provider identity, and (e) the target triple *only while libm remains platform-linked*.
Write it into every snapshot beside the `SIGN`/`METR` atoms, refuse on mismatch, and
expose it from the daemon. That single change subsumes F4, F9 and F11, replaces three
hand-stamped strings with one derived value, and converts "someone must remember to
bump the signature" into a build-time fact. It also makes the F1 scope honest: while
the target triple is in the fingerprint, the engine is *telling* you it is per-platform;
when the vendored libm lands, the triple drops out and the fingerprint narrows.

**Then close the two seams the value model already knows about.** The engine has a
correct UTF-16 string representation and a correct lossless `ToString`
(`to_string_units`), and it has a correct code-unit↔byte remap in the comment at
interp.rs:20166 — it just doesn't use them everywhere. F6, F7 and the JSON astral
refusals are all the same defect: a Rust `String`/`&[u8]` used as an intermediate for a
value the spec defines over `u16`. The fix is mechanical and worth doing as one sweep
rather than site by site: make `str_text` diagnostics-only by name, give `RegExpData`
and `ErrorInfo` `Vec<u16>` fields, and either land the offset remap or extend the
existing `!is_ascii()` refusal to the whole regexp surface. Do it before the string
representation is frozen into more snapshot fixtures, because every one of these
produces *persisted* wrong bytes.

**Finally, buy the enforcement.** Three cheap CI additions would have caught most of
what is above and will catch the next regression for free: a second `runs-on` platform
on `test-ironhorse` (catches F1, F2 immediately); a checked-in golden corpus of
`(program → result, computrons)` asserted by an oracle-free `cargo test` (catches
cost-table drift, and is the only thing that makes `COST_TABLE_VERSION` meaningful);
and a lockfile-agreement check between the root and engine workspaces (catches F4).
None of these needs the XS oracle, so all three fit in the fast PR lane. The engine's
internal discipline is good enough that these gates would mostly stay green — which is
exactly when they are worth adding, before the next contributor has to rediscover by
hand which of the design's promises the tree actually keeps.
