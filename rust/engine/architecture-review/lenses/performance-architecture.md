# Lens: Performance architecture — IronHorse engine

HEAD 97d8de25. All measurements taken by me on this host (4 vCPU, 15 GiB RAM),
`--release`, against the tree as-is. Probe crate lives outside the repo
(`scratchpad/perfprobe`, path-deps on `ironhorse-vm`/`ironhorse-compile`/
`ironhorse-snapshot`); no repo file was modified (`interp.rs` mtime restored
after the build-timing runs).

## 1. Assessment

The interpreter core is architecturally sound for a no-JIT, `forbid(unsafe_code)`
port, and its measured constant factor is respectable: 18–24 ns per dispatched
opcode (`empty_2M`: 26,000,026 dispatches in 507 ms; `arith_2M`: 46,000,034 in
1,083 ms), a property read about 2.4x a baseline dispatch, and the checked-in
`dispatch_bench` reports `dispatch_ms=956.95 slots_ms=403.24 chunks_ms=24.88`.
Nothing in the loop is execution-count-dependent, so the no-JIT rule holds by
construction. The problems along this lens are not in the `match` — they are in
three places the design either mis-describes or does not price at all: **memory
reclamation, the meter's fidelity as a cost proxy, and the per-crank persistence
cost**.

The largest is that **no wired configuration ever reclaims chunk space**. There
is no `collect_garbage`/`free_pages` call anywhere in `ironhorse-vm`
(interp.rs:43707, :44556 are the only definitions); the only production GC path
is `partial_collect` (machine.rs:1952), which is page-conservative over slots and
whose own doc says "only [the full collector] compacts chunk space"; and
`CadencePolicy::default()` sets `collect_every: 0` — "never" — with no supervisor
caller anywhere in `rust/endo`. The chunk arena only ever appends
(`ChunkArena::alloc`, value.rs:1470). Measured consequence: `for (i<16000) s = s +
'abcdefgh'` — final live string 256 KB — leaves `chunk_bytes = 2,048,520,572` and
peak RSS 4.0 GB for **343,678 computrons**; the same shape at 80,000 iterations
was OOM-killed (exit 137). That is a process-killing DoS reachable from ordinary
guest JS at a computron cost three orders of magnitude below any plausible crank
limit, and in the persistent path the garbage is durably checkpointed.

Second, the meter is a poor wall-clock proxy on exactly the paths where guests can
buy amplification, and the design's doctrine (§ Metering: "the best available
deterministic proxy for real (wall-clock) execution cost") is the thing being
violated, not XS parity. Measured, with computrons *exactly linear* in n while
wall time is quadratic: `Map.set` n=1k/2k/4k/8k → 2.30/8.41/30.94/119.27 ms
(computrons 25,305 → 202,141); `for-in` over n keys → 22.8/91.7/329/1,274 ms at
n=2k..16k; `for-of` over a string → 254 ms at 64 Ki chars, 3,643 ms at 256 Ki.
The mechanisms are in code: `collection_find` is a linear `position` scan
(interp.rs:34435) priced as a hash table, and `IterState` — which contains
`enum_keys: Vec<(u16,u32)>` and `str_bytes: Vec<u8>` — is `clone()`d whole on
every `next()` (interp.rs:32513, :32730).

Third, two design claims that were the *rationale* for architectural choices do
not hold in code. The UTF-16 chunk model was chosen (design:318–336) because
code-unit access becomes "intrinsically O(1) ... with no decode step" so the
"auxiliary constant-time-index machinery ... is deleted, not ported" — but every
`String.prototype` entry calls `string_this_units` (interp.rs:31025), decoding the
whole receiver into a fresh `Vec<u16>` before looking at the argument. Measured:
100,000 `s.charCodeAt(0)` calls cost 59.95 ms on a 16-char string and 221.43 ms on
a 4,096-char string at identical dispatch and computron counts. And the dispatch
design's "small register struct threaded through the loop, mirroring
`mxSaveState`/`mxRestoreState`" (design:346) does not exist: `pc` is the only
local in `dispatch_at_inner`; the other ~160 fields (47 of them `HashMap`s,
`size_of::<Interp>() == 4032`) are `self.*` mutated from the loop and from every
native it calls.

Fourth, the persistence seam's headline property is overstated. `checkpoint_to_store`
is genuinely O(dirty) for slot pages and chunk extents, but `small_state_of`
(machine.rs:902) re-encodes and re-hashes the **entire** side-table set, free
list, name table and stack on every commit. Measured: a `1 + 1` crank that
dirties nothing costs 0.44 ms / 4.93 ms / 24.10 ms of checkpoint at 1k / 10k / 50k
live array items, with `checkpoint_every: 1` by default.

Finally, the envelope has no machine-checked expression: six `#[ignore]`d benches
with no thresholds, none run by CI, one pointing at a file that does not exist.

Developer-performance datum requested: a no-op `cargo build -p ironhorse-vm --lib`
is 0.09 s; after `touch interp.rs` (content unchanged, rustc incremental absorbing
it) 2.94 s; with `CARGO_INCREMENTAL=0` — the cost shape of a real edit to a file
whose single `impl Interp` spans lines 5184–43488 — **11.5 s** for the crate alone
in debug. `cargo test --release -p ironhorse-snapshot --test dispatch_bench` from
a warm release target was 38.7 s of compilation plus 8.3 s of test.

## 2. Findings

### F1 (critical) — Nothing in any wired configuration reclaims the chunk arena; guest JS OOM-kills the worker for a few hundred thousand computrons

`rust/engine/ironhorse-vm/src/interp.rs:43707` (definition, no caller);
`rust/engine/ironhorse-snapshot/src/machine.rs:1936`;
`rust/endo/src/ironhorse_engine.rs:287–288`.

Claim: `Interp::collect_garbage` — the only code that compacts chunk space — has
no caller outside tests, `partial_collect` reclaims slot pages only, and the
default cadence never schedules even that, so a crank's chunk allocation is
retained for the machine's lifetime and a trivially bounded program exhausts host
memory.

Evidence:
```
grep -rn "collect_garbage\|partial_collect" --include=*.rs rust/ | grep -v tests/
  rust/endo/src/ironhorse_engine.rs:680:  partial_collect(session, &*self.store.borrow())...
machine.rs:1936  /// whose key is dead still roots its values' pages until the full
                 /// [`Interp::collect_garbage`] reclaims exactly (only
                 /// it compacts chunk space).
ironhorse_engine.rs:287  CadencePolicy { checkpoint_every: 1, collect_every: 0 }
value.rs:1470    pub fn alloc(&mut self, data: &[u8]) -> ChunkOffset {   // append-only
```
Measured (`perfprobe`):
```
strcat_16000: ms=3895.76 computrons=343678 chunk_bytes=2048520572 live_slots=718 [VmHWM: 4006988 kB]
striter (80000 1-char concats): Killed (exit 137)
alloc_200000: live_slots=400718 slot_bytes=12822976   // one object reachable at the end
```
Impact: a guest can OOM-kill a consensus worker with ~0.3 M computrons — the meter
cannot be the liveness backstop the design (§ Metering) makes it; and in the
persistent path the garbage is durably committed, so the store grows monotonically
too. Recommendation: give the engine an allocation-pressure trigger (a
`Halt::HeapExhausted` plus a `chunks.byte_size()`/`slots.live_count()` ceiling
checked at the loop top, and a mid-crank collect at a safe point, or at minimum a
hard arena cap that fails the crank deterministically); wire `collect_every` to a
non-zero default and make chunk compaction reachable from the deployed path.
Novelty: **new** relative to the store-seam ledger (the region map
`vm-heap-gc` candidate 1 raised the trigger question this wave; the OOM,
the durable-growth consequence and the measurements are mine).

### F2 (high) — The per-crank checkpoint is O(live side-table state), not O(dirty)

`rust/engine/ironhorse-snapshot/src/machine.rs:902` (`small_state_of`), consumed at
`machine.rs:1193` (`let small = small_state_of(interp).encode();`) and hashed as
`leaf_hash(LEAF_SMALL, 0, &small)`.

Claim: every commit re-encodes and re-hashes the whole small state — all ~28 side
tables, the entire free list, the program name table and the value stack — so a
crank that dirties nothing still pays a cost linear in heap content, contradicting
the design's "Steady-state checkpoint cost is proportional to pages dirtied since
the last checkpoint — the point of the seam"
(designs/ironhorse-snapshot-store-seam.md:3960).

Evidence:
```
fn small_state_of(interp: &Interp) -> SmallState {
    let tables = side_tables_of(interp);
    ...
    stack: interp.stack_slots().to_vec(),
    slot_free: interp.slots.free_list().to_vec(),
    names: interp.program_symbol_names().to_vec(),
    arrays: tables.arrays, collections: tables.collections, ...
```
Measured — checkpoint of a `1 + 1` crank after a build crank that made an
N-element array:
```
N=1000   trivial crank checkpoint: 0.70 / 0.50 / 0.44 ms
N=10000  trivial crank checkpoint: 4.95 / 4.73 / 4.93 ms
N=50000  trivial crank checkpoint: 23.79 / 25.27 / 24.10 ms
```
Impact: with `checkpoint_every: 1` (the default and "today's contract"), every
crank of a vat pays O(heap side-table bytes) of encoding + SHA-256; at a million
live array items that is ~0.5 s of per-crank overhead independent of what the
crank did. Recommendation: shard the small state into per-table leaves with their
own dirty bits (the mechanism already exists for pages/extents/free segments), or
at minimum leaf-hash each table separately so unchanged tables travel as an
unchanged leaf. Novelty: **partially-known** — the design states the whole-encode
at :602 and :3953 but then asserts the O(dirty) steady state at :3960; no ledger
item and no measurement exists.

### F3 (high) — Every `String.prototype` method decodes the whole receiver into a fresh `Vec<u16>`, defeating the stated rationale for the UTF-16 chunk model

`rust/engine/ironhorse-vm/src/interp.rs:31025` (`let content = self.string_this_units(code, this)?;`),
`:10877` (`str_units` → `be16_to_units`), `:31065` (`charCodeAt` then indexes `content`).

Claim: `s.charCodeAt(i)`, `s.charAt(i)`, `s[i]`-style reads and every other
`String.prototype` entry are O(|s|) in time and allocation, so a scan of an
n-char string is O(n²), although the design chose UTF-16 storage precisely
because "every code-unit-addressed operation ... is intrinsically O(1) per
code-unit access with no decode step" and the index machinery was therefore
"deleted, not ported" (designs/ironhorse-engine.md:318–336).

Evidence:
```
interp.rs:31025  let content = self.string_this_units(code, this)?;
interp.rs:10877  fn str_units(&self, off) -> Vec<u16> { be16_to_units(&self.str_content(off)) }
interp.rs:31076  Slot::integer(content[pos as usize] as i32)
```
Measured — 100,000 `s.charCodeAt(0)` calls, identical dispatch/computron counts:
```
len 16:   ms=59.95   computrons=2650151
len 256:  ms=67.46   computrons=2650237
len 1024: ms=102.34  computrons=2650280
len 4096: ms=221.43  computrons=2650323
```
Impact: a 1 MB string makes each `charCodeAt` copy 2 MB at a constant metered
price — an unbounded, unmetered CPU amplifier, and the reason the "deleted, not
ported" trade has not actually been taken. Recommendation: read code units
directly out of the chunk (`str_content` already returns a guarded byte slice) for
the index-addressed methods, and reserve the eager `Vec<u16>` for methods that
genuinely need the whole text. Novelty: **new**.

### F4 (high) — The meter is not a wall-clock proxy on the collection and iteration paths: quadratic host work at exactly linear computrons

`rust/engine/ironhorse-vm/src/interp.rs:34435` (`collection_find`),
`:32513` and `:32730` (`let st = self.iterators[&iter].clone();`),
`:3086–3090` (`IterState { enum_keys: Vec<(u16,u32)>, str_bytes: Vec<u8> }`),
`bulk.rs:259` (`entries: Vec<Option<(Slot, Slot)>>`).

Claim: `Map`/`Set` lookup is a linear scan and every iterator step clones the whole
`IterState` including the iterated string's bytes and the pre-collected for-in key
list, so wall time is quadratic in collection/string size while the metered cost
is linear — the design's doctrine (§ Metering, "the best available deterministic
proxy for real (wall-clock) execution cost") inverted.

Evidence:
```
interp.rs:34435  data.entries().iter().position(|entry| entry.is_some_and(|(k,_)| self.same_value_zero(&k, key)))
interp.rs:32513  let st = self.iterators[&iter].clone();      // string iterator: clones str_bytes
interp.rs:32730  let st = self.iterators[&iter].clone();      // for-in: clones enum_keys
```
Measured:
```
map_set n=1000/2000/4000/8000 : 2.30 / 8.41 / 30.94 / 119.27 ms ; computrons 25,305 → 202,141 (exactly linear)
for-in  n=2000..16000         : 22.8 / 91.7 / 329.2 / 1274.4 ms ; computrons linear
for-of over a string 64Ki/256Ki chars: 254.7 / 3643.2 ms        ; computrons linear (28/char)
```
Impact: a validator can be made to spend minutes for a computron budget that buys
under a second of arithmetic; the amplification factor grows without bound with
data size, so no fixed crank limit bounds it. Recommendation: either make the data
structures match the cost model (a real hash index for `Map`/`Set`; borrow the
`IterState` fields instead of cloning) or make the cost model match the data
structures (charge `collection_find` per probe, charge iterator `next` per cloned
byte). Novelty: **partially-known** — this wave's `interp-12` (candidates 1, 6) and
`vm-heap-gc` (candidate 6) leads; no prior-wave ledger item; the scaling
measurements and the computron-vs-time contrast are mine.

### F5 (medium) — The design's "small register struct threaded through the loop" is not what ships; interpreter state is 160 `self` fields, 47 of them `HashMap`s

`rust/engine/ironhorse-vm/src/interp.rs:11292–11294` (only `pc` is a local),
`:3651–4402` (the `Interp` struct).

Claim: `dispatch_at_inner` keeps exactly one value in a register (`pc`); the stack,
locals, id map, args, `this`, env, result, exception, strict flag and every callee
register live in `Interp` and are mutated both from the loop and from the natives
it calls, so the design's `mxSaveState`/`mxRestoreState` register-struct model
(designs/ironhorse-engine.md:346) exists nowhere.

Evidence:
```
interp.rs:11293  let len = code.len();
interp.rs:11294  let mut pc: usize = start_pc;
size_of::<Interp>() = 4032   (probe)
struct Interp: 160 fields, 47 HashMap<...>, 22 Vec<...>   (awk over 3652–4401)
```
Measured baseline: 19.5 ns/dispatch (`empty_2M`), 23.5 ns (`arith_2M`), 13 ns
inside a function frame (`C_getlocal`).
Impact: not a defect by itself, but it is the design's stated mechanism for the
throughput envelope and it is absent, so the envelope has never been reasoned
about against the implementation; it also means every native call is an optimizer
barrier over all interpreter state. Recommendation: either amend the design to
describe the real model, or (better, and cheap) hoist the genuinely hot registers
(`stack` length/top, `locals`, `id_map`) into locals across straight-line arm runs
and measure. Novelty: **new** as a design-vs-code finding (this wave's
`interp-06` map notes the same non-upheld claim as its item 9).

### F6 (medium) — Exotic-object dispatch by side-table membership puts up to 14 hash probes on the hottest opcode and 6 eager probes on every call

`rust/engine/ironhorse-vm/src/interp.rs:12687–13036` (`GET_PROPERTY`),
`:13583–13616` (`RUN`).

Claim: `GET_PROPERTY` tests membership in fourteen side tables in a fixed textual
order before reaching `ordinary_get`, and `RUN` computes all six callee-class
probes as unconditional `let` bindings before the dispatch chain, so both costs
grow with the number of exotic kinds the engine models rather than with the
object's actual type.

Evidence (guards, in order, within `GET_PROPERTY`): `arrays`, `temporal_instants`,
`temporal_durations`, `temporal_plains`, `temporal_zoneds`, `disposable_stacks`,
`array_buffers`, `typed_arrays`, `data_views`, `regexps`, `locales`, `collators`,
`functions`, `proxies`; and in `RUN`:
```
let callee  = func_ref.and_then(|(f, base)| self.native_of(f).map(...));
let method  = func_ref.and_then(|(f, base)| self.method_of(f).map(...));
let bound   = ... self.bound_functions.contains_key(&f) ...
let proxy_callee = ... self.proxies.contains_key(&f) ...
let promise_fn   = ... self.promise_functions.contains_key(&f) ...
```
Measured: a property read costs ~2.4x a baseline dispatch (`A_getprop` 788.07 ms /
38 M vs `B_const` 616.04 ms / 34 M — 43 ns per extra dispatch against an 18 ns
baseline).
Impact: every new built-in makes every property read and every call slower, and
the type of an instance has no single representation to switch on. Recommendation:
put an exotic-kind tag in the instance slot (`Slot.flag`/`kind` has room) or in one
`HashMap<SlotIndex, ExoticKind>` consulted once, and dispatch on it; make `RUN`'s
probes lazy. Novelty: **new** (this wave's `interp-06` candidate 7 raises the
modularity half; the eager-`RUN` and the measurement are mine).

### F7 (medium) — `CATCH` clones the frame's `id_map` on every `try` entry: wall cost scales with frame size at constant metered cost

`rust/engine/ironhorse-vm/src/interp.rs:15671`.

Claim: establishing a handler deep-copies the frame's `HashMap<u16, usize>` name
map into the `CatchJump`, so a `try` inside a loop in a function with many lexical
declarations pays a heap allocation and O(names) copy per iteration that the meter
does not see.

Evidence:
```
self.jumps.push(CatchJump { target_pc: target, stack_len: self.stack.len(),
    locals_len: self.locals.len(), id_map: self.id_map.clone(), ... });
```
Measured — 100,000 `try {} catch {}` iterations inside a function, identical
dispatch counts (3,200,051 vs 3,201,643) and computrons (3,200,056 vs 3,201,650):
```
2 locals   : 32.83 ms      (no-try baseline 19.19 ms)
50 locals  : 37.46 ms
200 locals : 50.07 ms
400 locals : 67.68 ms      (no-try baseline 18.77 ms)
```
Impact: modest today, unbounded in principle (a frame may hold up to the u16 name
space); it is also another metered-flat/wall-variable path. Recommendation: store
the handler's `id_map` as a copy-on-write `Rc<HashMap<..>>` or record only the
number of names to truncate, which is what `unwind_to_jump` actually needs.
Novelty: **partially-known** (this wave's `interp-06` candidate 9 named the clone;
the frame-size scaling measurement and the meter-flatness are mine).

### F8 (medium) — `Slot` is 24 bytes, not the documented 32; the footprint envelope is measured against a constant, not the layout

`rust/engine/ironhorse-vm/src/value.rs:298–312`, `:965–969`.

Claim: `size_of::<Slot>() == 24` and no `repr` attribute exists, while the type's
doc says "One 32-byte slot record ... `#[repr(C)]`-style field order" and
`byte_size()` reports `capacity * 32`, so the design's "heap within 1.1x (the slot
accounting is identical by construction)" (design:761–763) compares a constant
against XS rather than the real footprint — and it ignores the 47 `HashMap` side
tables that hold the per-instance state XS keeps inside slots.

Evidence:
```
value.rs:298  /// One 32-byte slot record. ... `#[repr(C)]`-style field order matches XS's `txSlot`
value.rs:967  pub fn byte_size(&self) -> usize { self.capacity() as usize * 32 }
probe:        size_of::<Slot>() == 24 ; size_of::<Interp>() == 4032
```
Impact: the one machine-readable footprint number in the engine cannot fail, so
the 1.1x bar is unfalsifiable; the actual overhead (side-table entries per array,
collection, typed array, proxy, function) is invisible to it. Recommendation: make
`byte_size()` report real bytes (or report both, named), add `#[repr(C)]` if the
field order is load-bearing, and add side-table bytes to the footprint instrument.
Novelty: **partially-known** (this wave's `vm-heap-gc` candidate 11 caught the 24
vs 32 doc drift; the envelope-unfalsifiability consequence is mine).

### F9 (medium) — The performance envelope has no machine-checked expression: six `#[ignore]`d benches, no CI lane, no thresholds, one stale cross-reference

`rust/engine/ironhorse-snapshot/tests/dispatch_bench.rs:51`,
`gc_bench.rs:52/211/302`, `attached_bench.rs:48`, `wake_latency_bench.rs:33/96`,
`.github/workflows/ci.yml` (only `cargo test -p ironhorse-vm -p ironhorse-snapshot`).

Claim: nothing in the repository compares any measurement against the design's
2.0x throughput / 1.1x footprint / no-latency-regression envelope; the benches
print medians and assert only fixture correctness, none is run by CI, and
`attached_bench.rs:20` points at `ironhorse-vm/tests/dispatch_bench.rs`, which does
not exist.

Evidence:
```
dispatch_bench.rs:51  #[ignore = "benchmark: run explicitly in --release on the trees being compared"]
dispatch_bench.rs:67  println!("BENCH dispatch_ms={dispatch:.2} slots_ms={slots:.2} chunks_ms={chunks:.2}");
attached_bench.rs:20  //! detached half lives in `ironhorse-vm/tests/dispatch_bench.rs`
ls rust/engine/ironhorse-vm/tests | grep -i bench  →  (empty)
```
Measured here (release, 4 vCPU): `BENCH dispatch_ms=956.95 slots_ms=403.24
chunks_ms=24.88` — the first recorded datum I could find for this tree.
Impact: F1–F4 are all regressions in the envelope's terms and none would have been
caught. Recommendation: fix the stale path; add a nightly (not PR) job that runs
the four benches plus a scaling assertion — the cheap, robust form is not a
wall-clock threshold but a *shape* assertion (`t(2n)/t(n) < 2.5` for `Map.set`,
for-in, string `for-of`, and `charCodeAt` on a fixed-length receiver), which is
host-independent and would have failed on F3 and F4 today. Novelty:
**partially-known** (this wave's `snapshot-tests` candidate 10; the shape-assertion
proposal and the baseline numbers are mine).

### F10 (medium) — The only chunk-space compactor fully reifies a lazily resumed arena and dirties the whole chunk space

`rust/engine/ironhorse-vm/src/gc.rs:170–182`, `value.rs:1548`
(`compact` → `ensure_all_resident()`).

Claim: `collect_full` compacts unconditionally, and `ChunkArena::compact` begins
by faulting in every extent and ends by downgrading the arena to plain fully
resident storage — so the one operation that reclaims strings destroys the
"resume is O(working set)" property and makes the following checkpoint a full
chunk write; two O(capacity) arena scans and a `HashMap<ChunkOffset, ChunkOffset>`
over all live chunks are paid on every collection as well.

Evidence:
```
gc.rs:183   let remap = chunks.compact(&live_offsets);
value.rs:1548  self.ensure_all_resident();   // inside compact()
gc.rs:172-199  for i in 0..slots.capacity() { ... }   // twice
```
Impact: combined with F1 this is a fork in the road — today nothing compacts (so
memory grows without bound), and the moment something does, a lazily resumed
machine loses its working-set advantage and pays a full-store rewrite.
Recommendation: an incremental/extent-local compactor, or a
`compact_if(fragmentation > threshold)` policy with the residency-preserving path
for untouched extents. Novelty: **known-open** — store-seam ledger item L10
("compaction slides the whole chunk space; post-compaction checkpoint rewrites
every surviving extent ... DEMAND-GATED ... OPEN by design"); the
`ensure_all_resident` interaction with lazy resume is the part I would add.

### F11 (medium) — `ChunkArena::alloc` narrows the arena length to `u32` with no guard, and F1 makes >4 GiB reachable

`rust/engine/ironhorse-vm/src/value.rs:1480–1481`.

Claim: the returned offset is `v.len() as u32` with only a `debug_assert_eq!`
behind it, so once the chunk arena passes 4 GiB — reachable, since F1 measured
2.05 GB from a 16,000-iteration string-concat loop on a 15 GiB host — offsets
alias earlier blocks in release builds instead of failing.

Evidence:
```
let v = self.bytes_mut();
v.extend_from_slice(&(data.len() as u32).to_le_bytes());
let off = v.len() as u32;
...
debug_assert_eq!(off as usize, header + CHUNK_HEADER);
```
Impact: silent chunk aliasing (wrong string values, and a length header read from
the middle of another payload) or a deterministic panic, in a consensus engine, on
a machine with enough RAM. Recommendation: make the narrowing checked —
`u32::try_from(v.len()).map_err(|_| ...)` returning a `Halt`, or a hard arena cap
(which F1 needs anyway). Confidence on the >4 GiB reachability is medium (host
RAM–dependent); the missing guard is certain. Novelty: **partially-known** (this
wave's `interp-12` candidate 2 named the cast; the 2 GB-per-crank measurement that
makes it reachable is mine).

### F12 (low) — Per-crank and per-eval fixed costs: whole-bytecode copy each crank, full intrinsics boot per `Machine::evaluate`

`rust/engine/ironhorse-vm/src/interp.rs:11162`;
`rust/engine/ironhorse-vm/src/compartment.rs:320` / `rust/endo/src/ironhorse_engine.rs:165`.

Claim: `run` copies the entire bytecode buffer into a fresh `Rc<Vec<u8>>` on every
crank whether or not any function is defined, and the non-persistent
`Machine::evaluate` path builds a whole new `Interp` (all intrinsics) per call.

Evidence:
```
interp.rs:11162  self.top_level_code = Some(std::rc::Rc::new(code.to_vec()));
```
Measured: `Interp::new()` + `link_intrinsics` = 0.17 ms and 716 live slots per
call; boot + run of `"1"` = 0.15 ms.
Impact: small in absolute terms, but it is a per-crank O(program size) copy on the
hot path the design describes as "allocation-free beyond the existing top-level
copy", and a 0.17 ms floor on every `evaluate`. Recommendation: hold the caller's
buffer as `Rc<[u8]>` supplied by the embedder (it already owns one), and let
`Machine::evaluate` reuse a boot image. Novelty: **new**.

### F13 (low) — Developer performance: one 38k-line `impl` block makes any `interp.rs` edit an 11.5 s crate rebuild

`rust/engine/ironhorse-vm/src/interp.rs` (44,942 lines; one `impl Interp` spans
5184–43488).

Claim: the monolith has a measurable iteration-time cost. Measured on this host
(4 vCPU): no-op build 0.09 s; `touch interp.rs` with content unchanged 2.94 s
(rustc's dep graph absorbs it); `CARGO_INCREMENTAL=0` after a touch — the shape of
a real edit — **11.50 s** for the crate alone in debug; the release build of the
crate inside `cargo test --release -p ironhorse-snapshot --test dispatch_bench`
was 38.7 s. Impact: every dispatch-loop experiment costs ~12 s (debug) or ~40 s
(release) before a single measurement, which is a direct tax on the performance
work stage 8 requires. Recommendation: split `impl Interp` across modules by
region (the region map boundaries this review used are a ready decomposition);
`impl` blocks may be split freely across files without changing the type.
Novelty: **new**.

## 3. Strengths

- **The dispatch core is honest and fast enough.** 18–24 ns per dispatched opcode
  with bounds-checked operand reads, a jump-table `match`, and no
  execution-count-dependent behavior anywhere — the no-JIT rule is upheld by
  construction, not by discipline, and the decode envelope costs nothing
  measurable (`instruction_len` + one `pc + ilen > len` test per instruction).
- **Index arenas really do make the snapshot structural.** The dirty-page/dirty-
  extent machinery is genuinely incremental for the parts it covers, and
  `collect_full` is careful not to dirty pages for identity remaps
  (`gc.rs:191–197`) — a subtle, correct performance decision written down with its
  reason.
- **`enter_call` avoids the obvious costs**: `std::mem::take` moves `locals`/
  `id_map`/`args` into the `CallerState` rather than cloning them, and the only
  per-call allocation is the argument `Vec` (nothing for a zero-argument call).
- **Metering and dispatch are one seam.** One `tick_code()` before the `match`,
  a feature-gated zero-sized `CostRecorder` (`cost-calibration` off by default,
  "instruction-identical to the pre-instrumentation build"), so instrumentation
  does not tax the hot loop.
- **No dynamic dispatch on the hot path.** `Native`/`NativeMethod` are enums
  matched statically; the only `dyn` in the interpreter are `meter_host`
  (touched at check points), `source_compiler`, and the GC visitor closures.
- **The store's steady-state root maintenance is O(dirty · log n)** via the live
  `RootLedger`, with a documented drop-on-failure discipline — the expensive
  slow path is taken only after a failed commit.
- **`ChunkSlice`'s byte-lexicographic `Ord` over UTF-16BE** makes string
  comparison a `memcmp` with no decode, which is exactly the win the encoding
  choice was supposed to buy (and is the counterexample that shows F3 is a
  fixable oversight, not an inherent cost).

## 4. Recommended architectural direction

**Make memory a first-class metered, bounded resource before stage 8.** The engine
today has three independent bounds — the computron meter, the dispatch step
ceiling, and a bounded-mode live-slot ceiling that is disabled in production
(`step_limit != u64::MAX` guards it, interp.rs:11339) — and none of them bounds
bytes. The minimum viable shape is: a hard `chunks.byte_size() + slots.byte_size()`
ceiling checked at the loop top with its own `Halt` variant, an allocation-pressure
GC trigger inside the interpreter (XS's `fxGrowSlots` point), and a default
`collect_every` that is not "never". Without this, no throughput envelope is
meaningful, because the deployed engine's failure mode under load is the OOM
killer rather than a slow crank.

**Close the meter-versus-wall-clock gap structurally, not case by case.** The
doctrine ("accuracy over parity") is the right one and it is what the code is
violating. The three amplifiers I measured — linear-scan collections priced as
hash tables, whole-state clones per iterator step, and whole-string decodes per
`String.prototype` call — are each a small local fix, but the class will recur
because there is no mechanism that notices. A cheap, host-independent guard is a
scaling test suite: for each of a dozen shapes, assert `t(2n)/t(n)` and
`computrons(2n)/computrons(n)` stay in the same complexity class. That test is
robust on a noisy CI box in a way a wall-clock threshold is not, and it is the
only form of the 2.0x envelope that can be enforced before the four-variant
benchmark exists.

**Then attack the constant factor where the design said it would.** Give the
exotic-object kinds a tag so `GET_PROPERTY` and `RUN` stop paying O(#kinds) hash
probes; hoist the genuinely hot interpreter registers into locals across the loop
(the design's "register struct", which does not exist today) and measure the
delta; shard the checkpoint's small state so per-crank durability is really
O(dirty). Each of these is measurable with the instruments already checked in,
and the first thing to do with those instruments is to run them in a nightly lane
so the numbers in this report become a baseline rather than a one-off.
